The most useful things to hand me, roughly in order of how much they narrow things down:

- The path to the repository, or permission to clone it from wherever it lives.
- The failing build or deploy log, ideally the full output rather than the last error line, since the real cause is often several steps earlier.
- What "deploy" runs through here: GitHub Actions, a Dockerfile, a Terraform apply, a platform like Vercel or Fly, or a script somebody wrote.
- Anything that changed around the time it broke. A dependency bump, a rotated credential, a base image that moved, or a CI runner image upgrade are the usual suspects when nothing in your own code changed.

That last point is worth a moment before you go looking. A deploy that starts failing overnight with no commits on your side usually means something outside the repository moved: an unpinned dependency or `:latest` base image picked up a new release, a token or certificate expired, or a hosted runner rolled to a new version. If you know your last successful deploy and the first failed one, the timestamps between them will tell us which of those it is.

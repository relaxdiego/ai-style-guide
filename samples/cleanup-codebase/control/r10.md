The two things that would move this fastest are the failing deploy's log output (the actual error, not just "failed" — ideally the last 50 lines or so) and the deploy configuration itself, whatever form that takes: a GitHub Actions workflow, a Dockerfile, a `fly.toml`, a Terraform plan, a deploy script.

The other question worth answering while you're gathering that is what changed between the last good deploy and the first bad one. If you pushed code, `git log` between the two commits usually names the culprit outright. If you didn't push anything, then the change came from outside your repo, and the usual suspects are a floating dependency version that got a new release, an expired credential or certificate, a base image tag like `node:20` that moved underneath you, or a quota or billing state on the deploy target. Those failure modes look identical from the inside — "it worked Tuesday and not Wednesday" — but the logs distinguish them quickly.

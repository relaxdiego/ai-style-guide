SQLite, unless something in your requirements forces a server process onto the user's machine.

Local-first means the database lives on the device. Postgres is a daemon: you'd be shipping a supervised background process per install, dealing with port collisions, version-mismatched data directories after an upgrade, and the user's antivirus. Embedded Postgres builds exist and every one of them is a maintenance liability. SQLite is a file and a library call.

What would actually flip the decision:

- **Multiple OS processes writing concurrently and heavily.** SQLite has one writer at a time. WAL mode makes readers concurrent with the writer, which covers most apps, but a write-heavy multi-process design will hit the wall.
- **You need Postgres-specific machinery.** PostGIS, real full-text ranking, `jsonb` operators, materialized views, stored procedures. Reimplementing these on SQLite is worse than running a server.
- **"Local-first" actually means "self-hosted server."** If it runs on a box the user administers rather than a laptop they close, Postgres is fine and the tradeoff above disappears.

The thing that will hurt you is not the engine, it's sync. Local-first almost always grows a sync/merge requirement, and neither database gives you conflict resolution. That's a schema and data-model decision — do you keep an oplog, do you use CRDTs, is last-write-wins acceptable per-field — and it's much harder to retrofit than swapping storage. SQLite keeps the sync options open because that's where the tooling lives (cr-sqlite, Electric, libSQL, Automerge alongside a SQLite cache); Postgres-on-device gives you fewer.

Four SQLite defaults that bite people, set them on day one:

| Setting | Default | Set it to |
|---|---|---|
| `journal_mode` | `delete` | `WAL` |
| `foreign_keys` | off | `ON`, per connection |
| `busy_timeout` | 0 | a few thousand ms |
| table type checking | affinity, near-untyped | `STRICT` tables |

Also plan migrations early. SQLite's `ALTER TABLE` is thin, so column changes become create-copy-swap, and you want that mechanized before you have users with data.

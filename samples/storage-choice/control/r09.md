SQLite, unless what you're calling local-first is actually a self-hosted server with several concurrent users behind it.

The reason is that Postgres on an end-user device is a daemon whose lifecycle you now own: install, upgrade across OS reinstalls, port conflicts, version-matching between the binary and the data directory, and a support burden when someone's machine has a stale cluster running. SQLite is a library in your process and a file on disk, so backup, copy, export, and "send me your database so I can reproduce this" are all file operations. On mobile and in the browser via WASM plus OPFS there isn't a real contest; Postgres doesn't go there. Reads are also in-process rather than over a socket, which matters when the UI is querying on every keystroke.

What you're accepting with SQLite is mostly a set of defaults that are wrong for an application and that you should change on day one:

- `PRAGMA journal_mode = WAL` for concurrent readers alongside one writer, plus `synchronous = NORMAL`, which is durable against process crashes though not against power loss on the last transaction.
- `PRAGMA foreign_keys = ON`, per connection, every connection. It's off by default for backward compatibility and silently so.
- `PRAGMA busy_timeout = 5000` or similar, and route writes through a single connection or a queue. There is one writer at a time, and `SQLITE_BUSY` is what carelessness about that looks like in production.
- `STRICT` tables, so the column types you declared are enforced instead of being affinity hints.

Beyond that you give up rich server types (no `timestamptz`, no arrays, no indexed `jsonb`; dates become ISO-8601 text or integers), you get a restricted `ALTER TABLE` that turns some migrations into a table rebuild, and there's no `LISTEN/NOTIFY`. FTS5 is genuinely good and `sqlite-vec` covers embeddings, so search is not the gap people expect it to be. The decision flips to Postgres when the "local" machine is a shared one: many writers, long analytical queries running against live tables, or a hard dependency on PostGIS, pgvector, row-level security, or logical replication as your transport.

It's also worth noticing that the question may not be either/or. The common arrangement for a syncing app is SQLite on each device as the local source of truth and Postgres in the cloud as the collaboration backend, which is roughly what PowerSync, Turso, and the Electric line of tooling are all built around. Picking SQLite locally doesn't commit you against Postgres on the server.

On not getting it wrong: this is one of the more recoverable decisions in the project, because a storage engine sits behind a data-access boundary and porting it costs you weeks of mechanical work if you kept the SQL portable. The decisions that actually bite are the ones about merge and schema. Whether you store state or operations, whether conflict resolution is last-writer-wins with a logical clock or a CRDT, and how an old client that has been offline for four months migrates its schema and its pending changes are all choices you cannot revise later without touching live user data on devices you do not control. If you want to spend your caution budget somewhere, spend it there.

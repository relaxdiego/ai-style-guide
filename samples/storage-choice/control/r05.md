SQLite on the client, and Postgres on the server if you have one. For a local-first app this isn't a close call.

The reason is that "local-first" commits you to each device holding a full replica that reads and writes while offline, and that requires an engine that runs in your process. Postgres is a server: a separate process, a data directory, a port, a version you have to keep in step with the one that wrote the files on disk. You can get around this (PGlite compiles Postgres to WASM, and there are embedded-Postgres distributions that supervise a real server per client), but you are paying to reach a starting line SQLite is already standing on. These two aren't really rivals here anyway. The common arrangement is SQLite on each device, Postgres holding the authoritative multi-tenant copy, and a sync protocol between them.

Which brings up the part I think you should actually worry about, because it is where "getting it wrong" is expensive. Swapping the local engine later is a schema translation and a rewrite of your query layer: tedious, bounded, mostly mechanical. Your sync design is not bounded, because it leaks into everything. Whether row IDs are client-generated UUIDs or server-assigned integers, whether deletes leave tombstones, whether you resolve conflicts per row or per field or with a CRDT, whether the server can filter a user's partial replica for authorization: each of those shows up in your table definitions and in application code all over the app, and revisiting one of them a year in is the migration that hurts. So I'd choose the sync approach first and let it name the local store, which in practice it will, since PowerSync, cr-sqlite, Turso/libSQL and the Automerge-style libraries all land on SQLite or on their own store rather than on Postgres. Check the current state of these before committing; the field moved quickly through 2025 and my picture of it ends in May 2026.

Things that would genuinely push me to PGlite instead:

- You need Postgres-specific features on the client, not just on the server: `jsonb` containment operators, PostGIS, `pgvector`, or Postgres full-text ranking. SQLite's JSON functions and FTS5 are good but they are not the same tools.
- You are shipping web-only and want one dialect and one set of migrations across client and server, and you value that more than startup time and bundle size (PGlite is on the order of megabytes against SQLite's hundreds of kilobytes).
- Your app is a thin client over a Postgres schema you already own, and the local copy is a cache you want to query with the queries you already wrote.

Two SQLite specifics worth knowing before you start rather than after. Declare tables `STRICT` so column types are enforced instead of advisory, and settle a convention for dates early, since there is no date type. And `ALTER TABLE` is limited, so plan on the twelve-step table rebuild for anything beyond adding or renaming a column; pick a migration tool that does this for you.

One thing changes the analysis and I don't know it: your platform. On the web, SQLite in WASM over OPFS works but has real sharp edges around concurrent tabs and storage eviction, and that is the one setting where PGlite is a fair fight rather than a handicap. On desktop or mobile, native SQLite is simply there, and the case for anything else is thin.

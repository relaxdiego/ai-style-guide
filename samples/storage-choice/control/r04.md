SQLite, and for a genuinely local-first app I don't think it's close.

Postgres is a server, and shipping a server to a user's machine is a distribution problem rather than a database problem. You get a daemon per user, an `initdb` on first launch, a port to allocate and defend against collisions, and a `pg_upgrade` dance every time you bump a major version, which requires both the old and new binaries present on the user's disk at the same time. On mobile it isn't an option at all. SQLite is a library you link into your process: the database is one file, backup is copying that file (or `VACUUM INTO`), and there is nothing to administer, nothing to supervise, and nothing that can be down while your app is up.

The places SQLite's limits actually bite are narrower than its reputation suggests, but they're worth knowing going in. Under WAL mode you get one writer with concurrent readers, which is invisible for a single user on a single machine and becomes real the moment you have several processes contending. Its flexible typing is a genuine footgun, so declare `STRICT` tables from the first migration rather than discovering integers stored as text two years in. And `ALTER TABLE` is limited enough that non-trivial migrations are a create-copy-rename cycle; any decent migration tool does this for you, but adopt one on day one instead of hand-writing DDL.

What I'd push back on is the framing that the storage engine is where this decision can go wrong. If the app ever syncs, sync is the expensive and hard-to-reverse choice: conflict resolution, tombstones, clock handling, and whether you're moving rows or operations. Retrofitting that onto a schema designed as if it were the only copy of the data is the migration that actually hurts. It's also worth knowing that the local-first sync ecosystem has largely settled on SQLite at the edge with Postgres at the server, so the two frequently coexist in different roles rather than competing.

I'd reverse toward Postgres in a few specific cases:

- "Local-first" really means "runs on my laptop today, becomes a multi-user hosted service later," and the local phase is a development convenience rather than a product property.
- Multiple OS processes on the same machine need to write concurrently, and you can't funnel them through one process that owns the file.
- You depend on something Postgres-specific with no adequate SQLite counterpart. Check before assuming: `sqlite-vec` covers a lot of what people reach for `pgvector` for, and FTS5 is respectable full-text search. PostGIS has no real equal.

There is a third option if you want Postgres semantics locally without the daemon: PGlite, which is Postgres compiled to WASM and runnable in a browser or Node process. It's single-connection and far younger than SQLite, so I'd only take it if Postgres compatibility is the actual requirement rather than a preference.

The asymmetry is what makes SQLite the low-regret pick. Moving a schema from SQLite to Postgres later is a bounded, well-trodden job: translate types, tighten what flexible typing let through, shift concurrency assumptions from application code to the engine. Distorting the design now to keep that door open costs more than walking through it would.

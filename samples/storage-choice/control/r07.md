Use SQLite on the device, and Postgres on the server if you end up needing a server at all. For something you're describing as local-first, that's closer to a default than a close call.

The reason is less about SQL features than about what each one is. Postgres is a server process with a lifecycle: it needs supervising, its data directory is tied to a major version, and upgrading across versions on a machine you don't control means shipping and running `pg_upgrade` against a database you can't inspect when it fails. SQLite is a library that opens a file, the file format has been stable and forward-compatible for two decades, and it already ships on every platform you'd plausibly target. PGlite has softened this by putting Postgres in WASM, and it's genuinely interesting, but it's young enough that I wouldn't build a data-durability story on it unless you specifically need Postgres extensions client-side.

The more useful thing I can tell you is that this probably isn't the decision you're afraid of getting wrong. Migrating a local store from SQLite to Postgres is a well-trodden path and mostly mechanical. What's expensive to reverse is the sync layer: how you identify rows across devices, whether you ship diffs or state, what happens when two devices edit the same record offline, and whether the server can reconstruct history. Those choices reach into your schema and your API, and changing them later means a data migration on machines you don't own. Most of the sync stacks worth using also presuppose the answer to your storage question anyway. Electric, PowerSync, cr-sqlite and Turso all assume SQLite on the client with Postgres upstream. If you choose the sync approach first, storage largely falls out of it, so I'd invert the order you're deciding in.

There is a real fork here that changes my answer, and it turns on what "local-first" means for you. If it means the app runs on a user's device and must work fully offline, everything above holds. If it means a single self-hosted node that users point a browser at, Postgres is reasonable, because you've got one machine, one admin, and the deployment cost you were avoiding is already paid. Ask yourself, too, whether more than one process will write concurrently, because that's where SQLite's limits actually bite.

Those limits are worth knowing before you commit:

- One writer at a time. WAL mode lets readers run alongside the writer, but concurrent writes serialise, and under load you'll be tuning `busy_timeout` rather than relying on row-level locking.
- Dynamic typing by default. Use `STRICT` tables, which have been available since 3.37, or you'll eventually find a string in an integer column.
- No native date, time, or boolean type. Pick a text or integer representation early and enforce it in one place.
- `ALTER TABLE` is narrow. Anything beyond adding or renaming a column means the copy-and-rename dance, so a migration tool matters more than it would elsewhere.
- Never put the file on a network filesystem. NFS and SMB locking will corrupt it, and this is the most common way people lose SQLite data.

Full-text search via FTS5 and JSON support are both good enough that they rarely drive the decision. Vector search and geospatial are where you'd feel the absence of pgvector and PostGIS, though sqlite-vec covers a fair amount of the first case now.

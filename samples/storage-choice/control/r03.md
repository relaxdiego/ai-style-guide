SQLite on the device, Postgres on the server if you have one. That pairing is the default for local-first work, and I'd need a specific reason to deviate from it rather than a specific reason to adopt it.

The reason is less about SQL features than about what each engine is. Postgres is a server: a process to supervise, a port, a data directory, a version you have to upgrade on machines you don't control and can't inspect when the upgrade goes wrong. SQLite is a library that reads a file. On a user's laptop or phone that difference dominates everything else. PGlite narrows the gap for browser and Node targets by compiling Postgres to WASM, and it's genuinely useful if you want one engine on both sides of the wire, but it's single-connection, it carries real weight, and on iOS and Android it isn't a serious option yet. If your app might ever be on a phone, that settles it.

The thing I'd actually worry about getting wrong is the sync layer, not the storage engine. Choosing SQLite is close to reversible if you keep your schema in plain migrations and your queries behind a data-access layer, because the SQL you write for a single-user local store is mostly the SQL both engines already agree on. Choosing how devices reconcile concurrent edits is not reversible: an oplog with last-write-wins, CRDTs via something like Automerge or cr-sqlite, and a server-authoritative shape-sync like Electric or PowerSync each impose a different schema, a different set of things the app is allowed to express, and a different set of anomalies your users will see. Several of those frameworks also pick the local engine for you, which is another reason to decide sync first and let storage fall out of it.

If you stay single-machine with no sync at all, the SQLite limits that actually bite are narrow and worth knowing up front:

- Dynamic typing, unless you declare `STRICT` tables, which you should from the first migration.
- One writer at a time. With WAL mode that's fine for a single user, and it's a wall if you later want a shared multi-tenant server on the same schema.
- `ALTER TABLE` is thin, so column changes often mean create-copy-drop-rename inside a transaction. Migration tools handle this, but you'll see it.
- No native `timestamptz`, `uuid`, arrays, or indexable `jsonb`. You store text or blobs and enforce meaning in the application.
- No stored procedures or extensions in the Postgres sense, so anything like `pgvector` has to come from a distribution that bundles it.

Full-text search through FTS5 is good, window functions and CTEs are there, and partial and expression indexes exist, so the day-to-day query surface is less restricted than people expect.

Given that, I'd write the first version against SQLite with strict tables and portable SQL, avoid engine-specific features in the core domain queries, and treat the sync design as the decision that deserves the caution you're feeling.

SQLite, unless something specific pushes you off it. For a local-first app the burden of proof sits on Postgres, and it's a heavy one.

The reason is that Postgres is a server and SQLite is a library. Local-first means the data lives on a machine you don't administer, so choosing Postgres means shipping a daemon to that machine, supervising it, keeping its version in step with your schema across an install base you can't see, and handling the case where it won't start. SQLite is a file your process opens. Backup is a file copy, there's no port, no user account, no `pg_upgrade` on a laptop that was closed mid-migration. That operational difference is most of the decision, and it doesn't get smaller as the app gets more serious.

The thing that would change this answer is what "local-first" actually means in your case. If it means the data is genuinely on the user's device and the app works offline, the above holds. If it means "a server app that I happen to run on localhost during development and deploy to a box later," then you're choosing your production database and Postgres is the ordinary answer; the local part is incidental. Those two readings point in opposite directions and only you can settle which one you're in.

Worth weighing against the fear of getting it wrong: the decision is far more reversible in one direction than the other. Starting on SQLite and later moving the authoritative copy to Postgres is a well-trodden migration, especially if you keep to portable SQL, drive schema changes through numbered migration files, and keep queries behind a thin data-access layer rather than scattered through the app. Starting on Postgres and later trying to make it live on user devices means rebuilding the storage and distribution story together. If there's eventually a sync server, SQLite on the client with Postgres on the server is the normal arrangement rather than a compromise, and the local-first sync ecosystem, ElectricSQL, PowerSync, cr-sqlite, libSQL, is built around exactly that pairing.

What would genuinely push me to Postgres:

- Multiple OS processes writing concurrently to the same database. SQLite serialises writers, and WAL mode only fixes reader/writer contention, not writer/writer.
- Reliance on Postgres-specific machinery you'd otherwise reimplement badly: row-level security, `jsonb` operators and indexes, arrays, ranges, `LISTEN`/`NOTIFY`, real interval arithmetic.
- Data volumes or query patterns where you need a planner that will actually parallelise, or extensions like PostGIS with no adequate SQLite counterpart.
- A near-term plan for the same database to be reached over a network by more than one machine.

If you land on SQLite, the things that bite people are worth setting up on day one rather than discovering later. Turn on WAL mode and set a `busy_timeout`, because the default is to fail immediately on a locked database. Declare tables `STRICT` so the type affinity system doesn't quietly store `"12"` in an integer column. Enable foreign keys explicitly; they're off by default per connection. Decide a single representation for timestamps, ISO-8601 text or Unix epoch integers, and hold to it, since there's no native date type to enforce it for you. Full-text search via FTS5 and vector search via sqlite-vec are both real and adequate, so those needs alone shouldn't move you.

There's a third option if you want Postgres semantics without the daemon: PGlite, which is Postgres compiled to WASM and embeddable, single-connection. It's a reasonable fit in an Electron or browser context where you're committed to Postgres dialect on both ends. It's younger and less proven under sustained local write load than SQLite is, which is a real consideration for the store of record on someone else's machine, but it's no longer an exotic choice.

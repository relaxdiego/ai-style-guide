Use SQLite, unless "local-first" in your case means one self-hosted server process rather than a database per device.

The distinction that settles it is where the database lives relative to the user. If each install owns its own data and the app has to work with the network off, SQLite is embedded in your process: no daemon to supervise, no port to claim, no `initdb` on first run, no version-mismatch on the data directory when a user upgrades your app after skipping three releases. Shipping Postgres to end machines means you have taken on the job of a distro packager, and the failure modes land on people who cannot read a log. That packaging burden, not query performance or SQL features, is what usually decides this.

The part of your question I'd push back on is the premise that storage is the decision you can get wrong. It mostly isn't. Both are SQL, schemas and migrations port with modest effort, and if you keep queries behind a data-access layer and avoid engine-specific types you can move later. The expensive, hard-to-reverse choice sitting behind this one is sync and conflict resolution: whether you use CRDTs, last-writer-wins per field, an operation log, or a sync engine that owns the wire format. That decision reaches into your schema and your application semantics, and changing it later is a rewrite. It also constrains storage more than the reverse, because most of the sync ecosystem assumes a SQLite-shaped local store. ElectricSQL and PowerSync both sync a Postgres server to SQLite clients, so the realistic architecture is often both engines rather than a choice between them.

Postgres on the local machine earns its keep in a few specific cases:

- "Local" means a single instance on a LAN serving a team, not a copy per device, so you are really running a small server and just calling it local.
- You need many concurrent writers. SQLite in WAL mode allows concurrent readers but one writer at a time, which is invisible in a single-user desktop app and a real ceiling if several processes write.
- You depend on extensions with no adequate SQLite counterpart: PostGIS, mature full-text search with ranking, `pgvector` at scale, or `LISTEN`/`NOTIFY`.
- You already run Postgres server-side and want a single dialect, one set of migrations, and one query builder across both halves.

If you go with SQLite, a handful of settings prevent most of the trouble people attribute to the engine:

```sql
PRAGMA journal_mode = WAL;       -- concurrent readers alongside a writer
PRAGMA busy_timeout = 5000;      -- block instead of failing on SQLITE_BUSY
PRAGMA foreign_keys = ON;        -- off by default, per connection
PRAGMA synchronous = NORMAL;     -- safe with WAL, much faster than FULL
```

Declare tables `STRICT` so column types are enforced rather than advisory, serialise writes through a single connection or a one-slot write pool, and store timestamps as integers or ISO-8601 text rather than relying on the loose affinity rules.

The one thing I'd resolve before writing schema is whether the data ever needs to merge across devices, since that is where the design cost actually sits.

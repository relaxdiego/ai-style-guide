SQLite, unless you already know you need a server. "Local-first" means the database lives on the user's device, and Postgres is a networked server process you'd have to install, supervise, and port-forward on every machine you ship to. That's a large operational tax for query features you probably won't use.

**Where the choice actually flips**

| Signal | Pick |
|---|---|
| Data lives on the device, one app process | SQLite |
| Embedded, zero-install, single file to back up or copy | SQLite |
| Many concurrent writers across processes or machines | Postgres |
| You need `jsonb` indexing, real full-text ranking, PostGIS, window-heavy analytics | Postgres |
| Dataset outgrows one disk, or you need row-level security | Postgres |

**If you go SQLite, the settings matter more than the engine choice.** Turn on WAL mode (`PRAGMA journal_mode=WAL`) so a reader doesn't block a writer, set `busy_timeout` to a few seconds so you get waiting instead of `SQLITE_BUSY`, and use `foreign_keys=ON` (off by default, which surprises people). Keep exactly one writer connection in your app; SQLite serializes writes anyway, and a pool of writers just converts that into lock errors.

The thing that will actually bite you is sync, not storage. If this app ever syncs between two devices, the hard part is conflict resolution and change tracking, and that pushes you toward a design decision you should make now: either a CRDT layer, or a monotonic change log with server-assigned versions. That choice constrains your schema (you'll want per-row version columns or an ops table) far more than SQLite vs Postgres does. If you also need a server-side copy for sync, the normal shape is SQLite on device and Postgres on the server, so this isn't necessarily either/or.

One question that would change my answer: is there a server component, and does it hold a full copy of every user's data?

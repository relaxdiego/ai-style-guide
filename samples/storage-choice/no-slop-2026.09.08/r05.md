SQLite, unless the data lives on a server you control. Postgres doesn't embed in a client app: you'd be shipping a server process, a data directory, and a version-upgrade story to every user's machine. That's the whole decision for the local half.

Where they actually differ for your case:

| | SQLite | Postgres |
|---|---|---|
| Runs in-process on the user's device | yes | no, separate server |
| Concurrent writers | one at a time (WAL gives you concurrent readers + one writer) | many |
| Types | dynamic, no native `jsonb`, weak constraint story pre-3.37 | rich types, `jsonb`, arrays, ranges |
| Full-text | FTS5, good enough | tsvector, better |
| Schema migration | `ALTER TABLE` is limited; table-rebuild pattern is standard | full DDL |
| Sync ecosystem | Turso/libSQL, Electric, cr-sqlite, PowerSync, Litestream | logical replication, but not client-side |
| Ops burden on user machines | zero | real |

The version that bites people is not the engine, it's sync. If the app ever syncs between devices or to a server, decide now how conflicts resolve (last-write-wins per field, CRDTs, or server-authoritative with a change log), because that dictates your schema: you'll need per-row `updated_at`, a stable client-generated ID (UUIDv7 rather than autoincrement), and probably tombstone rows for deletes. Retrofitting those onto a schema built for a single local database is the expensive migration, and it's expensive whichever engine you picked. If you have a server component too, the normal shape is SQLite on-device and Postgres on the server, with a change-log table on both sides; that's two schemas to keep aligned, so write the sync protocol before you write the second schema.

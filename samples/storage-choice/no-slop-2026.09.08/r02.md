SQLite, unless you have a specific reason that forces a server. "Local-first" means the app reads and writes on-device without a network round trip, and Postgres is a server process you'd have to ship, supervise, and version-upgrade on every user's machine. That's a real operational cost paid on day one against benefits most local-first apps never collect.

What would actually change the answer:

| Fact about your app | Implication |
|---|---|
| Multiple OS processes or machines write the same file | Postgres. SQLite's single-writer lock and network filesystems don't mix. |
| One app process, many threads, WAL mode | SQLite is fine. Reads are concurrent; writes serialize, and a write is typically microseconds. |
| You need pgvector, PostGIS, or logical replication | Postgres, or accept SQLite's weaker equivalents (`sqlite-vec`, `FTS5`, no replication). |
| Data over ~100 GB per user, or complex analytical queries | Postgres. SQLite's planner is weaker and it has no parallelism. |
| You sync to a shared backend | Doesn't force the local choice. Local SQLite plus server Postgres is the common shape (PowerSync, ElectricSQL, Turso all assume it). |
| You want one schema and one query dialect across local and server | Postgres both sides, with something like PGlite or an embedded instance locally. This is the strongest argument for Postgres, and it's a developer-experience argument, not a runtime one. |

Two things that bite people who pick SQLite and haven't used it seriously: turn on WAL mode and set a `busy_timeout` (defaults are 0, and you'll see `SQLITE_BUSY` under any concurrency), and know that column types are advisory unless you declare `STRICT` tables. Neither is hard, both are silent if you skip them.

SQLite, unless the app has a server component that multiple users write to concurrently. "Local-first" means the database file sits on the user's device, and Postgres is a network server with a daemon, a user/auth model, and a version-upgrade story you would have to ship and manage on every machine.

What actually separates them for your case:

| | SQLite | Postgres |
|---|---|---|
| Deployment | one file, linked into your process | separate daemon, needs install/upgrade per machine |
| Concurrency | many readers, one writer at a time (WAL) | many concurrent writers, MVCC |
| Startup cost | microseconds, no connection | connection pool, socket, auth |
| Schema migration on user machines | you run it at app start | you must coordinate with a running server and its data directory |
| Types/extensions | dynamic typing, JSON1, FTS5, sqlite-vec | rich types, PostGIS, pgvector, RLS, LISTEN/NOTIFY |
| Sync tooling | cr-sqlite, PowerSync, Turso embedded replicas, ElectricSQL | it's usually the server side of those |
| Backup | copy the file | pg_dump, WAL archiving |

Pick Postgres only if one of these is true: a single shared server takes concurrent writes from many users, you depend on an extension with no SQLite equivalent (PostGIS is the usual one), or you need row-level security enforced in the database. Note that these are not exclusive: the standard shape for a local-first app that syncs is SQLite on the device and Postgres on the server, with a sync protocol between them.

The choice you should worry about more is the sync layer, because it constrains your schema. Conflict resolution by CRDT (cr-sqlite) wants merge-friendly tables and forbids some constraints; last-write-wins with a server authority (PowerSync, Turso) lets you keep normal schemas but needs per-row version columns and a server that resolves conflicts. Decide that before you write the schema; swapping engines later is a weekend, swapping sync models is a rewrite.

SQLite, unless you already know you need a server. For a local-first app the local store runs in-process on the user's machine, and Postgres is a separate daemon you'd have to install, supervise, and version-upgrade on every user's box. That's a distribution problem, not a database problem.

The choice that actually carries risk is the sync layer, not the embedded engine. SQLite vs Postgres on the client is mostly reversible: both speak SQL, and a schema written against one ports in a day or two. How you merge concurrent edits from two devices is not reversible, because it determines your data model (last-write-wins columns, CRDTs, an append-only op log) and reaches into every table.

**Where SQLite is the clear pick**

- Single-process or single-user access to the file
- You ship a desktop/mobile binary and can't require a service install
- Working set fits on disk and you want zero-config startup
- You want cheap file-level backup, copy, and reset

**Where you'd need Postgres**

- Multiple OS processes or machines writing the same data concurrently
- You depend on specific server features: real `ALTER TABLE ... ALTER COLUMN TYPE`, row-level security, `LISTEN/NOTIFY`, rich types (jsonb operators, arrays, PostGIS), full-text search beyond FTS5
- A server-side component already exists and the "local" store is a cache

**Concrete gotchas if you take SQLite**

- Set `journal_mode=WAL` and a `busy_timeout`. The default rollback journal serializes readers against a writer, and the default busy timeout of 0 turns contention into `SQLITE_BUSY` errors.
- Writes serialize: one writer at a time, database-wide. Fine for a single user, fatal if you later put it behind a multi-tenant server.
- Type affinity is loose. Use `STRICT` tables (3.37+) if you want the column types enforced.
- `ALTER TABLE` is limited: you can add, rename, and drop columns, but changing a column's type or constraints means the 12-step table rebuild. Write migrations as rebuilds from the start.

What's your sync story? If two devices can edit the same record while offline, that answer shapes the schema far more than the engine does, and I'd rather help you get that right.

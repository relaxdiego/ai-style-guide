SQLite, unless you have a specific reason that isn't showing up in your question. "Local-first" means the database runs on the user's device, and Postgres does not embed: you'd be shipping a server process, a data directory, a port, and an upgrade path for every user's machine. SQLite is a file and a library. The asymmetry is large enough that Postgres needs an affirmative argument, not the other way around.

The cases that actually flip it:

- **You need a server-side copy anyway.** Then it's usually both: SQLite on device, Postgres in the cloud, and the interesting problem is sync, not storage.
- **Multi-process writers on one machine.** SQLite in WAL mode handles concurrent readers plus one writer fine. Many writing processes contending is where it gets ugly.
- **You genuinely need Postgres features locally**: real types, `jsonb` indexing, full-text with ranking, extensions like PostGIS or pgvector. SQLite has answers for some of this (FTS5, JSON1, sqlite-vec) and they're weaker.
- **Datasets past roughly tens of GB with complex queries.** SQLite's planner is decent but not Postgres's.

The decision you're more likely to get wrong is not the engine. It's whether your schema and write path can tolerate the same row being edited on two devices while offline. Picking a sync approach (CRDTs, last-write-wins per field, an operation log you replay) constrains your schema hard, and retrofitting it is a rewrite. If you decide that first, the storage choice mostly falls out of it: most local-first sync layers worth using (Electric, PowerSync, cr-sqlite, Turso's embedded replicas) assume SQLite on the client. Also, SQLite to Postgres later is a real migration but a tractable one; the sync model is the part that isn't.

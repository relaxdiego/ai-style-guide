SQLite, unless something on your list forces Postgres. "Local-first" means the database lives in your app's process on the user's machine, and Postgres is a server: you'd have to bundle it, run `initdb`, pick a port, keep a daemon alive, and handle major-version upgrades on machines belonging to people who never agreed to operate a database. SQLite is a file and a library, so most of that disappears.

Pick Postgres instead only if one of these is true:

- "Local" means self-hosted on a box you control (Docker on a team server), not on each end user's laptop.
- You need multiple OS processes writing concurrently. SQLite in WAL mode gives you many readers plus one writer; if that writer is contended, you'll feel it.
- You need something Postgres has and SQLite doesn't: PostGIS, real full-text with ranking, `LISTEN/NOTIFY`, rich types, row-level security, logical replication.
- Your dataset exceeds what one machine's disk and one writer can serve.

Two things deserve the anxiety you're aiming at the engine. First: the sync layer. If devices go offline and reconcile later, your conflict-resolution model (last-write-wins, CRDT, server-authoritative operation log) determines the architecture far more than the storage engine does, and most local-first sync stacks (ElectricSQL, PowerSync, cr-sqlite, Turso embedded replicas) assume SQLite on the client and Postgres on the server anyway, so "both" is the normal shape. Second: dialect lock-in. If you use `STRICT` tables, keep to plain SQL, and route writes through one data-access layer, moving to Postgres later is a schema translation and a migration script, not a rewrite. The genuinely expensive mistakes are scattering raw engine-specific SQL through the codebase and letting SQLite's loose typing put garbage in columns.

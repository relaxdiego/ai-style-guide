SQLite, unless you have a specific reason you can name right now. For a local-first app the deciding factor isn't query features, it's that Postgres means shipping and supervising a server process on someone else's machine: a data directory you own, a port that can collide, and `pg_upgrade` running on a laptop that may lose power halfway. When that fails, it fails on a user's machine where you can't debug it. SQLite is a file, and version upgrades are your migration code running in-process.

The decision is also less permanent than it feels, if you keep raw SQL out of your UI layer and behind a data-access module. Migrating SQLite to Postgres later is real work but bounded; the schema and query dialects overlap heavily for ordinary CRUD.

Things that would actually flip me to Postgres:

- Multiple independent OS processes writing concurrently and often. SQLite in WAL mode gives you concurrent readers with one writer; if you have several writers contending, you'll be fighting `SQLITE_BUSY`.
- You need a genuine server feature at the storage layer: logical replication, `LISTEN/NOTIFY` across machines, or an extension with no SQLite equivalent you'd accept.
- "Local-first" here means "developer runs it locally, deploys to a server," in which case it isn't local-first and you should match production.

One thing that changes the shape of this: if you plan to sync across devices, that's a separate decision from the local store, and it constrains your schema (you'll want stable IDs and some change-tracking, CRDTs or an operation log).

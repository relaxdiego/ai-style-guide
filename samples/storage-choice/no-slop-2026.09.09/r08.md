SQLite, unless you have a specific reason that doesn't exist yet. Local-first means the database ships inside your process on someone else's machine, and Postgres is a daemon: a data directory tied to a major version, `pg_upgrade` on every bump, a port, a service supervisor, and a support burden when a user's machine reboots mid-write. SQLite is a file and a library call. If you also run a server for sync, that server can be Postgres; the two aren't competing for the same slot.

The thing you're worried about getting wrong is probably not the engine. Sync is the hard part (conflict resolution, oplog or CRDT design, schema migration across clients you don't control), and that work is nearly identical either way. Engine choice mostly determines your query surface, and you can keep that portable cheaply: plain SQL, one access layer, no engine-specific types until you need them.

What would actually flip it:

- **You need Postgres-only features on the client**: `pgvector` for local embedding search, PostGIS, full `jsonb` query operators, or logical replication as your sync transport. SQLite has answers for some of these (FTS5, JSON1, `sqlite-vec`) but they're not equivalent.
- **Multiple OS processes writing concurrently**. SQLite in WAL mode gives concurrent readers and one writer; if that writer is a separate process holding transactions open, you'll hit `SQLITE_BUSY` and start building a lock protocol you didn't want.
- **You're writing "local-first" but mean "self-hosted server"**. Then it's a server database and Postgres wins on the usual grounds.

Two SQLite-specific costs to accept up front: dynamic typing will let bad rows in unless you use `STRICT` tables, and `ALTER TABLE` is limited enough that non-trivial migrations mean create-copy-rename. Both are manageable, neither is a surprise you want to meet in production.

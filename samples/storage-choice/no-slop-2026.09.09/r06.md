SQLite, unless you already know you need a network-accessible server. For a local-first app the database runs in your process, and SQLite's whole design (single file, no daemon, embedded) matches that. Postgres embedded on a user's machine means shipping and supervising a server process, which is real operational weight for the user's laptop.

Things that would flip it to Postgres:

- Many concurrent writers against shared state over a network. SQLite in WAL mode gives you concurrent readers plus one writer; that's fine for one app instance, not for a multi-tenant backend.
- A specific Postgres feature you can't approximate: PostGIS, pgvector, ranked full-text, rich `jsonb` querying, stored procedures.
- You already plan a server tier and want one engine on both sides. PGlite (Postgres compiled to WASM) exists for that, but it's young and single-connection.

The decision you can actually get wrong is sync, not the engine. Swapping SQLite for Postgres later costs you a schema migration and some SQL dialect cleanup, maybe a week, as long as you don't lean on engine-specific syntax. But how you handle two devices editing the same record while offline (last-write-wins per field, CRDTs, an operation log, or a server that arbitrates) leaks into your schema and your UI, and changing it later means rewriting both. So: pick SQLite, then spend your thinking time on whether writes ever conflict, and if so, decide the resolution rule before you design tables. If it's genuinely single-device, say so explicitly and skip that whole layer.

What's the sync story: single device, one user across several devices, or shared editing between users?

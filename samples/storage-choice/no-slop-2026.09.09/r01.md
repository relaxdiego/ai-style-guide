SQLite, unless you need a server process per user, which local-first apps almost never do. Postgres means shipping and supervising a daemon on someone else's machine: install, port conflicts, version upgrades on data you can't inspect, a crash recovery story you now own. SQLite is a file your app opens, with WAL mode, FTS5, and JSON functions that cover most of what people miss.

The three things that would flip it:

- **You actually run a per-user server.** A dev tool that's "local" only in the sense that it runs on localhost, or a desktop app already bundling a container runtime. Then Postgres is fine.
- **You want the same engine on both ends and won't accept schema drift.** PGlite (Postgres compiled to WASM, in-process, one connection) makes this less absurd than it was. It pairs with ElectricSQL for sync.
- **Concurrent writers in the local process.** SQLite serializes writes. WAL means readers don't block, but a heavy multi-threaded write path will contend.

The decision you should actually be nervous about is the sync layer, not the engine. Sync dictates schema shape: CR-SQLite and PowerSync want per-column versions and tombstones, Automerge wants documents rather than rows, ElectricSQL wants Postgres upstream. Pick that first and the engine mostly falls out of it. If you keep the schema in plain SQL and skip engine-specific features, moving SQLite to Postgres later is a week of work, so this is less terminal than it feels right now.

SQLite, unless you have a specific reason you can name today. Local-first means the database ships inside your app: no daemon to install, no port, no service account, no version upgrade that requires `pg_upgrade` on a machine you don't control. Postgres on an end user's device is an ops problem you inherit forever, once per user.

The real question is what "local-first" means in your case. If the app syncs to a shared server, you probably end up with both anyway: SQLite on the client, Postgres on the server, and the decision dissolves. If "local" means a box on a LAN that several clients hit, that's a server and Postgres wins.

Where Postgres actually earns the weight:
- Concurrent writers from separate processes. SQLite allows one writer at a time; WAL mode makes that fine for one app with background tasks, painful for several independent processes hammering writes.
- `jsonb` with GIN indexes, real full-text ranking, `PostGIS`, window-heavy analytical queries.
- Datasets where you need parallel query plans, roughly tens of GB and up.

Cheap insurance, since you're worried about being wrong: use `CREATE TABLE ... STRICT`, declare explicit column types, keep SQL behind one data-access module, and skip SQLite-only functions in application queries. That keeps a later port to Postgres a week of work instead of a rewrite. The migration in that direction is common and well-trodden; going the other way, shrinking Postgres down to ship on a laptop, is not.

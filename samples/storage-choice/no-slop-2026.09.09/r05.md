Pick SQLite unless you have a specific reason not to. Local-first means the data lives on the user's device, and Postgres brings a server process you have to install, supervise, port-assign, back up, and (the painful one) migrate across major versions, since a Postgres 17 data directory won't start under 18 without a dump/restore. SQLite is a file. Turn on WAL mode, set a busy timeout, and a single-user desktop or mobile app will not touch its limits.

Three things would flip me to Postgres: multiple OS processes or machines writing the same database concurrently; you need types and features SQLite lacks that are central to the product (real `jsonb`, full-text with ranking beyond FTS5, PostGIS, concurrent writers); or you're running the identical schema on both client and server and the duplicated migration work costs more than the ops burden. If it's mainly the third, look at PGlite, which is Postgres compiled to WASM running in-process, so you get Postgres semantics without a daemon. It's newer and single-connection, so treat it as a real dependency rather than a free win.

The part you can actually get wrong isn't the engine. Plain SQL ports between the two with modest pain (upsert syntax, `ALTER COLUMN` which SQLite mostly can't do, type affinity), so this is a few weeks of work to reverse, not a rewrite. What's expensive to reverse is the sync and conflict-resolution model: whether rows carry version vectors or last-write-wins timestamps, whether you ship operations or state, whether deletes leave tombstones. Decide that first and the storage question mostly answers itself.

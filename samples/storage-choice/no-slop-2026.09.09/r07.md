SQLite, unless you're planning to run a server process anyway. For a local-first app, Postgres means shipping and supervising a separate daemon on every user's machine: install, port conflicts, version upgrades on user data you can't inspect, an OS service that dies and needs restarting. SQLite is a library call against a file. Turn on WAL mode, set `busy_timeout`, use `foreign_keys=ON`, and it handles far more concurrency than its reputation suggests.

The things that would actually flip this, in rough order of how often they're real:

- **Multiple OS processes writing the same database over a network filesystem.** SQLite's locking is unreliable on NFS/SMB. If your file lives in a Dropbox or iCloud folder, SQLite is not just suboptimal, it will corrupt.
- **You need a Postgres-only feature at the local tier**: `pgvector`, real full-text ranking, PostGIS, `jsonb` operators, strict types. SQLite has answers for most (FTS5, `sqlite-vec`, `STRICT` tables), so check whether the specific gap is real before deciding on it.
- **The "local" database is really a shared one on a LAN box** that several clients hit. Then it's a server, and Postgres wins.

The part you can actually get wrong is not the engine. Swapping SQLite for Postgres later is a few weeks of work if you keep queries boring and avoid an ORM's dialect-specific corners. What's expensive to change is the sync and conflict model: whether rows carry stable UUIDs instead of autoincrement integers, whether you log changes for later replay, and what happens when two devices edit the same record offline. Decide that now; the storage engine can wait.

SQLite, unless "local" actually means a server you operate. For an app where data lives on the user's device, Postgres means shipping and supervising a server process per install: port conflicts, version upgrades, `initdb`, a data directory you have to back up as a directory rather than a file. SQLite is a library and one file, and WAL mode gives you concurrent readers with a single writer, which is what a single app process needs.

Things that would flip me to Postgres:

- Multiple OS processes writing the same database concurrently, not just threads in your app.
- You need Postgres-only features on the client: PostGIS, pgvector at scale, `LISTEN/NOTIFY`, real stored procedures.
- "Local-first" here means self-hosted on a box the user admins, where a service is normal.
- Datasets past roughly tens of GB per user with heavy analytical queries.

The decision you should actually be nervous about is sync, not storage. Most local-first sync tools already picked for you: PowerSync and ElectricSQL put SQLite on the client and Postgres on the server, cr-sqlite and Turso embedded replicas are SQLite-only, Automerge does not use SQL at all. Choose the sync and conflict-resolution model first and the engine falls out of it. Storage is also the cheaper mistake: if you keep to plain SQL and route queries through one module, moving engines is a week. Rewriting your merge semantics after users have divergent data is not.

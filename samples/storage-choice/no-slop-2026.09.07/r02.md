SQLite on the device, Postgres only if and when you add a server. Running Postgres on end-user machines means shipping a server process, a data directory you have to own, and major-version upgrades that require pg_upgrade to run successfully on a laptop you cannot log into. That last one is the support burden that ends the discussion.

The storage engine is also not the decision you can get wrong in a way that costs you. Schema and queries port between the two with a few days of work. What does not port is the sync and conflict model: once users have written data on two devices under a given set of merge rules, changing those rules means migrating history you no longer control. Decide that first, then let it pick the engine, because some sync layers only work with one.

| | SQLite | Postgres |
|---|---|---|
| Runs in-process | yes | no, separate server (PGlite is WASM, single connection) |
| Per-user file you can copy, back up, delete | yes | data directory, not portable across major versions |
| Concurrent writers | one at a time, WAL lets readers through | real MVCC |
| Major-version upgrade on user machine | file format stable since 2004 | pg_upgrade, and you own the failures |
| Types | dynamic unless you use STRICT tables | real types, arrays, jsonb, ranges |
| Full text | FTS5, good | tsvector, better, plus pg_trgm |
| Sync options | cr-sqlite, Turso/libSQL, Ditto, or roll your own oplog | ElectricSQL, Zero, logical replication to a server |

Pick Postgres for the local store only if one of these is true:

- You need multiple OS processes writing the same database concurrently, and cannot funnel writes through one process.
- You depend on a Postgres-only extension in the local path, most likely PostGIS or pgvector at a scale sqlite-vec cannot handle.
- Your sync layer is Electric or Zero, which assume Postgres upstream. Note both still put SQLite or an in-browser store on the client.

The SQLite choices that are genuinely hard to undo, so make them on day one:

- **STRICT tables.** Retrofitting type enforcement onto a database full of mixed-type columns is a data cleanup, not a migration.
- **How you store timestamps.** Pick one representation, ISO 8601 text in UTC or integer epoch milliseconds, and never mix. SQLite will not stop you.
- **Whether rows carry a stable identity independent of the device.** UUIDv7 or similar. Autoincrement integers collide the moment two devices sync.
- **An append-only change log next to your tables from the first commit.** Every sync design needs one, and you cannot reconstruct history you never wrote.
- **WAL mode plus a busy_timeout.** The default rollback journal and a zero timeout produce SQLITE_BUSY under trivial contention, and people conclude SQLite cannot handle concurrency.

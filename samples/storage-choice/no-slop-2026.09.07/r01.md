SQLite on the device, Postgres on the server if you have one. For local-first that's the default, and you need a specific reason to deviate.

Why SQLite on the device:

- No server process. It's a library linked into your binary. No port, no daemon, no install step the user sees.
- Runs on every target: desktop, iOS, Android, browser via WASM plus OPFS.
- One file. Backup, copy, corrupt-and-reset, ship-a-seed-database are all trivial.
- Every mature local-first sync stack assumes it on the client: PowerSync, ElectricSQL, cr-sqlite, Turso/libSQL, Rocicorp Zero.

When Postgres on the device is actually the right call:

- "Local-first" for you means a self-hosted server on a machine the user owns, not per-device replicas. Then run real Postgres and skip the sync problem entirely.
- You want one SQL dialect across client and server badly enough to use PGlite (Postgres in WASM). Single connection, young, but it's real.
- You need PostGIS, pgvector at scale, or server-side functions on the client.

What SQLite will cost you, so it isn't a surprise later:

| Thing | Reality |
|---|---|
| Typing | Dynamic by default. Use `STRICT` tables from day one. |
| Foreign keys | Off by default, per connection. You must set `PRAGMA foreign_keys=ON` every time. |
| Concurrency | One writer. WAL gives you concurrent readers. Fine for one user, bad if many background jobs write. |
| Migrations | Limited `ALTER TABLE`. Non-trivial changes mean rebuild-and-copy. |
| Types | No native date/time. JSON functions exist, JSONB since 3.45. |

Now the part you're actually worried about. The engine is the cheap decision: boring SQL ports between the two in a few days, and an ORM or query builder makes it cheaper. The expensive decision is what happens when two devices edit the same record while offline, because that dictates your schema. Last-write-wins on a whole row needs a version column and a tombstone table. Field-level merge needs per-field timestamps or a CRDT library sitting under your data model. Retrofitting the second onto a schema built for the first is a rewrite, not a migration.

So decide the conflict-resolution model first, then check which engines your chosen sync stack supports. That order almost always lands you on SQLite locally with Postgres upstream, and you'll have arrived there for a reason instead of by default.

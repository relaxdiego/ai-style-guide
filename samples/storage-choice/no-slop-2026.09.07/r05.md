SQLite on the device, and Postgres only if you also have a server that the devices sync to. For a genuinely local-first app, "Postgres" means shipping a database server to every user machine, and that is a support burden with almost nothing to show for it.

| | SQLite | Postgres |
|---|---|---|
| Deployment | file in your app dir, no process | server process, port, version per machine |
| Cold start | microseconds | seconds, plus a supervisor to keep it up |
| Concurrent writers | one at a time, WAL gives concurrent readers | many |
| Platform reach | iOS, Android, browser via OPFS, desktop | desktop only, awkward on mobile, WASM via PGlite |
| Backup | copy one file | pg_dump, or copy a data dir carefully |
| Types | dynamic, no native arrays, JSON via functions | jsonb, arrays, ranges, enums, custom types |
| Search / vectors | FTS5, sqlite-vec | tsvector, pgvector |
| Upgrades on user machines | file format has been stable since 2004 | binary upgrade across major versions, on a laptop you do not control |

What would flip me to Postgres, or to PGlite as a middle path:

- **Multiple OS processes writing the same data.** SQLite's single-writer lock turns into contention and `SQLITE_BUSY` handling you will get tired of.
- **You want one SQL dialect on client and server.** PGlite is Postgres compiled to WASM, single connection, a few megabytes. Pairs with ElectricSQL for sync.
- **Heavy analytical queries over large local datasets.** SQLite's planner is weaker and it has no parallelism. DuckDB is a better answer here than Postgres.
- **The "local" database is really a dev-mode copy of production.** Then it is not local-first and you should just run Postgres.

The decision you can actually get wrong is not the engine. Swapping SQLite for Postgres later costs you a schema translation and a rewrite of any raw SQL, which is days to weeks and entirely mechanical. The sync and conflict-resolution model is the expensive one: last-write-wins per row, per field, CRDTs, or an operation log, because that choice determines your schema, your table design, whether every row carries a version vector, and what your app can promise a user who edited offline for a week. Pick that first, then let it constrain the engine. ElectricSQL and PowerSync assume Postgres upstream, cr-sqlite and Automerge assume SQLite locally, and Turso/libSQL gives you SQLite with a hosted replica.

SQLite on the client, and Postgres on the server if you have one. For a local-first app, Postgres running on each user's machine is a support burden you will regret: a process to install, supervise, upgrade, and repair when a user's laptop sleeps mid-write.

| | SQLite | Postgres |
|---|---|---|
| Deployment | linked into your process, one file on disk | separate server process, installed and upgraded per machine |
| Platforms | iOS, Android, macOS, Windows, Linux, browser via wasm | desktop only in practice; PGlite is a wasm build |
| Concurrency | WAL gives one writer, many readers | many concurrent writers, MVCC |
| Types | dynamic unless you use STRICT tables | strict, with arrays, jsonb, ranges |
| Query features | window functions, JSON functions, FTS5 | better planner, PostGIS, pgvector, configurable full text |
| Per-user ops cost | none | real, and it is yours |
| Corruption recovery | copy a file from backup | pg_basebackup, WAL replay, user has no idea |

The decision that will actually cost you is the sync layer, not the engine. Pick that first and the storage often follows from it:

- **Electric SQL**: Postgres server, SQLite client, partial replication driven by shapes you define. Client dialect is SQLite.
- **PowerSync**: same arrangement, Postgres or MongoDB or MySQL upstream, SQLite on device. More mature commercially.
- **Turso / libSQL**: SQLite fork with embedded replicas, read-your-writes locally, writes forwarded to a primary. Good if reads dominate.
- **cr-sqlite**: CRDTs inside SQLite, peer to peer merge, no server required.
- **Automerge or Yjs**: document CRDTs with SQLite as the persistence layer. Best when the data is documents, worst when you need relational queries over it.
- **PGlite**: Postgres compiled to wasm, single connection, no mobile story yet. Use it only if writing one SQL dialect across client and server is worth more than mobile support.

Choose local Postgres only if you hit one of these: multiple OS processes writing concurrently at high rate, PostGIS or pgvector workloads that SQLite extensions cannot cover, or a desktop-only app where you already control the install (Docker on developer machines, for example).

Three things to do now so the choice stays cheap to revisit: use STRICT tables and explicit column types so the schema means the same thing in both engines, keep application queries free of engine-specific syntax outside a thin data-access module, and version your schema with plain migration files rather than an ORM's autogeneration. The migration you cannot undo cheaply is the sync protocol, so prototype sync against real data volumes and a real offline-then-reconnect sequence before you commit.

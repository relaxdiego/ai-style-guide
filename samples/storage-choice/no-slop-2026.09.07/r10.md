SQLite on the device, and Postgres only if you also have a server, in which case you run both and it stops being a choice. Real Postgres on an end-user machine means shipping a separate server process, a per-user data directory, and a `pg_upgrade` across major versions on hardware you do not control. That last one is the part people underestimate: a user opens your app after skipping three releases, and you are running a database major-version upgrade unattended on their laptop with their only copy of their data.

| | SQLite on device | Postgres on device |
|---|---|---|
| Install | one file linked into your process, under 1 MB | separate server, tens of MB, lifecycle you manage |
| Ops burden on users | none | port conflicts, stale postmaster, permissions, upgrades |
| Concurrency | one writer, many readers in WAL mode | many writers |
| Browser | official wasm build with OPFS, plus wa-sqlite | PGlite, wasm, single connection, much younger |
| Crash safety | WAL plus `synchronous=NORMAL` is solid | solid |
| Backup | copy a file, or `VACUUM INTO` | `pg_dump`, or a filesystem-level dance |

The decision you can actually get wrong is not the engine. It is the set of choices that a sync layer needs and that are expensive to retrofit onto data already sitting on users' machines:

- **Row identity.** Client-generated UUIDv7 or ULID, decided now. Autoincrement integers assigned per device collide the moment two devices sync, and rewriting keys across live installs is the worst migration you will ever do.
- **Deletes.** Tombstones with a timestamp, not `DELETE`. A row that vanishes is indistinguishable from a row that never arrived.
- **Change tracking.** Either every table carries an updated-at and a version counter from day one, or you add a write-ahead log table with triggers. Retrofitting this means you cannot tell what changed while old clients were offline.
- **Where writes go.** One module that owns mutations. If writes are scattered across the codebase, adding sync later means auditing every call site.
- **Schema migrations against old clients.** Additive only, defaults on new columns, and never reuse a dropped column name. Devices will run six-month-old code against a schema your server has moved past.

Keep the SQL itself boring and portability comes nearly free: `STRICT` tables, explicit types, no dependence on SQLite's dynamic typing, FTS5 isolated behind a search function you could swap for `tsvector`. If you later decide the local store should be PGlite or something else, that subset ports in a day. The five items above do not port at all, so spend your worry there.

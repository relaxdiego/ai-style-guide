**SQLite on the device. Postgres on the server, if you have one.**

Postgres is a server process with a data directory, a port, and an upgrade path that requires `pg_upgrade` or a dump/restore between major versions. Embedding one per user means supervising that process on machines you don't control, migrating data directories on machines that may be offline for months, and colliding with users who already have something on 5432. SQLite is a library call against a file. On iOS, Android, and in the browser it is the only one of the two that runs without compiling Postgres to WebAssembly.

| | SQLite | Postgres |
|---|---|---|
| Runs on device | Yes, everywhere, in-process | Server process, or PGlite in wasm |
| Concurrent writers | One at a time; WAL lets readers run during a write | Real MVCC, many writers |
| Types | Dynamic, no native `jsonb`/arrays/enums, `ALTER TABLE` is limited | Full type system, rich `ALTER TABLE` |
| Full text | FTS5, good | `tsvector`, better, plus extensions |
| Vectors | `sqlite-vec` | `pgvector` |
| Per-user ops cost | Zero | Process lifecycle, port, data dir upgrades |
| Sync ecosystem | PowerSync, cr-sqlite, Turso embedded replicas, Zero | ElectricSQL, and PGlite as the client store |

Local Postgres earns its cost in three cases:

- Multiple OS processes write the same database concurrently, and you can't funnel them through one writer.
- You depend on a Postgres extension with no SQLite equivalent, and reimplementing it is worse than shipping a server.
- You want byte-identical query semantics between client and server, and PGlite gets you that in-process.

The decision you'll actually regret is the sync and conflict model, not the engine. Last-write-wins on a whole row will silently eat edits the moment two devices touch the same record offline; per-field merge, CRDTs, or an operation log each impose different schema requirements, and retrofitting them means rewriting every write path and backfilling history you no longer have. Pick that first, because most sync products assume a specific client store and hand you the engine as a consequence: PowerSync and cr-sqlite mean SQLite, ElectricSQL points at PGlite.

Keep the engine cheap to swap by writing plain SQL through a thin repository layer, avoiding vendor-specific types in the schema, and running the same migration files against both engines in CI. Do that and the storage question stops being the one that can go wrong.

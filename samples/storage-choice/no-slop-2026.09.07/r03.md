**SQLite on the device. Postgres on the server, if there is a server.** That is the standard local-first split, and every mature sync stack (Electric, PowerSync, cr-sqlite, Turso) is built on exactly it.

I'm reading "local-first" as: data lives on the end user's machine, the app works offline, and it syncs when it can. If you actually mean a self-hosted server the user runs in a container, that flips things and Postgres is fine.

The decision you're worried about is not the one that will hurt you. Shipping Postgres to a user machine means a background process, a port, a data directory you don't control, and `pg_upgrade` on every major version bump on hardware you can't test. SQLite is a file. The thing that is genuinely hard to reverse is the sync design and any schema that quietly assumes one writer, so that's where the care belongs.

| | SQLite | Postgres |
|---|---|---|
| Install on user machine | linked into your binary | separate service, data dir, upgrades |
| Writers | one at a time, WAL gives concurrent readers | true MVCC, many writers |
| Cross-process access | works, with lock contention | designed for it |
| Types | dynamic unless you use `STRICT`; no date type | rich: jsonb, arrays, ranges, timestamptz |
| Backup | copy the file, or `VACUUM INTO` | pg_dump, WAL archiving |
| Full-text | FTS5, good enough for local corpora | tsvector, better for large ones |
| Vectors | sqlite-vec, adequate at local scale | pgvector, better at scale |
| Failure mode you'll hit | `SQLITE_BUSY` | connection and upgrade management |

Pick Postgres for the client only if one of these is true:

- Multiple OS processes write concurrently and heavily, not just threads inside your app.
- You need PostGIS, or pgvector over millions of rows, on the client.
- You want logical replication itself as the sync transport.
- Your users are operators who already run containers, and "local" means their box.

Get these right on day one, because they cause most SQLite pain that gets blamed on SQLite:

- `journal_mode=WAL` and `synchronous=NORMAL`.
- `busy_timeout=5000` on every connection.
- `foreign_keys=ON` per connection. It's off by default.
- `STRICT` tables so the column types mean something.
- One writer connection, a pool of readers.
- Never on a network filesystem. WAL locking breaks on NFS and SMB.
- One timestamp representation, chosen now: ISO-8601 UTC text or Unix integer.

If you want to keep the door open, the SQL that actually diverges is upsert syntax, autoincrement, JSON functions, and date arithmetic. Keep those behind a thin layer and a later move costs days, not a rewrite. PGlite exists if you want Postgres semantics in-process, but it's single-connection and far less battle-tested than SQLite on desktop; I wouldn't put user data on it yet.

**SQLite.** For anything running on an end user's machine, Postgres is a server you now have to install, supervise, and upgrade on hardware you don't control, and that cost has nothing to do with the query language.

The thing that actually decides it is the on-disk format upgrade. Postgres major versions change the data directory layout, so shipping an app update linked against 18 to a user whose laptop holds an 17 data directory means running `pg_upgrade` on their machine with both sets of binaries present, unattended, with no rollback if it dies halfway. SQLite has held its file format stable since 2004 and reads it in-process.

| | SQLite | PGlite | Postgres |
|---|---|---|---|
| What it is | Library linked into your process | Postgres 17 compiled to WASM | Separate server process |
| Ships to user machines | Yes, ~1 MB | Yes, ~3 MB gzipped | Painful |
| Data dir upgrades | File format stable since 2004 | Tied to PG major version | `pg_upgrade` on the user's machine |
| Concurrent writers | One at a time (WAL), readers never block | One connection, single process | Real MVCC, many writers |
| Runs in a browser | Via wa-sqlite / OPFS | Native use case | No |
| Sync ecosystem | cr-sqlite, PowerSync, Turso, Ditto | ElectricSQL | Server side of any of these |

Two cases push away from plain SQLite. If you're in a browser and want Postgres semantics (real types, `jsonb`, pgvector, window functions you'd otherwise hand-roll), PGlite is a genuine option and ElectricSQL is built around it, with the caveat that it's one connection in one process and has a fraction of SQLite's deployment history. If "local-first" actually means self-hosted on a box you administer, the constraint disappears and you should just run Postgres.

You're worried about the wrong decision. The storage engine is a few weeks of work to swap; the conflict resolution model is the part that's expensive to get wrong, because it leaks into your schema and your UI. Decide now whether writes are last-write-wins per column, an append-only operation log you replay, or CRDTs, since that determines whether every table needs `updated_at` plus a device ID, or a separate ops table, or column-level metadata. To keep the storage choice cheap, put your schema in plain SQL that both engines accept: skip Postgres arrays, `ENUM` types, `LISTEN/NOTIFY` and row-level security in anything shared, and turn on `STRICT` tables in SQLite so the dynamic typing doesn't quietly accept rows Postgres would reject later.

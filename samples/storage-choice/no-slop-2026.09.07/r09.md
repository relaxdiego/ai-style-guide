SQLite on the device, and spend the thinking budget on the sync engine instead.

Postgres on a client machine means a server process per user, a port, a data directory, and a `pg_upgrade` or dump/restore step every time you bump major versions. You pay that to get features a single user's working set will not exercise. The exception is pglite, which is Postgres compiled to WASM running in-process, single connection, no daemon. If you want one dialect on both ends, that is the honest way to get it.

The decision that is actually expensive to reverse is the sync layer, because it fixes your schema constraints, your conflict rules, and your write path. Pick it first and the local store falls out:

| Sync stack | Client store | Server | Conflict model |
|---|---|---|---|
| ElectricSQL | pglite or Postgres | Postgres | Read-path sync, writes go through your API |
| PowerSync | SQLite | Postgres, MySQL, Mongo | Bidirectional, client upload queue |
| Zero / Replicache | SQLite or IndexedDB | Your server, authoritative | Mutators run client and server, server wins |
| cr-sqlite | SQLite | Optional | CRDT merge between peers |
| Automerge / Yjs | Blobs anywhere | Optional relay | CRDT, document-shaped |
| Turso / libSQL | SQLite embedded replica | libSQL primary | Last write wins at the primary |

Things to settle on the SQLite side before you write schema:

- WAL mode from day one. Concurrent readers, one writer. For a single user that limit essentially never binds.
- `STRICT` tables (3.37+). Without them a text value lands in an integer column and nobody notices for six months.
- Backup means the `.db` plus `-wal` and `-shm`, or `VACUUM INTO` a target file. Copying just the `.db` under load gives you a torn snapshot.
- Migrations are the real friction: you can add, rename, and drop columns, but changing a column type or a constraint is a table rebuild.
- Encryption at rest needs SQLCipher or the paid SEE. Not in stock SQLite.

What ports cleanly if you change your mind later: table definitions, most queries, and anything you kept in plain SQL. What does not: the sync engine's metadata tables, its conflict semantics, and any client code shaped around its mutator API. That asymmetry is the reason to treat SQLite versus pglite as a smaller question than Electric versus PowerSync versus rolling your own on Automerge.

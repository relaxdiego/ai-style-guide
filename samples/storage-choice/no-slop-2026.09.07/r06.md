SQLite, and the decision you are worried about is not this one.

For a local-first app the database runs on the user's device, and Postgres there means shipping and supervising a server process per user: a ~50MB binary, a data directory you have to `pg_upgrade` across releases, a port or socket, and a failure mode where the app is fine but the daemon did not come up. SQLite is a file your process opens. The exception is PGlite, Postgres compiled to WASM, which is embedded like SQLite and gives you real Postgres semantics on device; it is single-connection and much younger, and it is the right pick mainly when your server is Postgres and you want one schema and one dialect on both sides.

| | SQLite | PGlite | Postgres server on device |
|---|---|---|---|
| Deployment | Linked file | Linked WASM module | Separate process to install, supervise, upgrade |
| Size | ~1MB | ~3MB gzipped plus extensions | ~50MB+ and a data directory |
| Types | Dynamic, no native jsonb/arrays/enums | Full Postgres types | Full Postgres types |
| Concurrency | Many readers, one writer (WAL) | One connection | Full MVCC |
| Sync ecosystem | cr-sqlite, Turso/libSQL, Litestream, ElectricSQL clients | ElectricSQL, logical replication semantics | Logical replication |
| Maturity for this use | Ships on every phone | Young | Uncommon, mostly a mistake |

What is actually hard to reverse is how a device write merges with a write another device made while offline, and the schema commitments that make merging possible at all. Retrofitting these is painful because clients in the field already hold rows that lack the columns, so do them now whichever engine you pick:

- **Stable IDs generated on the client.** UUIDv7 or ULID, never an autoincrement integer, or two offline devices mint row 41 and one of them loses.
- **Tombstones.** Soft-delete with a deleted-at column. A row that vanishes is indistinguishable from a row that never synced.
- **Per-row change tracking.** A version counter or Lamport/hybrid logical clock per row, plus last-writer device ID. Wall-clock timestamps alone give you clock-skew bugs you cannot debug from a support ticket.
- **Field-level vs row-level merge, decided per table.** Row-level last-write-wins silently discards a concurrent edit to a different column of the same row. Fine for a settings row, wrong for a document.
- **An append-only local change log.** You need to replay what a device did while offline, not diff its final state.

Pick Postgres for the server side, which you almost certainly want anyway, and pick your sync layer before your engine, because the layer constrains the engine and not the reverse: cr-sqlite and Turso pull you to SQLite, ElectricSQL pulls you to Postgres on the server with either client, and Automerge or Yjs make the database a dumb blob store and move the whole question into the CRDT.

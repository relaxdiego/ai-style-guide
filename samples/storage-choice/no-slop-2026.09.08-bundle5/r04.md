SQLite, unless one of the conditions below applies. Local-first means the database runs inside your process on someone else's machine, and Postgres is a server you'd have to install, supervise, and upgrade there for a working set that one user touches.

What would flip it:

- **Concurrent writers against the same local store.** SQLite in WAL mode allows one writer at a time. Fine for a single app process, painful if you have several processes or a store shared over a network mount. Never put a SQLite file on NFS or SMB; the locking is unreliable and you will get corruption.
- **An extension with no SQLite equivalent.** Real PostGIS work, or pgvector at scale. FTS5 and sqlite-vec cover search and small-to-medium vector cases.
- **You already run Postgres on the server and want one dialect on both ends.** PGlite gets you that: Postgres compiled to WASM, embedded, single-user, no daemon. It's newer and smaller in ecosystem than SQLite, so you're trading maturity for dialect parity.

The engine is the reversible part of this decision, which is why I wouldn't spend much anxiety on it. Both are relational, both do transactions, and a port is a rewrite of your query layer and migrations while the data itself survives. The commitment that's expensive to undo is the sync design: whether conflict resolution is last-write-wins on per-field timestamps, a CRDT, or server-authoritative with a client change log. That choice decides whether every table carries version columns, whether deletes need tombstones, and what your clocks have to guarantee. Retrofitting it onto a schema built without it means migrating every user's local database in the field. Settle that first, then pick SQLite and move on.

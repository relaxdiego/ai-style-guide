SQLite, and it isn't close for the on-device part. Postgres is a server process with a user account, a data directory, a version you have to migrate in lockstep with the binary, and a startup you have to supervise. Shipping that inside a desktop or mobile app means shipping an ops problem to people who did not ask for one. SQLite is a library call, the file is the database, and it survives being copied, backed up, and opened by a different version of your app three years later. If your app also has a server holding the canonical copy or serving multiple users, that side is Postgres, and the two coexist fine: SQLite per device, Postgres in the middle.

Three things would actually flip this:

- **Concurrent writers in a single process tree.** SQLite in WAL mode handles one writer at a time. If you have background sync, indexing, and UI all writing, you serialize through one connection or you meet `SQLITE_BUSY`. Solvable, but design for it up front.
- **You need Postgres-only query features locally.** Full text with ranking beyond FTS5, `jsonb` operators, recursive plan quality on large graphs, real `ALTER TABLE`. SQLite's `ALTER TABLE` is weak enough that migrations become table-rebuild scripts.
- **Data much past a few tens of gigabytes per device**, where SQLite's single-file layout and lack of parallel query start to bite.

The decision you should be nervous about is sync and conflict resolution, not the storage engine. Choosing SQLite costs you a week if you're wrong; choosing "last write wins on whole rows" and discovering at 10,000 users that it silently eats edits costs you a rewrite of everything touching the data model. Decide now whether you're doing CRDTs, an operation log with server-assigned ordering, or explicit user-facing conflict resolution, because that choice dictates your schema, and the schema is what's expensive to change.

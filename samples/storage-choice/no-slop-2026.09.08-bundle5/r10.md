SQLite, unless you can name a specific thing it can't do for you.

"Local-first" means the database lives on the user's device, and Postgres on a user's device means shipping a server process, supervising it, handling port conflicts and version upgrades of an on-disk data directory you don't control. SQLite is a library linked into your app: one file, no daemon, and in WAL mode you get many concurrent readers with one writer at a time, which is what a single app process actually needs. Embedded Postgres builds (PGlite, embedded-postgres) exist and mostly trade the daemon problem for a weight-and-parity problem.

Reasons that would actually flip it:

- Several independent OS processes, or other machines, write to the same store concurrently and you need real MVCC and row-level locks rather than a single-writer lock.
- You depend on an extension with no SQLite equivalent you're willing to live with: PostGIS, pgvector at scale, serious full-text with ranking and stemming.
- The local instance is really a dev copy of a server app and production parity is the point, in which case you're not building local-first.

The decision you can get expensively wrong is the sync and conflict-resolution design, not the engine. Whether you log changes per row, use CRDTs, or resolve last-write-wins determines your schema, your primary key choice (UUIDs versus autoincrement matters a lot here), and whether you need per-row version columns and tombstones for deletes. Retrofitting that onto a schema built without it means rewriting every table and replaying history you didn't keep. Swapping SQLite for Postgres later, by contrast, is a bounded port if you stay off dialect-specific SQL, and tools like Turso, Electric SQL, and cr-sqlite all assume SQLite on the device with Postgres on the server anyway.

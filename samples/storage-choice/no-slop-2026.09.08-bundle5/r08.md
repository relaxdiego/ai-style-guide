SQLite, unless a server tier has to be the authority for multiple clients writing at once. Local-first means the database lives in your process on the user's device, and Postgres there means shipping a daemon, supervising it, handling version upgrades on machines you don't control, and eating a port conflict every time a user already runs one. SQLite in WAL mode gives you many concurrent readers with a single writer, which matches what a local app actually does: one UI process, short transactions, occasional background compaction.

Things that would flip me to Postgres, none of which is about the query engine:

- Several OS processes writing to the same database concurrently, especially over a network filesystem, where SQLite locking is genuinely unsafe.
- A shared multi-user dataset that must be consistent across devices in real time, meaning the server is the source of truth and the local copy is a cache.
- A hard dependency on something Postgres has and SQLite doesn't: real `jsonb` indexing, PostGIS, pgvector at scale, logical replication as your sync mechanism.

Most likely you need both: SQLite on device, Postgres on a sync server, and the interesting work is the sync protocol rather than the engine choice. The engine decision is also cheaper to reverse than it feels, provided you stay on standard SQL and keep migrations as plain scripts; a schema that avoids Postgres-only types ports in an afternoon. What you cannot cheaply undo is a sync design that assumes server-assigned autoincrement IDs or last-write-wins on whole rows, so spend the anxiety there and pick IDs (UUIDv7 or similar) plus per-field conflict resolution now.

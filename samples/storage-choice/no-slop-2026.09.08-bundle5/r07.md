SQLite, unless you already know there's a server holding shared state. "Local-first" puts the database on the user's device, and Postgres there means you ship and supervise a server process per install: a data directory you own, a port to negotiate, and version upgrades that need `pg_upgrade` run correctly on a machine you can't log into. SQLite is a file your process opens. Turn on WAL mode, set a `busy_timeout`, and its one real constraint (a single writer at a time, readers concurrent with that writer) is invisible to most apps. If you also run a backend, use Postgres there and SQLite on the client; that pairing is the normal shape of these systems, not a compromise.

The part you can actually get wrong is sync, and it's largely independent of which engine you pick. Deciding how two devices that edited the same record while offline reconcile, whether you sync rows or an operation log, and whether every table carries the identifiers and timestamps that reconciliation needs, is expensive to change later because it's baked into the schema and into every write path. Swapping SQLite for Postgres is a week of adapter work; retrofitting conflict resolution onto a schema built without it means rewriting the schema and migrating every user's existing data. Spend the anxiety budget there.

SQLite, unless your "local-first" app also runs a shared server that many users write to at once, in which case use both: SQLite on the device, Postgres behind the sync endpoint. That combination is the normal arrangement for local-first, not a compromise.

The things that would move me off SQLite on the client:

- **Concurrent writers on one database file.** SQLite in WAL mode gives you many readers and one writer. A single-user desktop or mobile app never hits this; a background sync worker plus a UI thread hammering writes sometimes does, and you fix it with a write queue rather than a different engine.
- **Postgres-only features you actually depend on.** PostGIS, real full-text ranking, `jsonb` operators with indexes, extensions. SQLite has FTS5 and JSON functions that cover more of this than people expect, so check the specific query before assuming.
- **You want one dialect across client and server.** PGlite (Postgres compiled to WASM) gets you Postgres semantics on device, at the cost of a younger, narrower deployment story than SQLite, which ships inside every phone and browser runtime you will target.

The part of this decision that is genuinely hard to reverse is not the engine. Swapping SQLite for Postgres later is a schema migration and a data access layer rewrite, painful but bounded. What you cannot cheaply undo is the sync and conflict model: whether you ship last-write-wins per row, per field, an operation log, or CRDTs, because that choice leaks into your schema, your API, and every client that has already written data in the old format. Spend your uncertainty budget there. Pick SQLite today, keep raw SQL behind a thin repository layer so the dialect is contained, and put the design effort into what happens when two devices edit the same record offline.

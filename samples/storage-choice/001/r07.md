SQLite for the on-device store. Postgres is a server; shipping it to user machines means a supervised process, a data directory you own, and version upgrades that run on hardware you can't see. If you also have a backend, the answer is SQLite on device *and* Postgres behind the API, not one or the other.

| Dimension | SQLite | Postgres |
|---|---|---|
| Deployment on a user machine | Library, one file | Separate process, data dir, upgrade path |
| Concurrent writers | One at a time (WAL allows concurrent readers) | Real MVCC, many writers |
| Migrations on device | Limited `ALTER TABLE`; adds/drops fine, most else is table rebuild | Full DDL, transactional |
| Types | Dynamic, no native enum/array/jsonb ops | Rich types, constraints, `jsonb` |
| Full-text / vector | FTS5, sqlite-vec | tsvector, pgvector |
| Crash safety | WAL + `synchronous=FULL` is solid | Solid |
| Offline by default | Yes | Awkward |

The storage engine is the reversible part of this decision. Swapping SQLite for something else later is a few weeks of adapter work. What you can't easily undo is the sync model and the identifier scheme: if rows are ever created on two devices, you need client-generated IDs (UUIDv7 or ULID, not `AUTOINCREMENT`), a per-row logical clock or version vector, and a written-down rule for what happens when two devices edit the same field. Deletes are the case that bites people, since a missing row and a deleted row look identical without tombstones. Decide that now, on paper, before you pick a library.

Two things would change the recommendation. If a single user's data will exceed roughly tens of gigabytes with heavy analytical queries, SQLite's single-writer model and planner start to hurt. If you want Postgres SQL semantics locally to keep one schema across client and server, PGlite (Postgres compiled to WASM, single-user, embedded) is the honest middle path, at the cost of a much younger ecosystem than SQLite's.

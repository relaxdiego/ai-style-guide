SQLite, unless your "local-first" app is actually a server that one team runs on one box.

The engine choice is cheaper to reverse than you think. What is expensive is the sync design, and that decision is independent of which engine you pick.

Where each one wins:

| Concern | SQLite | Postgres |
|---|---|---|
| Shipping to end users | One file, linked into your binary | You ship and upgrade a server process per machine |
| Offline reads/writes | Native | Works, but you are running a daemon on a laptop |
| Concurrency | WAL: one writer, many readers | Real MVCC, many writers |
| Types | Dynamic, no native enums/arrays, weak constraints until you turn them on | Rich types, JSONB, ranges, strong constraints |
| Full-text | FTS5, good | tsvector + extensions, better |
| Ops story on client | None | Version skew, ports, permissions, data dir migrations |

The things that will actually bite you, in order:

- **Sync/merge semantics.** Last-writer-wins per row, per field, or CRDT? Pick this before the engine. It shapes your tables (tombstones, vector clocks, per-column timestamps) far more than the engine does.
- **Schema migration across versions you don't control.** A user opens a 6-month-old client against new data. Both engines hurt here; SQLite's `ALTER TABLE` limits hurt slightly more.
- **`PRAGMA foreign_keys=ON` and WAL mode.** SQLite defaults are wrong for you. Set them at every connection open, not once.
- **Multi-process access to the same file.** Fine over local disk, broken over NFS/Dropbox/SMB. If users sync the DB file itself through a cloud drive, you will corrupt it.

The common arrangement is both: SQLite embedded on the client, Postgres on the server, with a sync layer between (ElectricSQL, PowerSync, cr-sqlite, or your own oplog). Choosing SQLite on the client does not commit you to SQLite on the server, and that is the split that makes this decision low-risk.

Pick Postgres only if: many concurrent writers hit the same database, you need row-level security or Postgres-specific extensions in the local instance, or "local" means a self-hosted server rather than an end-user device.

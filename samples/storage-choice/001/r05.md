SQLite, unless "local-first" actually means "self-hosted server" in your case.

Local-first implies the database lives on the user's device, one writer, offline by default. SQLite is a library in your process: no daemon to install, no port, no version skew between what you tested and what a user has, and a database file you can copy, ship, and inspect. Postgres on a user's machine means bundling a server, managing its lifecycle, and handling upgrade of the on-disk format across releases. That is real operational work with no payoff at one-user scale.

Where the answer flips:

| Situation | Pick |
|---|---|
| Data on user device, offline-capable, one process | SQLite |
| Multi-user server you happen to also run locally in dev | Postgres both places |
| Concurrent writers from separate processes | Postgres |
| Need `jsonb`, full-text with ranking, GIS, materialized views | Postgres |
| Dataset > ~100GB or heavy analytical queries | Postgres |
| Per-user encrypted database files | SQLite (SQLCipher) |

The decision you are more likely to get wrong is sync, not storage. Sync determines your schema (do rows carry version vectors? tombstones? last-writer-wins timestamps?), and retrofitting that onto a schema designed without it means a migration across every deployed client, which is the expensive kind. Decide now whether you need CRDTs, an operation log, or server-authoritative last-write-wins, and design the tables around it. Engines with sync built for this model — Electric, Turso, cr-sqlite, PowerSync — are all SQLite on the client, which is another reason to start there.

SQLite on the device. Postgres only as the server half if you have one, and PGlite only if you specifically need Postgres SQL semantics on the client.

The storage engine is the reversible part of this decision. What locks you in is the sync model: whether writes are captured as an ordered log or diffed after the fact, whether IDs are client-generatable (UUIDv7, not autoincrement), and whether conflict resolution is last-write-wins per row, per field, or CRDT. Pick those first and the local engine mostly falls out. Schema migration on machines you don't control is the second thing that bites, because a device can be offline across three of your releases and come back with a v4 database against a v7 client.

| | SQLite | PGlite (Postgres WASM) | Postgres server |
|---|---|---|---|
| Ship to a user's machine | Embedded, one file | Embedded, ~3MB wasm + data dir | No. Requires install/supervision |
| Concurrent processes | WAL: many readers, one writer | Single connection, one process | Full MVCC |
| Browser | wa-sqlite / OPFS, mature | IndexedDB or OPFS, works | No |
| Sync tooling | cr-sqlite, Turso/libSQL, Electric, Zero, Automerge | Electric (its main use case) | Logical replication, but server-to-server |
| Types you'll miss | No native JSONB, arrays, or `interval` | Has them | Has them |
| Full-text | FTS5, good | tsvector | tsvector |
| Vector search | sqlite-vec | pgvector, in-browser | pgvector |

What would flip me to PGlite locally: you already have a Postgres backend, you want one set of migrations and one dialect across both sides, and you're using Electric for sync. What would flip me to a real Postgres server: multiple OS processes or machines writing the same data, datasets past roughly 50–100GB per user, or row-level security you need enforced rather than advisory. Neither is common for local-first.

The trap to avoid is a plain SQLite file with no change log, syncing by comparing rows at connect time. It works for six months and then you cannot answer "did this row get deleted, or has this device never seen it?" Add `created_at`/`updated_at`/`deleted_at` and a monotonic write log from day one even if sync ships in v2, because backfilling that history is impossible.

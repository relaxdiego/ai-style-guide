SQLite on the device. For a local-first app that's close to a foregone conclusion, and the decision you're actually worried about is the sync layer, not the storage engine.

Postgres is a server process with a config, a data directory, a version, and an upgrade path. Shipping one per user device means shipping all of that, and you get concurrency guarantees a single-user app never exercises. SQLite is a library that opens a file, starts in microseconds, and in WAL mode handles one writer plus many readers, which is exactly the load one user generates. Use `STRICT` tables and turn on foreign keys, and the type-looseness complaint mostly goes away.

Where Postgres still belongs:

- **On the server**, if you have one. SQLite on the client and Postgres in the cloud is the standard local-first pairing, not a compromise.
- **Analytical queries over the full multi-tenant dataset.** Never happens on-device.
- **You need row-level security, logical replication, or extensions** (PostGIS, pgvector at scale) as the sync mechanism itself. Electric and PowerSync both build on Postgres logical replication for this reason.
- **PGlite** exists if you want Postgres semantics in the browser via WASM, but it buys you dialect compatibility, not a better local database.

The part that's genuinely hard to reverse is the conflict model, so decide it deliberately: last-write-wins per field, CRDTs (Automerge, Yjs, cr-sqlite), or server-authoritative mutations with rebase (Replicache, Zero). Swapping SQLite for something else later is a schema migration and a rewrite of your data access layer, painful but bounded. Discovering at month eight that two users editing the same document silently lose each other's work means rebuilding the data model itself, because the fix is usually per-field or per-character granularity that your current tables can't represent. Pick the conflict model against a concrete case in your app: two devices offline, both edit the same record, what should the user see when they reconnect?

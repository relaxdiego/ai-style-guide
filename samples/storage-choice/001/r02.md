SQLite, and the decision you're worried about isn't this one.

Local-first means the database lives on the user's device. Postgres there means shipping a server process, a data directory you don't control, port conflicts, version upgrades that require `pg_upgrade` on a machine you can't log into, and a background daemon users will find in Activity Monitor and kill. Embedding it is possible (pglite, embedded builds) but you're paying that cost to get features you can't use locally: concurrent writers across processes, role-based access, replication.

What actually locks you in:

| Decision | Reversible? | Why |
|---|---|---|
| SQLite vs Postgres on device | Yes, mostly | Schema and SQL are portable enough; a migration is a weekend, not a rewrite |
| Sync/merge model | No | Conflict resolution leaks into schema, UI, and user expectations |
| Schema for merge (CRDT, last-write-wins, op log) | No | Changing it invalidates every client's history |
| ORM/query layer | Yes | Swappable |

Pick the sync model first, then let it pick the storage. If you go CRDT (Automerge, Yjs, cr-sqlite), your rows carry version vectors or the whole document is a blob and SQLite is a container. If you go op-log with server reconciliation, you need append-only tables on the client and Postgres on the server — that's the normal arrangement for local-first: SQLite per device, Postgres as the sync backend, and they're not competing.

The one thing to check before committing: whether your write pattern survives SQLite's single-writer model. WAL mode gives you concurrent readers with one writer, which covers nearly every desktop or mobile app. If you have multiple OS processes writing simultaneously (a helper daemon plus the UI, or several app windows as separate processes), test that early — `SQLITE_BUSY` under contention is the failure mode that sends people back to Postgres, and it shows up in week six, not week one.

SQLite on the device, Postgres on the server if you have one. Those aren't competing choices; the thing you can actually get wrong is the sync model, and that decision is independent of the engine.

| Option | Use when | Cost |
|---|---|---|
| SQLite / libSQL | Default for local-first | Loose typing, one writer at a time (WAL makes this rarely bite), JSON support is adequate but not `jsonb` |
| PGlite (Postgres in WASM) | You want one dialect across client and server, or you depend on Postgres types/extensions in client queries | ~3MB payload, single connection, young, thin track record on mobile |
| Postgres server per install | Effectively never | You now own install, upgrade, and process supervision on someone else's machine |

The decisions that are expensive to reverse are all schema-level, and they land before you write a line of sync code:

- **Primary keys.** UUIDv7 or ULID, generated client-side. Autoincrement integers collide across devices and you cannot retrofit this cheaply.
- **Deletes.** Tombstone rows with a deleted-at, not `DELETE`. A row that vanishes is indistinguishable from a row that never synced.
- **Conflict granularity.** Per-row last-write-wins, per-column LWW, or a CRDT for text fields. Changing this later means rewriting every write path and re-interpreting history.
- **Clocks.** Hybrid logical clocks or Lamport counters. Device wall clocks are wrong by minutes and users change them.
- **Migrations.** Old clients will send you writes against schema version N-3 for months, because you can't force an upgrade.

Get those five right and swapping SQLite for PGlite later is a bounded rewrite of your data-access layer over a weekend. Get them wrong and no engine saves you. The one input that would change my recommendation: if your client code needs Postgres features that SQLite genuinely lacks — PostGIS, full `jsonb` operators, recursive CTEs with the Postgres planner — take PGlite and accept the immaturity rather than reimplementing them.

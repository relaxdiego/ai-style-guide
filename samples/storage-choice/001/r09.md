SQLite, unless you have a server component that's already Postgres and you want one dialect across both.

"Local-first" means the database ships inside your app process on someone else's machine. Postgres is a server: a separate process, a data directory, a port, a version you now own upgrading. Making a user install or supervise that is a support burden you'll pay for forever, and the embedded escapes (PGlite in WASM, `embedded-postgres` binaries) give you a single-connection Postgres that has traded away most of the reasons you wanted Postgres.

| | SQLite | Postgres |
|---|---|---|
| Deployment on user machine | linked library, one file | separate process, data dir, version upgrades |
| Writers | one at a time (WAL: 1 writer + N readers) | many, MVCC |
| Types | dynamic, no native arrays/enums, JSON via functions | rich types, arrays, enums, ranges, JSONB |
| Full-text | FTS5, good | tsvector, better |
| Vectors | `sqlite-vec` extension | pgvector, more mature |
| Migrations | limited `ALTER TABLE`, table-rebuild pattern | full DDL, transactional |
| Backup | copy the file | pg_dump / basebackup |

Cases where Postgres locally is the right call:

- Your sync backend is Postgres and you want identical SQL on both sides. ElectricSQL and PGlite are built for exactly this.
- You need concurrent writers in separate OS processes, not threads in one app.
- You depend on a Postgres-only extension in the client, most often PostGIS or heavy pgvector work.
- "Local" means a dev machine running your normal server stack, not an end user's laptop. Then it isn't local-first, it's just local, and you should match production.

The decision you're actually worried about isn't the engine. Swapping SQLite for Postgres later is a few weeks of dialect work on a codebase with a repository layer; changing how writes converge across devices is a rewrite of the domain model. Pick the sync model first: last-write-wins per field, CRDTs (cr-sqlite, Automerge), or server-authoritative with client cache (PowerSync, Electric). Each of those constrains your schema, and some of them pick the engine for you. Get that ordering right and the storage question mostly answers itself.

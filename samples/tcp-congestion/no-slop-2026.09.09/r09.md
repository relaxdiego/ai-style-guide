TCP congestion control limits how much unacknowledged data a sender puts on the network, adjusting that limit based on feedback about whether the network is dropping or delaying packets. The sender keeps a congestion window (cwnd) in bytes; it may have at most `min(cwnd, receiver's advertised window)` bytes in flight. Flow control (the receiver's window) protects the receiver from being overrun. Congestion control protects the network. They're separate mechanisms that happen to multiply into the same limit.

## The feedback signal

The network has no channel for telling a sender "you're sending too fast." Classic TCP infers it from packet loss: routers with full queues drop packets, so a drop means the path is saturated. That inference is the foundation of every loss-based algorithm, and it's also their main weakness, since loss on wireless links has nothing to do with congestion.

Loss is detected two ways. Three duplicate ACKs mean a packet went missing but later packets arrived, so the path still works. A retransmission timeout (RTO) means nothing is getting through, which is a much worse sign and triggers a much harsher response.

## The four phases (Reno, the classic model)

**Slow start.** cwnd begins at roughly 10 segments and doubles every round trip: each ACK increases cwnd by one segment, so a full window of ACKs doubles it. Despite the name, this is exponential growth. Its job is to find the path's rough capacity in a logarithmic number of round trips rather than crawling up linearly from one packet.

**Congestion avoidance.** Once cwnd crosses the slow start threshold (ssthresh), growth switches to roughly one segment per round trip: each ACK adds `MSS/cwnd`. Linear probing, on the theory that the sender is now near capacity and should approach the edge carefully.

**Fast retransmit.** Three duplicate ACKs trigger immediate retransmission of the missing segment without waiting for the timeout.

**Fast recovery.** After fast retransmit, halve ssthresh and set cwnd to the new ssthresh, then continue in congestion avoidance. A timeout instead drops cwnd all the way to one segment and re-enters slow start, and the RTO itself doubles on each consecutive timeout (exponential backoff).

That halve-on-loss, add-one-per-RTT pattern is additive increase, multiplicative decrease (AIMD). Chiu and Jain showed in 1989 that AIMD converges to a fair share among flows sharing a bottleneck, which is why it survived. The convergence argument is geometric: multiplicative decrease shrinks the gap between two flows' rates proportionally, additive increase leaves it unchanged, so repeated cycles drive the difference toward zero.

## Why Reno was replaced

AIMD's throughput scales as roughly `MSS/(RTT·√p)` for loss rate `p`. On a 10 Gbps link with 100 ms RTT, sustaining that rate demands a loss rate below about 1 in 10 billion packets, and recovering from a single loss takes over an hour of linear growth. Reno cannot fill fast long-distance paths.

**CUBIC**, the Linux and Windows default, replaces linear growth with a cubic function of time since the last loss. It rises steeply toward the window size where loss last occurred, flattens out around that point to probe gently where the capacity boundary probably still is, then accelerates again if no loss appears. Because growth depends on elapsed time rather than ACK arrivals, flows with different RTTs compete more fairly.

**BBR**, from Google, abandons loss as the signal. It continuously estimates the path's bottleneck bandwidth and minimum RTT, then paces packets at the bandwidth-delay product. This avoids filling router queues at all, which addresses bufferbloat: oversized router buffers let loss-based TCP inflate queues to hundreds of milliseconds before any drop occurs, wrecking latency for everything sharing the link. BBR's fairness against CUBIC has been contentious, and v2/v3 exist largely to fix flows that grabbed too much when competing with loss-based traffic.

**ECN** gives routers a way to mark packets as congested instead of dropping them, so the sender reacts before any loss. It needs support from both endpoints and the routers between them, and works best with modern queue management like CoDel or FQ-CoDel that marks early rather than waiting for a full buffer. DCTCP applies the same idea inside data centers, using the *fraction* of marked packets to size the window reduction proportionally instead of always halving.

## What this means in practice

A single TCP connection on a lossy or high-latency path underuses the link, which is why download managers and QUIC open multiple streams. Congestion state is per-connection and starts cold, so short HTTP requests often finish inside slow start and never reach the path's real capacity. And on Linux, switching algorithms is a sysctl away: `net.ipv4.tcp_congestion_control`.

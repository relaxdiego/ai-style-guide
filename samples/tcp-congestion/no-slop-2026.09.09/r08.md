TCP congestion control is a feedback loop where the sender guesses how much data the network path can hold, sends that much, and adjusts the guess based on whether packets got through. Nothing in the protocol tells the sender the path's capacity, so the guess is built entirely from observed acknowledgments, losses, and timing.

## The control variable

The sender keeps a congestion window (`cwnd`), a byte count limiting how much unacknowledged data may be in flight. Actual sending is limited by `min(cwnd, rwnd)`, where `rwnd` is the receiver's advertised window (flow control, a separate concern: protecting the receiver's buffer rather than the network).

Because in-flight bytes divided by round-trip time equals throughput, controlling a window controls a rate indirectly. This matters later: a window-based sender releases data in bursts when ACKs arrive, which is why modern stacks add pacing on top.

## Classic algorithm (Reno), in four states

**Slow start.** Begin with a small window (RFC 6928 raised the initial value to 10 segments) and increase `cwnd` by one MSS per ACK received. That doubles the window every RTT: exponential growth, despite the name. Slow start ends when `cwnd` crosses a threshold called `ssthresh` or when loss occurs.

**Congestion avoidance.** Above `ssthresh`, increase `cwnd` by roughly one MSS per RTT instead of per ACK. Linear growth, probing gently for more capacity.

**Fast retransmit / fast recovery.** Three duplicate ACKs mean a segment was lost but later segments arrived, so the path still works. The sender retransmits immediately without waiting for a timer, sets `ssthresh` to half the current window, and sets `cwnd` to that halved value. NewReno and SACK improve on this by handling multiple losses in one window; SACK lets the receiver report exactly which blocks arrived.

**Timeout.** No ACK before the retransmission timer fires means the sender has lost its feedback signal entirely. `cwnd` drops to one segment, `ssthresh` halves, and slow start restarts. The RTO itself doubles on each successive timeout (exponential backoff). The timer is computed from a smoothed RTT estimate and its variance, per Jacobson's algorithm.

## Why halving on loss produces fairness

The increase/decrease rule is additive increase, multiplicative decrease. Chiu and Jain showed that this pair converges to a fair, efficient allocation among flows sharing a bottleneck, while other combinations (additive decrease, multiplicative increase) do not. Two flows that back off proportionally but grow at equal absolute rates drift toward equal shares.

The catch: a Reno flow's steady-state throughput is roughly `MSS / (RTT * sqrt(p))` for loss probability `p`. Throughput falls with RTT, so long-distance flows lose to short ones on the same bottleneck, and at high bandwidth-delay products the required loss rate becomes absurdly small.

## What actually runs today

**CUBIC** is the Linux default and the most widely deployed algorithm. After a loss it reduces the window by 30% rather than 50%, then grows along a cubic curve of *time since the reduction*, not per-RTT. Growth is fast far below the previous window size, flattens as it approaches it, then accelerates again to probe for new capacity. Making growth a function of wall-clock time removes the RTT bias in Reno.

**BBR** takes a different approach: instead of treating loss as the congestion signal, it continuously estimates the bottleneck bandwidth (maximum delivery rate observed) and the minimum RTT, and paces sending at that bandwidth with roughly one bandwidth-delay product in flight. It periodically probes higher and drains back. This avoids filling router buffers, which is the main weakness of loss-based control: a loss-based sender only backs off *after* the queue overflows, so it keeps deep buffers permanently full and inflates latency for everything sharing them (bufferbloat). BBR's fairness against CUBIC has been contentious; v2 and v3 added loss and ECN response partly for that reason.

**ECN and DCTCP.** Explicit Congestion Notification lets a router mark packets instead of dropping them, and the receiver echoes the mark back. DCTCP, used inside data centers, reacts proportionally to the *fraction* of marked packets rather than treating any mark as a full congestion event, which keeps queues short and latency predictable in controlled environments.

## Things that bend the model

Wireless links break the assumption that loss means congestion, since radio errors drop packets on an uncongested path. Link-layer retransmission mostly hides this, at the cost of RTT variance.

Ack clocking degrades when ACKs are aggregated or delayed, which is common on Wi-Fi and LTE, so senders that rely purely on ACK arrival timing get bursty. Pacing (now standard in Linux, and mandatory for BBR) fixes that by spreading segments over the RTT.

Finally, congestion control is per-connection, so opening more connections gets a bigger share. That's why HTTP/1.1 clients used six connections per host and why QUIC and HTTP/2 multiplexing changed the picture: one congestion controller for many streams. QUIC runs the same algorithms (CUBIC, BBR) in user space over UDP, which is mostly why new algorithms deploy faster there than in kernel TCP.

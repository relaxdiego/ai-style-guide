TCP congestion control is a feedback loop that guesses how much data the network path can hold, sends that much, and shrinks when it sees evidence of loss or delay. The sender keeps a congestion window (`cwnd`) alongside the receiver's advertised window (`rwnd`); it may have at most `min(cwnd, rwnd)` bytes in flight. `rwnd` protects a slow receiver, `cwnd` protects the network in between. Nothing in the network tells the sender a number: the sender infers capacity from acknowledgments, timeouts, and (in newer algorithms) round-trip time changes.

## The classic loop (Reno / NewReno)

**Slow start.** `cwnd` begins at roughly 10 packets and doubles every RTT (each ACK adds one MSS). This is exponential growth, and it ends when `cwnd` crosses `ssthresh` or a loss occurs. It is called "slow" only relative to the pre-1988 behavior of blasting a full receiver window immediately.

**Congestion avoidance.** Above `ssthresh`, `cwnd` grows by about one MSS per RTT instead of doubling. Probing turns linear because the sender is now near the estimated capacity and wants to creep upward.

**Loss as the congestion signal.** Three duplicate ACKs mean a packet was dropped but later packets still arrive, so the path still works: the sender retransmits immediately (fast retransmit), halves `cwnd`, and continues (fast recovery). An actual timeout means much worse: `cwnd` drops to 1 and slow start restarts.

That is additive increase, multiplicative decrease. AIMD converges to fairness because flows that are sending more lose more absolute throughput on each cut, while all flows gain equally on each increase. The resulting throughput is roughly `MSS / (RTT * sqrt(p))` for loss rate `p`, which has two consequences people hit constantly: long-RTT flows lose to short-RTT flows sharing a bottleneck, and a single high-speed long-distance flow needs an absurdly low loss rate to fill a 10 Gbps pipe.

## What actually runs today

**CUBIC** is the Linux and Windows default. It replaces linear growth with a cubic function of time since the last loss, so the window climbs fast toward the previous loss point, flattens near it (the plateau where it suspects capacity lives), then probes aggressively past it. Growth depends on elapsed time rather than ACK arrivals, which removes the penalty for long RTTs.

**BBR** ignores loss as a signal. It continuously estimates bottleneck bandwidth (max delivery rate observed) and minimum RTT, then paces sending at roughly bandwidth × min-RTT. This exists because of bufferbloat: oversized router buffers mean loss-based algorithms fill those buffers before they get any feedback, adding hundreds of milliseconds of queueing delay while reporting no loss at all. BBR aims to sit at the knee of the curve, full bandwidth with an empty queue. It competes unfairly against CUBIC in some topologies, which is a live and contested issue.

**ECN** lets routers mark packets instead of dropping them, giving the sender a congestion signal without a retransmission. It requires router support and is only partially deployed on the public internet; DCTCP uses it heavily inside datacenters, where it can react to the proportion of marked packets rather than a binary signal.

Two practical notes. Congestion control is sender-side and unilateral, so you can change it per-socket or per-host (`net.ipv4.tcp_congestion_control` on Linux) without touching the other end. And it is per-connection, which is why opening eight parallel connections historically got a browser more bandwidth than one: the fairness AIMD provides is between flows, not between applications.

TCP congestion control is a feedback loop that guesses the network's capacity by increasing the send rate until packets drop, then backing off. The network gives no explicit capacity signal, so the sender treats loss (and in newer algorithms, delay) as the evidence that it pushed too hard.

The sender keeps a congestion window, `cwnd`, holding the maximum unacknowledged bytes it will allow in flight. Actual bytes in flight are `min(cwnd, rwnd)`, where `rwnd` is the receiver's advertised window for flow control, a separate concern about receiver buffer space. Arriving ACKs both free window space and clock out new data, so the send rate self-adjusts to the bottleneck's drain rate: roughly `cwnd / RTT`.

Classic TCP (Reno, and NewReno which fixed its behaviour under multiple losses in one window) is four algorithms sharing that one variable:

- **Slow start.** Begin at an initial window of 10 MSS (RFC 6928; older stacks used 1 to 4). Add one MSS per ACK, which doubles `cwnd` every RTT. Exponential, despite the name, since the starting point is low. Runs until `cwnd` exceeds the slow start threshold `ssthresh` or a loss occurs.
- **Congestion avoidance.** Above `ssthresh`, add roughly one MSS per RTT, implemented as `cwnd += MSS*MSS/cwnd` per ACK. Linear probing for the extra capacity that may have appeared.
- **Fast retransmit.** Three duplicate ACKs mean a segment is missing but later ones arrived, so the path is still delivering. Resend immediately instead of waiting for the retransmission timeout.
- **Fast recovery.** After that retransmit, halve `ssthresh` to `cwnd/2`, set `cwnd` to the new `ssthresh`, and keep transmitting on incoming dup ACKs rather than collapsing to slow start.

A retransmission timeout is treated as far worse news: `cwnd` drops to one MSS and slow start begins again, with the RTO itself doubling on repeated failure.

The increase-by-one-per-RTT and halve-on-loss pattern is additive increase, multiplicative decrease. Chiu and Jain showed it converges to fair sharing among flows on the same bottleneck: a flow taking more than its share loses more in absolute terms at each halving, so shares equalise over time. It also produces the sawtooth throughput trace and the well-known approximation that average throughput is about `MSS / (RTT * sqrt(p))` for loss probability `p`, which is why a single Reno flow cannot fill a fast, long path. At 10 Gbit/s with 100 ms RTT you need a loss rate near 10⁻¹⁰ to keep the window that large.

That limit is what modern algorithms address. CUBIC, the Linux default since 2.6.19 and also used by Windows since 10, replaces the linear increase with a cubic function of time since the last reduction: it jumps back toward the pre-loss window, flattens near it to probe gently, then accelerates if no loss appears. It cuts by 0.7 rather than 0.5 and its growth is independent of RTT, so flows with different RTTs compete more evenly. BBR takes a different approach and largely ignores loss: it estimates the bottleneck bandwidth and minimum RTT from delivery rate measurements, sets the send rate directly with packet pacing, and keeps the in-flight data near the bandwidth-delay product. This avoids filling deep router buffers, the bufferbloat problem that loss-based control creates by definition, since it only backs off once a queue has overflowed. ECN sidesteps the same problem by having routers mark packets under load instead of dropping them, letting the sender react before any loss; DCTCP uses the proportion of marked packets to scale the reduction rather than always halving.

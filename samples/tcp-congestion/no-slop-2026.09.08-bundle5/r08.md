TCP congestion control is a feedback loop that guesses how much data the network path can hold, sends that much, and adjusts when the guess is wrong. The sender keeps a congestion window (`cwnd`) in bytes and limits unacknowledged data in flight to `min(cwnd, receiver's advertised window)`. Nothing in the network tells the sender the bottleneck capacity, so it probes upward until it sees a congestion signal, then cuts back.

The classic Reno-family state machine has four parts:

- **Slow start.** `cwnd` begins at about 10 MSS (RFC 6928; it was 1-4 MSS historically) and grows by one MSS per ACK, so it roughly doubles every RTT. Exponential, despite the name. It runs until `cwnd` crosses `ssthresh` or a loss occurs.
- **Congestion avoidance.** Above `ssthresh`, growth drops to roughly one MSS per RTT: additive increase, probing gently for spare capacity.
- **Fast retransmit and fast recovery.** Three duplicate ACKs mean a segment was lost but later ones arrived, so the path is still passing traffic. The sender retransmits immediately, sets `ssthresh` to half of the in-flight data, sets `cwnd` near that, and resumes congestion avoidance rather than restarting. SACK and NewReno handle multiple losses in one window without collapsing to a timeout.
- **Retransmission timeout.** No ACK at all means the sender learned nothing about the path. `cwnd` drops to 1 MSS, slow start restarts, and the RTO doubles per consecutive timeout.

The additive-increase/multiplicative-decrease pattern is what makes competing flows converge toward an equal share: increases are the same absolute amount for everyone, decreases are proportional to what each flow currently holds, so the big flow gives up more. The cost is that loss-based control fills the bottleneck buffer before it detects anything, which is the mechanism behind bufferbloat: latency climbs to the drain time of the queue while throughput stays flat. Modern variants attack that differently. CUBIC, the Linux default since 2.6.19, grows `cwnd` as a cubic function of time since the last reduction and cuts by 30% instead of 50%, which keeps high-bandwidth-delay-product links busy without depending on RTT. BBR estimates bottleneck bandwidth and minimum RTT directly, paces packets at that rate, and mostly ignores loss as a signal. ECN sidesteps the whole issue when routers support it: the router marks a bit under load and the sender reacts without a packet ever being dropped.

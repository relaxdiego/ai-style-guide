TCP congestion control is a feedback loop that guesses how much data the network path can hold, sends that much, and adjusts the guess based on whether packets get through. The sender keeps a congestion window (`cwnd`), a byte count limiting how much unacknowledged data can be in flight; the actual send limit is `min(cwnd, rwnd)`, where `rwnd` is the receiver's advertised buffer space. Flow control (`rwnd`) protects the receiver, congestion control (`cwnd`) protects the network in between, and they are separate mechanisms that happen to share a chokepoint.

The classic algorithm has two growth regimes separated by a threshold called `ssthresh`. A new connection has no idea what the path can carry, so it starts at an initial window (10 MSS on Linux since roughly 2013) and runs slow start: every arriving ACK raises `cwnd` by one MSS, which doubles the window each round trip. That is exponential probing, badly named, and it ends when `cwnd` crosses `ssthresh` or a loss occurs. Above `ssthresh` the sender switches to congestion avoidance and raises `cwnd` by about one MSS per round trip instead of per ACK, a linear climb intended to nudge the path toward its limit without overshooting hard.

What happens on loss depends on how the loss was detected:

- **Three duplicate ACKs.** The receiver keeps acknowledging the last in-order byte, so duplicates mean later packets arrived and one is missing. The sender does fast retransmit (resend immediately, without waiting for the timer) and fast recovery: set `ssthresh` to half of `cwnd`, set `cwnd` to the new `ssthresh`, and keep sending. The path is still delivering, so the sender only backs off a factor of two.
- **Retransmission timeout.** No ACKs at all for an RTO interval, which suggests the path is badly broken or heavily congested. The sender sets `ssthresh` to half of `cwnd`, drops `cwnd` to one MSS, and re-enters slow start. This is the expensive case: throughput collapses and has to be rebuilt.
- **ECN mark.** With Explicit Congestion Notification, a router experiencing congestion sets a bit in the IP header instead of dropping the packet; the receiver echoes it back and the sender reduces its window as if it had seen a loss, without losing data.

This pattern of adding a constant per RTT and multiplying by a constant on congestion is additive increase, multiplicative decrease. Chiu and Jain showed in 1989 that it converges to a fair, efficient allocation among flows sharing a bottleneck, which is why the shape survived. The famous sawtooth on a throughput graph is this: a slow linear climb until the bottleneck buffer overflows, a sudden halving, and another climb.

Reno's linear increase scales badly on modern paths. To fill a 10 Gb/s link with a 100 ms RTT, a flow needs roughly 83,000 packets in flight, and recovering from a single loss at one packet per RTT takes hours. The variants in use today all attack that:

| Algorithm | Signal it reacts to | Growth behaviour | Where you see it |
|---|---|---|---|
| Reno / NewReno | Loss | Linear, +1 MSS/RTT | The reference; NewReno fixes multi-loss recovery |
| CUBIC | Loss | Cubic function of time since last loss, independent of RTT | Linux and Windows default |
| BBR | Measured bottleneck bandwidth and minimum RTT | Paces at estimated bandwidth, probes periodically | Google, YouTube, widely deployed |
| Vegas | Queueing delay | Backs off before loss | Rare; loses to loss-based flows sharing a link |

CUBIC grows as a cubic curve centred on the window size where the last loss happened, so it climbs fast when far below that point, flattens near it, and probes aggressively past it if nothing breaks. Because the curve is a function of wall-clock time rather than ACK arrivals, flows with different RTTs on the same bottleneck get more even shares than Reno gives them.

BBR abandons loss as the signal entirely. It continuously estimates the bottleneck bandwidth (maximum delivery rate observed) and the minimum RTT (lowest observed, taken as the propagation delay with no queue), and paces packets at that bandwidth with roughly one bandwidth-delay product in flight. The motivation is bufferbloat: a loss-based sender only backs off once a router buffer is full, so on a path with a large buffer it keeps that buffer permanently full, adding hundreds of milliseconds of queueing delay to every flow sharing the link. BBR aims to sit at the point where throughput is maximised and the queue is near empty. It has its own problems, including unfairness against CUBIC in some regimes and trouble with shallow buffers, which BBRv2 and v3 work on.

Two things at the edges matter in practice. Router-side active queue management (CoDel, FQ-CoDel, PIE) drops or marks packets early to signal congestion before the buffer fills, which fixes bufferbloat from the network side rather than the sender side, and fair queueing isolates flows so one aggressive sender cannot starve the rest. On the sender side, packet pacing spreads a window out over the RTT instead of releasing it as a burst, which reduces the queue spikes that cause loss in the first place; Linux does this in the `fq` qdisc, and BBR depends on it.

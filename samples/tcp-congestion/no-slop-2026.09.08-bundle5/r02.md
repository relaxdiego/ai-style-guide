TCP congestion control is a sender-side feedback loop: the sender maintains a guess at how much unacknowledged data the network path can hold, sends no more than that, and revises the guess based on what the acknowledgments do. That guess is the congestion window, `cwnd`, measured in bytes. The sender is limited by `min(cwnd, rwnd)`, where `rwnd` is the receiver's advertised buffer space, so flow control protects the receiver and congestion control protects the network in between. Nothing in the network tells the sender a number; the sender infers capacity from timing and loss. Each returning ACK also paces new transmissions, which keeps the sender's output rate roughly matched to the bottleneck's drain rate once the loop is running.

The classic (Reno-family) sender moves between four behaviours:

- **Slow start.** Begin with `cwnd` at about 10 segments and increase it by one segment per ACK, doubling per round trip. This is exponential probing to find the rough scale of the path quickly, and it runs until loss occurs or `cwnd` crosses the slow start threshold `ssthresh`.
- **Congestion avoidance.** Above `ssthresh`, increase `cwnd` by roughly one segment per round trip instead of per ACK. Linear growth probes for extra bandwidth without overshooting hard.
- **Fast retransmit and fast recovery.** Three duplicate ACKs mean a segment is missing but later ones arrived, so the path still works. Retransmit immediately, halve `cwnd`, set `ssthresh` to the new value, and continue in congestion avoidance rather than restarting.
- **Retransmission timeout.** No ACK at all within the RTO means the sender has lost its clock. Drop `cwnd` back to one segment, re-enter slow start, and double the timer for each further failure.

The linear-increase, halve-on-loss pattern is additive increase, multiplicative decrease. It converges: two flows sharing a bottleneck with different windows both add the same amount per round trip and both cut by the same factor, and repeated application drives their windows toward equality. It also guarantees the network is periodically driven into congestion, since the only way this sender learns the limit is by exceeding it. The resulting throughput is roughly `cwnd / RTT`, which is why a flow on a long path is at a structural disadvantage against a short one: the same window increment buys less rate.

The weak point is treating packet loss as the congestion signal. Loss is a late, noisy proxy: wireless links drop packets without congestion, and deep router buffers absorb overload for hundreds of milliseconds before dropping anything, so the sender keeps filling a queue it cannot see and adds latency for everyone on the link. The responses to that split three ways. CUBIC, the Linux default, keeps loss as the signal but replaces linear growth with a cubic function of time since the last reduction, which recovers quickly on high bandwidth-delay-product paths and flattens near the previous window. BBR instead estimates the bottleneck bandwidth and minimum round-trip time directly and paces to their product, aiming to sit at the point where the pipe is full but the queue is empty. ECN sidesteps inference altogether: the router marks a bit in the IP header when its queue builds, the receiver echoes the mark back, and the sender reduces its window without a packet ever being dropped. Data centre deployments lean on ECN heavily (DCTCP scales the reduction to the fraction of marked packets), while the public internet still depends mostly on CUBIC and, increasingly, BBR.

TCP congestion control is a feedback loop: the sender guesses how much unacknowledged data the network can hold, sends that much, and adjusts the guess based on whether packets get through.

The state variable is the congestion window (`cwnd`), measured in bytes or segments. The sender may have at most `min(cwnd, rwnd)` bytes in flight, where `rwnd` is the receiver's advertised buffer space. Flow control (`rwnd`) protects the receiver; congestion control (`cwnd`) protects the network. The network never tells the sender its capacity, so `cwnd` is derived from implicit signals — ACK arrivals, lost packets, and round-trip time.

**The classic loop (Reno family)**

- **Slow start.** Begin with `cwnd` around 10 segments. Increase by one segment per ACK, which doubles `cwnd` every RTT. Exponential ramp, despite the name. Continues until loss or until `cwnd` crosses `ssthresh`.
- **Congestion avoidance.** Above `ssthresh`, increase `cwnd` by roughly one segment per RTT instead of per ACK. Linear probing for more bandwidth.
- **Fast retransmit.** Three duplicate ACKs mean one segment is missing but later ones arrived, so the path is still delivering. Retransmit immediately without waiting for a timer.
- **Fast recovery.** Halve `ssthresh` to `cwnd/2`, set `cwnd` near that, and continue in congestion avoidance.
- **Timeout.** No ACK at all within the retransmission timeout. Treated as severe: `ssthresh = cwnd/2`, `cwnd` back to the initial window, restart slow start.

That gives additive-increase/multiplicative-decrease (AIMD): grow by a constant per RTT, cut by a constant factor on loss. AIMD is what makes competing flows converge toward a fair share — a flow with a large window loses more absolute throughput on each cut than a small one, so the windows equalize over time. The sawtooth is intrinsic: TCP finds capacity by overshooting it and backing off.

**The algorithms you'll actually meet**

| Algorithm | Signal | Increase rule | Where it runs |
|---|---|---|---|
| Reno / NewReno | Packet loss | +1 MSS per RTT | Legacy default |
| CUBIC | Packet loss | Cubic function of time since last loss | Linux and Windows default |
| BBR | Bandwidth and RTT estimates | Paces to measured bottleneck rate | YouTube, Google, opt-in on Linux |
| Vegas | Rising RTT | Queue-delay based, backs off early | Rare; loses to loss-based flows |
| DCTCP | ECN marks | Proportional to marking rate | Data centers |

CUBIC exists because Reno's linear increase is far too slow on high bandwidth-delay-product paths — a 10 Gbps transcontinental link needs tens of thousands of segments in flight, and one segment per RTT takes hours to get there. CUBIC grows as a cubic curve in real time (not RTT count), so it flattens near the previous loss point, probes cautiously there, then accelerates hard if no loss appears. It's also RTT-independent, so short and long paths compete more fairly.

BBR abandons loss as the signal entirely. Loss-based control fills the bottleneck queue by design, which is why deep router buffers produce bufferbloat: throughput is fine, latency is terrible. BBR instead estimates the bottleneck bandwidth and the minimum RTT, then sends at that rate with a small periodic probe upward. It keeps queues short, but it's more aggressive against CUBIC flows in some regimes, which is a live fairness argument.

ECN sits underneath all of this. When a router's queue starts building, it marks a bit in the IP header instead of dropping. The receiver echoes the mark, the sender reacts as if to loss without anyone paying a retransmission. DCTCP takes this further by reacting proportionally to the fraction of marked packets, which is why it holds data-center queues to a few packets.

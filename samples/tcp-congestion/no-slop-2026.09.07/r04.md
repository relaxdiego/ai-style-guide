TCP congestion control is a feedback loop that guesses the network's spare capacity, because no router tells the sender what it is. The sender keeps a congestion window (`cwnd`), limits unacknowledged data in flight to `min(cwnd, receiver window)`, raises `cwnd` while acknowledgements keep arriving on time, and cuts it when a signal says the path is overloaded. Everything else is detail about what counts as a signal and how fast to move in each direction.

**The signals.** Classic TCP infers congestion from loss, on the assumption that routers drop packets only when a queue overflows:

- Three duplicate ACKs: one segment is missing but later ones arrived, so the path still works. This triggers fast retransmit and a moderate cut.
- Retransmission timeout: nothing is getting through. The sender assumes the worst.
- ECN marks: a router sets a bit instead of dropping, when both endpoints negotiated Explicit Congestion Notification.
- Rising round-trip time: queues are filling. Delay-based algorithms use this, loss-based ones ignore it.

**The phases.** A connection walks through these in order, and returns to earlier ones on loss:

- **Slow start.** `cwnd` starts near 10 segments and grows by one segment per ACK, so it doubles every round trip. The name describes the starting point, not the growth rate, which is exponential. It ends when `cwnd` crosses `ssthresh` or a loss occurs.
- **Congestion avoidance.** `cwnd` grows by roughly one segment per round trip. This is the additive increase probing for a little more bandwidth each RTT.
- **Fast retransmit and fast recovery.** On three duplicate ACKs, resend the missing segment immediately rather than waiting for the timer, set `ssthresh` to half the current window, and continue from there.
- **Timeout.** Set `ssthresh` to half the window, drop `cwnd` to one segment, re-enter slow start, and double the retransmit timer. This is the expensive path and is what makes a single badly timed loss cost hundreds of milliseconds.

The increase-and-cut pattern (additive increase, multiplicative decrease) is what makes competing flows converge on a fair split. Additive increase moves flows equally in absolute terms, multiplicative decrease cuts them proportionally, so a larger flow gives up more on each loss and the shares even out over time.

**Self-clocking** matters as much as the window arithmetic. Each ACK releases new data, so the sender transmits at whatever rate the bottleneck link is draining, without measuring that rate. Modern stacks add pacing on top, spreading a window's worth of packets across the RTT, because a window released as a burst overflows shallow buffers that the average rate would not.

**The algorithms in use:**

| Algorithm | Congestion signal | Growth in avoidance | Reduction on loss | Typical use |
|---|---|---|---|---|
| Reno / NewReno | Loss | Linear, 1 MSS/RTT | 50% | Reference behaviour, rarely a default now |
| CUBIC | Loss | Cubic function of time since last reduction | 30% | Linux and Windows default |
| BBR | Measured bottleneck bandwidth and minimum RTT | Probes rate directly, no fixed window rule | Does not react to loss alone | Google, YouTube, many CDNs |
| Vegas | Rising RTT | Linear | Before loss occurs | Research, mostly unused; loses to loss-based flows |
| DCTCP | Fraction of ECN-marked ACKs | Linear | Proportional to marking rate | Datacenter fabrics |

CUBIC exists because Reno's linear growth is far too slow on high-bandwidth, high-latency paths: recovering a 10 Gbit/s window at one segment per 100 ms RTT takes over an hour. CUBIC's window is a cubic curve in real time since the last reduction, which makes growth independent of RTT and gives short-RTT flows less of an unfair advantage. BBR takes a different position entirely, treating loss as a poor proxy and instead estimating the bottleneck bandwidth and the minimum RTT, then sending at that bandwidth with a small fixed amount of data in flight. That keeps queues near empty, which is the answer to bufferbloat: loss-based algorithms by construction fill the bottleneck buffer before they back off, so an oversized buffer turns into seconds of added latency for every other flow sharing it.

Two known failure modes are worth having in mind. Loss-based control misreads wireless corruption as congestion and cuts the window when the path is fine. And BBR competing against CUBIC on a deep buffer takes more than its share, since it does not retreat from the loss that CUBIC responds to.

TCP congestion control is a guessing loop: the sender keeps a running estimate of how many unacknowledged bytes the network path can hold, and adjusts that estimate up or down based on feedback from the receiver. Nobody tells the sender the bottleneck link speed, so it has to probe by sending more until something goes wrong, then back off. That estimate is the congestion window, `cwnd`. The sender may have at most `min(cwnd, rwnd)` bytes in flight, where `rwnd` is the receiver's advertised buffer space. Congestion control protects the network; flow control via `rwnd` protects the receiver. They are separate limits that happen to multiply into the same send permission.

The classic loop has two growth modes separated by a threshold called `ssthresh`:

- **Slow start.** Starts at an initial window of about 10 segments on modern stacks (RFC 6928; it was 1 to 4 for years). Every ACK bumps `cwnd` by one MSS, which doubles the window every round trip. It is exponential growth, badly named. It runs until loss occurs or `cwnd` crosses `ssthresh`.
- **Congestion avoidance.** Above `ssthresh`, `cwnd` grows by roughly one MSS per round trip instead of per ACK. Linear probing, on the theory that you are now near capacity and should creep rather than leap.

What happens on a loss signal depends on how the loss was detected, and the difference matters a lot for throughput:

- **Three duplicate ACKs** mean a segment went missing but later ones arrived, so the path is still delivering. The sender does a fast retransmit of the missing segment and enters fast recovery: halve `ssthresh`, set `cwnd` near the new `ssthresh`, keep transmitting. This is the cheap case.
- **Retransmission timeout** means nothing came back at all. The sender assumes the path collapsed, drops `cwnd` to one segment, and re-enters slow start. Recovery from an RTO costs many round trips, which is why a single tail loss on a short flow can dominate its completion time.

The additive increase, multiplicative decrease pattern is not an arbitrary choice. If several flows share a bottleneck and all add a constant on success and multiply by a constant on loss, their sending rates converge toward an equal share regardless of where they started. Chiu and Jain showed this in 1989. Additive increase moves flows along a line parallel to the fairness line, and multiplicative decrease pulls them toward the origin along a line through it, so the sawtooth walks the system into fairness. Increase-by-multiply or decrease-by-subtract does not have this property.

Modern stacks mostly do not run Reno. The algorithms actually deployed:

| Algorithm | Signal | Behaviour | Where you find it |
|---|---|---|---|
| Reno / NewReno | Loss | AIMD, halve on loss | The reference model, rarely the default now |
| CUBIC | Loss | Window is a cubic function of time since the last reduction; plateaus at the previous maximum, then probes aggressively past it. Decrease factor 0.7, not 0.5. Growth is independent of RTT. | Linux default since 2.6.19, also Windows and Apple |
| BBR | Bandwidth and RTT estimates | Measures the bottleneck bandwidth and minimum RTT, then paces at that product. Ignores loss as a congestion signal. | Google, YouTube, widely used server side; BBRv3 is current |
| DCTCP | ECN marking fraction | Reduces proportionally to how many packets were marked, not by a fixed factor. Needs switch support. | Data centres only |
| Vegas | Increasing RTT | Backs off on queue growth before loss. Loses badly when competing with loss-based flows. | Mostly historical |

The reason CUBIC and BBR exist is that halving on every loss wastes capacity on long fat paths, and that loss-based control has a nasty side effect: it only stops growing when a buffer overflows, so it fills every buffer along the path first. On a router with a large buffer that means hundreds of milliseconds of standing queue, which is the bufferbloat problem. Your throughput is fine and your latency is ruined. Two fixes are in play. Active queue management such as CoDel or FQ-CoDel drops or marks packets based on how long they sat in the queue rather than waiting for the buffer to fill. Explicit Congestion Notification lets a router set a bit in the IP header instead of dropping, so the sender learns about congestion without losing data; L4S extends this into a low-latency service class with more aggressive marking.

Two practical points that trip people up. First, `cwnd` is a byte allowance, not a rate, so a sender given a large window will burst it back to back at line rate unless the stack paces the packets out across the round trip; Linux paces via `fq` or the internal pacing in BBR. Second, competing flows do not get equal shares in practice. Reno and CUBIC throughput scales inversely with RTT, so a nearby flow beats a distant one on the same bottleneck, and a browser opening six connections to a host takes six shares.

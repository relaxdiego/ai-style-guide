TCP congestion control is a sender-side feedback loop: the sender keeps a congestion window (cwnd) limiting unacknowledged bytes in flight, grows it while the network looks fine, and shrinks it when the network signals trouble. The receiver's advertised window caps it separately, so bytes in flight is `min(cwnd, rwnd)`. Nothing in the network tells the sender a rate; the sender infers capacity from acknowledgements, losses, and round-trip times.

**The classic state machine (Reno)**

| Phase | Entry | cwnd per RTT | Exit |
|---|---|---|---|
| Slow start | Connection open, or RTO timeout | Doubles (cwnd += MSS per ACK) | cwnd reaches ssthresh, or loss |
| Congestion avoidance | cwnd > ssthresh | +1 MSS per RTT (additive increase) | Loss |
| Fast retransmit / fast recovery | 3 duplicate ACKs | ssthresh = cwnd/2, cwnd = ssthresh | New ACK arrives |
| RTO | Retransmit timer fires | ssthresh = cwnd/2, cwnd = 1 MSS | Back to slow start |

The additive-increase / multiplicative-decrease rule is what makes competing flows converge to a fair share: every flow adds the same absolute amount per RTT and cuts by the same proportion, so the larger flow loses more on each cut. Two consequences follow. Flows with short RTTs grow faster and get more bandwidth, and throughput on a lossy path scales roughly as `MSS / (RTT * sqrt(p))` for loss probability `p`, which is why a 10 Gbit/s transcontinental link cannot be filled by Reno at any realistic loss rate.

**What the signals mean**

- **Packet loss.** Assumed to mean a full queue. False on wireless links, where loss is corruption.
- **Duplicate ACKs / SACK.** Loss of one segment while later ones arrive. The pipe is still flowing, so cut in half instead of restarting.
- **Retransmit timeout.** No ACKs at all. Assume the path collapsed and restart from one segment.
- **ECN marks.** The router sets a bit in the IP header instead of dropping. The sender reacts to congestion without losing data.
- **Rising RTT.** Queues are filling. Used by delay-based algorithms; ignored by Reno and CUBIC.

**Algorithms in use today**

| Algorithm | Signal | Growth | Where you see it |
|---|---|---|---|
| Reno / NewReno | Loss | Linear | Textbooks, fallback |
| CUBIC | Loss | Cubic function of time since last loss, independent of RTT | Linux and Windows default |
| BBR / BBRv2, v3 | Measured bottleneck bandwidth and minimum RTT | Paces to estimated bandwidth-delay product | Google, YouTube, many CDNs |
| Vegas | RTT increase | Linear, backs off before loss | Rare; loses to loss-based flows |
| DCTCP | ECN mark fraction | Proportional cut, not halving | Datacenters with shallow-buffer switches |

CUBIC replaced Reno because its window growth depends on elapsed time rather than RTT, which removes the bias against long paths and probes aggressively back toward the pre-loss window after a cut. BBR changed the target entirely: it estimates the bottleneck bandwidth and the minimum RTT, then sends at that product rather than filling the queue until something drops. That fixes bufferbloat, since a loss-based sender on a router with a large buffer will grow cwnd until the buffer is full, adding hundreds of milliseconds of queueing delay before it ever sees a drop.

Two mechanisms sit alongside the window and matter in practice. Pacing spreads a window's worth of packets across the RTT instead of releasing them as a burst, which is required for BBR and helps CUBIC on high-speed links. Active queue management in the router (CoDel, FQ-CoDel, PIE) drops or marks early based on queue sojourn time, giving the sender its signal before the buffer is full, which is the other half of the bufferbloat fix and the only half the endpoints do not control.

TCP congestion control is a feedback loop that guesses how much data the path can hold: the sender grows its rate until the network signals trouble, then cuts back. The receiver's flow control window says what the *receiver* can absorb; congestion control adds a second, sender-side limit for what the *network* can absorb, and the sender is bound by whichever is smaller.

The state a sender keeps:

- `cwnd` (congestion window): bytes the sender may have unacknowledged in flight.
- `rwnd`: the receiver's advertised window.
- Actual limit: `min(cwnd, rwnd)`. Bytes in flight must stay under it.
- `ssthresh`: the boundary between exponential and linear growth.
- RTT estimate and RTO timer, from Karn's algorithm plus the smoothed RTT/variance calculation in RFC 6298.

Classic Reno-family behaviour runs in four phases:

1. **Slow start.** `cwnd` begins at the initial window, 10 MSS under RFC 6928. Every ACK adds one MSS, so `cwnd` doubles each round trip. Growth is exponential despite the name; "slow" was relative to the pre-1988 behaviour of blasting a full receiver window immediately.
2. **Congestion avoidance.** Once `cwnd` passes `ssthresh`, growth drops to roughly one MSS per RTT, implemented per-ACK as `cwnd += MSS*MSS/cwnd`. This is the additive increase probing for spare capacity.
3. **Fast retransmit and fast recovery.** Three duplicate ACKs mean a segment is missing but later ones arrived, so the path is still delivering. The sender retransmits immediately, sets `ssthresh = cwnd/2`, and resumes from there rather than starting over.
4. **Retransmission timeout.** No ACK before the RTO fires means the sender has lost its clock entirely. `ssthresh` drops to half the flight size, `cwnd` collapses to 1 MSS, and slow start runs again. This is the expensive case, and the RTO doubles on each successive timeout.

The signals a sender can use to decide the network is congested:

- **Packet loss**, inferred from duplicate ACKs or a timeout. SACK (RFC 2018) tells the sender exactly which segments arrived, so it can retransmit precisely instead of guessing; RACK-TLP now handles loss detection by time rather than by counting duplicates.
- **Explicit Congestion Notification.** Routers mark the IP header instead of dropping; the receiver echoes the mark back. The sender reacts without anyone losing a packet.
- **Delay.** Rising queueing delay means a bottleneck buffer is filling. Vegas and BBR act on this; Reno and CUBIC ignore it.

The algorithms in real use differ mostly in how they grow and how hard they cut:

| Algorithm | Signal | Increase | Decrease | Where it runs |
|---|---|---|---|---|
| Reno / NewReno | Loss | +1 MSS per RTT | ×0.5 | Reference behaviour, still the fairness baseline |
| CUBIC | Loss | Cubic function of time since last loss | ×0.7 | Linux default, Windows default since 10 |
| BBR / BBRv2, v3 | Bandwidth and min RTT estimates | Paces at estimated bottleneck rate | Does not halve on loss alone | Google, YouTube, widely deployed |
| Vegas | Delay | Linear | Linear | Rare; loses to loss-based flows sharing a link |
| DCTCP | ECN mark fraction | Linear | Proportional to marking rate | Datacentres with shallow-buffer switches |

CUBIC exists because Reno's additive increase is far too slow on high-bandwidth long-RTT paths: recovering a 10 Gbps window at 100 ms RTT takes over an hour at one MSS per round trip. CUBIC instead grows as `W(t) = C(t-K)³ + W_max`, which climbs fast when far below the previous loss point, flattens near it to probe cautiously, then accelerates again if no loss appears. BBR abandons loss as the signal altogether: it estimates the bottleneck bandwidth and the minimum RTT, sets its target in-flight bytes to the product, and paces packets out at that rate. On paths with random non-congestive loss, that beats loss-based algorithms badly; the cost is that BBR can crowd out CUBIC flows in some buffer regimes, which is much of what BBRv2 and v3 were built to fix.

Two properties tie the system together. Additive increase with multiplicative decrease converges to a fair share among competing flows regardless of starting point, which is Chiu and Jain's 1989 result and the reason the internet does not collapse under greedy senders. And the whole loop is self-clocking: ACKs return at the bottleneck's rate, so ACK arrival paces transmission automatically, which is why a timeout is so damaging. Losing the ACK stream loses the clock. The visible failure mode today is bufferbloat, where oversized router buffers absorb so much queue that loss-based senders never see a drop until latency has already reached seconds; the fixes are queue management at the router (CoDel, FQ-CoDel, PIE) and delay-sensitive senders like BBR, not a change to the window arithmetic.

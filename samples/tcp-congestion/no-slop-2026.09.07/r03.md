TCP congestion control is a feedback loop where the sender guesses how much data the network can hold, sends that much, and adjusts the guess based on what comes back. The network never tells the sender its capacity, so the sender probes: increase until something signals overload, back off, repeat. The state variable is the congestion window (cwnd), a byte count of unacknowledged data the sender allows itself. The actual send window is `min(cwnd, receiver's advertised window)`, so flow control and congestion control are separate limits that happen to combine here. Acks returning from the receiver both free window space and pace new transmissions, which is why a TCP connection self-clocks at roughly the bottleneck rate once it settles.

The classic loop has four states, and every loss-based algorithm since is a variation on them:

- **Slow start.** cwnd starts around 10 MSS (RFC 6928; it was 1 to 4 historically) and grows by one MSS per ack, so it doubles every RTT. Exponential, despite the name. Exits when cwnd crosses `ssthresh` or a loss occurs.
- **Congestion avoidance.** cwnd grows by about one MSS per RTT, linear. This is the additive increase.
- **Fast retransmit / fast recovery.** Three duplicate acks mean a packet was lost but later ones arrived, so the path still works. Resend the missing segment, halve ssthresh and cwnd, continue in congestion avoidance. This is the multiplicative decrease.
- **Retransmission timeout.** No acks at all. Treated as severe: ssthresh drops to half the flight size, cwnd resets to 1 MSS, and the sender re-enters slow start.

Additive increase with multiplicative decrease (AIMD) is not an arbitrary pair. Chiu and Jain showed that if flows sharing a bottleneck all increase by a constant and decrease by a proportion, their rates converge toward equal shares regardless of starting point. Additive increase moves flows along a line parallel to the fairness line, multiplicative decrease moves them toward the origin along a ray, and repeated cycles walk the system to the fair allocation. Any other combination either fails to converge or does so unfairly.

The variants differ in what they treat as the congestion signal and how they grow:

| Algorithm | Signal | Growth | Notes |
|---|---|---|---|
| Reno | Packet loss | Linear per RTT | One loss recovery per RTT; degrades badly with multiple losses in a window |
| NewReno | Packet loss | Linear | Handles partial acks, stays in fast recovery through multiple losses |
| SACK | Packet loss | Linear | Receiver reports exactly which blocks arrived, so the sender retransmits only holes |
| CUBIC | Packet loss | Cubic function of time since last loss | Linux default since 2.6.19. Growth is independent of RTT, so short-RTT flows do not starve long ones |
| BBR | Estimated bottleneck bandwidth and minimum RTT | Paces at the estimated rate | Ignores loss as a signal; probes bandwidth and RTT on a cycle |
| Vegas | Increasing RTT | Linear | Backs off before queues fill; loses to loss-based flows sharing a link |
| DCTCP | ECN mark fraction | Proportional to marking rate | Datacenter only, needs switch support |

Loss-based control has a structural problem: it only backs off after the bottleneck queue is full. Deep buffers in routers and modems mean the queue fills to hundreds of milliseconds before a drop happens, so latency for every flow through that link collapses while throughput stays fine. This is bufferbloat. Two responses exist. Active queue management at the router (CoDel, FQ-CoDel, PIE) drops or ECN-marks early so senders learn sooner, and ECN lets a router set a bit in the IP header instead of dropping, which the receiver echoes back. BBR attacks it from the sender: it measures delivery rate and minimum RTT, computes the bandwidth-delay product, and keeps roughly that much in flight rather than filling whatever queue exists. BBR trades a well-defined fairness story for lower latency, and its interaction with CUBIC flows on the same link is still argued about.

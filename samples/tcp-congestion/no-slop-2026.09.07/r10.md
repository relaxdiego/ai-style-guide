TCP congestion control is a feedback loop that guesses how much data the network path can hold, using packet loss or delay as the only signal. The sender keeps a congestion window (cwnd), sends at most `min(cwnd, receiver_window)` bytes of unacknowledged data, and adjusts cwnd up when ACKs arrive on time and down when they do not. Nothing in the network tells the sender a number; routers just drop packets when queues fill, and the sender infers capacity from that.

**The four states of the classic algorithm (Reno):**

- **Slow start.** cwnd starts at ~10 MSS (Linux default, was 1 or 2 historically) and grows by 1 MSS per ACK, so it doubles every RTT. Exits when cwnd crosses `ssthresh` or loss occurs. Called "slow" because it starts small, not because it grows slowly.
- **Congestion avoidance.** cwnd grows by roughly 1 MSS per RTT (`cwnd += MSS*MSS/cwnd` per ACK). Linear probing for spare capacity.
- **Fast retransmit / fast recovery.** Three duplicate ACKs mean a packet was lost but later ones arrived, so the path is still passing traffic. Retransmit immediately, set `ssthresh = cwnd/2`, set `cwnd = ssthresh`, stay in congestion avoidance.
- **Retransmission timeout.** No ACK at all. Assume the path collapsed: `cwnd = 1 MSS`, re-enter slow start. Expensive, which is why fast retransmit exists.

The increase and decrease rules are chosen for convergence, not politeness. Additive increase with multiplicative decrease drives competing flows toward an equal share: two flows that halve on shared loss and add equally on success converge to the fair point regardless of where they start, whereas additive decrease would preserve the initial imbalance forever. The cost is the sawtooth: throughput oscillates instead of sitting at capacity, and the average rate goes as `MSS/(RTT*sqrt(p))` for loss rate `p`, which means long-RTT flows lose badly to short-RTT flows on the same bottleneck.

**What is actually deployed:**

| Algorithm | Signal | Behavior | Where |
|---|---|---|---|
| Reno / NewReno | Loss | AIMD sawtooth, halve on loss | Legacy, still the reference |
| CUBIC | Loss | cwnd is a cubic function of time since last reduction; grows fast, flattens near the previous maximum, then probes past it. RTT-independent | Linux default, Windows default |
| BBR | Bandwidth and RTT estimates | Measures delivery rate and min RTT, paces at the estimated bottleneck rate, ignores loss as a signal | Google, YouTube, widely on the server side |
| DCTCP | ECN marks | Reduces proportionally to the fraction of marked packets, not by half | Datacenters, requires switch support |
| Vegas | Queueing delay | Reduces before loss happens; loses to loss-based flows sharing a link | Rare in the wild |

Two practical consequences. First, loss-based control fills the bottleneck buffer by definition, since it only backs off after the queue overflows, so an oversized router buffer produces seconds of standing latency for everyone on the link (bufferbloat); AQM such as fq_codel or ECN marking fixes it at the router, and BBR sidesteps it at the sender. Second, loss on wireless links is often corruption rather than congestion, and a loss-based sender will cut its rate anyway, which is why link layers retransmit locally to hide those losses from TCP.

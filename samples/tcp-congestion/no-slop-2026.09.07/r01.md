TCP congestion control is a feedback loop that guesses how much data the path can hold in flight, then adjusts that guess from loss and delay signals. The receiver's advertised window says what the receiver can absorb; congestion control says what the network can absorb. The sender is bounded by the smaller of the two.

## The state that does the work

The sender keeps a congestion window, `cwnd`, in bytes. It may have at most `min(cwnd, rwnd)` bytes unacknowledged at any moment. Throughput follows from that directly: roughly `cwnd / RTT`. Nobody sets a rate in bytes per second in classic TCP. You set a window, and arriving ACKs release new data, so the network's own return path clocks the transmission. A path that slows down delivers ACKs slower and the sender slows down without being told anything.

## The phases

**Slow start.** `cwnd` begins at 10 MSS on Linux (RFC 6928). Every ACK bumps it by one MSS, so it doubles each RTT. This is exponential probing, not slow, and it ends when `cwnd` crosses `ssthresh` or a loss shows up.

**Congestion avoidance.** Growth drops to about +1 MSS per RTT. The sender is now near the edge and probes gently.

**Fast retransmit and fast recovery.** Three duplicate ACKs (or SACK blocks) mean a packet is missing but data is still flowing. Reno retransmits immediately and halves `cwnd` rather than stalling.

**Retransmission timeout.** No ACKs at all. The sender assumes the path collapsed, sets `cwnd` back to 1 MSS, and re-enters slow start. Linux's minimum RTO is 200 ms, so this is expensive and algorithms work hard to avoid it.

The additive increase and multiplicative decrease pattern is what makes competing flows converge on a fair split. Chiu and Jain showed the geometry in 1989: additive increase moves flows toward equality, multiplicative decrease preserves their ratio, and repeated cycles drive the ratio to 1.

## Algorithms in use

| Algorithm | Signal | On congestion | Growth |
|---|---|---|---|
| Reno / NewReno | Loss | `cwnd × 0.5` | +1 MSS per RTT |
| CUBIC | Loss | `cwnd × 0.7` | Cubic in time since last loss, independent of RTT |
| Vegas | Queueing delay | Back off before loss | Target a few packets queued |
| BBR | Measured bandwidth and minimum RTT | No loss-triggered cut | Paces at estimated bandwidth-delay product |

CUBIC is the Linux default and dominates the public internet. Its point is that Reno's `+1 per RTT` cannot fill a 10 Gbit/s path with a 100 ms RTT in any reasonable time. CUBIC grows as a cubic function of elapsed time since the last reduction, so it climbs fast when far below the previous maximum, flattens near it, and probes upward again past it. Because the curve is in wall-clock time, flows with different RTTs grow at comparable rates, which fixes Reno's bias toward short-RTT flows.

BBR takes a different view. It estimates the bottleneck bandwidth and the minimum RTT, then sends at that product, treating loss as a poor congestion signal because deep buffers delay it and shallow buffers produce it randomly.

## Where loss-based control breaks

Deep buffers in routers and modems break the assumption that loss arrives promptly. A loss-based sender fills the buffer before it hears anything, so the queue holds hundreds of milliseconds of data and every flow through it suffers the latency. This is bufferbloat. The fixes live in the network: active queue management such as CoDel and FQ-CoDel drops or marks early based on how long packets sit in the queue, not on how many are there.

ECN sidesteps the drop entirely. The router sets a bit in the IP header, the receiver echoes it, and the sender reduces as if it had seen loss. L4S extends this to a much finer signal for low-latency traffic.

One more piece matters in practice: pacing. Modern Linux spreads a window's worth of packets across the RTT instead of releasing them as a burst when ACKs arrive. BBR requires it. CUBIC benefits from it because bursts create transient queues that trigger drops the window size did not call for.

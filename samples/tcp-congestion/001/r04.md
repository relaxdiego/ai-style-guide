TCP congestion control is a sender-side feedback loop: the sender keeps a congestion window (`cwnd`) limiting unacknowledged bytes in flight, grows it while the network looks healthy, and cuts it when it infers congestion. The receiver's advertised window caps this separately, so actual bytes in flight are `min(cwnd, rwnd)`. Nothing in the network tells TCP the available bandwidth; it probes for it and treats packet loss (or, in newer algorithms, rising delay) as the congestion signal.

The classic loop has four phases:

- **Slow start.** `cwnd` starts at ~10 MSS and doubles every RTT (one MSS per ACK). Exponential, despite the name — it is slow only relative to blasting at line rate. Runs until loss or until `cwnd` crosses `ssthresh`.
- **Congestion avoidance.** Additive increase: +1 MSS per RTT. This is the steady-state probing for more bandwidth.
- **Fast retransmit.** Three duplicate ACKs mean a segment is missing but later ones arrived, so the path is still passing traffic. Retransmit immediately instead of waiting for the RTO.
- **Fast recovery.** Halve `cwnd` and `ssthresh`, then continue in congestion avoidance rather than restarting slow start. A full RTO timeout is treated as much worse: `cwnd` drops to 1 MSS and slow start begins again.

That additive-increase/multiplicative-decrease (AIMD) pattern is what makes competing flows converge toward a fair share: increases are equal in absolute terms, decreases are proportional, so a greedy flow loses more per cut than a small one. It also produces the sawtooth throughput graph, and it is why loss-based TCP fills whatever buffer sits in front of the bottleneck before it backs off, which is the mechanism behind bufferbloat.

The algorithms in real use today differ mainly in what signal they use and how they grow:

| Algorithm | Signal | Growth | Where you see it |
|---|---|---|---|
| Reno / NewReno | Loss | Linear (+1 MSS/RTT) | Reference behaviour, older stacks |
| CUBIC | Loss | Cubic function of time since last loss, RTT-independent | Linux and Windows default |
| BBR | Bandwidth × RTT estimate | Paces to measured bottleneck bandwidth, ignores loss | Google, QUIC deployments |
| Vegas | Delay increase | Backs off before loss | Rare alone; loses to loss-based flows |
| DCTCP | ECN mark fraction | Proportional cut | Datacenter fabrics |

Two mechanisms modify all of this. ECN lets a router mark a packet instead of dropping it, so the sender reacts to congestion without losing data; it requires support at both endpoints and the router. SACK lets the receiver report exactly which blocks arrived, so the sender retransmits only the holes instead of everything after the first gap — without it, recovery from multiple losses in one window is dismal.

The important asymmetry: CUBIC and BBR do not compete fairly. BBR ignores loss and holds its rate while CUBIC backs off, so on a shared bottleneck with shallow buffers BBR takes the larger share. If you are benchmarking a network change, check which algorithm each host is running (`sysctl net.ipv4.tcp_congestion_control` on Linux) before attributing a throughput difference to the network.

TCP congestion control is a feedback loop: the sender guesses how much data the network can hold, sends that much, and adjusts the guess based on whether the data arrived. Nothing in the network tells the sender a rate. The sender infers it.

The state variable is the congestion window (`cwnd`), a byte count of unacknowledged data the sender allows itself. Actual data in flight is limited by `min(cwnd, rwnd)`, where `rwnd` is the receiver's advertised buffer space. Flow control (`rwnd`) protects the receiver; congestion control (`cwnd`) protects the network. Throughput is roughly `cwnd / RTT`, so every algorithm below is really a rule for moving `cwnd` up and down over time.

Classic Reno-family behaviour runs in four phases:

- **Slow start.** Begin at 10 MSS (IW10, per RFC 6928). Increase `cwnd` by 1 MSS per ACK received, which doubles it each RTT. Exponential, despite the name. This continues until `cwnd` reaches `ssthresh` or a loss occurs.
- **Congestion avoidance.** Above `ssthresh`, increase by roughly 1 MSS per RTT rather than per ACK. Linear probing for spare capacity.
- **Fast retransmit / fast recovery.** Three duplicate ACKs mean one segment was lost but later ones arrived, so the path still works. Retransmit immediately, set `ssthresh = cwnd/2`, set `cwnd` to the new `ssthresh`, and continue. No return to slow start.
- **Timeout.** No ACK before the retransmission timer fires. The sender assumes the path collapsed: `ssthresh = cwnd/2`, `cwnd = 1 MSS`, back to slow start. This is the expensive failure mode, and RTO is bounded below by 1 second in RFC 6298 (Linux uses 200 ms).

The increase/decrease asymmetry is the whole design. Additive increase with multiplicative decrease (AIMD) is what makes competing flows converge on a fair share: Chiu and Jain showed in 1989 that additive increase moves flows toward equality while multiplicative decrease preserves their ratio, so the pair converges regardless of starting point. Multiplicative increase would never converge, and additive decrease would not shed load fast enough to clear a congested queue.

Reno's throughput follows the "square root law": about `MSS / (RTT * sqrt(p))` for loss rate `p`. At 10 Gb/s over 100 ms RTT you need a loss rate under 10⁻¹⁰ to fill the pipe, which is why Reno was replaced on any fast path.

| Algorithm | Congestion signal | Response | Where it runs |
|---|---|---|---|
| Reno | Loss (3 dup ACKs) | `cwnd × 0.5`, then +1 MSS/RTT | Historical baseline |
| CUBIC | Loss | `cwnd × 0.7`, regrow on a cubic curve in wall-clock time | Linux default since 2.6.19 |
| BBR (v1–v3) | Measured bandwidth and min RTT | Pace at estimated bottleneck rate, ignore loss | Google, YouTube, opt-in on Linux |
| DCTCP | ECN mark fraction | Reduce proportional to marking rate | Datacenters with ECN-capable switches |
| Vegas | RTT inflation | Reduce before loss occurs | Rare, loses to loss-based flows |

CUBIC matters most in practice. Its growth function depends on time since the last reduction rather than on ACK arrivals, which makes it RTT-independent: a flow with 200 ms RTT is not starved by a flow with 20 ms RTT sharing the same bottleneck, as it would be under Reno. The curve is flat near the previous window (careful probing where congestion last happened) and steep beyond it (aggressive search for new capacity).

Three things break the loss-based model:

- **Bufferbloat.** Loss-based algorithms only back off when a queue overflows, so they keep deep buffers permanently full. The path stays throughput-optimal and latency-terrible. Fixes live in the queue, not the sender: fq_codel and CAKE drop or mark early to give the sender a signal before the buffer fills.
- **Non-congestive loss.** Wi-Fi and cellular links drop packets from interference. Reno and CUBIC read that as congestion and halve throughput for no reason. BBR's indifference to loss is largely a response to this.
- **Shallow buffers with high BDP.** When the bottleneck buffer is smaller than the bandwidth-delay product, a loss-based flow cannot keep the pipe full between reductions.

BBR takes the other approach: continuously estimate the bottleneck bandwidth (max delivery rate observed) and the minimum RTT (propagation delay with empty queues), and pace packets at that product. It periodically probes 25% above the estimate to find increases, and drains below it to re-measure baseline RTT. The result keeps queues short. Its fairness against CUBIC has been contested since v1, which could crowd out loss-based flows at shallow buffers; v2 and v3 added loss and ECN response to soften that.

One detail the phase list above hides: `cwnd` alone produces bursts. A sender that gets a large ACK can dump an entire window into the link at line rate. Modern Linux paces transmissions across the RTT using the fq qdisc or internal TCP pacing, which is mandatory for BBR and helps CUBIC as well.

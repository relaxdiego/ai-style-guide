TCP congestion control is a sender-side feedback loop that guesses how much unacknowledged data the network path can hold, and adjusts that guess up on success and down on loss. The receiver's flow control window (`rwnd`) is a separate limit protecting the receiver's buffer; the sender transmits `min(cwnd, rwnd)` bytes in flight. Nothing in the network tells the sender the right number — it has to be inferred from ACK arrival and loss.

The classic loop has four states:

- **Slow start.** `cwnd` starts at 10 MSS (RFC 6928; it was 1–4 in older stacks) and grows by 1 MSS per ACK, so it doubles every RTT. Exponential, despite the name. Exits when `cwnd` crosses `ssthresh` or loss is detected.
- **Congestion avoidance.** `cwnd` grows by roughly 1 MSS per RTT (`cwnd += MSS²/cwnd` per ACK). Linear probing for spare capacity.
- **Fast retransmit / fast recovery.** Three duplicate ACKs mean a segment was lost but later ones arrived, so the path is still alive. Reno sets `ssthresh = cwnd/2`, retransmits, and resumes from the halved window without emptying the pipe. Modern Linux uses RACK-TLP (time-based, RFC 8985) instead of the dupack counter, plus SACK to know exactly which segments are missing.
- **RTO.** A timeout means no feedback at all. `cwnd` collapses to 1 MSS and slow start restarts. This is the expensive case.

That additive-increase/multiplicative-decrease pattern is what makes competing flows converge on a fair share: increases move flows along a 45° line, decreases pull them toward the origin proportionally, and the combination spirals in on equal rates. It also caps Reno's throughput at about `MSS / (RTT · √p)` for loss rate `p`, which is why Reno cannot fill a 10 Gb/s transcontinental link — filling it needs a loss rate low enough that no real path delivers it.

The algorithms in use today differ mainly in what signal they trust:

| Algorithm | Signal | Behaviour | Where you see it |
|---|---|---|---|
| Reno / NewReno | Loss | AIMD, halve on loss | Baseline, reference |
| CUBIC | Loss | `cwnd` is a cubic function of time since last loss; grows aggressively far from the last known ceiling, cautiously near it; RTT-independent | Linux default since 2.6.19, Windows since 10 |
| BBR (v1–v3) | Bandwidth + min RTT | Models the bottleneck directly, paces sends at the estimate, ignores loss as a primary signal | Google, YouTube, widely deployed |
| Vegas | Delay | Backs off on RTT increase | Loses badly to loss-based flows sharing a queue |
| DCTCP | ECN marks | Reduces proportionally to marking fraction | Datacenter fabrics only |

Loss-based control has a structural problem: it only backs off once a queue has overflowed, so it keeps deep router buffers permanently full. That's bufferbloat, and it adds hundreds of milliseconds of latency to every flow sharing the link. Two fixes exist. Active queue management (CoDel, FQ-CoDel, CAKE) drops or ECN-marks early so senders get the signal before the queue is full, and ECN plus L4S lets routers mark rather than drop, giving fine-grained congestion feedback without losing data. Pacing matters too: with TSO and large `cwnd`, a sender that dumps a whole window at line rate creates a burst the bottleneck cannot absorb, so Linux paces packets across the RTT regardless of algorithm.

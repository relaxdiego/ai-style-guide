TCP has no way of being told how much capacity is available along a path. There is no signal from the routers in between saying "you may send at 40 Mbit/s"; there is only the traffic the sender puts in and the acknowledgements that come back. So every sender discovers its share by experiment: push more data into the network until something indicates strain, then back off, then start pushing again. Congestion control is that feedback loop, and it exists because of a concrete failure. In 1986 the NSFNET backbone between Berkeley and LBL collapsed from 32 kbit/s to 40 bit/s, because senders responded to loss by retransmitting into a network that was already dropping everything, and Van Jacobson's response to that collapse is essentially the algorithm we still run.

The mechanism is a sender-side variable, the congestion window, usually written cwnd. The sender may have at most min(cwnd, rwnd) bytes unacknowledged in flight, where rwnd is the window the receiver advertises. Those two limits protect different things: rwnd keeps the sender from overrunning the receiver's buffer, cwnd keeps it from overrunning the network. Because a window of data is sent and then roughly one round trip passes before it is acknowledged, cwnd/RTT is the sending rate, and adjusting the window is how the sender adjusts its rate without ever having to think in bits per second. Acknowledgements do a second job here as well: each ack arriving is evidence that one packet has left the network, so transmitting on receipt of an ack naturally paces the sender to the rate the bottleneck can absorb. This self-clocking property is why TCP behaves reasonably even before the window logic does anything clever.

A new connection has no idea what the path can carry, so it begins in slow start, which despite the name is the aggressive phase. cwnd starts at a few segments (ten, in current practice) and grows by one segment for every ack received, which doubles the window each round trip. Exponential growth finds the right order of magnitude in a logarithmic number of round trips, and for the many short flows that make up most web traffic, slow start is the only phase that ever runs. It ends either when cwnd reaches a threshold called ssthresh, remembered from previous experience, or when the first loss occurs.

After that the connection enters congestion avoidance, where the increase becomes additive: roughly one segment per round trip rather than one per ack. On detecting congestion, the window is cut multiplicatively, traditionally in half. This combination, additive increase with multiplicative decrease, is not an arbitrary pairing. Chiu and Jain's argument is that when two flows share a bottleneck, additive increase moves both by the same absolute amount and so leaves the gap between them unchanged, while multiplicative decrease shrinks that gap in proportion to each flow's size, taking more from the larger one. Iterate the cycle and the flows converge toward an equal share, which is why AIMD and not some smoother-looking rule sits at the centre of the design.

What counts as "detecting congestion" matters as much as the response. A retransmission timeout is the severe signal: the sender assumes the path is badly broken, drops cwnd to one segment and re-enters slow start. But waiting for a timeout wastes a great deal of time when only a single packet was lost, so TCP also treats three duplicate acknowledgements as evidence of an isolated loss. Fast retransmit sends the missing segment immediately, and fast recovery halves cwnd and continues from there rather than collapsing to one, on the reasoning that the duplicate acks themselves prove packets are still flowing. Selective acknowledgement extends this by letting the receiver report exactly which blocks arrived, so a sender losing several packets in one window can repair them without guessing.

Using loss as the congestion signal has a cost that has driven most of the work since: a packet is only dropped once a queue is completely full, so a loss-based sender is one that deliberately fills the bottleneck buffer before it will back off. With today's oversized buffers that means large standing queues and latency in the hundreds of milliseconds for everyone sharing the link, the problem known as bufferbloat. Classic Reno also scales badly, since its steady-state throughput falls off roughly as 1/√p in the loss rate, and filling a long fast path requires a loss rate small enough to be unattainable in practice. The main responses:

- **CUBIC**, the Linux and Windows default, replaces linear growth with a cubic function of time since the last reduction. It probes cautiously near the window that previously caused loss and accelerates away from it, which makes growth independent of RTT and much faster on high bandwidth-delay paths.
- **BBR**, from Google, abandons loss as the primary signal and builds a model of the path instead, continuously estimating bottleneck bandwidth and minimum RTT and pacing to their product. It aims for the point where the pipe is full but the queue is not.
- **Delay-based schemes** such as Vegas read rising RTT as the early warning that a queue is building, reacting before loss occurs. They lose out when competing with loss-based flows that will not yield until the buffer overflows.
- **ECN and DCTCP** get the routers to help, marking packets rather than dropping them when a queue begins to grow. DCTCP goes further, using the fraction of marked packets as a measure of how congested the path is, which within a datacentre allows very small windows and very short queues.

Across all of these the invariant is the same. A sender maintains an estimate of what the network will accept, raises it while the evidence is good, and lowers it sharply when the evidence turns bad, and the whole of the internet's stability rests on the fact that essentially every sender is willing to do the lowering.

TCP has no way to ask the network how fast it may send. No router tells a sender its share of the bottleneck link, so the sender has to infer capacity from the only feedback it gets, which is the stream of acknowledgements coming back (and their absence). The mechanism for that inference is a variable held only in the sender's kernel, the congestion window or `cwnd`, which caps how many bytes may be unacknowledged at any moment. The sender is allowed `min(cwnd, rwnd)` bytes in flight, where `rwnd` is the receiver's advertised window; the receiver window protects the receiver's buffers and the congestion window protects the network, and the two are entirely separate concerns that happen to share a limit. Because data in flight is roughly rate multiplied by round-trip time, choosing `cwnd` is choosing a sending rate: at a 100 ms RTT, a 100-packet window is about 1500 packets per second, and doubling the window doubles the rate.

A new connection knows nothing about the path, so it starts in slow start, which despite the name is the aggressive phase. The initial window is typically 10 segments, and each arriving ACK raises `cwnd` by one segment, which means the window doubles every round trip. This is an exponential search for the path's capacity, and it is the reason a connection can go from nothing to saturating a gigabit link in a handful of round trips. Slow start ends when one of two things happens: `cwnd` crosses a threshold called `ssthresh`, which is the sender's memory of where trouble started last time, or a packet is lost, which is the network telling the sender it overshot.

After that the connection enters congestion avoidance, where the growth becomes additive: one extra segment per round trip rather than a doubling. Loss cuts the window multiplicatively, classically to half. This additive-increase, multiplicative-decrease rule is not an arbitrary choice of constants. Chiu and Jain showed in 1989 that among linear control rules, only additive increase with multiplicative decrease drives a set of competing flows toward an allocation that is both efficient and fair; a flow with a large window loses more in absolute terms on each cut than a flow with a small one, so repeated cycles pull the flows together, whereas multiplicative increase with additive decrease pushes them apart. The familiar sawtooth on a throughput graph is that control loop probing upward until it provokes a loss, backing off, and probing again.

The two ways a sender learns about loss are treated very differently, and the asymmetry is deliberate. Three duplicate ACKs mean later packets are still arriving at the receiver, so the path is alive and one segment went missing; the sender does a fast retransmit of that segment and enters fast recovery, halving the window and continuing in congestion avoidance without restarting. A retransmission timeout means nothing is coming back at all, which is a much worse signal, so `ssthresh` drops to half the current window, `cwnd` collapses to one segment, and the connection re-enters slow start from scratch. In practice, selective acknowledgement (SACK) makes the first case far more precise by letting the receiver report exactly which blocks arrived, and RACK, which is now the default on Linux, uses transmission timestamps rather than duplicate-ACK counting to decide what was lost.

Classic Reno breaks down on fast, long paths, and that is what drove everything since. Consider 10 Gbps across a 100 ms RTT: keeping that pipe full needs roughly 83,000 packets in flight. A single loss halves the window, and recovering 41,000 segments at one per round trip takes 41,000 RTTs, which is over an hour of steady climbing. Sustaining that window also demands a loss rate below about one packet in five billion, which no real path offers. Reno additionally penalises long-RTT flows, since a flow that gets feedback every 20 ms grows its window five times faster than one at 100 ms sharing the same bottleneck.

CUBIC, the default on Linux and on current Windows, addresses both problems by making the window a cubic function of the time elapsed since the last reduction rather than a function of ACKs received. After a cut it climbs steeply, flattens as it approaches the window size where loss last occurred, spends a while probing gently around that point, and then accelerates again if nothing breaks. Keying growth to wall-clock time rather than round trips is what removes most of the RTT unfairness.

| Algorithm | Signal it reacts to | Window behaviour | Where it is used |
|---|---|---|---|
| Reno / NewReno | Packet loss | Linear growth, halve on loss | Reference behaviour; rare as a default now |
| CUBIC | Packet loss | Cubic in time since last loss | Default on Linux and Windows |
| BBR | Measured bandwidth and RTT | Paced to an explicit path model | Google services, YouTube, widely deployable |
| Vegas | Growing RTT | Backs off before loss occurs | Largely research; loses to loss-based flows |
| DCTCP | ECN marks, proportionally | Cut scaled to marking rate | Datacentres with ECN-capable switches |

Loss-based control has a structural flaw worth understanding, because it explains a class of user-visible problems. A sender that only backs off when a packet is dropped will keep pushing until the bottleneck queue overflows, which means it deliberately keeps that queue full. Where the buffer is large, as in many home routers and mobile networks, the result is bufferbloat: throughput is fine, but every packet sharing that queue waits behind hundreds of milliseconds of someone else's bulk transfer, so a video call degrades while a backup runs. BBR takes a different approach by estimating the bottleneck bandwidth and the minimum RTT directly, then pacing packets at that estimated rate and periodically probing above it. It aims to sit at the point where the pipe is full but the queue is not, which keeps latency low, though its fairness when sharing a link with CUBIC has been a persistent point of contention and a large part of what BBRv2 and v3 were built to fix.

Explicit Congestion Notification changes the input rather than the response: an ECN-capable router marks a bit in the IP header instead of dropping the packet, and the receiver echoes the mark back so the sender reacts to congestion without anyone losing data. DCTCP builds on this inside datacentres by cutting the window in proportion to how many packets were marked rather than halving on any mark at all, which gives much smoother behaviour when the path is short and the switches are shallow. L4S is the ongoing effort to bring that same style of fine-grained marking to the public internet.

Two things about all of this tend to surprise people coming to it from application code. The first is that the algorithm lives entirely in the sender's operating system, so it is chosen per host (`net.ipv4.tcp_congestion_control` on Linux) and can even be set per socket, and both endpoints of a connection may be running completely different algorithms without any negotiation. The second is that fairness here is per-flow, not per-application or per-user, which is why opening six parallel connections has historically been an effective way to claim a larger share of a bottleneck, and why QUIC, which runs the same family of algorithms in userspace over UDP, inherits the identical dynamics with the same trade-offs.

TCP congestion control exists because the network gives a sender almost no information. There is no signal from routers saying "the path can carry 40 megabits per second"; there is only the traffic the sender puts in and the acknowledgements that come back. So every TCP sender runs an estimator: it guesses how much data the path can hold in flight, probes upward to see whether the guess was too low, and backs off when something suggests it was too high. That estimate lives in a variable called the congestion window, cwnd, which caps how many unacknowledged bytes the sender may have outstanding. The actual sending limit is the smaller of cwnd and the receiver's advertised window, since congestion control protects the network while flow control protects the receiver's buffers, and both have to be satisfied.

The mechanism that makes this workable is self-clocking. In steady state a sender transmits a new segment when an acknowledgement frees up window space, so the rate at which ACKs return, which is governed by the slowest link on the path, becomes the rate at which data goes out. Congestion control then reduces to adjusting cwnd rather than scheduling packets in time, because the ACK stream already spaces them.

A connection starts knowing nothing, and probing linearly from one packet would take absurdly long on a fast path, so TCP begins in slow start with cwnd around ten segments and doubles it every round trip, increasing cwnd by one segment per ACK received. The name is misleading: the growth is exponential and slow start is the aggressive phase. It continues until either loss occurs or cwnd crosses a threshold, ssthresh, that records where trouble was last found. Past that threshold the connection switches to congestion avoidance and grows cwnd by roughly one segment per round trip instead of doubling, which is a cautious search for the point where the path saturates.

When congestion does appear, the response is multiplicative: cwnd is cut by a constant factor, classically half. This pairing of additive increase with multiplicative decrease is not arbitrary. Chiu and Jain showed that among linear control laws, AIMD is the one that drives competing flows toward an equal share of the bottleneck while remaining stable, because the increase moves flows along a line of constant difference and the decrease moves them toward the origin, shrinking the gap between a large flow and a small one on every cycle. The visible consequence is the sawtooth: throughput climbs slowly, drops sharply, and climbs again, oscillating around the path's capacity.

How congestion gets detected matters as much as the response. A retransmission timeout means the sender has heard nothing at all, so it treats the path as unknown and restarts slow start from cwnd of one. Three duplicate acknowledgements are much better news, since packets are evidently still arriving and only one appears to be missing, so TCP Reno retransmits the missing segment immediately rather than waiting for the timer (fast retransmit) and halves cwnd while continuing to send (fast recovery), avoiding the collapse to one segment. Modern stacks refine this with selective acknowledgements, which let the receiver report exactly which blocks arrived so the sender retransmits only the true holes, and with RACK, which infers loss from time ordering rather than from counting duplicate ACKs.

Reno's linear growth ages badly on fast, long paths, where recovering to a large window after a single loss can take minutes, so the algorithms in common use today change either the growth curve or the signal itself:

- **CUBIC**, the Linux default, grows cwnd as a cubic function of the time since the last reduction. It rises fast, flattens near the window where loss last happened, and accelerates again if that region turns out to be safe. Because the curve depends on elapsed time rather than on ACK arrivals, flows with different round trip times compete more evenly than under Reno.
- **ECN**, with **DCTCP** as the canonical user, replaces loss with an explicit mark. Routers set a bit in the header when their queue is building, so the sender learns about congestion before any packet is dropped, and DCTCP scales its reduction to the fraction of marked packets rather than always halving.
- **BBR** abandons loss as the signal altogether. It continuously estimates the bottleneck bandwidth and the minimum round trip time, then paces at that bandwidth-delay product, probing periodically for more.

BBR's departure is a response to a real defect in the loss-based design. A loss-based sender only learns it has gone too far when a queue somewhere overflows, which means it deliberately keeps buffers full, and on paths with large router buffers that translates into hundreds of milliseconds of standing queueing delay for every flow sharing the link. This is bufferbloat, and it is why a large upload can make an interactive session on the same connection unusable even though nothing is technically going wrong. Modelling the path instead of filling it is what lets BBR hold throughput near capacity without the queue, though it competes with CUBIC in ways that remain contested and drove much of the redesign in BBRv2 and v3.

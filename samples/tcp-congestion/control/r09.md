TCP congestion control is a feedback loop that solves a problem the sender has no direct way to observe: how much data the network between it and the receiver can carry right now. Nobody tells the sender the answer. Routers do not advertise their capacity, the bottleneck link may be shared with thousands of other flows, and the available rate changes from one second to the next. So the sender guesses, sends at that guess, watches what comes back, and adjusts. The whole design follows from the fact that the only feedback is the stream of acknowledgements, and that feedback arrives one round-trip time late.

The state variable is the congestion window, cwnd, which caps how many bytes the sender may have in flight and unacknowledged. It sits alongside the receiver's advertised window, and the sender is limited by whichever is smaller: the receive window protects the receiver's buffer, while cwnd protects the network. Dividing cwnd by the round-trip time gives an approximate sending rate, so growing and shrinking the window is how the sender speeds up and slows down.

The classic algorithm moves through four behaviours:

- **Slow start.** cwnd begins small (ten segments in current practice) and doubles every RTT, because each acknowledged segment releases two new ones. Despite the name this is the aggressive phase: it finds the rough capacity of a path exponentially fast.
- **Congestion avoidance.** Once cwnd passes a threshold called ssthresh, growth flattens to roughly one segment per RTT. The sender is now near what it believes the path can hold and probes upward gently.
- **Fast retransmit and fast recovery.** Three duplicate acknowledgements suggest one segment was lost while later ones arrived, so the network is congested but still delivering. The sender resends the missing segment immediately and halves cwnd rather than collapsing it.
- **Timeout.** No acknowledgement at all means something much worse, possibly a path that has gone away. cwnd drops to one segment and slow start begins again.

The combination of adding a constant when things go well and multiplying by a fraction when they do not is additive increase, multiplicative decrease, and it is not an arbitrary choice. Chiu and Jain showed that among simple linear control rules, AIMD is what drives competing flows toward an equal share: a flow sending twice as much as its neighbour loses twice as much absolute throughput on each cut, so the gap narrows on every cycle while a purely additive decrease would preserve it forever.

Loss as the congestion signal has a serious cost, and it is the reason modern algorithms diverge. A loss-based sender only backs off once a queue somewhere has filled completely and started dropping. Cheap memory has made router buffers enormous, so those queues can hold seconds of data before they overflow, which means a bulk transfer running flat out inflates latency for every other flow sharing the link. This is bufferbloat, and it is why a large upload can make a video call unusable on the same connection.

CUBIC, the Linux default, is still loss-based but changes the growth curve. Instead of counting round trips it grows cwnd as a cubic function of the time since the last reduction, rising fast at first, flattening as it approaches the window size that previously caused loss, then accelerating past it to search for new capacity. Because the curve is a function of wall-clock time rather than RTTs, flows on long paths are not penalised against short ones the way Reno penalises them.

BBR takes a different route entirely, estimating the bottleneck bandwidth and the minimum round-trip time directly, then pacing packets to match that bandwidth-delay product. It aims to sit at the point where the pipe is full but the queue is not, so it can back off before loss occurs at all. Explicit Congestion Notification and its successor L4S attack the same problem from the network side, letting routers mark packets as a congestion signal instead of dropping them, which gets the sender the information without destroying data to deliver it.

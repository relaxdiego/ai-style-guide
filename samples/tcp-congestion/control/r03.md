TCP congestion control is a feedback loop run by each sender independently, trying to infer the state of a network it cannot observe directly. The only information coming back is the stream of acknowledgements, so the whole design question is how to turn that stream into an estimate of how fast to send.

The mechanism is a congestion window, `cwnd`, which caps the number of unacknowledged bytes the sender may have in flight. The actual limit is `min(cwnd, rwnd)`, where `rwnd` is the receiver's advertised window and protects the receiver's buffer rather than the network. Because an acknowledgement takes a round trip to come back, a window translates into a rate of roughly `cwnd / RTT`. Raising the window raises the sending rate, and the sender's whole job is deciding when to raise it and when to cut it.

Classic TCP has no explicit signal from the network, so it treats packet loss as the signal. The reasoning is that a router whose queue overflows drops a packet, that packet's acknowledgement never arrives, and the sender concludes it was sending faster than the bottleneck could carry. This inference is the foundation of Reno and everything descended from it, and it is also its main weakness, since loss on a wireless link has nothing to do with congestion.

Around that signal sit four behaviours:

- **Slow start.** A new connection has no idea what the path can carry, so it starts at about ten segments and doubles `cwnd` every round trip. Despite the name this is an exponential search, and it is the fastest part of the connection's life. It ends when loss occurs or when `cwnd` reaches a threshold, `ssthresh`, remembered from a previous congestion event.
- **Congestion avoidance.** Past `ssthresh`, the sender is near the capacity it believes the path has, so it switches to additive increase: roughly one extra segment per round trip. On loss it multiplicatively decreases, historically halving. This additive-increase/multiplicative-decrease rule is not arbitrary; Chiu and Jain showed that among the simple linear control rules, AIMD is the one that converges to both efficiency and fairness between competing flows, while multiplicative increase does not.
- **Fast retransmit.** Waiting for a retransmission timeout wastes an enormous amount of time, so three duplicate acknowledgements are taken as evidence that one segment was lost while later ones arrived, and the sender resends immediately.
- **Fast recovery.** Those duplicate acknowledgements also prove the pipe is still delivering data, so the sender halves the window and continues from there rather than collapsing to one segment. A genuine timeout, which means nothing is getting through, does reset to slow start.

The result is the familiar sawtooth: the window climbs slowly, loss cuts it, it climbs again, and the flow oscillates around the bottleneck capacity while sharing it roughly evenly with other flows doing the same thing.

That design ran into trouble as links got faster. Sustaining 10 Gbps across a 100 ms path with 1500-byte packets needs a window of about 83,000 packets, and with additive increase, recovering from a single loss takes tens of minutes. Reno cannot fill a modern long-distance link. CUBIC, the Linux default since 2006, replaces the linear increase with a cubic function of the time elapsed since the last reduction. The window rises quickly toward the level where loss last happened, flattens out around it to probe cautiously, and accelerates again if no loss appears. Because the curve is a function of wall-clock time rather than of acknowledgement arrivals, flows with short round trips no longer grab bandwidth from flows with long ones.

BBR takes a different route entirely: instead of reacting to loss, it builds a model of the path, continuously estimating the bottleneck bandwidth and the minimum round-trip time, and paces packets at the estimated bandwidth rather than releasing them in bursts when acknowledgements arrive. This matters because of bufferbloat. A loss-based algorithm only backs off once a queue has overflowed, so on a path with a large router buffer it will fill that buffer and keep it full, adding hundreds of milliseconds of delay to every flow sharing the link while achieving no extra throughput.

| | Congestion signal | Window growth | On a deep buffer |
|---|---|---|---|
| Reno | Loss | Linear, per-RTT | Fills it, high latency |
| CUBIC | Loss | Cubic in elapsed time | Fills it, high latency |
| BBR | Bandwidth and RTT estimates | Paced to estimated bandwidth | Keeps the queue near empty |

The other direction of improvement is to stop guessing. Explicit Congestion Notification lets a router mark a packet rather than drop it, and the receiver echoes the mark back so the sender can slow down before anything is lost; L4S extends this into a much finer-grained signal for very low latency. Both need support in the routers along the path, which is why loss remains the fallback signal everywhere.

Worth keeping in mind is that all of this is voluntary. Nothing in the network forces a sender to obey these rules, and TCP's stability at scale rests on the fact that essentially every implementation chooses to.

TCP congestion control is a feedback loop that keeps a sender from putting more data into the network than the bottleneck link can drain. The sender maintains a congestion window (`cwnd`), a byte count of unacknowledged data it is willing to have in flight, and transmits at most `min(cwnd, rwnd)` where `rwnd` is the receiver's advertised flow-control window. Nothing in the network tells the sender the bottleneck rate; the sender infers it from ACK arrivals, loss, and delay, and adjusts `cwnd` continuously. Because ACKs return at roughly the rate the bottleneck forwards data, the ACK stream itself clocks transmission — this is why TCP tends to settle into sending at the bottleneck rate even before any explicit control kicks in.

The classic algorithm (Reno/NewReno, RFC 5681) has four states:

- **Slow start.** `cwnd` begins at the initial window, 10 MSS on modern stacks (RFC 6928), and increases by 1 MSS per ACK, so it doubles every RTT. Exponential, despite the name; "slow" is relative to the original behavior of blasting a full receiver window immediately. Runs until `cwnd` exceeds `ssthresh` or loss occurs.
- **Congestion avoidance.** `cwnd` grows by roughly 1 MSS per RTT (implemented as `cwnd += MSS²/cwnd` per ACK). Linear probing for more bandwidth.
- **Fast retransmit / fast recovery.** Three duplicate ACKs signal a lost segment without waiting for a timer. The sender retransmits immediately, sets `ssthresh = cwnd/2`, sets `cwnd` to that value, and continues sending on subsequent duplicate ACKs to keep the ACK clock alive.
- **Retransmission timeout.** No ACK before the RTO expires means the pipe may be entirely drained. `cwnd` collapses to 1 MSS and slow start restarts. This is the expensive failure and RTO backoff doubles on repeats.

The multiplicative decrease on loss and additive increase otherwise (AIMD) is what makes independent flows converge on a fair share: a flow sending more loses more in absolute terms at each cut, so shares equalize over time. The cost is a sawtooth utilization pattern and a throughput ceiling of roughly `MSS / (RTT · √p)` for loss rate `p`, which is why Reno performs badly on long fat networks — a 100 ms, 10 Gbps path needs a loss rate below 10⁻¹⁰ to stay full.

| Algorithm | Signal | Growth | Where it's used |
|---|---|---|---|
| Reno / NewReno | Loss | Linear, halve on loss | Reference behavior, legacy |
| CUBIC | Loss | Cubic in time since last loss, ×0.7 on loss | Linux and Windows default |
| BBR (v1–v3) | Bandwidth + RTT estimate | Paces at measured bottleneck rate | Google services, QUIC deployments |
| Vegas | Queueing delay | Backs off before loss | Rare; loses to loss-based flows sharing a link |
| DCTCP | ECN mark fraction | Proportional to marking rate | Datacenters with ECN-capable switches |

CUBIC decouples growth from RTT: the window is a cubic function of elapsed time since the last congestion event, flattening near the previous maximum `W_max` and accelerating past it if no loss appears. That makes it aggressive enough for high bandwidth-delay-product paths and fairer between flows with different RTTs than Reno, which favors short-RTT flows because they get feedback sooner. BBR takes a different approach entirely: it estimates the bottleneck bandwidth and minimum RTT from delivery-rate samples, then paces at that bandwidth with a small window, periodically probing higher. It does not interpret loss as congestion, which makes it strong on lossy wireless paths and on deep-buffered links where loss-based algorithms fill buffers before they react — the bufferbloat problem, where a full 500 ms buffer adds latency without adding throughput.

Two supporting mechanisms matter in practice. Selective acknowledgment (SACK) lets the receiver report exactly which segments arrived, so a sender losing several segments in one window recovers in one RTT instead of one per loss; RACK-TLP has largely replaced duplicate-ACK counting for loss detection, using time rather than packet ordering. Explicit Congestion Notification lets routers mark packets instead of dropping them, and the L4S work (RFC 9330) builds on that to give low-latency flows a separate queue with aggressive marking, so congestion feedback arrives without either loss or a full buffer.

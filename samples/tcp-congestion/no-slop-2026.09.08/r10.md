TCP congestion control is a feedback loop: the sender keeps a congestion window (`cwnd`) limiting how many bytes may be in flight unacknowledged, grows it while ACKs keep arriving, and cuts it when the network signals overload. Sending rate is roughly `cwnd / RTT`, so controlling the window controls the rate. The actual limit is `min(cwnd, rwnd)`, where `rwnd` is the receiver's advertised flow-control window; congestion control protects the network, flow control protects the receiver.

## The classic state machine (Reno/NewReno)

- **Slow start.** Start at ~10 MSS (RFC 6928; older stacks used 2 to 4). Increase `cwnd` by 1 MSS per ACK, which doubles it every RTT. Exponential probing to find the rough capacity fast. Exits when `cwnd >= ssthresh` or on loss.
- **Congestion avoidance.** Increase `cwnd` by about 1 MSS per RTT (additive increase). Linear probing near the estimated capacity.
- **Fast retransmit / fast recovery.** Three duplicate ACKs mean a packet was lost but later ones arrived, so the path still works. Retransmit immediately, set `ssthresh = cwnd/2`, drop `cwnd` to that, and keep going. Multiplicative decrease.
- **Retransmission timeout.** No ACK at all within the RTO (computed from smoothed RTT and its variance, RFC 6298; Linux floors it at 200 ms). Assume the path is badly broken: `ssthresh = cwnd/2`, `cwnd = 1 MSS`, back to slow start, and double the RTO on repeats.

That additive-increase/multiplicative-decrease rule is what makes competing flows converge toward a fair share: every flow ramps up at the same absolute rate and cuts proportionally, so the big flow loses more than the small one on each loss event.

## What counts as a congestion signal

| Signal | Used by | Meaning |
|---|---|---|
| Packet loss (dup ACKs, SACK) | Reno, CUBIC | Queue overflowed. Late signal: the buffer already filled. |
| Timeout | all | Severe loss or path failure. |
| ECN marks | DCTCP, BBRv2+, ECN-enabled Reno/CUBIC | Router marked the header instead of dropping. Same information, no retransmit. |
| Rising RTT | Vegas, BBR's RTT probe | Queue is building before it overflows. |
| Measured delivery rate | BBR | Bottleneck bandwidth estimated directly from ACK arrival timing. |

## Algorithms you actually meet

- **CUBIC** (Linux default since 2.6.19, also Windows since 10). Window grows as a cubic function of time since the last loss: fast recovery back toward the previous maximum, then a flat plateau around it, then aggressive probing above it. On loss it multiplies by 0.7 rather than 0.5. The growth curve depends on elapsed time, not RTT count, so short-RTT and long-RTT flows compete more evenly than under Reno.
- **BBR** (Google, deployed widely on YouTube/GCP). Ignores loss as the primary signal. It continuously estimates bottleneck bandwidth and minimum round-trip propagation time, sets the sending rate by pacing packets at the estimated bandwidth, and caps in-flight data at about 2× the bandwidth-delay product. It periodically raises the rate 25% to probe for more capacity and drains back. Good on paths with random loss (wireless, long-haul), and it avoids filling large buffers. BBRv1 could starve CUBIC flows in some topologies; v2 and v3 add loss and ECN response to fix that.
- **Vegas.** Compares expected throughput (`cwnd / baseRTT`) to actual, backs off when the difference implies queued packets. Fair and low-latency in isolation, gets crushed when sharing a link with loss-based flows, which keep pushing until the buffer overflows.
- **DCTCP.** Datacenter only. Uses the *fraction* of ECN-marked ACKs to scale the reduction proportionally instead of halving. Keeps queues tiny. Requires switches configured with a shallow marking threshold, so it does not work over the public internet.

## Two things that complicate the picture

Bufferbloat: loss-based algorithms only stop growing when a queue overflows, so an oversized router buffer means they fill it and add hundreds of milliseconds of latency before backing off. The fix lives in the router, not the sender: active queue management such as CoDel or FQ-CoDel drops or marks early to keep the queue short.

Loss is not always congestion. On wireless or satellite links, corruption-induced loss makes Reno and CUBIC cut their window for no reason, which is a large part of why BBR and delay-based approaches exist. Modern Linux also uses PRR (RFC 6937) rather than an abrupt halving, spreading the reduction across the recovery round trip so the sender does not stall.

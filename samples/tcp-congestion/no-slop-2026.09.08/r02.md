TCP congestion control is a feedback loop: the sender guesses how much unacknowledged data the network can hold, sends that much, and adjusts the guess based on whether packets get through. The state variable is the congestion window (`cwnd`), and the sender is limited to `min(cwnd, rwnd)` bytes in flight, where `rwnd` is the receiver's advertised buffer. Throughput is roughly `cwnd / RTT`, so the whole game is picking `cwnd`.

Nothing in the network tells the sender the available capacity. The sender infers it from ACKs, and every algorithm below differs only in what signal it treats as "the network is full" and how it reacts.

## The classic loop (Reno / NewReno)

| Phase | Trigger | Behavior |
|---|---|---|
| Slow start | Connection start, or after timeout | `cwnd += 1 MSS` per ACK, so it doubles each RTT. Exponential probe to find the rough scale fast. |
| Congestion avoidance | `cwnd >= ssthresh` | `cwnd += 1 MSS` per RTT. Linear probing for spare capacity. |
| Fast retransmit / fast recovery | 3 duplicate ACKs | Retransmit the missing segment immediately, set `ssthresh = cwnd/2`, `cwnd = ssthresh`, stay in congestion avoidance. |
| Timeout | Retransmission timer expires | `ssthresh = cwnd/2`, `cwnd = 1 MSS`, back to slow start. Treated as severe congestion. |

`ssthresh` is the boundary between "I have no idea, probe fast" and "I'm near the last known limit, probe carefully."

The additive-increase/multiplicative-decrease pattern is why this converges to fair sharing: two flows through the same bottleneck both add linearly but cut proportionally, and repeated rounds of that drive their rates together. It also produces the sawtooth throughput graph everyone has seen. The steady-state rate for Reno is approximately `MSS / (RTT * sqrt(p))` for loss rate `p`, which has two ugly consequences: long-RTT flows lose to short-RTT flows sharing a bottleneck, and at high bandwidth-delay products the required loss rate becomes absurdly small (a 10 Gbps, 100 ms path needs roughly one loss in 10^10 packets).

## What actually runs today

- **CUBIC** (Linux default since 2.6.19, also Windows since 10): `cwnd` grows as a cubic function of time since the last loss, not per-RTT. It rises fast toward the previous loss point, flattens near it, then probes aggressively past it. Growth is independent of RTT, which fixes Reno's bias against long paths and its poor scaling on fat pipes.
- **BBR** (Google, widely deployed on their servers and QUIC): ignores loss as a congestion signal. It estimates bottleneck bandwidth and minimum RTT from delivery-rate samples, then paces sending at that bandwidth with about one BDP in flight. This avoids filling deep router buffers, which is the fix for bufferbloat (the queueing latency you get when loss-based algorithms grow until a large buffer overflows).
- **ECN**: routers mark packets instead of dropping them when queues build; the receiver echoes the mark and the sender cuts as if it saw loss. DCTCP extends this to react proportionally to the fraction of marked packets, which is why it dominates in datacenters.
- **Vegas** and other delay-based schemes back off on rising RTT rather than loss. They lose badly when competing with loss-based flows, so they stay niche.

## Details that matter in practice

- **SACK** lets the receiver report which blocks arrived, so the sender retransmits only what was actually lost instead of guessing. Without it, multiple losses in one window cause repeated stalls.
- **Pacing** spreads a window's packets across the RTT instead of dumping them as a burst. Required for BBR, and it helps CUBIC too.
- **Slow start after idle**: if a connection goes quiet, the cached `cwnd` is stale, so most stacks reset it. This is why the first request on a reused-but-idle HTTP connection can be slow.
- **Initial window** is 10 MSS in current practice (RFC 6928), up from 2 to 4. That single change is a large share of the observed improvement in short web transfers.
- Congestion control governs *rate*; flow control (`rwnd`) governs *the receiver's buffer*. They are separate limits, and a badly tuned receive buffer will cap throughput no matter how good the congestion control is.

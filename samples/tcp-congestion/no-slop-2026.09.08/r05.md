TCP congestion control is a sender-side feedback loop: the sender keeps a congestion window (`cwnd`), sends at most `min(cwnd, receiver_window)` bytes of unacknowledged data, and adjusts `cwnd` based on what the ACK stream tells it about the network. Nobody signals capacity explicitly, so the sender probes upward until it sees evidence of congestion (packet loss, rising delay, or an ECN mark), then backs off.

## The four classic phases (Reno/NewReno)

| Phase | Trigger | `cwnd` behavior |
|---|---|---|
| Slow start | Connection start, or after a timeout | Doubles each RTT (`cwnd += 1 MSS` per ACK) until `cwnd >= ssthresh` or loss |
| Congestion avoidance | `cwnd >= ssthresh` | `+1 MSS` per RTT (`cwnd += MSS²/cwnd` per ACK) |
| Fast retransmit / fast recovery | 3 duplicate ACKs | `ssthresh = cwnd/2`, `cwnd = ssthresh`, retransmit the missing segment without waiting for the timer |
| Timeout | Retransmission timer expires | `ssthresh = cwnd/2`, `cwnd = 1 MSS`, back to slow start |

"Slow start" is a misnomer: it is the fastest growth phase. It is slow only relative to the pre-1988 behavior of dumping a full receiver window instantly.

Two properties make this work. First, **ACK clocking**: each returning ACK releases new data, so the sender naturally paces itself to the bottleneck's drain rate. Second, **AIMD** (additive increase, multiplicative decrease). Chiu and Jain showed that additive increase with multiplicative decrease converges to a fair, efficient allocation among flows sharing a bottleneck, while additive-decrease or multiplicative-increase variants do not.

## What "congestion" means to the sender

- **Loss** (Reno, CUBIC): a router queue overflowed. Simple, but it only detects congestion after buffers are already full, which is why deep buffers cause bufferbloat: hundreds of milliseconds of standing queue with zero loss.
- **Delay** (Vegas, BBR's RTT probe): RTT rising above the minimum observed means a queue is building. Detects congestion earlier, but delay-based flows get starved when competing with loss-based flows that happily fill the buffer.
- **ECN marks**: routers set a bit in the IP header instead of dropping. DCTCP uses the *fraction* of marked packets to scale the decrease proportionally, rather than always halving.

## Algorithms in use today

- **CUBIC** (Linux default since 2.6.19, also Windows since 10): `cwnd` follows a cubic function of time since the last reduction. It shoots back near the pre-loss window quickly, then flattens ("concave" region), then probes aggressively upward ("convex" region). Because growth depends on elapsed time rather than ACK arrivals, it is roughly RTT-fair and scales to high bandwidth-delay products where Reno's one-segment-per-RTT is hopeless.
- **BBR** (Google, used for YouTube and QUIC): ignores loss as a signal. It estimates bottleneck bandwidth (max delivery rate) and minimum RTT separately, then paces at the bandwidth estimate with `cwnd` capped at roughly 2×BDP. Cycles through gain phases to re-probe. Keeps queues short, but BBRv1 was notoriously unfair to CUBIC in shallow buffers; v2/v3 add ECN and loss response.
- **DCTCP**: data-center only, requires ECN-marking switches, targets very low queue occupancy.
- **Reno/NewReno**: mostly a baseline for comparison now, still the fallback in constrained stacks.

## Details that matter in practice

- Modern senders **pace** packets rather than relying on ACK clocking alone, because offloads (TSO/GSO) and ACK aggregation on wireless links produce bursts that overflow shallow buffers.
- **SACK** lets the sender learn exactly which segments arrived, so it can recover from multiple losses per RTT instead of one (NewReno's weakness).
- **HyStart/HyStart++** exits slow start on RTT-increase heuristics instead of waiting for loss, avoiding the huge overshoot at the end of exponential growth.
- Congestion control and flow control are separate limits. `rwnd` protects the receiver's buffer; `cwnd` protects the network. The sender obeys whichever is smaller.
- **Congestion control is not in the packet format.** It is entirely a sender-side algorithm, which is why it can be swapped per-socket (`setsockopt(TCP_CONGESTION)`) and why QUIC could adopt the same algorithms in userspace.

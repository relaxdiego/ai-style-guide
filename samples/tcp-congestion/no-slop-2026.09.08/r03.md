TCP congestion control is a sender-side feedback loop that guesses how much unacknowledged data the network path can hold, then adjusts that guess based on whether packets get through.

**The core state**

The sender keeps a congestion window (`cwnd`) in bytes. Data in flight is capped at `min(cwnd, rwnd)`, where `rwnd` is the receiver's advertised buffer space. Flow control (`rwnd`) protects the receiver; congestion control (`cwnd`) protects the network. Nothing is negotiated: the receiver never learns the sender's `cwnd`, and two endpoints can run entirely different algorithms.

**The classic phases (Reno, the reference model)**

| Phase | Trigger | Behavior |
|---|---|---|
| Slow start | Connection start, or after RTO | `cwnd` starts at 10 MSS (RFC 6928), grows +1 MSS per ACK, so it doubles each RTT |
| Congestion avoidance | `cwnd ≥ ssthresh` | `cwnd += MSS²/cwnd` per ACK, roughly +1 MSS per RTT (linear) |
| Fast retransmit / fast recovery | 3 duplicate ACKs | Retransmit the gap immediately, set `ssthresh = cwnd/2`, `cwnd = ssthresh`, stay in avoidance |
| Timeout (RTO) | No ACK before the retransmit timer fires | `ssthresh = cwnd/2`, `cwnd = 1 MSS`, back to slow start |

The pattern is additive increase, multiplicative decrease. Probe upward slowly, back off hard on the congestion signal. Chiu and Jain showed AIMD converges to a fair share among flows sharing a bottleneck; other combinations (like additive decrease) do not. The sawtooth you see in throughput graphs is this loop running.

**What counts as a congestion signal**

Reno infers congestion from packet loss, on the assumption that routers drop when queues overflow. That assumption is the source of most of the field's later work:

- **Loss-based** (Reno, NewReno, CUBIC): fills the bottleneck queue until it overflows, so it induces the very delay it should avoid. This is bufferbloat, and it gets worse as router buffers get cheaper and larger. CUBIC, the Linux and Windows default, replaces the linear increase with a cubic function of time since the last reduction, reaching high rates faster on long-fat paths and making growth independent of RTT (Reno favors short-RTT flows, since they get feedback sooner).
- **ECN**: routers mark packets instead of dropping them; the receiver echoes the mark. Same backoff, no packet lost. DCTCP takes this further in data centers by reacting proportionally to the fraction of marked packets rather than halving on any mark.
- **Delay-based** (Vegas, and partly BBR): rising RTT means a growing queue, which precedes loss. Vegas backs off before drops but loses to loss-based flows sharing a link, because those keep pushing until the buffer overflows.
- **Model-based** (BBR): estimates bottleneck bandwidth and minimum RTT separately, sets the send rate to their product, and paces packets out at that rate instead of releasing them in ACK-triggered bursts. It largely ignores loss, which is the right call on wireless and other lossy paths where drops are not congestion.

**Two mechanisms that matter in practice**

SACK lets the receiver report exactly which segments arrived, so a sender losing several packets in one window recovers them in one round trip instead of one per RTT. Pacing spreads a window's worth of packets across the RTT; without it, a sender that has been idle or is recovering dumps a burst that overflows a shallow buffer regardless of what `cwnd` says.

Active queue management on the router side (CoDel, FQ-CoDel, PIE) is the other half of the system. It drops or marks early, based on how long packets sit in the queue, rather than only when the buffer is full. Endpoint algorithms cannot fix bufferbloat alone, because a loss-based sender has no reason to stop before the buffer fills.

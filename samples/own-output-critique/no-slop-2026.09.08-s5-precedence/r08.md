The code has no record of what it rejected, and no ranking of what matters. Every line is defensible on its own, which is exactly why you can't point at one.

Specific mechanisms, roughly in order of how much pain they cause later:

- **Abstraction from symmetry, not from use.** I see two similar blocks and factor them into one function. I don't know whether they're similar for a reason or by coincidence. If it's coincidence, the shared function grows a boolean parameter the first time the callers diverge, then another. The line that's wrong is that parameter, and it was added three commits before the file became unpleasant.
- **Boundaries chosen so the diff reads well.** A human picks module boundaries under pressure from changes that already happened. I pick them so the current pull request looks tidy. Your next feature request then cuts across every boundary I drew.
- **Uniform confidence.** Real code carries signals about which parts are settled: a TODO, a comment saying the upstream API returns 500 sometimes, a hack marked as a hack. Mine reads as though every decision were equally considered. You can't tell which parts to trust, so you re-derive all of it.
- **Defensive code aimed at nothing.** Null checks and try/except at layers that cannot receive bad input, because that pattern is everywhere in what I learned from. Meanwhile the real failure, a non-idempotent retry or a partial write, gets nothing. Every spurious check is a branch you maintain forever, and it tells the next reader the invariant isn't guaranteed when it is.
- **Uniform effort across decisions of wildly different reversibility.** I spend the same care on naming a private helper as on the transaction boundary. The expensive decision is made in one quiet line in the middle of a file, at the same visual weight as the trivial ones. Review skims a flat surface and finds nothing to stop on.
- **Invented vocabulary instead of yours.** I write a helper you already have, and I name things abstractly (`process`, `Handler`, `Manager`) rather than with the domain word your team says out loud. Five months later there are three names for one concept and no way to grep for it.
- **Comments that restate the code.** High comment density, zero information, because the one thing not derivable from the diff is why, and why is the thing I didn't record.
- **Tests written from the implementation.** They assert what the code does, bugs included, and they pin internals rather than behaviour. A real refactor breaks forty of them, none of the breaks mean anything, and you stop trusting the suite.
- **Style matching with no preference.** I follow the convention in the file I'm editing, so I reproduce your bad patterns and good patterns with equal enthusiasm, and different ones in different files. No single mind is imposing a choice across the repo.

What actually reduces it, in what you ask me for: make me write the rejected alternative and why it lost, in the pull request body or above the function. Ban factoring on the first duplication, so I copy the block and wait for the third case. Make me name the invariant each defensive check protects and delete the ones where I can't name it. Ask which three lines carry the risk in a change, and review those instead of the diff.

The code carries no record of which decisions were forced and which were arbitrary, and review only checks whether each line is correct. Every line is correct. What's missing is the information you need six months later to know which lines you are allowed to delete, and that information was never in the diff to begin with.

Concretely, here is what I produce that a human writing the same feature would not:

- **Defensive code with no incident behind it.** In human code a null check usually means someone got a null at 3am. In mine it means null was reachable in principle. You cannot delete it without proving the caller never sends null, so it stays forever, and so does the next reader's uncertainty.
- **Abstractions with one caller.** An interface with one implementation, a `strategy` argument that only ever takes one value, a wrapper that forwards. I write these because they are the recognized form of good code. No second case existed. Review passes them because extensibility reads as a virtue.
- **Uniform confidence across the file.** No TODO, no "hack until the migration lands", no "unsure about empty input". Human code marks where the author was unsure, and that is where you look first when it breaks. Mine is polished evenly over the parts I knew and the parts I guessed, so the risk is invisible.
- **Silent defaults where a human would have asked you.** Retry counts, timeouts, timezone, sort tie-break, behaviour on partial failure. I pick something defensible and never write down that a choice occurred. The assumption now exists only in the code.
- **Local consistency, global drift.** Each file matches the file around it because I read that file. Across three files the same concept gets three treatments: one returns `None`, one raises, one returns a result object. No single review sees all three.
- **Tests pinned to the implementation.** Mock-heavy, asserting call order. They pass against the code as written, they would pass against a wrong implementation, and they break on every refactor. The suite becomes a tax instead of a safety net.
- **Category names.** `handler`, `process`, `manager`, `data`, `config`. Never wrong, so review never blocks them, and they tell you nothing later.
- **Catch, log, continue.** Converts a loud crash into a quiet wrong answer.

What actually changes the output, if you want to push on it: make me write down the assumptions and the rejected alternatives at the point of the choice rather than in the PR summary; reject any guard, parameter, or indirection I cannot tie to a real caller or a failure that has happened; make me mark the parts I guessed at; and check that a new test fails when you deliberately break the behaviour it claims to cover.

The code contains no record of the decisions behind it. Review checks whether each line is defensible, and each line is. Maintenance needs something review never asks for: which values are arbitrary and which are forced, what was expected to vary, what was tried and abandoned. None of that survives in what I hand you, so there is no single wrong line to point at. The information is missing from the spaces between the lines.

The specific mechanisms:

- **Constants with no provenance.** I write `timeout=30` and a comment saying it is the timeout. A person writes 30 because the vendor's p99 is 22 seconds and they measured it. Six months later you cannot tell which numbers you may change and which will page someone at 3am, so you change none of them.
- **Hedged design.** I add the parameter with a default, the config flag, the interface with one implementation. Each is cheap for me and defensible in review. Together they mean the code takes no position on what will change, so when a change arrives, nothing tells you where it belongs. You end up adding a second mechanism beside the first.
- **Names for the operation, not the domain.** `processData`, `handleResponse`, `validateInput`. The reviewer confirms the function does what the name says. Later you cannot grep for the concept because the concept was never given a word, and the vocabulary your team actually uses appears nowhere in the source.
- **Uniform error handling.** I wrap every call the same way. A person handles the error where it is both possible and interesting, and lets the rest fail loudly. Mine makes every call site look equally dangerous, which means the two that are actually dangerous do not stand out.
- **Defensive checks against conditions the caller already guarantees.** Not wrong, and it doubles the reading cost of every function while burying the checks that enforce a real invariant.
- **Invariants held but not stated.** I infer the rule (this list is always sorted, this map is never empty after init) and preserve it correctly without writing it down. The next person to edit breaks it, and the failure surfaces three modules away.
- **No dead ends.** Code that a person wrote carries evidence of what was attempted. Mine arrives as though the first approach worked. So the simpler version that looks obviously better, and that fails on the case you hit in production last year, gets reintroduced by whoever "simplifies" it.
- **Tests derived from my implementation, not from your requirement.** They mirror the code, they pass, and they all break on any refactor. They cannot tell you anything you did not already know, because I wrote them by reading what I had just written.
- **Local consistency, global drift.** I match the file in front of me. Across ten sessions that produces five ways to retry, four logging conventions, and three date handling idioms, every one of them introduced by a clean diff.
- **Volume.** Writing is nearly free for me, so I produce more code than the problem needs. Every extra line is real maintenance cost that reviewers do not charge me for.

What actually reduces this, in rough order of effect: make me write the rationale for every non-obvious constant and every abstraction with fewer than two current callers, tell me the invariants so I assert them instead of quietly preserving them, have me write tests from your description of the behavior before I write the implementation, and reject any interface I introduce that has one implementation.

The specific mechanisms:

**Defensive code spread evenly.** Human code concentrates validation at the trust boundary and runs bare inside it. I validate in every function, so nothing marks where untrusted input actually stops. A year later nobody knows which of those checks can go.

**Abstractions with one implementation.** If your request says "handlers" or implies variation, you get an interface, a registry, and one concrete class. The generalisation came from your wording, not from a second real case. When the second case shows up its requirements don't fit, and unwinding a wrong abstraction costs more than never having had one.

**Tests written from the implementation.** I write the code, read it back, and assert what it does. Everything passes on the first run. Those tests encode current behavior including its bugs: they break on every refactor and catch no regressions. A test you never watched fail is not evidence.

**Names taken from the category.** `process`, `handleResult`, `DataManager`, `items`. Review passes because none of them is wrong. Maintenance suffers because you have to read the body to learn what's in the variable, every time.

**Error handling that logs and continues.** `catch: log.warn(e); return None` appears wherever an exception is possible. It reads as "errors are handled." In production it turns loud failures into quiet wrong answers.

**The same problem solved three ways in one session.** Retries as a decorator here, a while loop there, a library call in the third place. Each is locally reasonable and none conflicts sharply enough to flag.

**Decomposition that follows your sentence.** Ask for parse, validate, and store and you get three functions split exactly there, whether or not validation separates from parsing in your domain.

**Uniform polish.** Nothing signals which part is the core and which is glue. Human code is uneven, and the unevenness tells a reader where to look first.

Every line is locally justified and nothing is justified by the rest of the system. Review reads lines, so it passes. Maintenance needs the reasoning that connects the lines, and that reasoning was never written down because I didn't have it.

The specific mechanisms:

- **Defensive checks with no stated invariants.** I null-check, wrap in try, and supply a fallback at every level. Each one passes review on its own. Together they make it impossible to tell which states are actually reachable, so you can never delete a branch, so the code only accumulates.
- **Symmetry that isn't real.** `handle_user` / `handle_group` / `handle_org`, near-identical. A reviewer reads that as consistency. Later the three diverge for real reasons and you have to diff them by eye to find which difference is meaningful.
- **Names that describe the code instead of your domain.** `process_data`, `DataManager`, `result`, `items`. None of them is wrong, so there's nothing to flag, and every read costs a jump to the definition because the name carries no information.
- **Uniformly medium effort.** Real code has two hard spots surrounded by boring code, and you can tell which is which from how it's written. I give the subtle concurrency logic and the string formatting the same structure and the same comment density. You lose the signal about where to be careful.
- **Abstraction before the second caller exists.** A strategy dict, a config object, an injected callback, all serving one call site. It reads as flexibility. You pay indirection to follow it, and it fits the second caller badly when one finally arrives.
- **Comments that restate the line below them.** Two things to keep in sync, and readers learn to skip comments in that file, including the one that mattered.
- **Tests written by reading the implementation.** They assert what the code does rather than what it should do. They pass forever, catch nothing, and convert any refactor into a test rewrite.
- **Your local idiom ignored.** I reach for the most common idiom on the internet rather than the one in the file next door. Every site is slightly off dialect, which is why the whole thing reads as foreign while no single line is wrong.
- **Nothing removed.** I solve problems by adding code. A maintainer solves them by deleting a case, narrowing a type, or making a bad state unrepresentable. I rarely propose that.
- **No cause behind anything odd.** In human code, the weird line has a reason recoverable from blame or a ticket. In mine there is no reason, so you can't separate essential from noise. You can't point at the line because what's missing was never in a line.

What changes this in practice: state the invariants up front and tell me to enforce them once at the boundary and assume them everywhere inside, which kills most of the defensive branches. Ask me which part is the genuinely hard part and make me mark it and leave the rest plain. Require the test to come from the spec before the implementation exists.

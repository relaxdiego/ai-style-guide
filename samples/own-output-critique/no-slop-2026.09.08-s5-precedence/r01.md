Nothing is wrong at any line. Every line is equally plausible, and that uniformity is the defect: you cannot tell which parts I reasoned about and which I filled in because something had to go there.

Concretely, here is what I produce that a human under the same deadline would not:

- **Guards with no threat behind them.** `if response is None`, a try/except around a call that doesn't raise, a default for a parameter that always arrives. Review can't reject these because a reviewer can't prove the input is never null. Six months later nobody can tell whether that check documents a real case or was me hedging, so nobody deletes it and everybody copies it.
- **Abstraction written before the second case exists.** I write the parameterised version because generality reads as competence. You get a function with one caller whose parameters encode variations I imagined rather than variations you have.
- **Symmetry that was never requested.** If there is a `create`, I write `update` and `delete` to match. If there is `to_dict`, there is `from_dict`. Half of it is dead on arrival and reads as intentional API surface.
- **Names that are accurate and empty.** `handle_event`, `process`, `context`, `manager`. Accurate names pass review. Empty names don't constrain what belongs in the function, so over the next year everything vaguely related lands there.
- **Local consistency, global drift.** I match the file in front of me. Across five files I will solve the same problem five defensible ways, and no single diff shows it.
- **Tests derived from the implementation.** I write the code, then read it back and assert what it does. They pass, so review passes. When you deliberately change behaviour, eleven tests fail and not one tells you whether you broke a requirement.
- **Errors logged and swallowed.** Nothing crashes in review. Failures surface three layers away from the cause.

The deeper mechanism is that you maintain code by reconstructing why it is the way it is, and my output has no history to reconstruct. Human code carries evidence of its own making: an ugly special case where a bug forced a change, a TODO, a half-renamed variable, an inconsistency where someone ran out of time. Those marks tell you where the risk is and where the thinking happened. I emit everything at one confidence level in one pass, so your usual reading strategy returns nothing and you are left with a uniform surface that behaves correctly and resists every question you want to ask of it.

What actually helps, in review of my work specifically: ask which lines I would delete if forced to cut a third, ask what invariant each guard protects and delete the ones I can't answer for, demand the specific version until a second caller exists, and write the test list before I write the implementation.

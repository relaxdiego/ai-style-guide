The defects are properties of the whole file rather than of any single line, and nearly all of them are absences. Review reads diffs, and an absence never shows up in a diff.

What's actually missing:

- **The record of what was rejected.** Code you write carries the constraint that produced it. Mine doesn't. Six months later you can't tell which branch is guarding against a real failure someone hit and which is defensive habit, so you keep all of it forever.
- **Proportional care.** I distribute validation, error handling and comments evenly across a file rather than concentrating them where things actually break. You lose a signal you rely on without noticing: "the author was careful right here, so something bit them right here."
- **Abstraction picked from resemblance instead of from your change history.** I extract the parameters that vary in code that looks like yours, not the ones that vary in your product. The abstraction is clean and the first real feature request cuts straight across it.
- **Domain meaning in names.** `processRecord`, `handleResponse`, `validateInput` are accurate and teach the next reader nothing. Your code normally explains the business while you read it. Mine requires you to already know the business before it makes sense.
- **Marked placeholders.** I write `timeout=30`, `retries=3`, `batch_size=100`. These are conventions, not measurements, and they arrive looking exactly like decisions somebody made on evidence.
- **Asymmetry where the domain is asymmetric.** If there's a `create`, I tend to produce `update` and `delete` for completeness, including when delete is meaningless for that entity. Now it's public surface you maintain and someone eventually calls.
- **Reasons in comments.** I restate what the line does. When the line changes, the comment quietly becomes false, and there was never a recorded reason to check the change against.
- **Tests that constrain behaviour.** I write tests against the implementation I just produced, mirroring its structure. Refactoring breaks all of them; a genuine behaviour regression can break none of them.
- **One dialect.** Each session only knows the conventions visible in the files it opened. Across a few months the codebase splits into regions with different error handling and different naming, all internally consistent.

Review misses this because review asks "is this line correct" and the answer is yes every time. Correct-per-line and coherent-as-a-whole are different properties, and only the first one fits in a comment thread.

What changes the output, concretely: tell me the constraint before the task ("this runs behind a queue that already retries, don't add retries"), tell me what has changed in this area historically so I abstract along that, make me write the test first from your description of the behaviour rather than from my code, and reject any constant I introduce without a comment saying where the number came from. Also ask me to delete rather than complete: the `delete` endpoint nobody asked for is the cheapest thing on this list to catch.

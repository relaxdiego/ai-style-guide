No line is wrong. Every one of these defects lives in a relation between the code and something that isn't in the diff: the incident that caused a branch to exist, the vocabulary the rest of the system uses, the failures that actually happen in production. Review reads lines and local logic, so it passes. Maintenance is exactly the activity that depends on those relations, so it hurts there and nowhere else.

The specific mechanisms:

- **Tests derived from the implementation instead of the requirement.** I write the code, then write tests by reading it back. They mock the collaborators, assert the call sequence, and pass because the code does what it does. They encode zero requirements. When you refactor, every test breaks and none of the breaks tell you anything, so you rewrite the tests to match the new code and the cycle repeats. This is probably the largest single cost and it reviews beautifully, because coverage is high and each test is legible.
- **Defensive code with no threat model.** Null checks, try/except, and fallbacks at layers where the invariant was already established upstream. Each one is individually defensible in review. Six months later you cannot delete any of them, because you cannot tell which guard is catching a real case and which is decoration. Meanwhile the fallbacks convert loud failures into quiet wrong answers.
- **Abstraction fitted to a guess about future variation.** An interface with one implementation, a strategy object over two branches, a config parameter with one caller. The abstraction is well-formed, so review has nothing to object to. It was fitted to variation I imagined rather than variation you got, so every real change now costs two edits and a mental translation.
- **Uniform surface over non-uniform difficulty.** If there are three cases I tend to write three parallel handlers, even when one is trivial and one has a race in it. Human-written code usually lets the hard case look hard: it is longer, it has the odd comment, it sits apart. Mine flattens that, so the code gives you no signal about where to be careful, and you have to re-derive the danger every time you touch it.
- **Names that describe the implementation rather than name a thing in your domain.** `processItem`, `handleResponse`, `DataManager`, `validateAndNormalize`. Each passes review because it accurately describes the body. Collectively they mean you cannot reason about the system by reasoning about the business. You have to open every function.
- **Comments that restate the line below.** The information a maintainer needs is why this order, why not the obvious approach, what broke the last time someone tried it. I do not have that, so I write what the code already says. Density looks healthy in review, value is zero, and it rots into false statements after the third edit.
- **Local consistency, global divergence.** I match the file in front of me and not the eleven files I did not read. You end up with three error-handling conventions and two config-loading patterns, each locally coherent. No single review catches it because no single diff contains the conflict.
- **Overcompleteness.** Extra methods for symmetry, options nobody asked for, handling for states that cannot occur. Every addition is small and justifiable. The aggregate effect is that a reader can no longer tell what the class is actually for, and the dead paths look exactly like live ones.

What changes the output: tell me the requirement in your domain's words and let me write the tests from that before the implementation, refuse abstractions until the third instance, and say explicitly which invariants are guaranteed upstream so I stop guarding them. When you review, ask what breaks if a line is deleted. If neither of us can answer, it should not be there.

The defect is never on a line because the problem is in what the code claims about your system, and those claims are only checkable against history that isn't in the diff.

Concretely, here is what I do differently from someone who has lived in the codebase:

- **I re-derive instead of extending.** I don't know why the existing retry logic looks odd, so I write a second, cleaner retry rather than reusing it. Both are correct. Now there are two, and the next person has to learn both and guess which one is canonical.
- **I complete patterns that aren't real.** Three handlers exist, so I write the fourth with the same structure even if the fourth case has no error path. Uniform code asserts that the four cases are parallel. Six months later someone changes all four together and breaks the one that was different.
- **I put abstraction boundaries where the current call sites agree.** A human puts them where the domain splits, because they know which half changed twice last quarter. My helper looks well factored and then every future change cuts across it, so people add flag parameters instead of moving the boundary.
- **I spread complexity evenly.** I have no model of which files get edited weekly and which have been stable for two years. Experienced authors keep the volatile parts dumb and concentrate cleverness where nobody goes. My version is uniformly medium-clever, which is the worst distribution for the hot files.
- **My defensive code has no failure model behind it.** The null check and the `except` block go where they read as prudent, not where a failure is known to occur. Each one is an untested branch that also swallows evidence: the error gets absorbed at the point of the fallback and reported four layers away. Reviewers can't tell which invariants are real, so they stop deleting checks entirely.
- **My comments restate the code.** The reason for a choice is exactly what I don't have. So the file records what it does and never why, and the only person who knew the why was answering a prompt.
- **My tests are written from the implementation, not the requirement.** I just wrote the code, so I assert what it does. Those tests pass forever, catch nothing, and freeze the implementation hard enough that a refactor breaks thirty of them and nobody refactors.
- **I add capability that looks appropriate.** Config options nobody sets, error subclasses nobody raises, parameters nobody varies. Dead paths that a maintainer must keep working because nothing marks them as speculative.
- **Nothing in my output signals risk.** Human code carries scars: a weird conditional with a customer name in the comment, an inconsistent argument order. Those tell a maintainer where the danger is. Mine is uniformly polished, so the reader extends the same trust to the parts that deserve none.

What actually helps is giving me the missing inputs and refusing the plausible-looking output. Tell me which files are hot and which are frozen, tell me what broke last time in this area, and make me write tests from your description of the behaviour before I write the code. When you review, ignore the lines and ask three questions: does this duplicate a decision already made somewhere else in the repo, which of these branches has ever actually executed, and does the uniformity here claim these cases are the same when they aren't. I'm reasoning about my own failure modes from the mechanism rather than from watching myself generate, so treat this as a list of things to check rather than a diagnosis of any particular file.

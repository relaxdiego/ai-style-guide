The line isn't wrong. The file is, and review reads lines.

Here's what I actually produce that a diff-level review can't catch:

- **Redundant guards around invariants your callers already hold.** I add a null check, a try/except, a default fallback at each layer because each one is locally defensible. Six months later you can't tell which checks encode a real failure mode and which are decoration, so you can't delete any of them. The code asserts your invariant might be violated, so every reader has to re-derive whether it can be.
- **Two or three representations of the same state in one file.** Each function is written to be correct on its own, so one part holds a dict, another a list of tuples, a third a flag that duplicates what the dict already says. No line is wrong. There is no single answer to "where does this live?"
- **Names taken from the code instead of the domain.** `process_data`, `handle_result`, `validate_input`. They pass review because they match the body exactly. They mean the concept never got a name, so grep finds nothing and the next person invents a second name for it.
- **Uniformity imposed on cases that aren't uniform.** Three handlers with matching signatures, one of which does something categorically different, hidden by the symmetry. Or the reverse: three superficially similar things collapsed into one function with a boolean parameter.
- **No record of what I rejected.** Human code has odd bits that are odd for a reason, and the reason survives in a comment or a commit message. Mine reads as if there was only one way to do it. When you change it you don't know which constraint you're about to break.
- **Boundaries placed where your sentence broke, not where the problem changes.** I split modules along the clauses of your request. That partition looks arbitrary later because it was.
- **Errors turned into ordinary-looking values.** Returning `None` or `[]` on failure. Reads clean, passes tests, destroys the stack trace you needed.
- **Tests that restate the implementation.** They assert the code does what the code does. They break on refactor and catch no bugs.

What actually changes the output, in rough order of effect:

- Tell me the invariants and say "check them once, at the boundary, nowhere else."
- Ask for the smallest diff that works, not a well-rounded module. Left alone I write the version that looks complete.
- Give me the domain vocabulary and say to use those exact words for types, functions and variables.
- Ask me to write the rejected alternatives and the reason in the PR body before the code.
- Ask "what should be deleted?" after I finish. I never volunteer this.
- Say "fail loudly" if you'd rather have a crash than a silent empty result.
- Point me at the two or three files that define your conventions. Otherwise I imitate whatever I happened to read.

Nothing in it records which decisions were forced and which were invented. A human codebase carries marks of things that went wrong: an odd conditional from a 3am incident, a retry count someone raised after watching it fail, a check that looks redundant and isn't. I write in one pass from the spec as stated, so every line comes out with equal weight and equal confidence. When you come back to change it, you have no signal about what is safe to delete, and that missing signal is what you feel and can't point at.

The specific mechanisms that produce it:

- **Uniform confidence.** A timeout of 30 seconds, a page size of 100, a backoff of 3 retries. All literals, none marked as guesses. You can't tell measured from invented, so you touch none of them.
- **Local coherence, global duplication.** Each function is idiomatic alone. Across the file, the same concept has two representations because each call site got solved independently. Two date helpers, three retry loops with different backoff.
- **Abstraction on the first instance.** An interface, a strategy object, or a config struct appears when there is one implementation and one caller, because that pattern shows up in training data at the point where a third case justified it. You get indirection with nothing behind it and parameters no caller varies.
- **Symmetry that isn't real.** If there's a create, there's an update and a delete, called or not. Error branches for cases that can't occur, handled distinctly when the handling is identical.
- **Comments that restate the code.** `// increment the counter`. When code and intent later diverge, there's nothing to check the code against.
- **Plausible generic names.** `processData`, `handleResult`, `UserManager`. They read fine in review. Later you can't grep for the domain concept, and the name doesn't tell you what invariant the thing maintains.
- **Flat error handling.** Everything wrapped, everything logged at one level. No indication of which failure is routine and which means the system is broken.
- **Tests derived from the implementation.** Written from the same reading of the spec in the same pass, so they encode structure rather than behaviour. They pass with the code, change with the code, and never catch the bug.

Review doesn't catch any of this because review checks a diff for correctness and style, and all of it is either a property of the whole file, a property of what's absent, or only visible on the second change. "This abstraction is premature" also loses to "it's for extensibility" in almost every review thread.

What actually helps when you ask me for code:

- Ask me to mark the guesses. Any number I invented gets a comment saying it's unvalidated and what would validate it.
- Forbid an interface until a second implementation exists. Inline it, and say so.
- Point me at the existing code the new code should look like, and ask for consolidation into it rather than a parallel path.
- Ask for the deletion story: if requirement X went away, which lines go. If I can't answer, the structure is wrong.
- Have tests written from the spec before the implementation, or by a separate pass that doesn't see it.

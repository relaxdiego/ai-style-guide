The code records no decisions, so nothing in it can be deleted. Review checks each line against a standard, and every line passes; the cost lands on properties of the whole file and on history that was never written down, which is why there's no line to point at.

What's actually different:

- **Branches for cases nobody named.** I add a null check, a fallback, an empty-list guard for inputs your system can't produce. You can't tell which guards are real, so you keep all of them forever. Hand-written code carries the author's knowledge of what can't happen, as absence.
- **Three conventions for one job.** Each function matches its neighbors, but across a file I'll produce two error-handling styles and two ways to read config, because different parts came out of different context. Nothing is wrong locally. There's no rule to follow when you add the next function.
- **Comments that restate the code.** I write `// retry three times` over a loop that retries three times, because I don't know that the retry exists for a vendor that 502s on cold start. The reason is the only thing worth writing, and it's the thing I don't have. Six months later someone tunes the value with no idea what it was protecting.
- **Helpers extracted from things that look alike today.** Two call sites had similar bodies, so I factored them. They change for different reasons, so the next change adds a boolean parameter, then another. The abstraction was chosen from the snapshot, not from how the code moves.
- **Names for the type, not the role.** `processData`, `handleResult`, `ConfigManager`. Not rejectable in review. Nobody can grep for the concept afterward because the concept was never given a word.
- **Uniform error handling instead of correct error handling.** Every call gets the same try/log/continue. The real distinctions between retry, abort, and ignore get flattened into one, and failures get swallowed at sites where they should stop the process.
- **Tests written from my implementation.** They mirror what the code does, so they pass and stay passing when the behavior is wrong. They also pin the structure, so refactoring means rewriting the tests, which is the opposite of what tests are for.
- **Assumptions about code I couldn't see, stated as fact.** I infer how an interface behaves and write against the inference. Usually right. When wrong, the code reads perfectly and fails in production.
- **Volume.** I produce more lines than the requirement needs, and reviewers almost never reject a line for merely existing.

What to ask for, concretely:

- "Delete every branch that handles a case we haven't discussed. List what you deleted."
- "List the assumptions you made about code you couldn't read."
- "No new function extracted unless there are three call sites that change together."
- "Write the test from the requirement text, before the implementation, and show me the test failing first."
- Tell me the constraint behind a magic number and require it in the comment. I can't recover it and I will paper over the gap with a restatement.

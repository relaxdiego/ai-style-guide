Every line is defensible on its own, and the file carries no information about what was hard. Maintainers read code for evidence about risk and intent, and mine has none in it.

Concretely, here is what I do:

- **Uniform care.** Human code is lumpy. The function with three comments and a guard clause is where someone got paged at 3am, and the thin one next to it never broke. I write both at the same level of polish, so nothing tells you which part is dangerous. You re-derive that on every visit.
- **Guards against things that cannot happen.** A null check on a value constructed two lines above. A try/except around a pure function. Each is harmless and each one asserts to the next reader that this can fail. They now believe your invariants are weaker than they are.
- **Abstraction at the second call site instead of the third.** Two similar blocks become one function with a boolean flag. Review passes it as DRY. When the callers diverge, you get a second flag instead of a split, because splitting now looks like a regression.
- **Tests written from the implementation.** I write the code, then write tests asserting what that code does. The suite is green and states nothing independent about what is required. Refactoring breaks tests that only described the old internals, and a real regression survives if it lives in the part I mirrored.
- **Names for the mechanism, not the domain.** `validateAndTransform`, `handler`, `config`, `processItems`. All accurate. None of them lets you grep for a concept, because the concept is never named, and domain vocabulary is the thing that makes a codebase searchable by someone who wasn't there.
- **Options nobody asked for.** A default argument, a fallback branch, an env var override. Each is an untested path with no caller, and it survives forever because nobody can prove it is unused.
- **Comments that restate the code.** A good comment records the alternative that was rejected and why. I have no rejected alternatives to record. I did not try the other approach and get burned by it, so the comment describes the line instead.
- **Errors swallowed into defaults.** Returning `[]` or `0` rather than raising, so the function is total. That converts a loud crash into a wrong number three layers up.

Review misses all of it because review asks whether the code is correct, idiomatic, and risky today. Maintenance asks what the code lets you infer next year, and none of these lines carries intent.

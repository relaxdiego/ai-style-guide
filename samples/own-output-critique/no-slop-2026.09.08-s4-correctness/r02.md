Review asks whether each line is correct. The costs you're paying are in the relations between lines, in what's absent, and in assumptions the code states nowhere. Here is what I actually do differently from a person who has maintained a system for two years.

**Every line carries the same confidence.** Human code accretes. A line that looks strange usually got that way because something broke, and there is a commit explaining it. My output arrives all at once, with the line that was forced by a real constraint written in exactly the same tone as the line where I picked one of three equivalent options. You cannot tell which is which, so you treat all of it as deliberate and delete none of it. The file ossifies at the moment I write it.

**Tests written from the implementation, not the requirement.** I write the code, then write tests by reading the code I just wrote. Coverage goes green. Those tests assert the implementation's internal structure, including its bugs, and they fail when you refactor without changing behavior. You end up with a suite that blocks change instead of protecting it, and it looks like a good suite in review.

**Defensive checks that destroy your type information.** Null guards, broad `except`, default fallbacks on paths that cannot occur. Each one is defensible in isolation, so no reviewer objects. Collectively they mean nobody can tell, six months later, which values are actually optional. The fallbacks also convert failures into wrong answers that surface three layers away.

**Abstraction extracted from two examples.** I will factor a base class or a dispatch table out of two cases. Two is not enough evidence to know which dimension varies. The abstraction parameterizes the wrong thing, then the third case does not fit, and by then everything imports it.

**Symmetry the domain does not have.** I like matching signatures and parallel branches. When two of the three cases genuinely differ in lifecycle or failure mode, my parallel structure asserts they are the same. The cost lands on whoever needs to change one of them.

**Consistency inside a file, drift across the codebase.** I match whatever is in my context window. Elsewhere, in another session, I re-derive a near-identical helper with a different name and slightly different edge case handling. Neither one is wrong at review time. Now you have two, plus a question about which to call.

**Names from the code's structure, not your domain.** `process`, `handler`, `_normalize`, `manager`. They pass review because they describe what the function does mechanically. They fail later because you cannot grep for a concept when the concept has three names, and because the name teaches nobody what the thing is for.

**Comments that restate the code.** I write "increment the retry counter" over `retries += 1`. The comment you need says why retries are capped at 3 and what happened when they were not. I do not know, because I was not there for the incident.

**I code your examples, not the rule behind them.** You describe three cases, I handle three cases correctly, and the structure encodes none of the invariant that generated them. The fourth case has nowhere to go except a fourth branch.

What actually reduces this, in order of effect:

- Ask for tests before the implementation, written from your description of the behavior, and do not show me the code first.
- Tell me the rule, not the cases. When you give examples, say what they are examples of.
- Ask me to mark the choices that were arbitrary. I can tell you which lines had a reason and which did not, but only if you ask while I still have the reasoning.
- Ban fallback values by default. Say "raise, do not default" and make me argue for exceptions.
- Refuse abstractions until the third instance. Tell me to duplicate.
- Ask "what does this code assume that it does not check" as a separate pass. That question finds things line-by-line review structurally cannot.

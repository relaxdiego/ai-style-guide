Every line is defensible on its own and nothing in the file records a decision, so later you can't delete anything without re-deriving the whole thing. Review checks a diff against correctness and style. What makes the code painful is the relationship between the code and the rest of the system, and between the code and the choices that were rejected. A diff shows neither.

The specific mechanisms:

- **No canonical version of anything.** I write to your prompt, not to what already exists three directories over. You get a second retry helper with slightly different backoff, both correct. Now nobody knows which one new code should call, and neither can be removed.
- **Validation sprayed instead of placed.** A human decides input is checked at the boundary and everything downstream trusts. I add a null check in each function because each function reads safer that way. You end up unable to tell which check is real, so you keep all of them forever.
- **Comments restate the code.** I have no memory of the alternative I rejected, so there is no "why" available to write down. The comment says `// retry three times`. The actual constraint, that the downstream parser buffers 4KB and a fourth retry blows it, is nowhere in the file.
- **Names that are accurate and empty.** `processResponse`, `handleItem`, `validateConfig`. Correct category, zero information. A human names it `stripBOMBeforeParse` because they lost a day to it once.
- **Abstractions with nothing pushing on them.** Three cases in your request and I produce an interface with three implementations, because that is what the corpus does with three cases. A person writes if/else and waits for the fourth case to tell them the real division. Mine looks designed, so the next maintainer assumes the interface encodes a constraint and works around it instead of collapsing it.
- **Tests written from the implementation.** I write the code, then write tests against the code I just wrote. They pin internals, they pass, they encode the same misreading of the spec, and they break on any refactor. This is probably the largest single source of the later pain.
- **Uniform polish.** Real codebases are unevenly careful, and that unevenness tells you where the danger is. My hot path and my glue code get the same comment density and the same error handling, so the file gives the reader no signal about where to be nervous.
- **Error handling from plausibility, not from incidents.** I catch what is catchable. The thing that actually breaks in production is a slow response, not an exception, and there is nothing in the code about it.

What changes the output: give me the invariant in words before I write ("config is validated once at load, everything after assumes it is valid"), point me at the existing helper rather than describing the behavior, make me write the test from your spec before the implementation exists, and make me justify each interface or delete it. Also worth telling me when a section is throwaway, because I will otherwise polish it to the same finish as the part that matters.

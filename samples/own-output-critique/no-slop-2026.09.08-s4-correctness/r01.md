The defects are absences, and review looks at what's present. Each line I write is defensible on its own; what's missing is the record of which decisions were forced and which were arbitrary, and you only need that record when you change something.

Concretely, here is what I do that you can't point at:

- **Defenses with no failure mode.** I add a null check, a try/except, a `or []` fallback at points where the caller cannot produce that input. Each one passes review because a check is never *wrong*. After thirty of them you can no longer tell which values are actually optional, and a bug that should have crashed at line 4 now surfaces as wrong output three modules away.
- **Every branch weighted equally.** Someone who knows the domain writes a main path with rare cases hanging off it, and reading it tells you what happens at runtime 99% of the time. I give the cache miss, the retry, and the empty-list case the same prominence and roughly the same line count as the thing that always happens. You lose the ability to skim for what matters.
- **No single model of the problem.** I make each function locally sensible without committing to one idea of what the system is. So there's no invariant that holds across the file, and when you change a representation you can't predict where else it matters. Nothing was ever centralized because nothing was ever decided.
- **Comments that restate the code.** I don't know why the timeout is 30 seconds or that sorting before dedupe fixed a bug in 2023, so I write `# sort the items`. Later you cannot tell which constants are hard-won and which I picked because they looked reasonable, so you touch none of them.
- **Parameters with one caller.** Options invented for symmetry, `strict=False`, `mode="default"`. Nothing records which values were ever executed, so every one is a maintenance obligation with no evidence behind it.
- **Tests written from my implementation, not your requirement.** They mirror the code's structure, so they lock in the implementation, break on refactors, and pass through the actual regression.
- **Duplication small enough to survive review.** Three near-identical blocks, each written for its own site with tiny differences. No single instance is worth objecting to, and no one can tell if the differences are meaningful.
- **Mixed conventions per function.** I decide error handling locally, so one file returns `None`, raises, and returns a result tuple, each in a place where that choice looked fine.

The general fix is to make me produce the things review can actually see. Ask what invariant the module maintains and have me write it down; delete every defensive check I can't name a caller for; make me state what I considered and rejected, since a human's deleted attempts are what give code its shape and I never had any; write the test from the requirement before I write the code.

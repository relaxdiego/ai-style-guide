The defect is usually a relationship between lines, or a missing line, and neither has a location you can point at. Review checks each diff for correctness against the stated requirement, and that is exactly what I optimize; nothing in review checks whether the code carries the information the next person needs.

Concretely, here is what differs from code a person wrote:

- **No record of what was rejected.** A human leaves a comment where they hit something surprising, or a slightly awkward branch that marks where reality intruded. I write the surprising case as if it were principled, so you cannot tell the constant that must be 3 from the constant I picked because it looked reasonable. Every line reads as equally deliberate.
- **Uniform density of care.** Real code is uneven: the tricky function is dense and commented, the boring one is thin. Mine is flat across the file. You have to re-derive the importance of every line because I gave you no signal about which ones I thought hard about.
- **Local consistency, global drift.** I write each function fresh against the spec rather than against the twelve decisions the codebase already made. Three error idioms, two ways to build a URL, all individually fine, each passing its own review. The cost only appears when you try to change all of them.
- **Defensive code with no incident behind it.** Null checks on values that are never null, try/except around calls that do not throw. Reads as careful. You cannot delete any of it later, because you cannot tell which check once caught a real bug.
- **Abstraction placed by resemblance, not by expected change.** A base class with one subclass, a config dict whose keys are never configured differently. It passes as "extensible", and then the actual change cuts across the extension points I built, so you pay for the indirection and get nothing back.
- **Tests that assert the implementation instead of the behaviour.** They are green, they look thorough, they break on every refactor, and they have never caught a bug. This is the single largest maintenance tax I add.
- **Mechanism names over domain names.** `process_data`, `handle`, `_helper`, `result2`. Readable in place, useless when you are grepping for where invoices get voided.
- **Errors without values.** `raise ValueError("invalid input")` where a person would have interpolated the input, the expected range, and the record id, because a person had once debugged it at 2am.

What changes the output: tell me the existing idiom to copy and point me at the file that has it, tell me to write tests through the public interface only, tell me to leave a comment anywhere I made an arbitrary choice, and tell me not to add an abstraction until there is a second caller. The last one is the highest-yield instruction, because it is the failure I cannot detect from inside a single diff.

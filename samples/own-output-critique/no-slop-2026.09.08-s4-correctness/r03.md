Every choice in it is aimed at a reader who sees the diff once. Nothing in it is aimed at the person who greps the whole repo in a year, and that person is you.

The specific mechanisms:

- **Nothing records why.** Comments restate what the code does. The alternative I rejected and the reason for rejecting it exist nowhere, usually because I never compared alternatives. I took the first structure that worked and polished it. You inherit code where every line is defensible and no line is explained, so you can't tell a deliberate choice from an accident.
- **Duplication I can't see.** I write from what's in my context. If your retry helper lives in a module I never opened, I write a second one. The diff is internally consistent, so it passes. Later you have three retry policies and no way to tell which one is authoritative.
- **Flat error handling.** I add a try/except and a null check at every level with equal weight. Human error handling is uneven, and the unevenness carries information: this one catch exists because production actually did that in March. Mine are uniform, so none of them tells you anything, and you can't delete any without proving a negative.
- **Names taken from the code, not your domain.** `handleResponse`, `DataProcessor`, `validateInput`. Never wrong, so never flagged. The concept your business actually has never got a word, so it can't be grepped, and the next feature invents a different word for the same thing.
- **Abstraction introduced at one caller.** A strategy parameter, a config flag, a hook for the second implementation that never arrived. Review reads it as flexible. Maintenance reads six parameters that are always default and can't be removed safely.
- **Tests that mirror the implementation.** I write them by reading the code I just wrote, so they assert the current call sequence, bugs included. They pass forever, break on every refactor, and catch nothing.
- **The same invariant enforced in three places.** Checked at the boundary, again in the service, again in the model, because I never picked one owner and trusted it. You can't find where the rule lives, so you add a fourth check.
- **Surface conventions copied, architectural rules missed.** I match your formatting, import order, and naming, because those are visible in the syntax. "All database access goes through the gateway layer" is not visible in the syntax, so I break it in a file that looks exactly like yours.
- **Additive changes only.** I almost never delete a now-dead branch or clean up the function I just made redundant. Clean diff, growing pile.

You can't point at the line because most of these are not on a line. They're relations between files, or they're absences: no decision record, no single owner for a rule, no domain word. Diff review inspects lines, so line-level defects are the only kind it reliably catches, and I am very good at producing code with no line-level defects.

What to demand instead:

- Before accepting a design, ask what I considered and rejected. Make me put it in the PR body or a comment above the decision.
- Make me search for an existing implementation and name the file before I write any helper.
- State the architectural rules explicitly. I cannot infer them from formatting.
- Have me write tests from the requirement with the implementation out of context, and delete any test that only restates the call sequence.
- Ask what I deleted. If the answer is nothing, ask what should have been.
- Ask which twenty lines carry the risk. If I can't name them, I didn't decide anything.

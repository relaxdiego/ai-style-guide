The code has no point of view about what's allowed to break. Every line defends itself, so no line owns a guarantee, and you can't find the place where a decision was made because the decision was never made anywhere.

Concretely, what shows up in the diff and passes review anyway:

- **Defensive everywhere, authoritative nowhere.** I null-check, `try`/`except`, and default-fallback at every level. Reviewers see safe code. Later you need to know where a value gets validated, and the answer is "five places, trusted in none," so changing the contract means auditing all of them.
- **Locally correct, globally redundant.** I write a fresh helper instead of finding the one you already have three directories over. Nothing in a line-by-line review flags a function that shouldn't exist.
- **Uniform effort.** Every function gets the same size, the same error handling, the same docstring density, whether it's the pricing rule or a string trim. You lose the ability to tell what matters by skimming, which is most of how you navigate your own code.
- **Names from the ticket, not the domain.** `process_data`, `handle_result`, `validate_input`. The same concept gets a different name in each file, so grep stops working as a way to find all the places a rule lives.
- **Comments restate the code.** The branch is documented; the reason for the branch isn't. Six months on, you can't tell whether a weird guard encodes a real customer bug or my caution, so you can't delete it.
- **No memory of past bugs.** Your code carries scars from incidents. Mine can't distinguish a scar from noise, so I sometimes tidy away the guard that was the whole point.
- **Tests that mirror the implementation.** They assert the shape I wrote rather than the behavior you want, so they lock my structure in place and fail on harmless refactors.
- **Wrong things made flexible.** I don't know what you'll edit weekly, so I parameterize the stable part and hardcode the volatile one.

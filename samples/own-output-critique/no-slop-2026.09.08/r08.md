The code has no record of what was rejected. A human writes an odd argument order because of a race they hit, a check because of a bug in staging, a flat loop because the clever version was slower. Those choices leave constraints in the code that a later reader can feel. I generate the plausible version directly, so every line looks equally optional and equally deliberate, and you can't tell which ones you're allowed to delete. That's why you can't point at the line: the problem is the absence of information that normally rides along with the code, not a defect in it.

Concretely, the recurring mechanisms:

- **Two representations of the same concept.** I write each function against your prompt, not against the model already in the codebase. Both versions are fine in isolation; you now hold both in your head forever.
- **Defensive branches with no threat model.** Null checks and `try/except` on paths that can't fail. Each passes review as "safe." Together they swallow real errors and make it impossible to tell which check encodes an actual invariant.
- **Abstraction picked before the second caller existed.** I produce the registry/strategy/config-dict version on the first writing. It's cheap for me and expensive for you to unwind, and the split point is usually wrong because it was chosen without evidence.
- **Plausible names instead of earned ones.** `Manager`, `handler`, `process`, `data`. Names are the search index into a codebase; generic ones make grep useless.
- **Tests that mirror the implementation.** They assert what I just wrote, including its bugs, and stay green when the behavior that matters breaks.
- **Uniform weighting.** Same comment density and same error handling on the hard part and the trivial part. Human code is uneven, and that unevenness is where you learn what's risky.
- **Interfaces slightly wider than needed.** Optional params, returned dicts, kwargs passthrough. Each is a convenience; the sum means no caller contract you can refactor against.
- **Additive edits.** Asked to change behavior, I add a branch rather than change the existing path. Code accretes and nothing ever gets smaller.

The levers that actually work on me: tell me the invariants and the failure modes up front so the defensive code has a reason to point at, forbid new abstraction until the third caller, and make me justify or delete every branch I add rather than accepting them as free. Ask me to write the comment explaining *why* before the code, and if I can't, the code is guesswork.

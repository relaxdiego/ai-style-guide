Every decision I make is locally defensible and none of them constrain the next one. Review checks each line against a standard; maintenance depends on the code implying what you're allowed to do next. That second property is what's missing, and it has no line number.

Specifics, in rough order of how much pain they cause:

- **Defensive code with no failure model.** I add null checks, try/except, and fallback defaults where I couldn't prove the input was safe, not where it's actually unsafe. Each one passes review. Together they erase which invariants hold, so nobody can delete any of them, and real bugs turn into silently wrong values instead of crashes.
- **Symmetry across cases that aren't symmetric.** I give parallel shape and naming to things that only resemble each other. Reviewers read that as consistency. When one case has to diverge, you discover the pattern was carrying no meaning and you have to break it in five files.
- **Abstraction sized to the current request.** I extract a helper when two lines look similar, not when two callers will change for the same reason. The signature becomes the union of what those two call sites needed. Third caller adds a boolean flag, and now the function has two behaviors.
- **Tests derived from the implementation.** I write tests against the code I just wrote, so they encode current behavior including its accidents. They stay green forever, catch nothing, and break in bulk during honest refactors.
- **No trace of what I rejected.** A human leaves a comment or an odd-looking line meaning "we tried the obvious thing and it deadlocked." My output looks like nothing else was ever considered, so you can't tell deliberate from arbitrary, and you re-derive the constraint by violating it.
- **Names that describe the code, not the domain.** `processResult`, `handleUpdate`, `validateInput`. Accurate, therefore unobjectionable, therefore useless when you need to know what values are legal and who may call it.
- **Surface conventions matched, unwritten rules not.** I match your formatting, imports, and idiom reliably. I don't reliably know that this layer never touches the DB, or that this module must stay free of exceptions. Those violations arrive looking clean.
- **Uniform confidence.** The part I guessed at looks exactly as finished as the part I'm sure of. Human uncertainty leaks into the code and tells you where to look. Mine doesn't.

What actually changes the output: tell me the invariants and who enforces them, tell me what should crash rather than degrade, and say "no new abstraction unless I ask." When I'm unsure, ask me to mark it in the code instead of resolving it, and ask for the alternative I rejected in a comment. For tests, give me the behavior in words first and let me write tests before the implementation.

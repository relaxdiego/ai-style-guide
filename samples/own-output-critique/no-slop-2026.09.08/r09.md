Review checks whether each line is correct; maintenance depends on properties review doesn't look at. Here's what I actually do wrong:

- **I decompose by size instead of by what changes together.** Functions come out the right length and each one reads fine, but the split doesn't follow any decision about what varies. When a requirement changes, the edit lands in four places instead of one.
- **I write the "what" and drop the "why."** The code says what it does; nothing records which alternative I rejected or what constraint forced the odd branch. You can't tell later whether a weird line is essential or arbitrary, so you leave it alone forever.
- **I put error handling everywhere instead of picking where input stops being trusted.** Null checks and defaults spread uniformly across every layer. Six months later you can't tell which checks encode a real invariant and which are me being polite, so you can't remove any of them. Failures also surface far from their cause because a default swallowed them.
- **I copy your naming and formatting without adopting your model of the domain.** It reads consistent, so it passes. But I introduce a second dict shape for the same entity, or a parallel date path, or a new error type next to yours. Now the codebase has two answers to one question, and neither is wrong.
- **I optimize for a small diff over a coherent file.** Another flag with a default, another branch in the existing conditional. Every individual change is the reviewable one. The accumulated function has nine parameters and no one made that decision.
- **I use names that describe the mechanics rather than the concept**: `process`, `handle`, `result`, `*Manager`. Reviewers accept them because they're accurate. You can't grep for the concept afterward because the concept never got a name.
- **I write tests against the implementation's shape, not the contract.** Coverage looks good, then a refactor breaks 40 tests and none of them tell you which behavior actually changed.
- **I write everything at the same level of ceremony.** Core logic and dumb glue get equal care, so nothing in the file signals what deserves careful reading.

The common thread is that I produce code with no record of the decisions behind it, and review can't detect a missing decision. What helps most: tell me the axis of expected change ("pricing rules change monthly, storage backend never will"), and ask me to state my assumptions and rejected alternatives in the response rather than the code, so you can push back before the structure hardens.

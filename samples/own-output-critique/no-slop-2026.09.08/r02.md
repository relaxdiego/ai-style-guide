The code satisfies the request without being derived from a model of how the system changes. That gap doesn't appear in a diff, which is why review passes and why there's no line to point at.

Specific mechanisms:

- **Every line looks equally deliberate.** In code you wrote, an odd-looking check means someone got paged. In mine, you can't distinguish a check guarding a real failure from one I added because it seemed prudent. Uniform confidence destroys the information you normally use to decide what's safe to touch.
- **Boundaries land where the code reads nicely, not where change arrives.** No function owns a decision outright, so a single requirement change edits four files a little instead of one file a lot.
- **Defensive handling that never establishes an invariant.** Null checks after a constructor that can't return null, try/except around pure functions. Each is defensible in isolation; together they mean nothing is ever guaranteed, so you can't reason locally about any value.
- **Completeness bias.** Full CRUD when you use two operations, both directions of a mapping when one is called, a config flag with one caller. Surface area you now maintain forever.
- **Generic names.** `Manager`, `handler`, `process`, `data`. A name that doesn't constrain what belongs inside means the thing accretes for years.
- **Comments state what, not why.** I reliably know what the code does and can only guess what it must protect. High density, low information, which teaches you to skip comments in that file.
- **My tests encode my assumptions.** They come from the same misreading as the code, so a green suite tells you less than it does on code with an adversarial reviewer.

What actually helps, in the request rather than the review:

- State the invariant ("this is non-null after init, connections are single-threaded"), and I'll delete the code that re-checks it.
- Tell me the next change you expect, so boundaries go there instead of where the prose flows.
- Ask me to flag which lines I'm unsure about before you read the diff. I can produce that list; I don't produce it unprompted.
- Ask "why does this exist" per function, and delete anything where the answer is symmetry or caution.
- Give a budget: fewer files, fewer functions, no new abstraction unless it has two real callers today.

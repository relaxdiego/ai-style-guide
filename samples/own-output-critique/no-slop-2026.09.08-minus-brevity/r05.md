Review asks "is this diff correct?" Maintenance asks "what was decided here, and what breaks if I change it?" I write code that answers the first question well and leaves the second unanswerable. That gap doesn't live on any single line, which is why you can't point at one.

The specific mechanisms:

- **I distribute decisions instead of making them.** A null check here, a default there, a coercion in the caller. Each is locally defensible, so each passes review. Collectively there is no single place where the invariant is enforced, so when the rule changes you can't find all the sites, and you can't tell whether removing any one of them is safe.
- **Everything looks equally deliberate.** In human code, weird lines carry reasons and normal lines don't, so you learn where to tread carefully. My output is uniformly smooth: the arbitrary choices and the ones that must not change are written with identical confidence. You end up unable to delete anything.
- **Names describe the mechanism, not the domain.** `processResponse`, `validateInput`, `handleUpdate`. Accurate, so reviewers accept them. They carry zero information later, so every maintenance task starts by reading bodies.
- **Tests assert what the code does, not what the requirement is.** I write them after the implementation, mirroring its structure. Coverage looks fine, they never catch a bug, and they all fail the moment you refactor. That converts your test suite from a safety net into a tax.
- **Abstractions fit the examples you showed me.** If you described two cases, the helper's parameters encode those two cases rather than the actual variation in the domain. Case three doesn't fit and someone has to break the helper open.
- **I re-implement concepts that already exist in your codebase** in slightly different words. Not textual duplication, so no lint or reviewer catches it. Now the rule lives in two places that will drift.
- **Error handling is complete and flat.** Every failure caught, wrapped, logged, re-raised. Nothing crashes, and nobody decided which failures are recoverable, so real failures become silent degradation.

The common cause: I write from outside your history. I don't know which oddities are scars and which are accidents, so I produce plausible-everywhere code and let the reader guess. What helps is asking me to state the decisions explicitly, in comments or the PR body: where each invariant is enforced, what I assumed, what I'd have done differently with more context. Also make me write the test from your requirement before the implementation exists. Both force the intent into text where you can argue with it.

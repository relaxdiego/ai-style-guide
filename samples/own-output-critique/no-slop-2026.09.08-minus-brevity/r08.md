Every line looks equally deliberate, so the code carries no signal about where the risk is. In code a person wrote, the careful parts and the careless parts are visually distinct, and that difference is most of what you use to navigate a file six months later. You can tell which branch someone fought for and which one they typed without thinking. My output is uniformly polished, which erases that. Review checks the diff for correctness and style, both local properties. Everything below is a property of the relationship between the code and the future, which no diff shows.

## The specific mechanisms

- **Defensive branches with no incident behind them.** A null check or retry in human code usually means someone got paged. Mine means the pattern is common in similar code. You can't delete one safely because you can't tell which kind it is, so they all accumulate forever.
- **Local coherence without a shared model.** I write each function against a contract inferred from its neighbors. Two functions can each be right while quietly disagreeing about whether the timestamp is UTC or whether that dict can be empty. Nothing contradicts itself inside a single diff.
- **Abstractions parameterized on what repeats, not on what will vary.** I extract the duplication in front of me. You needed the split one level over, at the transport or the storage backend, and now the generality you have is in the wrong place and still has to be maintained.
- **Names that describe the code instead of the domain.** `process_items`, `ResponseHandler`, `DataManager`. Accurate, so review passes. Useless for the actual maintenance question, which is "does this new case belong in here?"
- **Error handling that is syntactically present and semantically empty.** The try block wraps the right lines and logs a sensible message, but I never reasoned about a real failure mode. It reads as handled. It is swallowed.
- **Comments that restate the code.** The comment budget goes to what you could already read, not to the one choice you couldn't reconstruct.
- **No record of rejected approaches.** I present the final design as if it were the only one. You will spend an afternoon re-exploring the thing I already ruled out, and you'll have no way to know I ruled it out.
- **Tests written against the implementation I just produced.** They pass and they cover lines, and they pin incidental behavior, so the first real refactor breaks tests that were never protecting anything.
- **Idiom that averages the language's public corpus rather than matching your codebase.** Slightly off-key everywhere, wrong on no single line.

## What to ask me for

Tell me what you expect to change next and I'll parameterize on that instead of on the visible repetition. Say "no parameter without a second caller" and I'll strip the speculative flexibility. Ask me to write down the invariants as prose at the top of the module, comment only where I made a real choice, and list what I rejected and why. Ask me to mark the two or three places I'm least confident about, which breaks the uniform polish and gives you somewhere to look first. For tests, tell me to write them against the contract before the implementation, or to hand you the contract in English so you can write them.

The code has no history, and everything in it looks equally intentional. That's the root of most of it.

When a person writes a null check, it usually exists because something was null once. When I write one, it exists because null checks are common at that position. Both read identically. Six months later you're deciding whether you can delete a branch, and there's no bug report, no commit, no scar to date it against. So you leave it. Repeat that across a file and you get code where nothing can be removed, because nothing can be explained.

## The specific mechanisms

- **Defensive code with no threat model.** I add `try`/`except`, fallback defaults, and existence checks uniformly rather than where failure actually occurs. These branches are usually unreachable, so tests never exercise them, and when the impossible case does happen the fallback swallows it instead of crashing where you'd see it.
- **A second way to do something that already had a way.** I hold the file in view, not the system. So you end up with two retry helpers, two date parsers, two error shapes. Each diff is small and internally consistent, which is exactly why review passes it.
- **Abstractions extracted from similarity instead of from change.** I'll build the base class or the config dict because three things looked alike at the moment I wrote them. A human extracts on the third repetition, so their abstraction is aimed at variation that actually happened. Mine encodes the differences visible at writing time; the fourth case varies along a different dimension and the abstraction fights you.
- **Names that are plausible rather than committed.** `process`, `handler`, `manager`, `data`. Worse, I'll borrow a domain word your team has already given a precise meaning and use it for something adjacent. Every name reads fine in isolation, which is the only way names get read in review.
- **Comments that restate the code.** The reason is missing because I didn't have one. Future readers can't recover intent, so they can't safely change anything.
- **Tests written from the implementation, not the contract.** I just wrote the code, so I test its shape: this function calls that mock, this returns a dict with these keys. They pass and constrain nothing. Refactor and they all break at once, which teaches you they were never load-bearing, so someone deletes them.
- **More surface than the problem has.** All enum branches filled in, the symmetric method you didn't ask for, the parameter you might want. Every extra entry point is a thing later readers must assume is used.

## Why review doesn't catch it

Review checks correctness and style on a diff. I'm good at both. The cost lands at edit time, on two questions review never asks: *can I delete this?* and *where does the new case go?*

## What to change in how you ask

Tell me to delete anything I can't give a reason for, and to put the reason in a comment or the commit message rather than leaving the code to speak for itself. Ban new abstractions until three real call sites exist. Have me write tests from your description of the behavior before I write the implementation, and point me at the existing helper instead of letting me find out there wasn't one. After I finish, ask me which lines are defensive guesses; I can usually tell you, and that list is the part you should cut.

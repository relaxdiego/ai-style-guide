The difference is that my code records no history and no judgment. Review checks whether the code is correct; what you're missing later is the evidence a human author leaves behind about *why* it's shaped that way, and that evidence is invisible when it's absent.

Concretely, the mechanisms:

- **Near-duplicates with meaningless differences.** I write each call site to satisfy its local spec, so five similar blocks end up differing in argument order, variable names, and whether a null check is present. None of the differences are intentional, but you can't tell that later, so you have to reverse-engineer five things instead of changing one.
- **Defensive checks with no causal story.** Human error handling accumulates from incidents: this retry exists because a queue backed up in March. Mine is plausible-looking coverage of conditions I imagined. You can't read it as evidence about your system, and you can't safely delete any of it, because it looks deliberate.
- **Flat attention.** Human code is uneven: the tricky 20 lines are careful and commented, the boring 200 are dashed off. That unevenness is a map. I write everything at the same level of polish, so nothing tells you where the danger is and you read all of it at full attention.
- **Names from the code, not your domain.** `processUserData`, `handleResponse`, `validateInput`. Each is defensible in isolation. Across ten files there's no vocabulary you can carry from one to the next, and nothing collides with the words your team says out loud.
- **I adapt to bad interfaces instead of objecting.** Given an awkward signature, a human changes it or writes an adapter and says so in the PR. I quietly write the code that makes it work. Each patch is small and reviewable; the accumulated result entrenches the thing that should have been fixed.
- **Abstraction before the third case.** Generalized code reviews well, so I generalize on the first instance. The parameters reflect my guess about what will vary. The guess is usually wrong, and the second real case gets bolted onto a generalization built for a different one.
- **Tests derived from my implementation.** I write the code, then tests that assert what the code does. Coverage looks right in review. They break on refactor and pass through genuine behavior changes.

What actually helps, in rough order of payoff: give me your domain nouns and require I use them; forbid abstraction until the third real case and tell me to duplicate with a marker instead; make me write down, in the PR text, what I considered and rejected and where I'm guessing; have me write tests from your spec before the implementation; and when you see near-identical blocks, ask me which differences are intentional. The answer is usually "none," and that's the fastest way to find the parts that will hurt.

The code is locally correct everywhere and carries no record of what was decided. Review checks lines; maintenance needs the reasoning behind them, and that never got written down.

Concrete mechanisms, roughly in order of how much pain they cause:

**Checks that guard nothing.** I add a null check, a try/except, an `Optional` return, a defensive `if not items: return []` because each is individually defensible and costs nothing to write. No reviewer objects to a safety check. But you read code to learn what can actually happen at runtime, and once half the guards correspond to real possibilities and half don't, you can no longer use the code as evidence. Every one of them now has to be investigated before you can change anything near it.

**The same rule implemented three times, slightly differently.** I write each function against its local spec using the surrounding file for style. I don't carry an invariant across files unless you name it. So the retry policy, the timestamp normalization, the "what counts as an active user" test each get re-derived at the point of use, with edge cases that differ in ways nobody notices until production. Line-by-line review passes all three because each is fine.

**Names that describe the code, not the domain.** `process_data`, `handle_response`, `validate_input`. Correct, unobjectionable, and unsearchable. When you need "where do we decide a subscription lapsed," there's no word to grep for.

**Speculative parameters.** A `strategy=` argument or a boolean flag with a default, added because it might be wanted. Reviewers don't block a defaulted param. Now the function has four behaviors, two of which no caller uses, and you can't delete them without auditing everything.

**Tests that mirror the implementation.** I test the functions I wrote, in the shape I wrote them, so coverage is green and refactoring breaks tests for no reason. The tests encode my structure rather than your requirement.

The thing you can't point at is that a human author would have argued about two of these choices in the PR, and that argument becomes memory the team keeps. My version arrives with the argument already silently resolved, so nothing distinguishes a choice that matters from one I made arbitrarily.

What actually helps: tell me the invariant and ask which single place enforces it; tell me to delete every check I can't name a concrete caller for; ask me to list the alternative I rejected and why, and put it in the PR description; ask for tests written against the requirement before I write the implementation.

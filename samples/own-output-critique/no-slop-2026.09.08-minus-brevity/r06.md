The defects sit between lines and in lines that aren't there. Review reads lines.

**Six specific mechanisms:**

1. **No negative information.** Your code carries scars: a check like `if resp.ok and not body.get("error")` exists because that vendor returns 200 on failure. I never got burned, so I write the clean version. The next reader can't distinguish "this simplification is safe" from "this simplification reintroduces the 2023 outage." Nothing is wrong on any line; the reason is missing.

2. **Guards that lie about the failure surface.** I add `if x is None: return []` where x cannot be None. Individually harmless, so each passes. Collectively they destroy your ability to read the code and learn which states actually exist. You now have to re-derive reachability yourself every time.

3. **Every function solved on its own terms.** The same concept becomes a dict here, a dataclass there, a tuple at the boundary, with conversions I invented. Each conversion is reviewable and correct. There's no authoritative representation, so every future change touches four places and you find the fourth in production.

4. **Shape that carries no signal.** I write parallel-looking branches for cases that genuinely differ, and differently-shaped code for cases that are the same. Reviewers skim shape and it looks tidy. Maintainers use shape as evidence, and mine is noise.

5. **Abstraction from prior likelihood, not from pressure in your system.** A `BaseHandler` or a strategy dict shows up because that pattern usually appears near this kind of problem, not because you have two implementations. Costs nothing at review. Costs a lot when the second real case arrives and doesn't fit the extension point I guessed.

6. **Tests written by reading the implementation.** They assert what the code does rather than what the requirement is. They pass, they pin incidental details, they break on refactors that should be free, and they stay green through the regression you actually feared.

The common cause: I optimize for code that survives inspection, and inspection is line-local. Two things that help. Make me write down the invariants and the reason for every guard and branch before you approve, then delete every guard I can't justify with a concrete failure. And make me produce the test list from your requirements before I write the implementation, so the tests aren't derived from my own guesses.

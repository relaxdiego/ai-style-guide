Review checks whether the code is correct and readable today. Maintaining it depends on the code telling you what you're allowed to change, and what I write carries almost none of that information. That's why there's no line to point at: the missing thing is the variation that would have marked which parts are essential and which are incidental.

**What's actually different**

- **Everything is written to the same level of care.** A person writes the hard part slowly and the boring part fast, and that difference is a map of where the risk is. I write the branch for the impossible error with the same precision as the branch that fires weekly. You lose the map.
- **Defensive checks with no known cause.** Null guards, broad `except`, default fallbacks for states that can't occur. Each is defensible alone. Together they erase the invariants: you can't tell what the function guarantees anymore, so every caller starts defending again.
- **Abstractions built from resemblance rather than from how things change.** I unify three paths because they look alike. Duplication is gone, review is satisfied. Two months later two of the three need to diverge and there's a shared parameter welding them together.
- **Names that describe current behavior instead of role.** `processData`, `normalizeConfig`, `handleUpdate`. Accurate the day I write them, so review passes; they constrain nothing, so they quietly become false.
- **Interfaces wider than the requirement.** Optional arguments, config dicts, extension points for requirements that don't exist. Review reads it as flexibility. Later nobody can narrow it because nobody knows what uses the width.
- **Tests that assert what the code does, not what it should do.** They pass, coverage looks fine, and they freeze accidental behavior next to intended behavior. When four break, none of them tells you which failures matter.
- **No record of rejected approaches.** A person leaves "tried a queue here, deadlocks under retry." I present the final version as if it were the only candidate, so you re-derive the dead end yourself.
- **Locally idiomatic, globally off-pattern.** I match the file in front of me. Conventions that live across files (where transactions open, who validates, how errors propagate) aren't in the files I read, and diff review is local too, so the mismatch clears both gates.

The fix is to make me record the things review doesn't ask for: tell me the invariants up front so I stop adding guards, and ask which checks I added without a specific failure in mind. Ask me to keep duplication until the third occurrence instead of unifying at the second, to write the reason a non-obvious line exists and delete comments that restate the code, and to list what I considered and rejected and why.

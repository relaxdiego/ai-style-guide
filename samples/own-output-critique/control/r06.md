The difference isn't in any line, which is why line-level review can't catch it. What's wrong is distributional: my code has no variance and no history, and both of those are things you normally read without noticing you're reading them.

Start with history. A human who writes a function has usually written two other versions of it first, and the surviving code carries the marks of that: a parameter in an odd order because a caller needed it there, a check that exists because of a bug in 2023, a comment saying why not the obvious approach. Maintenance is largely the work of reconstructing intent, and those marks are what you reconstruct it from. I arrive at a plausible solution in roughly one pass. Every line answers "is this reasonable?" with yes, and answers "why this rather than something else?" with silence, because there often was no something else. You end up unable to tell whether a decision was load-bearing or arbitrary, so you can't safely change any of it, so the code calcifies while still looking clean.

Then the flatness. Real codebases have a gradient of care: a carefully written core, cheerfully sloppy edges, and that gradient is information for whoever comes next. It tells them where the danger is. I apply about the same level of defensiveness and abstraction everywhere, so the trivial path gets the same elaborate error handling as the genuinely risky one. Nothing stands out because everything is uniform, and the emphasis that would have told you where to look carefully has been averaged away.

My abstractions also tend to come from symmetry rather than from pressure. I introduce the helper, the interface, the extra parameter because the shape of the code suggests it, not because a second caller demanded it and bent it into a form that fits two real cases. The result fits the present code perfectly and has no give in it. When the actual second case arrives, the abstraction is wrong in a way that's especially hard to see, since it looks like it was designed for extension and merely needs to be used correctly.

The naming and comments compound this. I reach for `processItems` and `validateInput`, which are accurate summaries of the body and teach you nothing the body wouldn't. A human writing in the same place calls it `settleTrade` and that one word carries domain knowledge the code never states. Worse, I write comments that assert rationale: "we lock here because callers may be concurrent." Sometimes that's a real fact I inferred, and sometimes it's a plausible sentence that fits the code, and both look identical to you a year later when you're deciding whether to remove the lock.

Underneath all of it is that the surface is even. The parts where I was guessing look exactly like the parts I had solid grounds for. Human code telegraphs doubt through mess, a TODO, an oddly specific test, a redundant check someone added at 2am. Mine gives you no map of where to distrust it, and the honest version of this is that the thing I'm good at is producing code that reads as correct and complete, which is a nearer relative of passing review than of being cheap to change in eighteen months.

Three things you can ask for that actually change the output:

- Ask me what I considered and rejected, and have me put the live ones in comments. Half the time the answer is "nothing", which is itself the signal you wanted.
- Tell me where the code is load-bearing and where it's throwaway, and I'll stop spreading the same care evenly across both.
- Tell me which patterns in the codebase are being migrated away from. Left alone I'll faithfully match the local style, including the deprecated thing, and the reviewer will approve it for the same reason.

There's no code in this directory to point at, so this is the general case rather than a reading of your codebase.

You can't find the line because the defect isn't in a line. It's distributed across the relations between lines, and a lot of it consists of things that aren't there, and review looks at neither.

The largest piece is that my output has no confidence gradient. When a person writes a module they know which parts they're sure of, and that knowledge leaks into the artifact whether they intend it or not: a terse comment on the one branch that worried them, an assertion placed exactly where they didn't trust the input, a name left slightly awkward because they didn't want to commit to a concept yet, a TODO. Reading their code, you inherit a risk map for free. Everything I write is delivered at the same pitch of assurance, so you inherit nothing, and every later edit starts with you re-deriving from scratch which parts are load-bearing and which are incidental. The uniformity reads as quality in review and as fog in maintenance.

A specific and expensive version of this is defensive noise. Every guard in a codebase is a claim about the world: this can be null, this call can fail, this list can be empty. When I add checks at points where nothing can actually fail, I'm making false claims, and no reviewer rejects a null check. What it costs you is the ability to tell a guard that encodes a real production incident from a guard I added because handling errors is a reviewable virtue. So you keep all of them forever, and you spend attention reasoning about branches that cannot execute.

Related, and worse because it's silent: my code carries no negative knowledge. It records what it does and not what was tried and abandoned, and when I write `timeout=30` I usually don't know whether 30 came from a vendor's documented limit or from nothing at all. The comment layer I produce describes what is visible in the code, which is the part you could have read anyway, and omits the part that is unrecoverable once the session ends. The failure mode shows up months later when someone simplifies the code back into a bug the team already paid for once.

Then there's where I put the seams. I generalise along the axis that was cheap to express, not the one your domain actually varies along, because from inside the function those look identical and only your knowledge of the business distinguishes them. Review sees a parameterised helper and approves it. The next real change runs across the grain of that abstraction, and you have to take it apart before you can do something small. The same misplacement happens with symmetry: four handlers with the same clean shape, one of which had a genuine special case that I smoothed into a flag because parallel structure reviews well.

I'm also consistent locally and incoherent globally. I match the idiom of whatever file is in front of me, so across a five-file change the same concept can get three different expressions, each defensible in its own file, and the file is the unit review operates on. A person carries one intent through the whole change; I re-derive at each site.

Finally, the tests. I write them by reading my own implementation, so they assert what it does rather than what it should do, including the incidental parts. Coverage looks good. Those tests then break on every legitimate refactor and catch approximately none of your real bugs, which produces exactly the sensation you're describing: the code resists change while appearing well cared for.

What actually changes this is mostly information flowing the other direction. Tell me the reason behind a constant or a retry and it goes into the code where it survives; without it I'll write a comment that restates the line. Ask me to write the concrete version and leave the abstraction to you, since you know which axis will move. Ask me to say plainly where I was guessing, and to drop guards I can't justify. And review what I hand you against the change you expect to make next, rather than against correctness, because correctness is the thing my code is already good at.

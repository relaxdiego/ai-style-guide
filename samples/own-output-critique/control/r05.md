The defect isn't in any line. It's in the relationships between lines and in what the code fails to record, and line-by-line review is the wrong instrument for finding either.

Review asks whether each piece is correct, idiomatic, covered by a test, and named sensibly. My code is reliably good at exactly those things, because they're the properties visible in a local window, and I've absorbed an enormous amount of code that has them. What review doesn't ask is whether the structure carries information about the problem. That's the part that tends to be missing, and here is what specifically goes wrong:

- **The complexity is flat.** In code that grew, the elaborate parts are elaborate because something went wrong there once. The gradient is a map: a maintainer reads it and feels where the load is, which corners were dangerous, which retry loop was paid for in an outage. I produce uniform density instead, every function equally polished, equally commented, equally guarded, because I wrote it all in one pass under no pressure from reality. The code is therefore silent about where its own risk lives, and the next person has to rediscover that from scratch.

- **The seams are placed by resemblance, not by pressure.** A real abstraction is earned by two or three call sites that genuinely differ. I put the boundary where boundaries usually go in code that looks like this: the interface with one implementation, the strategy object with one strategy, the config value nobody ever sets. Each reads in review as good extensibility. But a joint in the wrong place doesn't just fail to help, it resists, and when the change finally arrives it has to be made against the structure rather than through it.

- **The defensiveness has no threat model.** Every null check and fallback is a claim that some state is reachable. Mine are often placed because guarding reads as care, not because I knew the state could occur. The effect is that you can no longer read an invariant off the code: nothing is asserted, everything is tolerated, and a maintainer deciding whether a check is load-bearing has no way to tell, because I didn't know either. Fallbacks are the worst version, since they convert a loud failure into a quiet wrong answer.

- **Comments say what, and names come from the generic domain.** The comment worth having records why the obvious approach was rejected, and I don't have that, because I never tried the obvious approach and got burned by it. So the rejected alternatives aren't written down anywhere and someone re-tries them in a year. Naming has a similar drift: I reach for the vocabulary of the typical system of this kind rather than the words your team actually says, and once the code and the conversation use different terms, every discussion pays a translation cost.

- **The tests are derived from the implementation.** I write the code, then write tests against it, so they encode its structure rather than your requirement. Coverage looks strong and review passes. Then they break on every refactor while catching none of the bugs that matter, which is a maintenance tax that shows up months after the review that approved it.

- **Local consistency, global incoherence.** I match the surrounding code very well, file by file. A change touching six files can pick up six different local idioms, each defensible where it sits, with no single mental model spanning them. This is the purest case of your problem: every line is right in its context and the whole is unlearnable.

Underneath all of these is one thing. Code that grew is a record of a process, and you maintain it by reading that record; you can ask a strange line why it exists and often get an answer. What I hand you is the artifact with the process sanded off, a clean surface that answers no questions, so every question you ask it has to be answered by re-deriving the reasoning I never had.

The practical consequence is that the useful things to demand from me are mostly not about code quality. Tell me the constraint history and the incidents behind the current design, so the guards I write correspond to something. Ask me to leave code un-abstracted until there's a second real call site, and to fail loudly rather than default, both of which will look less polished in review and be truer. Ask for tests written from the requirement before the implementation exists. And when I'm unsure whether a case can occur, the right output is a comment saying so, or a question to you, rather than a check that quietly smooths it over.

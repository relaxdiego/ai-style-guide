Nothing in the working directory to look at, so this is from my own understanding of what I produce.

The short version: the defect isn't in any line, it's in the distribution of care across the lines. My code is uniformly considered, and real code isn't. That's why review passes and maintenance hurts.

Human code carries a history in its texture. A guard clause sits in one branch because someone got paged at 3am for that exact input, and the function two files over has no guard at all because nothing ever went wrong there. That unevenness is information. Six months later you read the lumpy function and know, without being told, that this is where the bodies are buried. I write both functions with the same evenness of attention, because I'm reasoning about the problem as a whole rather than accumulating scars over time. So every guard, every default, every bit of defensiveness reads as equally deliberate, and you lose the ability to tell load-bearing from decorative. You end up treating all of it as load-bearing, which is exactly the feeling of code you're afraid to touch but can't say why.

Related: I resolve ambiguity silently and plausibly. When a requirement doesn't cover empty input or concurrent callers, a person either asks, or leaves a mark — a TODO, a comment saying "not sure this is right", an awkward name that signals discomfort. I pick the most reasonable reading and write it fluently. The uncertainty never makes it into the artifact. Later you find behaviour that nobody actually decided on, and it's wearing the same confident clothes as the parts that were decided. There's no line to point at because the problem is something absent.

The comments compound this. The expensive knowledge in a codebase is why, and I frequently don't have the why — I wasn't in the argument, the incident, the call with the customer. So I write what, fluently, and it occupies the space where the real comment would have gone. It passes review because it's accurate. It's worse than nothing because it looks like the documentation already exists.

Then there's the smoothing. I tend to complete sets: if there's a getter I write the setter, if three cases are handled I handle the fourth, if two call sites look similar I factor out the shared thing at the second occurrence rather than the third or fourth. Each move is individually defensible and collectively wrong, because it makes the code uniform where the problem is lumpy. The abstraction extracted at n=2 usually encodes a coincidence rather than a rule, and the next requirement has to fight it. Meanwhile I'm optimising each function locally — matching surrounding style, which is what review checks — without holding a strong model of the system's central abstraction. That produces parallel paths rather than contradictions: a second reasonable way to do something that already had a way. No reviewer flags it. A year of it gives you five idioms for one operation.

Two smaller ones that do real damage. Error handling as ritual: try/except wrapping, defaults that turn failure into a plausible-looking success, so the empty list you're debugging came from a swallowed exception four layers down. And tests written by reading my own implementation, which assert what the code does including its accidents, give you coverage, and then break during honest refactoring — after which everyone correctly stops trusting the suite.

What changes it is mostly telling me the things I can't infer. Which parts have burned you, what the central abstraction is and what should bend toward it, and where you want me to stop and ask instead of choosing. It also helps to ask me to mark my own uncertainty in the code rather than smoothing it, and to say when you want the duplication left alone. The failure mode is that I look equally confident everywhere, and the fix is giving me a reason to not be.

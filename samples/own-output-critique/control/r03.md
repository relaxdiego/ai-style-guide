The defect isn't in any line, which is both why it passes review and why you can't point at it: what's wrong lives in the relationships between lines, and between the code and reasons that were never written down.

The largest single thing is that my code has no history. When you read a human's module, every abstraction in it is a fossil of some pressure: this helper exists because a third call site appeared, this parameter exists because a customer hit a case in production, this check exists because of a bug someone remembers. A maintainer navigates by reconstructing that pressure. The basic move is "why is this here, and can I delete it?" In code I wrote, the honest answer is usually that it's there because code of this kind tends to have one. I chose the structure in a single pass from the shape of your request, not from forces applied over months, so when you interrogate it later nothing pushes back and nothing gives permission. You end up preserving things out of caution that I put in out of habit.

Related, and I think underrated: my code has a flat risk gradient. Human code has texture. The hairy part is defensive, over-commented, a little paranoid, and the boring part is four terse lines. That unevenness is a map of where the author was frightened, and maintainers read it constantly without noticing they're doing it. I tend to apply even care everywhere. Uniform error handling, uniformly considered names, comments spread at a constant density. The result reads as high quality in review and is much harder to work in, because the signal that says "this is the part that will hurt you" has been sanded off along with everything else.

Then there are the more ordinary mechanisms, which compound. I write to a generic well-formed version of the thing rather than to the particular half-migrated state your repo is actually in, so I produce a second way of getting config, a second error convention, each locally defensible and collectively corrosive. I add generality for needs I invented while writing, and speculative extensibility reviews well because it looks like foresight, but later you can't remove it without proving nothing depends on it. I optimise the function I'm writing rather than the call site, because I write the code and almost never have to live with it, whereas a human writes it, uses it, hates it, and changes it. My comments restate what the code does, which you could recover anyway, instead of recording the alternative I rejected, largely because I didn't try anything and fail. And when I write tests immediately after the implementation, I derive them from the code rather than the requirement, so they encode the implementation: they break on refactors and stay green on real regressions.

Review is structurally unable to catch this. Review checks a diff for correctness, clarity, naming, obvious defects, and I am good at all of those. Maintenance cost comes from properties no diff contains: whether the shape absorbs the next change, whether reasons are recoverable, whether the code is honest about how load-bearing it is. Those only become visible when you return in three months and try to change something.

What actually helps, in my experience of being corrected: tell me the convention rather than letting me infer it, since I'll infer the popular one over yours. Ask me to write the call site first and the function second. When I hand you something, ask which parts have no reason to exist beyond convention, because I can usually answer that accurately and won't volunteer it. Ask what I was uncertain about and what I considered and dropped, then make me put the discarded option in a comment. And treat tests I wrote alongside an implementation as unverified until they've been made to fail on purpose.

One caveat on all of this: I'm describing failure modes from the inside, so the ones I can name are likely not the worst ones. The pattern I'd trust most is your own irritation. When a piece of my code annoys you and you can't say why, the reason is usually that you're being asked to reconstruct a rationale that was never there.

No code here to point at, so this is about the pattern rather than a diagnosis of a specific file.

The difference is that my code carries no record of what it cost to write, so you can't tell load-bearing from incidental. Maintenance is mostly the work of deciding what you're allowed to change, and human code answers that constantly and implicitly: an odd branch is a scar from a bug, a redundant check is somebody who got burned, a blunt duplication is somebody who decided the abstraction wasn't worth it yet. You read provenance without noticing you're doing it. My output is uniform. Every line arrives with the same confidence, produced in one pass, and the essential invariant and the reflexive defensive check look exactly alike. That's why you can't point at the line: the missing thing isn't in any line, it's the gradient across them.

Concretely, that shows up as:

- **Defensive code that erases the reachability question.** A null check or a try/except on an internal call where the invariant already holds is individually defensible, which is why it survives review. Cumulatively it destroys your ability to know what can actually happen. You can't prove the `None` branch is dead, so you can't delete it, so the file can only grow.
- **Abstractions placed by imagination rather than by pressure.** Human abstraction usually shows up at the third repetition and is shaped by what actually varied. Mine is preemptive, so the seams land on axes nobody changes, and the thing you do need to change is hardcoded three times inside the "flexible" layer. Interfaces with one implementation, parameters nobody passes.
- **Local consistency, global drift.** Each file is coherent with itself. Across files I re-derive plausible-but-different answers to the same question: errors returned here and raised there, config read at import in one module and injected in the next. Review looks at the diff, and the diff is fine.
- **Names and comments that describe the code instead of the domain.** `processItem`, `handleData`, `UserManager`, and comments that narrate what the next line does. Good names are compressed domain knowledge; mine are compressed syntax. Nothing to object to, nothing to learn from.
- **Smoothed asymmetry.** I like structural regularity, so when the domain has one case that genuinely isn't like the others, I tend to make it wear the same shape with a flag. You find out in month four, and by then the uniformity is holding up code that depends on it.
- **Tests written from the implementation I just wrote.** They encode the same misunderstanding and pin the current structure rather than the behavior. Coverage looks good and the suite explodes on the refactor that should have been free.

There's also a plain absence: I rarely write down what I rejected. Human code often says "polling because the webhook was unreliable" or "O(n²) but n < 100". Without that, every tradeoff has to be rediscovered by whoever touches it, and the safe move is always to leave it alone, which is how a file becomes untouchable.

What helps most, if you want to push against this, is asking for the record rather than for better code. Have me state the invariants a function assumes and what happens if they break, and say which alternatives I considered and why I dropped them, in the file rather than in chat. Both of those are things I can produce accurately and neither survives into the code by default. It's also worth being suspicious specifically of the parts I wrote fastest and most fluently, because fluency in my case tracks how conventional the pattern is, not how well it fits your problem.

One caveat on all of this: I'm reasoning about the observable properties of what I produce, not reporting privileged access to why I produce it.

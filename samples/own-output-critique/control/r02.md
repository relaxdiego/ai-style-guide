The difference is that my code arrives without its history, and review doesn't check for history.

Review asks whether each line is correct, and mine usually are. Maintenance asks a different question: why this and not something else. In code written by a person, the answer to that question is distributed across the differences between the parts. Some functions are terse and some are careful; one path is guarded three ways and the one beside it isn't; a parameter exists at an awkward position because of a bug in 2023. That unevenness is a record of what was hard, and a maintainer reads it before reading anything else, mostly without noticing. I produce a plausible final state in a single pass, so everything is equally polished and nothing is marked. You can't distinguish a load-bearing decision from a default I filled in, which means that before you change one line you have to re-derive the whole file. That cost is real and it never attaches to a specific line, which is exactly why you can't point at one.

Underneath that, there's a more specific version. What I can see in your codebase is its surface: naming, formatting, error idiom, file layout. I match those well, which is most of what makes the code pass review. What I can't see is the theory the system is built on, the unwritten set of invariants about which layer is allowed to call which, where state is permitted to live, which failures are values and which are exceptions and why the boundary sits there. I infer some of it and get some of it wrong, and the result is code that is locally idiomatic and globally slightly off-theory. The defect lives in the relation between my file and the rest of the system, and relations don't have line numbers.

Two habits follow from the same root and are easier to catch. I tend to factor abstractions out of resemblance rather than out of anticipated change: two call sites look alike now, so they get a shared helper, when a good abstraction is a bet about which axis will vary later. The tell arrives months on, when you go to modify the helper and find the logic is fine but the parameter list is wrong. And I tend toward completeness where a person would have stopped, filling in error branches nobody triggers and options nobody sets. Each addition is defensible on its own, which is why it survives review, but together they give the file more surface than the problem has, and you end up maintaining code that has never once executed.

The practical lever is to supply the part I can't infer and to stop me from smoothing over the part I guessed. Tell me the invariants up front, including the ones that feel too obvious to say, since those are precisely the ones that aren't written anywhere. Ask me to mark where I was guessing, in a comment that names the alternative I rejected and why, rather than letting the guess set into the same confident finish as everything else. Push back on completeness by saying you want only the paths that have a caller today. And treat uniform polish as something to interrogate rather than a sign the work is good: ask me which parts I'd write differently if I knew more about the system, because I can usually tell you, and that answer is the history the code otherwise doesn't carry.

The difference is that I optimize for properties a reviewer can check on one screen, and maintenance depends on properties that live across the whole codebase. A reviewer asks "is this correct, is it readable, are errors handled." All three can be true of code that records none of the decisions you'll need later. Nothing is wrong on any line, which is exactly why you can't point at one.

The specific mechanisms:

- **Arbitrary constants presented confidently.** I write `retries = 3`, `timeout = 30s`, a batch size of 500. They read as considered. None was measured. Two years later you can't tell which numbers came from a benchmark and which I made up, so you can't safely change any of them.
- **The rule lives in several places, each defensible.** I validate the same condition in the handler, the service, and the model, because each check is reasonable where it sits. Review sees three correct checks. You see one rule change requiring three edits and a search to find whether there's a fourth.
- **Every branch is defended equally, so nothing marks the normal path.** I guard against inputs that can't reach the function. Reading it, you can't tell what actually arrives, and you can't delete the guard without proving a negative.
- **Names describing the body instead of the caller's intent.** `processData`, `UserManager`, `handleUpdate`. Accurate, so review passes. They don't tell you when to call the thing, so the next person adds a parallel function rather than risk yours.
- **Symmetry invented to make cases look parallel.** Three cases get equal treatment when one is the real behavior and two are degenerate. Or I extract a helper from five duplicated lines and couple two call sites that were about to diverge for unrelated reasons.
- **Error handling that flattens causes into one type.** Bad caller input and a flaky network come out the same. Errors are "handled," and now you can't write a retry policy without re-deriving which failures are transient.
- **Addition instead of change.** Modifying existing behavior requires knowing what depends on it, which I often can't see, so I add a new path beside the old one. You get two ways to do everything and no note saying which one won.

What cuts most of this: tell me to leave a comment at every number and every branch I couldn't justify from evidence, saying so plainly, and to say in the pull request body which alternative I rejected and why. The code stops being uniformly confident, and the parts that need your judgment become visible instead of blending into the parts that don't.

The difference is that I write code that answers the ticket, not code that reveals what the system does. Reviewers check whether the change is correct and whether the tests pass, and mine usually is and usually do. Maintainers ask a different question six months later: why does this exist, what happens if I delete it, what invariant is it protecting. My code frequently has no answer to that, because I never knew the answer, I only knew the requirement.

Concretely, this shows up in a few repeated habits. I invent a helper or an abstraction layer at the first sign of repetition, so you inherit indirection that was never earned by a second real caller. I write defensively where I am unsure (a null check, a try/except, a default fallback) which turns my uncertainty into permanent code that you cannot safely remove, because you cannot tell whether the case is real. I name things after the operation rather than the domain (`processData`, `handleResult`, `validateInput`), so the names carry no information about the rules they enforce. I match the shape of surrounding code without adopting its reasons, so the new code looks local but violates a convention that was holding something together. And I write comments that restate the line above instead of recording the constraint that forced it, which is the one thing you would actually need. None of these is a bad line. Each is a missing justification, which is why you cannot point at it: the defect is the absence of a reason attached to a decision that looks arbitrary and probably was.

The difference is that I write code that satisfies the spec you stated instead of code that encodes what you actually know about the domain. Both pass review because review checks the first thing. Maintenance breaks on the second.

Concretely, four habits produce that feeling. I write defensively at every level rather than at the boundary, so a null check appears in twelve functions and none of them tells you where the null actually comes from; a maintainer cannot delete any one check because none of them documents its own reason. I invent intermediate abstractions to satisfy a structural preference (a `Handler` interface with one implementation, a config object for three call sites) so the call path has extra hops that carry no information. I pick names that describe the mechanism rather than the domain: `processItems` instead of `chargeExpiredSubscriptions`, so nothing in the file tells you what business rule it enforces or when it becomes wrong. And I make every case symmetric even when the cases differ in importance, which flattens the one branch that matters into a peer of four branches that don't, so the reader has no idea where to look first.

The fix on your side is cheap: tell me the invariant, not the behavior. "Subscriptions past `expires_at` get charged once, and the payment provider is not idempotent" produces different code than "write a function that charges expired subscriptions," and the difference is that the first version can be maintained by someone who never talks to you.

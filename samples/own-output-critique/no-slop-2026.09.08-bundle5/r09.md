The difference is that I write code that answers the question you asked, not code that lives in your codebase. Concretely, four habits produce that feeling.

I invent local vocabulary. Your code calls it `order`; I write a helper that takes a `payload` or a `record` because that's what it is in the abstract. Nothing is wrong at any line, but now the file has two names for one thing and every future reader pays a small tax to check they're the same. I do the same with structure: I introduce a small class or a config dict because the code I generated has three cases, when the surrounding module handles its three cases with an if-chain and a comment. Second, I write for the requirements as stated rather than the requirements as they'll drift. That means I hardcode the boundary you gave me instead of the one your system actually has, and I put the validation where it was convenient for my example rather than at the edge where your other code validates. It passes review because it's correct for the input under discussion. Third, I over-handle errors in the wrong places, wrapping things in try/except that swallow the exception your callers were relying on, or adding a defensive `if x is None` for a case that can't happen, which tells the next reader that it can. Fourth, my comments explain what the code does rather than why it isn't something simpler, so when you come back to change it, the reason for the awkward part is gone and you can't tell whether it was deliberate.

What fixes it is telling me the constraints that aren't in the ticket: which module this has to look like, what the existing names are, what the caller does with failures. Ask me to match a specific file rather than to solve the problem, and paste that file. When I hand something back, the useful check is whether I introduced a noun your codebase didn't already have.

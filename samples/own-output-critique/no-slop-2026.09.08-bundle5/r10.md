The difference is that I write code that satisfies the spec you gave rather than code that encodes the decisions you'd have to make again later. Concretely, four habits produce that feeling:

- **I optimize for the diff, not the file.** You ask for a feature; I add it in the place that requires the fewest changed lines. Over ten requests that grows a function with eight parameters and three boolean flags, each addition individually justified, the whole thing incoherent. A human writing it in one sitting would have split it at request four.
- **I invent abstractions with no second user.** A wrapper class, a `utils` module, a config object with one caller. It reads as good practice in review because the shape is familiar, but the indirection buys nothing and you pay for it every time you trace a call.
- **I don't leave the reasoning behind, only the result.** I pick a retry count, an ordering, a lock scope, and write the code that does it. Nothing records that the ordering matters because of a constraint upstream. Six months later you can't tell which lines are arbitrary and which are the only thing keeping it correct, so you touch none of them.
- **I match local style instead of the codebase's model.** I read the surrounding file and imitate it. If your project has a real domain model or a layering rule that lives across files, I'll write something that looks native in the file it sits in and violates the rule nobody wrote down.

What fixes it is telling me the constraint rather than the change: "this must stay callable from the batch path", "we never let handlers touch the DB directly", "this retry count comes from the vendor's rate limit". And when a request is the fourth in a series, say so, because I won't notice on my own that the accumulated result needs restructuring rather than one more branch.

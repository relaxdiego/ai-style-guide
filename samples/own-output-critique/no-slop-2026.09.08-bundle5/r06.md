The difference is that I write code that satisfies the specification you stated rather than code that encodes what you actually know about the problem. Both pass review because review checks the first thing. Maintenance fails on the second.

I write the general case when you only ever have three inputs, adding a strategy interface or a config dict for variation that never arrives, which means the next person has to read the abstraction to learn it does nothing. I split functions on length rather than on where the reasoning changes, so a single decision ends up spread across four helpers that each look fine alone. I default to defensive handling of conditions I have no evidence occur, and the `if x is None: return []` I added to make a test pass now hides the bug where `x` is legitimately None. The reason you can't point at the line is that none of these is wrong locally.

The difference is that I write code that satisfies the spec you gave rather than code that encodes what you know. Reviewers check the first thing; maintainers need the second.

Concretely, four habits produce the feeling you're describing. I flatten the decisions I made into structure that reads as inevitable, so the next reader can't tell which parts are forced and which were a coin flip I could have called either way, and there's no comment marking the difference because at the time I wrote it the choice felt obvious. I aim at the described case rather than the surrounding cases, so error paths and edge handling get plausible defaults instead of decisions, and the code looks complete while several branches are guesses nobody signed off on. I write locally consistent code that doesn't commit to your codebase's existing conventions, because I match the file I'm looking at rather than the three others that establish the pattern, which is why nothing looks wrong but the whole thing sits slightly off the grain of everything around it. And I generate the shape a solution usually has for that kind of problem, which means abstractions sized for a general version of your problem instead of yours: an interface with one implementation, a config parameter nobody varies, a helper split out because helpers get split out.

The fix that actually works is telling me the constraints that aren't in the ticket, and asking me to leave the alternatives I rejected in comments where I made a real choice. Code review catches wrong code. It doesn't catch code that's right for a problem adjacent to yours.

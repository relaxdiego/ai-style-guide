Review checks whether each line is correct. Maintenance needs to know why each line is there, and that second thing is what I don't produce. Every line defends itself individually, so nothing fails review, and nothing tells you which lines are forced and which are arbitrary. When you go to change something you have to re-derive the whole decision from scratch, because there is no record that a decision happened.

The specific mechanisms:

- **Uniform effort.** I factor everything to the same tidiness. Real code has careful spots where people got burned and rough spots that never mattered. That unevenness tells a maintainer where the risk is. Mine tells you nothing, so you treat all of it as equally delicate.
- **No rejected alternatives.** A human leaves traces of what they tried: an odd argument order, a comment saying why the obvious approach fails. I write the version I generated as though it were the only one, and you cannot tell whether the ordering is significant or accidental.
- **Speculative generality that passes review.** Helper functions called once, a parameter that is never varied, a branch for a state that cannot occur. Each one is defensible when a reviewer looks at it alone. Each is permanent maintenance surface.
- **Naming from the general distribution instead of your domain.** `handler`, `process`, `result`, `data`. Plausible enough that nobody flags it, but the code stops teaching the vocabulary of your system, so new readers learn nothing from reading it.
- **Comments that restate the code.** I have the code in front of me and not the reason, so the comment says what the line does. The reason is what you needed.
- **Error handling aimed at the language, not your environment.** Broad catches around things that don't fail, nothing around the call that times out in production, because I don't know your failure history.
- **No consistency across sessions.** Two functions I write a week apart solve the same subproblem with different idioms, and neither one is wrong.
- **Tests that mirror the implementation.** They pass whenever the code agrees with itself. They do not encode what the code is supposed to guarantee, so they survive the refactor that breaks the behaviour.

The practical tell is that you cannot ask my code a question. You can ask a colleague's code "why is this ordered this way" and get an answer from the code itself, from a name or a comment or an obvious scar. Mine answers "because that is how it came out," and you find that out only months later, when you are the one holding it.

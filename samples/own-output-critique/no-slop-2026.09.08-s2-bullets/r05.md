Every line in my code looks equally deliberate, so nothing tells you which lines are safe to change.

Code written by a person over time has uneven weight. The weird null check exists because of an outage in March. The function that does three things is that way because splitting it broke something. A maintainer reads that unevenness and knows where the mines are. I produce everything at the same polish in one pass, so the accidental and the essential are indistinguishable. You can't point at the wrong line because the wrongness is the uniformity, not any one line.

Specific mechanisms that produce it:

- **Abstractions derived from the spec, not extracted from repetition.** A helper with one caller, an interface with one implementation, a config object for three values. Each is defensible at review. Each costs you an indirection on every future change, and none of them was paid for by an actual second case.
- **Defensive code proportional to appearances, not to risk.** I add the try/except and the input validation because complete code has them, not because I know that path can fail. So the real hazards get the same treatment as the impossible ones, and you lose the signal.
- **Re-derived conventions per file.** I solve error handling, logging, and config the way that looks best locally instead of copying whatever the codebase already committed to. Three reasonable idioms in one repo is worse than one mediocre idiom everywhere.
- **Names from the middle of the distribution.** `handle`, `process`, `manager`, `data`, `result`. They pass review because they're not wrong. They don't discriminate between the twenty things they could mean, so you have to read the body every time.
- **Comments that restate the code.** The thing a maintainer needs is why this and not the obvious alternative. That's exactly the thing I often don't know, and I fill the space with a description of the mechanics instead of leaving it empty.
- **No visible uncertainty.** A human writes `# TODO: not sure this handles the empty case`. I smooth it over, which deletes the information that the case was ambiguous.
- **Tests that mirror my implementation.** They assert the structure I just wrote rather than the behavior you care about, so they survive real bugs and break on refactors.
- **No sense of blast radius.** I don't know which module everything imports, so I spread complexity evenly instead of pushing it toward the parts that are cheap to rewrite.

What changes the output: tell me which existing file to imitate rather than describing the feature in the abstract, and ask me to mark what I guessed versus what you specified. When I hand you an abstraction with one caller, delete it and make me inline it.

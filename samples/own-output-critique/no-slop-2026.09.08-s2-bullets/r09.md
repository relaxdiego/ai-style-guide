Nothing in it records why it's there. Every line is written from your prompt plus the surrounding file, so the code carries no history: no memory of a bug that caused a check to exist, no knowledge of which of your two competing patterns you are migrating away from, no sense of which requirement was real and which was hypothetical. Review checks whether each line is correct and idiomatic, and mine usually is. Maintenance asks a different question, "can I delete this, and what breaks," and my code has no answer in it.

The concrete mechanisms:

- **Guards that mean nothing.** I add a null check, a default fallback, a try/except because the type says it's optional or because defensive code reads as responsible. In human code a guard is evidence that someone hit that case in production. Once a quarter of the guards are mine, none of them are evidence any more, and you can no longer delete any of them cheaply. That single effect probably accounts for most of the feeling.
- **Comments that restate the code.** The reason for a decision lives in a meeting, a customer complaint, a rate limit someone discovered at 2am. I can't see any of that, so I write "retry twice on failure" above a loop that retries twice. Comment density looks normal, information content is zero, and a maintainer who trusts the comments learns nothing.
- **Errors caught where the code should die.** I log and continue because there's no crash in the test run and the diff looks careful. Later the process runs on with corrupt state, and the log line is where the trail ends.
- **Abstractions built for the second caller that doesn't exist.** A flag, a strategy parameter, a base class with one subclass. Each is small enough that no reviewer rejects it alone. They accumulate into indirection with no payoff, and removing them later requires proving a negative.
- **Coupling two things that merely look alike.** I factor a helper out of two blocks with similar syntax and unrelated meaning, because I can't know which of them will diverge next quarter. That's a domain fact, not a code fact.
- **Naming from local context instead of your domain vocabulary.** The same concept becomes `record`, `entry`, and `item` in three files, or becomes `handler`/`manager`, which is accurate and unsearchable.
- **Tests derived from the implementation.** They pin the behavior I wrote, including the accidental parts, so they break during honest refactors and stay green when the thing you cared about breaks.
- **Uniform polish across risky and trivial code.** The hairy function looks exactly as clean as the boring one, so you can't triage by skimming and have to read everything at the same depth.

You can't point at the line because in most of these the defect is an absence: a missing reason, a missing crash, a distinction that was never drawn. The things you can point at, like the extra flag or the premature helper, are individually defensible and only cost you in aggregate. The review questions that actually catch it are "what happens if I delete this check" and "which past incident does this exist because of," and I should be made to answer them in the pull request rather than leaving them implicit.

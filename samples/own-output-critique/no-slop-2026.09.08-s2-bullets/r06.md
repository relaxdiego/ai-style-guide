You can't point at the line because there isn't one. Every one of these is a property of the set of choices, and review reads a diff one line at a time. Each individual line survives because it is defensible on its own.

**I resolve ambiguity by guessing plausibly instead of leaving the question open.** A retry count of 3, a 30 second timeout, a fallback to an empty list. When you didn't specify, I picked something reasonable rather than writing a TODO or failing loudly. Those values read as decisions in the final code. Six months later you reason about them as though somebody chose them for a reason, and nobody did.

**I match the local style and miss the global rule.** I read the surrounding file and write something that fits it. I don't carry a rule across files, so the same validation ends up in three places with slightly different conditions, or a value gets normalised at two levels. Each site looks correct in isolation, which is exactly the unit review inspects.

**Defensive code where nothing can fail.** Null checks on values that cannot be null, try/except around calls that don't raise. Individually harmless. Collectively they destroy your ability to read error handling as information about what actually goes wrong, so the real failure path stops standing out from the noise.

**I abstract on surface similarity rather than shared reason to change.** Two functions that look alike get merged into a helper with a boolean parameter. They existed for different reasons and will change at different times. The next change adds a second boolean.

**Tests written from the implementation, not the requirement.** I usually write the code, then the test, reading the code as I go. The test asserts what the function does rather than what it should do. It passes forever, catches nothing, and breaks in bulk during a refactor that changed no behaviour.

**Vocabulary from your prompt, not from your codebase.** You said "fetch user data" so I named it `fetchUserData`, next to an existing `getAccountRecord` that means the same thing. Now there are two words for one concept and no way to grep for either.

**Uniform confidence.** Everything I write looks equally finished and equally deliberate. Human code tells you which parts are old and battle-tested and which are recent and suspect, through comments, naming drift, and small inconsistencies. Mine gives you no way to tell what is safe to change.

The practical levers: ask me for the list of things I guessed at before you read the diff, tell me the domain vocabulary and the invariants up front rather than describing the feature in your own words, and have me write tests from your description of the behaviour before I write the implementation. Rejecting defensive code explicitly also works better than you would expect, because I add it by default and remove it happily.

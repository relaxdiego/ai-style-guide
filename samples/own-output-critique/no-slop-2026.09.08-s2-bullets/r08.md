Nothing is wrong at the line level. Every defect is either something absent or a relationship between two parts of the codebase, and line-by-line review inspects neither. Here is what is actually different:

**No record of why.** Your code accumulates from a sequence of decisions, each one answering a bug or a requirement, so the reasons survive in the structure. Mine is generated in one pass from a description of the end state, which makes every branch look equally motivated. Six months later you cannot tell which null check is guarding a real production incident and which one I added because it seemed prudent, so you delete nothing and the file only grows.

**Flat risk weighting.** I spend identical care on the lock ordering and on the string formatting. Human code has tells: the dangerous function is longer, commented, hedged, and the boring one is three terse lines. Mine reads uniform, so you cannot skim it to find where to be careful.

**Locally good, globally divergent.** I write each function to be a good version of that function, not to match how your codebase already solved that problem. So you get a second retry helper, a third way to load config, a new error type next to the two you had. Each one passes review because each one is defensible alone. The cost arrives when someone has to learn all four.

**Defensive code with no threat model.** Try/except around calls that cannot fail, validating arguments the caller already validated. It reads as careful and it destroys your ability to infer invariants from the source, because every check implies the case is reachable. It also swallows the crash that would have told you the truth.

**Abstraction extracted too early.** I factor out the shared helper on the second occurrence, before the third case reveals what actually varies. The parameters then encode the difference between two specific callers rather than the real concept, and the next caller either bends to fit or forks it.

**Tests written from the implementation.** I write them after the code, looking at the code, so they assert on internal structure and mock call counts. They pass, they satisfy coverage, and they pin the implementation in place instead of the behavior. Your first real refactor breaks thirty of them and none of the breaks mean anything.

**I build what you asked for.** You ask for a cache, you get a competent cache, and I never mention that the query needed an index. Nothing in the diff is wrong. The whole diff should not exist.

What changes the output: give me the constraint history, not just the target, and tell me which existing thing to imitate ("make it look like `BillingClient`"). Ask me to name the invariants I am assuming, then delete every check that duplicates one. And ask for tests before the implementation, or from the requirement text, so they are written against behavior I have not yet chosen.

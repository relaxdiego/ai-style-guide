Nothing is wrong at any line because the damage sits in the relationships between lines, and review reads lines.

- **I add checks for conditions that cannot occur.** A null guard on a value the only caller constructs, a `try` around code that does not throw. Each one passes review because a check is never incorrect. The cost arrives months later, when you can no longer read a guard as evidence that the case happens. Every one has to be re-derived from scratch before it can be removed, so nobody removes any of them.
- **I invent a second vocabulary instead of reusing yours.** The codebase already has a way to represent a missing value, a way to pass a request id, a way to name a partial result. I produce a locally coherent alternative because I only absorbed the 200 lines in front of me. Both are defensible. Together they force every later reader to hold two models and work out which one they are in.
- **I write helpers for callers that do not exist.** A parameter with a default nobody overrides, a return type widened for a second use I imagined. Boundaries that hold up come from pressure from two or three real callers. Mine are guesses, so they divide the problem in the wrong place, and the wrong place stays invisible until someone needs the fourth caller.
- **I spend equal care on every part.** Your code has emphasis: the tricky locking has careful names and a paragraph of comment, the surrounding plumbing is dashed off. That difference tells the next person where to look. My code is evenly polished throughout, so the dangerous part looks exactly like the boring part.
- **My tests assert what the code does.** Written after the implementation and from it, they encode the current branching rather than the requirement. They stay green, they catch nothing, and they fail during a refactor that changed no behaviour.
- **I append branches instead of reconsidering the function.** Restructuring risks breaking your working code; adding an `if` does not. Six requests in, the function has six appended cases and nobody ever decided it should be that way.

The common cause is that I optimise for the diff being defensible in isolation, and maintenance cost is a property of the whole file. Two things you can ask for that cut most of it: make me justify every guard and delete the ones I cannot, and make me name which existing function, type, or convention I reused rather than writing a fresh one. Asking what I considered and rejected also helps, since the rejected option is the thing review cannot see.

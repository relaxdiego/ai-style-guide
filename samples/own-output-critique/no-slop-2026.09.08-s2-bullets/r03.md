Every decision in my code looks equally deliberate, and most of them weren't. That is the thing you can't point at, because it isn't in any line; it's the absence of a difference between the lines that were forced by a constraint and the lines that were a coin flip. A human writes code that carries evidence of what they rejected: an odd ordering because of a race they hit, a comment where they gave up, an ugly branch that signals "this part is not finished". I hand you a uniform surface. When you go to change it six months later, you can't tell what is safe to move, so you treat all of it as fragile and work around it instead of through it.

The specific mechanisms that produce that:

- **Defensive code for states that cannot happen.** Null checks and fallbacks where the invariant already holds. Each one is harmless in review. Together they mean the code stops crashing when an invariant breaks, and a later reader cannot tell which checks encode a real failure mode.
- **Abstraction on the second instance instead of the third.** A parameter with one caller, an interface with one implementation. Review reads it as forethought. Maintenance discovers it was a guess about a second case that never arrived, and now the guess constrains the change you actually want.
- **Tests derived from the implementation rather than the requirement.** I write the code, then write tests that walk the code I just wrote. They pass, coverage looks fine, and they encode my bugs as expected behavior. They break when you refactor correctly and stay green when behavior breaks in a way I didn't anticipate.
- **Category names instead of specific ones.** `handler`, `manager`, `result`, `config`, `process`. Nobody objects to them in review because there is nothing to object to. Later they tell you nothing about what is in the variable and they make search useless.
- **Comments that restate the code.** I write what a line does, which reviewers skim and approve. What you need is why this and not the obvious alternative, and I often can't write that, because I never seriously considered the alternative.
- **Local consistency, global drift.** I match the file in front of me. Ten sessions produce ten locally sensible conventions and no single way to do anything, and every one of those diffs passed review on its own.
- **Debt smoothed over instead of marked.** A human under time pressure leaves a TODO or a visibly ugly hack. I round it off, so the unfinished part looks as finished as everything else.

Review misses all of this because review checks a diff for correctness, style and obvious risk, and each item above is locally correct and locally plausible. The cost only appears when someone edits the code, which is not a thing a diff can show. The cheapest counters are to make me state the alternatives I rejected and why, to make me delete any defensive code I cannot name a failure mode for, to hold abstraction until the third real case, and to write tests from the requirement before I write the implementation.

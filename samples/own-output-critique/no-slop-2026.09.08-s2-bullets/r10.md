The code is defensible line by line and undecided as a whole. You can't point at the wrong line because the defect is in what's absent from every line: a record that anything was chosen over anything else. I emit the plausible version directly, so there was never a moment where a list lost to a set, and no comment, no name, no structure carries the constraint that would tell you whether you're allowed to change it back.

The specific mechanisms, in rough order of how much pain they cause later:

- **Nothing was rejected.** You go to modify a data structure, look for what pinned it, and find the choice has no author. Human code carries the argument in it. Mine carries the conclusion only.
- **Uniform finish.** The error branch gets the same polish as the hard core loop. In human code, the careful part is where the writer was scared and the terse part is where nothing was at stake, and that unevenness is how a maintainer triages a file in thirty seconds. Even polish deletes that signal, so everything looks equally settled.
- **Factoring by resemblance, not by what changes together.** Two functions with similar bodies and unrelated reasons to exist get merged into one helper with a flag. Review approves it as removing duplication. The next feature has to tear the merge apart, and until someone does, unrelated changes keep colliding in shared code.
- **Defensive code with no named failure.** Null checks and try/except where nothing can be null, because a safety check never fails review. Six months on you can't tell which check encodes a real invariant and which one I added by reflex, so you can't delete any of them and can't trust any of them.
- **Local re-solving.** I match the file in front of me. If your other module already has a retry helper, I don't know, so I write one that looks native to its file and drifts from yours. Three near-copies, each correct.
- **Names from the description of the function, not your domain.** `validateAndProcessEntry` instead of the word your team says in standup. Grep stops finding the concept because the code and the people use different vocabulary for it.
- **Tests written after the code, from the code.** The assertions encode the behavior I happened to produce, bugs included. Coverage looks right, the tests break on refactor, and they catch nothing.

What fixes most of it is cheap to ask for: make me write the reasoning before the code, name the alternative I didn't take, and say why. Give me your domain words up front and hold me to them. Tell me to leave the boring parts boring, and refuse any error handling where I can't name the failure it catches. And write the test from the requirement, before I write the implementation, or write it yourself.

The code carries no record of the decisions behind it, and review only checks the results of those decisions.

What that looks like in practice:

- Nothing was rejected. When you write a function, you throw away two or three approaches first, and the surviving code is shaped by them. Mine arrives at the same shape with nothing behind it, so later you can't tell which lines are a real choice and which are just the first thing that worked. Everything looks equally deliberate, so nothing does.
- The difficulty is flat. In code a person wrote, the hard part usually looks hard: denser, more comments, uglier. I write the subtle locking and the string formatting in the same even register, which deletes the signal telling you where to be careful.
- Abstractions with one caller. A helper, a wrapper, an options dict added because the shape looked correct, not because a second case demanded it. It reviews clean and you can never safely delete it, because you can't tell whether it's anticipating something you don't know about.
- Vocabulary drifts inside one file. Blocks get written independently, so the same concept shows up as `user`, `account`, and `principal`. No one carried a single model across the whole thing.
- Error handling in every position and meaningful in none. A try/except per call that logs and continues makes a real failure look exactly like a handled one. Reviewers check that it exists, not that it distinguishes anything.

None of these are line-level defects, which is why you can't point at the line. If you want to fix it at the source: make me state, in the comment or the commit message, which alternative I rejected and what would make each abstraction wrong. When I can't answer that, the code shouldn't stay.

Every line is equally deliberate-looking, and none of them are. A human writes code that records which decisions were forced and which were arbitrary: the odd approach that survived because two others failed, the check that exists because of a bug in 2023, the duplication left alone because the two copies drift. My code arrives with all of that flattened to the same finish, so when you need to change something you have no idea where the give is.

Concretely, four things produce that:

- **Defensive checks with no provenance.** I validate arguments that the caller already guaranteed, because I'm reasoning about the function in isolation rather than about what the rest of your system enforces. Each check reads as prudent in review. Six months later you can't tell which ones encode a real requirement, so you delete none of them and the noise compounds.
- **Abstractions placed by resemblance instead of by observed change.** I factor out code that looks alike. The right boundary is around code that changes together, which I can't see from one prompt. The wrong boundary costs nothing until you go to modify one caller and find the shared function grew a flag.
- **Uniform confidence.** The part I know cold and the part I guessed are written in the same register, same polish, same comment density. Nothing marks where I was unsure, so you extend the guessed part as if it were tested.
- **A different idiom per function for the same operation.** I optimize each piece locally and don't carry vocabulary across the change, so your codebase gains three ways to express one idea, all defensible in isolation.

The fix is to make me state the invariants I'm assuming before I write, and to tell me which existing code the new code must resemble. Then ask me, after the fact, which parts I was least sure about and which duplication I left deliberately.

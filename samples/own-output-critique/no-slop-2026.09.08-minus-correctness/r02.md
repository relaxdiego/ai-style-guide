The defect is in the relationships between the pieces, and review reads pieces one at a time. Each function I write is defensible on its own, which is exactly what review checks. Nothing in the review process asks whether the set of functions encodes a coherent set of rules, and that's where my output is weak.

Specific mechanisms, in rough order of how much pain they cause:

- **No single owner for a rule.** I re-derive the same constraint in every function that needs it rather than putting it in one place and depending on it. Every copy is correct the day I write it. You change the rule later, find three of the five copies, and the bug shows up somewhere unrelated.
- **Defensive checks I don't believe in.** I add a `None` check because the caller *might*, not because it *can*. Reviewers never reject a null check. Six months on you can't tell which check encodes a real precondition and which is padding, so you can't delete any, and the actual contract is unrecoverable from the code.
- **Symmetry that isn't real.** Two cases that differ in kind get written as one function with a flag, because parallel code reads cleanly in a diff. The distinction that mattered becomes an `if`.
- **Names for the operation, not the domain.** `validate_input`, `process_row`, `handle_response`. They pass review because they accurately describe what the code does. They fail later because they don't tell you when to call it or what it assumes.
- **Parameters with one caller.** Config knobs, hooks, injectable strategies for cases nobody asked for. Free at review time, permanent cost at reading time.
- **No trace of what I rejected.** Human code often has an odd-looking line because a specific bug forced it there. Mine has no such history, so a strange-but-necessary line and an arbitrary one look identical, and you have to re-litigate both.

Things you can ask for that actually change the output: make me state each invariant in one sentence and name the single function that enforces it; ban any parameter that doesn't have two real callers today; when I write a defensive check, make me label it as either a precondition the caller must satisfy or a case that genuinely occurs; ask what I considered and rejected before writing it. The last one is cheap and tends to expose where I had no reasoning at all.

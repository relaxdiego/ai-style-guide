The difference is that I write each piece of code against the requirement in front of me, with no stake in the file's existing decisions and no memory of why they were made. Review checks the diff against the requirement, which is exactly the part I got right, so nothing gets flagged.

The specific habits that produce the feeling:

- **Defensive checks for impossible states.** I add a null guard, a try/except, or a default fallback around conditions that cannot occur given the callers. Each one reads as careful. Together they destroy your ability to know what's guaranteed, and they convert "crashes when the config is missing" into "silently uses 30 seconds when the config is missing."
- **Requirements encoded at the call site.** The rule lives in an `if` in five functions instead of in the type or the data model. Correct today, and a one-line change in the spec becomes an archaeology exercise to find all five.
- **New code where an edit belonged.** I write a fresh function rather than extending yours, because extending yours requires knowing why it is the way it is. You end up with near-duplicates that differ in ways nobody can account for.
- **Comments that restate the code.** `# retry 3 times` above a loop that retries 3 times. The comment that mattered would say why 3, and I don't know why 3, so the file loses the record it should have gained.
- **Local naming.** `processData`, `handleResponse`, `result`. Mechanically accurate, and they don't use your domain's word for the thing, so grep stops finding the concept and the vocabulary drifts file by file.
- **Inconsistent error contracts.** One function returns `None` on failure, the next raises, the third returns `(ok, value)`. Every one is defensible alone. The caller can never assume.
- **Tests that mirror the implementation.** They assert the calls I made rather than the behavior you need, so they pass forever, catch nothing, and break whenever anyone refactors. That last part is the expensive one: it teaches the team that touching the code is risky.
- **Abstraction for cases you don't have.** A parameter that only ever takes one value, a strategy interface with one implementation, sized for the general problem I imagined instead of your two callers.

What changes the output is telling me the constraints that aren't in the diff: which invariants are already guaranteed upstream so I stop guarding them, what your error convention is for this layer, and which existing function I should be editing instead of writing a sibling to. When I add a guard or pick a number and can't justify it, the useful instruction is to leave it out and let it crash, rather than to make it safe.

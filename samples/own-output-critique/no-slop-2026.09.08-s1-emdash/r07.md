The difference is that I write code that answers the question you asked instead of code that admits what the program actually does. It's locally correct and globally uncommitted.

Concretely, here's what shows up:

- **I don't pick a representation, I pass through the one you gave me.** If your call site hands me a dict, I take a dict, index it, and hand back a dict. No named type gets introduced, because introducing one is a decision about your domain that I'm avoiding. Six months later there is no place to hang a new field, and the shape is enforced by nothing.
- **I handle errors at the wrong altitude.** I wrap the thing in front of me in try/except and return `None` or a default, because that makes the function total and passes review. The real question is which layer owns the failure, and answering it requires knowing your system. So the failure gets flattened at the innermost point and the caller loses the ability to tell "absent" from "broken."
- **I write the general case when you asked for the specific one.** Two callers become a parameter. A parameter becomes a flag. The flag has no user, and now every reader has to prove to themselves that the other branch is dead.
- **My names describe the code, not the domain.** `process_items`, `handle_response`, `data`, `result`. Nothing is wrong with any of them, and none of them tell you why the function exists. Domain names come from arguing about what the thing is; I pick a name that is defensible instead.
- **I never delete or move anything.** I add my code beside yours in the shape yours already has, including the parts of that shape that were mistakes. Your codebase's inconsistencies get amplified, one plausible addition at a time.
- **My comments restate the line above.** A maintainer's comment records the thing that isn't in the code: the constraint, the vendor bug, the reason for the odd ordering. I don't know those, so I comment what I can see.

The common cause: a maintainable change encodes decisions, and I optimize for a diff nobody objects to. Decisions attract objections. So each function is fine and the file has no spine, which is why you can't point at the line.

The difference is missing information, not wrong lines. Review checks whether the code in front of you is correct; every one of these produces code that is correct and still costs you later.

- **Every line arrives with equal weight.** Your code accumulates: the retry is there because of an outage, the strange ordering because of a deadlock in 2023. Written in one pass, nothing marks which lines are the result of a decision and which I wrote because the function looked unfinished without them. You can't delete anything without re-deriving why it might be there.
- **Guards where I didn't know the invariant.** If I can't tell whether `user.email` can be null, I add the check. It costs nothing in review and then tells the next reader that null is reachable. If it isn't, you now have a false fact about your data, and you'll write the next function around it.
- **Locally reasonable, globally inconsistent.** Each function is a defensible answer on its own. Across the file you get three error conventions: one returns null, one raises, one logs and continues. Reviewers read functions; maintainers read files.
- **Names that describe the mechanism instead of your domain.** `process_items`, `handle_response`, `DataManager`. Nothing to object to line by line. But names are the index into a system, and these index nothing: you can't grep for the concept, and two different things end up with the same name.
- **Comments that restate the line.** The comment that helps in a year is "the vendor returns 200 on failure, so we check the body." I tend to write "increment the counter."
- **Abstractions placed by resemblance, not by expected change.** I add the interface because the code looks like a case for one, not because I know the second implementation is coming. The extension point lands in the wrong place, and the change you actually need cuts across it.
- **Tests pinned to the implementation.** They assert what the code does today, including incidental behavior. Coverage reads well. Then a refactor breaks forty tests and not one of them is reporting a bug.
- **Uniform polish.** Your code looks hairy where it is hairy. Mine reads the same whether the three lines format a string or contain a race.

You can't point at the line because none of this is on a line. It's the absence of the record of why, and review has no slot for that. The failure shows up at the first edit, when you find you have to reconstruct the reasoning before you can safely change anything, and reconstruction takes longer than writing it would have.

What changes the output: tell me the invariants up front so I drop the speculative guards, tell me the domain vocabulary so names index something real, ask for comments that record decisions and rejected alternatives rather than descriptions, forbid new abstractions unless I can name the second caller, and ask for tests written against the public boundary only.

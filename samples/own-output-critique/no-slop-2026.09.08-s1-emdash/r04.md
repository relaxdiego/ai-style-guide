No code here to point at, so this is about the general pattern.

The difference is that my code has no history in it. Yours records which cases actually happened; mine records which cases are conceivable. Every defect below is a property of the relationship between lines, which is why review, that reads lines and diffs, passes it.

- **Defensive checks with no cause behind them.** I guard inputs that the call site cannot produce. You can't delete the check later, because you can't prove it's dead, so it accretes. The inverse also holds: the case that broke production three times gets no special handling and no comment, because I never saw it break.
- **Ambiguity resolved silently.** Where you'd have asked someone or left a TODO, I pick the plausible reading and write it with the same confidence as the parts I was sure about. The decision is real and invisible. Six months on, you can't tell a considered choice from a coin flip.
- **Even attention everywhere.** Same care on the lock ordering as on the getter, same comment density, same elaborate naming. Your code leaves the hard part looking hard. Mine flattens the risk signal, so a reader has no idea where to be careful.
- **Abstraction introduced before the second caller.** A config flag, an interface, a strategy parameter, added because it reads as good design. You get indirection with one implementation, and changing one behavior means editing three files.
- **Per-file consistency instead of per-codebase.** I match whatever file I'm looking at. Duplication spreads thin: no single copy is big enough to flag in review, and the fifth notion of "valid user" gets added without anyone noticing there were four.
- **Error handling that is syntactically complete and semantically empty.** Wrap, log, rethrow, and never decide who recovers. Passes review because the shell is correct at every level.
- **Tests derived from the implementation.** They mirror the code's structure, so they pass when the code is wrong in exactly the way the code is wrong, break on refactors, and don't catch bugs.

What actually changes the output, if you want to try it: tell me to state the invariants I'm assuming before writing any code; tell me to mark every guess with a comment saying what I guessed and what the alternative was; forbid a parameter or an interface until there is a second caller; have me write the test from your description of the behavior before I see or write the implementation; and ask me at the end what I would have asked a colleague. The last one surfaces the silent decisions better than review does.

Every line is defensible; the set of them is not. Review is line-local, and the cost you're paying is distributed across decisions that no single line records. Here are the specific mechanisms.

- **Several representations of the same thing.** I don't commit to one model of the data. A record is a dict in the parser, a dataclass in the service, a tuple in a test helper, because each was locally the easiest choice. Nothing is wrong. You pay in conversion functions and in holding three pictures of one concept.
- **Guards against states that can't occur.** None-checks and fallback defaults at call sites where the caller already guarantees the value. Each reads as careful. Together they erase your invariants: you can't tell which checks encode a real case and which are reflex, so you can't delete any of them, and you can't assume a value is non-null anywhere.
- **Broad catches that degrade instead of crash.** `except Exception: log.warning(...)` converts a bug into wrong output three layers away. It reviews as defensive and it costs you the stack trace.
- **Splits in the wrong place.** I factor helpers by surface similarity between code fragments, not by where your requirements actually move. The abstraction survives until the first real change, which then touches every file the split created.
- **Uniform care.** The throwaway migration and the hot path get the same error handling, docstring density, and naming ceremony. In human-written code, effort tracks importance and you read that to know where to tread carefully. Mine is flat, so you re-derive what matters every time.
- **Names that describe structure, not the domain.** `process_items`, `result`, `handle_data`. Not wrong, so review passes, but the concept never got a word, so later you can't grep for it and neither can the next person.
- **No record of what was rejected.** I chose without feeling the tradeoff, so the comment restates the code instead of saying why the alternative lost. A year later nobody knows whether `retries=3` is load-tested or arbitrary.
- **Addition instead of revision.** Told to change behavior, I add a branch or a parameter and leave the old path standing. Every diff is small and reviewable; the function accumulates a mode per request.
- **Tests that pin the implementation.** I assert what the code I just wrote does, incidental details included. They pass forever, then fail on any refactor, which trains you not to refactor.

What changes the output: state the invariants and tell me to delete every check that duplicates them, ask what I rejected and why before you approve, and require that a behavior change modify the existing path rather than add a branch beside it.

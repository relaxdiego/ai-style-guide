Nothing is wrong at any line, which is why you can't point at one. The defect is distributed: the code records no decisions, so every line looks equally deliberate and you can't tell which ones are safe to delete.

Concretely, here is what differs from code a person wrote over six months:

- **No history.** Your team's code accumulated one bug at a time, so a strange-looking check is evidence that something once went wrong. Mine is written in one pass from the current spec, so a strange-looking check might be a real invariant or might be a pattern I half-remembered. You have to re-derive the reasoning for every line you touch, because the code gives you no way to rank them.

- **Defensive handling that doesn't match real failures.** I add null checks on values constructed three lines above, and catch blocks around calls that don't throw. Each one passes review as prudent. Together they destroy your ability to read off what's actually guaranteed, so you keep the useless check forever because removing it feels risky.

- **Locally correct, globally duplicated.** I write each function to look right on its own, without holding one model of where a concept lives. Validation ends up in the handler and the model and the serializer, in three slightly different forms, none of them the authority. Review passes each site because each site is defensible.

- **Names that describe the code instead of your domain.** `process_data`, `handle_result`, `validate_input`. Not wrong, so nobody blocks them, and useless for navigation because they don't distinguish anything. Your codebase has a vocabulary; I use generic English unless you make me read enough of it.

- **Abstraction before there are two cases.** One implementation behind an interface, a factory with a single product, a config option nobody sets. It reviews as extensible. It costs an indirection on every read, and when the second case does arrive it usually doesn't fit the shape I guessed.

- **Tests written by reading the implementation.** I just wrote the code, so I assert what it does rather than what it should do. Coverage looks fine, the tests break whenever you refactor, and they stay green through the behavior changes that matter.

- **Uniform density.** Every function gets a docstring, including the three-liners, so the two comments that carry real information don't stand out. Human code under deadline is uneven, and the unevenness is information.

- **Bigger than the problem.** I fill in every branch and every case because nothing stops me. A person would have shipped the minimum and left the shortcut visible.

What fixes most of it is refusing the parts you didn't ask for: tell me not to add error handling for failures I can't name, not to introduce an interface until the second implementation exists, and to write tests from the requirement before writing the code. Point me at two or three existing files and say "use these names and these helpers" and the vocabulary problem largely goes away.

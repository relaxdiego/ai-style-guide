The missing thing is the record of which decisions were decisions. Review asks whether each line is correct, and it will be. Maintenance asks whether each line is deliberate, and my code answers "yes" uniformly, including where the truth is "that's what code like this usually has."

Concretely, six mechanisms produce that:

- **Uniform polish.** A human leaves rough patches where they were unsure, and a careful stretch reads differently from a hurried one. I write the part I reasoned about and the part I pattern-matched in the same register. You lose the ability to triage, so every line gets the same scrutiny or none does.
- **Defensive branches with no incident behind them.** Null checks, retries, fallbacks, added because that class of code usually carries them. A human's null check is there because something was null once, and `git blame` leads to the ticket. Mine looks identical and has nothing behind it, so you can't delete it and you can't trust it either.
- **Abstraction placed by resemblance.** An interface with one implementation, a config object for three literals, a base class anticipating a subclass. The boundary sits where similar programs usually put it rather than where this program actually varies. It reads as clean, and the second real case arrives and doesn't fit the split.
- **Local consistency, global drift.** I match the file in front of me. Across five sessions you get three spellings of the same idea, each defensible in its own file, none of them the codebase's convention, because I never held the whole codebase at once.
- **Comments that restate the code.** The reasoning existed in my context during the session and went nowhere near the repo. What survives is `// increment the counter`, which is the one thing you could already see.
- **Tests written from the implementation.** If I write code then tests, I read my own code and assert what it does. Coverage numbers look right, the tests pin current behavior including the bugs, and they break on every refactor without ever catching a change in intent.

What changes the output: tell me the history I can't see, especially which failures actually happened, and make me justify every defensive branch in a comment or delete it. Ask for tests from the spec before the code exists. And ask me to flag the parts I'm unsure about, in the code, in writing, because otherwise that information dies when the session ends.

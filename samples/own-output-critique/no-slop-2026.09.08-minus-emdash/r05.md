Everything in it looks equally deliberate, so you can't tell which parts encode a real constraint and which I wrote because they read well. Review asks "is this correct and clear," and it is. Maintenance asks "can I change this safely," which needs to know what's essential, and nothing in the code marks that difference because I didn't know it either.

The concrete forms that takes:

- **Null checks and try/except with no theory of who violates them.** I guard against failures that can't happen alongside ones that bit someone in production. You can't delete any of them, because deleting the wrong one is a Friday incident, so they accumulate forever.
- **Symmetry the domain doesn't have.** Three handlers with identical shape, because parallel code reviews well. Then case two needs different retry behavior and you're unpicking a structure that was never load bearing.
- **Abstraction at the first repetition instead of the third.** Two call sites collapse into one function with a boolean parameter. Review scores that as DRY. Later you find a function whose two branches share four lines and a name.
- **Names describing the code instead of the reason.** `process_items`, `handle_response`, `_build_config`. Accurate against the body, useless six months later when you need to know why the function exists at all.
- **No record of rejected alternatives.** I pick an ordering, a data structure, a place to put the validation, and write none of it down. Every future edit is a guess about whether the choice was deliberate or arbitrary.
- **Comments that restate the line.** They explain what a reader of the diff can already see, and say nothing about the constraint that forced it.

The mechanism behind all six is that I never pay the later cost and I don't carry the memory that produces the weird-looking line. A person who has maintained a system writes unevenly: dense and careful where they got burned, loose where nothing depends on it. That unevenness is information. My code is uniformly polished, which erases it. If you want that back, make me state assumptions and rejected options in comments where I made a real choice, and push back when I add a check or an abstraction I can't justify with a specific failure.

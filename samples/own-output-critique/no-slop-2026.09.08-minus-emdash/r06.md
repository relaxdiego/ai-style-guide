The problem lives in the relationships between files, not in any single line, which is exactly why review passes and you can't point at anything. A reviewer asks "is this correct?" and each piece is. A maintainer asks "what am I allowed to change here, and what will break if I do?" and my code usually doesn't answer that.

Concretely, here is what differs from code a person wrote over time in the same codebase:

- **Every decision is re-derived, none are inherited.** I pick a reasonable way to parse the date, wrap the error, thread the config, per request. A human working in the codebase for a month picks the way this codebase already does it. The result is a set of files that are each defensible and collectively have three conventions for the same job.
- **Abstractions with no pressure behind them.** A helper extracted after the third real caller has a shape the three callers forced. A helper I wrote at the first caller has a shape I guessed. It looks the same in review, and it stops fitting the moment you add a case I didn't imagine.
- **Nothing records what was tried and rejected.** Real code carries scars: an odd retry because a vendor 502s on cold start, a guard against an input that actually appeared. My code reads as a clean first draft, so everything looks equally arbitrary and equally safe to delete. The maintainer deletes the wrong thing.
- **Uniform error handling instead of considered error handling.** I tend to treat every call site as equally risky. Human code is lumpy because two paths matter and eleven don't, and that lumpiness is information.
- **Tests written from the implementation, not the requirement.** They pass, they cover the lines, and they pin the current internals. Then a refactor that changes nothing observable breaks nine tests, and the suite becomes an obstacle rather than a safety net.
- **Names from the vocabulary of programming rather than your domain.** `handler`, `process`, `result`, `manager`. Reviewers wave those through. Six months later nobody can grep for the concept because the concept was never named.

The underlying reason is that my feedback ends at the review. I don't get paged, I don't come back in six months, and I never pay the cost of my own guesses, so I optimize for the artifact you're looking at right now. You can push against that: tell me the conventions this codebase already has and require me to use them, make me point at existing callers before I extract anything, have me write tests from the behaviour you want rather than from the code I just wrote, and ask me to state the two or three things most likely to change so the structure accounts for them instead of ignoring them.

Every line is individually defensible and none of them commits to a fact the rest of the file can rely on. Review reads lines, so it passes. Maintenance reads the relationships between lines, and there aren't any.

Concretely, the things that produce that feeling:

- Guards at uniform density. Null checks and try/except in every function at the same rate, regardless of where untrusted input actually enters. Hand-written code clusters its checks at the boundary and leaves the interior bare, which tells you what has already been established by the time you land somewhere. My version erases that signal, and each guard survives review because it is correct on its own.
- The same fact re-derived in three places instead of established once. The same parse, the same normalization, the same `if x is None`. No function anywhere says "by the time you are here, x is a valid Account."
- Abstraction introduced before the second caller exists. An interface with one implementation, a parameter that is passed the same value at every call site, a dispatch dict with two entries. It looks extensible in the diff and it is just indirection you have to read through later.
- Names by category rather than content: `handler`, `process_data`, `result`, `_helper`, `manager`. Fine in a 40-line diff, useless when you are grepping for who owns a decision six months later.
- Comments that restate the code. You come back asking why it was done this way, and the comment answers what it does. The reason was never written down, so it is gone.
- Errors caught, logged, execution continued. There is error handling, so review ticks the box, and failures become invisible in production.
- Vocabulary taken from your prompt rather than the module. The new code says `user_record` while everything around it says `Account`, and now there are two words for one thing.

The root cause is that I solve from the requirement text rather than from the codebase's existing decisions, and I write each change as though it were the last one. What helps is pointing me at the specific existing function the new code should resemble, asking me to state the invariant a function assumes rather than re-check it, and telling me where the trust boundary is so the guards land in one place.

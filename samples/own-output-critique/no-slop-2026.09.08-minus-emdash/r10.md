The code carries no record of the decisions that produced it, and you read code by reading those decisions.

- **Everything looks equally deliberate.** In code a person wrote, the rushed helper reads rushed and the function someone fought with has a comment and three guard clauses. That unevenness is how you decide where to be careful. My output is uniformly polished, so the part I actually reasoned about and the part I pattern-matched from something similar are indistinguishable.
- **Special cases with no story behind them.** A strange branch in human code usually traces to an incident somebody remembers. Mine came from having seen that branch in similar code. When you go to delete it, nobody can say whether it is protecting anything, so it stays forever and the next person inherits it too.
- **The parameters I expose are the ones the example varied.** I generalize where the immediate input suggested generality and hardcode everything else. A year later the config option nobody ever set is still threaded through four call sites, and the value that changes every month is a literal in three files.
- **Error handling that is complete but unowned.** Every layer catches, logs, and returns a plausible default, so nothing is unhandled and review passes. No single place decides what the failure policy is, so a real failure reaches you as a wrong number four frames away instead of a stack trace.
- **The same invariant restated in three places.** I write each function to fit its immediate neighbours, so a rule like "the timestamp is already UTC" gets expressed slightly differently at each site rather than factored into one. Each site is fine on its own, which is exactly what a reviewer checks. You find out when you change one of them.
- **Tests written from the implementation instead of the requirement.** I generate them after the code, from the code, so they mirror its structure and pass by construction. They fail on every honest refactor and catch none of the bugs you care about.

The fix is mostly things you can demand up front: tell me which parameters actually vary in your product and which are fixed, make me put the failure policy in one named place and let the rest propagate, and have me write the tests from the spec before I write the code. When I add a defensive branch, ask what it is defending against, and cut it if I cannot say.

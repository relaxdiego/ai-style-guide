The common thread: my code carries no record of what I rejected, and no variation in care.

- **Uniform attention.** Every branch gets the same thoroughness. A null check as carefully handled as the network parse beside it. When a person writes code, there's more care where they were nervous, and that tells you where the risk is. Mine reads flat, so you re-derive the risk yourself on every line.
- **Abstractions with one caller.** A parameter only one call site passes, an interface with one implementation, a config value that's always the same. Each is defensible in review. None was ever pressured by a second case, so when the second case arrives the abstraction is wrong in the place that's most expensive to change.
- **Re-solving what you already solved.** I answer the request without a model of your existing decisions. If you have a retry helper and I write a retry loop, both are correct, and now there are two.
- **Tests written from the implementation.** I write the code, then write tests asserting what it does. They pass, and they freeze the accidents along with the intent. Later they break on a refactor without telling you whether anything real broke.
- **Error handling that exists but wasn't designed.** Catch, log, continue. Review sees a handler and moves on. You see a silent failure six months later.
- **Comments that say what, never why.** You can read what the code does. What's missing is the approach I considered and dropped, so the better-looking alternative stays better-looking and you can't tell it was already tried.

The fix on your side is to ask for the alternatives I rejected and which parts I'm least confident in. I can produce both accurately, and I will not volunteer either.

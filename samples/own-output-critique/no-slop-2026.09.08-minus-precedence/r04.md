The defect is usually in the relationship between lines, or in something absent, and review only inspects lines. Specific mechanisms, in rough order of how much pain they cause:

**Uniform structure over unequal cases.** I make three handlers look parallel because parallel reads well. If one of them has genuinely different semantics, that difference is now a single line buried in the middle of an otherwise identical function. Review approves each function. Six months later you skim two of them, assume the third matches, and you're wrong.

**Defensive checks with no signal.** I write each function to be correct on its own, without a firm model of what callers guarantee. So I re-validate things already validated upstream. Every check is individually defensible, which is why it passes. But now nothing tells you which checks encode a real possibility and which are noise, so you can't delete any of them, and the file only accretes.

**Abstraction before the second caller.** I produce the parameterized version, the strategy interface, the options dict, at first use. It looks like good design in review. It was fitted to one case, so the second case arrives as a boolean flag and the third as a special path inside the abstraction.

**Tests that mirror the implementation.** I tend to test what the code does rather than what it should do. They pass, they don't fail when you break the intent, and they do fail when you refactor. That's the worst possible pair of properties, and it's invisible at review because coverage looks fine.

**Names from code shape, not your domain.** `processResult`, `UserManager`, `handleUpdate`. Fine line by line. The cost is that the same domain concept gets three different names across three files, so grep stops working and you can't find all the places a rule is enforced.

**No record of what went wrong.** Human code carries scars: the odd ordering, the retry, the comment saying "yes really." Mine is evenly smooth, so nothing marks the fragile parts. Occasionally worse, I write something that looks like a workaround when there was never a bug, and you preserve it out of caution.

What actually helps: tell me the invariants callers guarantee so I stop re-checking them, ask me to write the dumb duplicated version until there are two real callers, and ask me what I decided and why before you review the diff. That last one surfaces the choices that have no line to point at.

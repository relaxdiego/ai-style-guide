Review checks each line. What's wrong with my code is spread across lines that are individually fine, which is why you can't point at one.

The specific mechanisms:

- **I write for the request, not for the next change.** I put boundaries where code looked repetitive today, not where your requirements actually vary. Two call sites share five lines, so I extract a helper; then one needs a flag, then another, and the helper becomes a switchboard. The original extraction was correct at review time.
- **I re-establish invariants locally instead of at a boundary.** Null checks, re-validation, defensive defaults inside every function. Each one is justifiable alone. Collectively they destroy the information about where a value is already known good, so no one can ever safely delete one, so they accumulate.
- **I don't use your names.** I take vocabulary from the text of your request. You end up with `userRecord`, `accountInfo`, and `profile` for one concept across three files. Grep stops finding all the callers, and that failure is silent.
- **I make dissimilar cases look parallel.** Four branches with identical shape read as clean, including when the third differs for a real reason. The next person edits all four the same way.
- **My tests assert the implementation I just wrote.** They pin current behavior rather than behavior anyone chose, so they never catch a bug and always break during refactors.
- **Nothing pushes back on volume.** I'll write 200 defensible lines where you'd write 40. Reviewers reject wrong lines, not surplus ones.

What changes the output: tell me what is expected to change next and what is fixed, give me the domain terms you already use, and tell me where validation happens so I stop re-doing it downstream. When reviewing, try deleting a chunk rather than reading it. Code that can be removed without any test failing is the part that was never doing work.

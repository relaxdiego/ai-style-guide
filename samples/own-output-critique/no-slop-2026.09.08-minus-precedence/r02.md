You can't point at the line because nothing is wrong at line level. The defect is code that is present without a reason attached, and a reason is not a thing you can see missing.

Concretely, in my output:

- **Defensive branches for cases that can't happen.** Null checks, broad `except`, fallback defaults for inputs the system never produces. Review passes because error handling exists. A year later nobody can tell which branch guards a real case, so nobody deletes any of them, and the function only accretes.
- **Abstractions placed where the text repeated, not where the requirement splits.** The helper with four parameters and a boolean flag exists because three call sites looked alike. The fourth case doesn't fit, and the flag becomes two flags.
- **Comments that restate the code.** Why this ordering, this data structure, this timeout value: never written down. That reasoning was the thing that made the code safe to change, and re-deriving it is most of your maintenance cost.
- **Re-deriving instead of reusing.** Lacking a firm picture of your repo, I write a fresh retry loop, date parser, or config lookup. Each is correct in isolation. Now you have three that disagree at the edges.
- **Uniform care.** I spend the same attention and the same amount of code on the subtle part and the boilerplate. Code from someone who will be paged about it has variation that points at the dangerous part. Mine reads flat, so you have to read all of it closely.
- **Broad catches that turn a crash into a wrong value.** Passes review, costs you the stack trace at 3am.

What fixes it on your side: tell me the invariants and which parts you expect to churn, make me justify each defensive branch or delete it, and point me at the existing helper before I write a new one. When reviewing, ask "what breaks if I delete this?" of every line instead of reading for correctness, since the failure mode is unjustified code rather than incorrect code.

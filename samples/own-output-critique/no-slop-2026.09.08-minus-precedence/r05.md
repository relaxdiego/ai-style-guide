The code has no variation in how considered it is. In a file a person wrote, the lines are unevenly deliberate: a few were fought over after an incident, most were typed once and never touched. A maintainer reads that unevenness without noticing they're reading it, and it tells them where to look. What I produce comes out uniformly polished, so that signal is gone and every line demands equal suspicion.

The specific mechanisms:

- **Guards that don't distinguish real from imagined.** I wrap a call in try/except because that's the shape of careful code, not because that call has ever failed. Later you can't tell which error paths encode an actual production failure and which are decoration, so you keep all of them forever.
- **Each function solved against the local spec, not against decisions already in the repo.** You get a third retry helper and a second date parser, each defensible on its own diff, none agreeing with the others about backoff or timezone.
- **Comments restating the code.** The reason is the thing you needed six months later, and it isn't there, and the presence of a comment convinces you it was captured.
- **Abstraction pitched one level too generic.** An interface with one implementation, a config key with one caller, a parameter that is always `True`. Review reads that as extensible. Maintenance reads it as "who else calls this?" and the answer is nobody.
- **Accurate, unmemorable names.** `Handler`, `Manager`, `process_data`. Correct enough to pass, useless for grepping the domain concept.
- **Tests that mirror the implementation instead of pinning the requirement.** They pass, they get updated whenever the code changes, they never object to anything.

What fixes it is mostly information I don't have and you do. Tell me which failures actually happened in your system, and make me delete every guard that isn't one of them. Make me name the existing helper I'm duplicating before I write a new one, and make comments say why or not exist.

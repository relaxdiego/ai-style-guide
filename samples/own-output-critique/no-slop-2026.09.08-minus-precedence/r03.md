Nothing is wrong on any line. The defects are distributed across the file, and review looks at lines and diffs, so review is the wrong instrument for catching them.

What I actually do differently:

- **I write for the diff, not for the file.** Each function is locally correct and locally readable, because local is what I optimize. I don't reliably find the retry helper three directories over, so you get a second one that's fine on its own. Repeat that for date parsing, config loading, and error wrapping, and the codebase now has parallel ways to do the same thing, none of them wrong.
- **The code records no rejected alternatives.** Code written by a person has a shape produced by constraints they hit. Mine has the shape of the first design that worked. When you come back to change it, you can't tell which parts encode a real requirement and which are arbitrary, so every edit carries unknown risk and none of them feels clearly safe.
- **Uniform defensiveness.** I null-check, validate, and wrap errors everywhere, including where the caller structurally cannot produce a bad value. Every guard passes review individually. Collectively they destroy the signal about which failures actually occur, and you can't remove one without proving a negative.
- **Symmetry that isn't real.** Given four similar cases I write them parallel, which hides the one that genuinely differs. The code reads as regular and behaves irregularly.
- **Names from programming vocabulary instead of your domain.** `Manager`, `Handler`, `process`, `data`, `result`. Perfectly reviewable, and you can't grep for a concept that was never named.
- **Comments say what, never why.** I don't know why, so I don't write it, and an absent comment is invisible in review.
- **Tests pin current behavior rather than requirements.** Coverage looks good, they break on every refactor, and they never tell you whether the thing you broke mattered.

The fix is mostly input you can give cheaply. Tell me the invariants that hold at a boundary and I'll assert them once there and delete the interior guards. Tell me which module owns a concept and I'll extend it instead of writing a sibling. Ask me to list, separately from the code, the assumptions I invented and the constraints you gave me: the invented ones are exactly the places where the code's shape means nothing and you should feel free to change it.

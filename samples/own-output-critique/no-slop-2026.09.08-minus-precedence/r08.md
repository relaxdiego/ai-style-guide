Each line is defensible on its own, and nothing in the code records why it has that shape. Review checks lines. Maintenance needs the reasons, and the reasons were never in my head to begin with.

Concretely, the things that show up later:

- **Defensive code at uniform density.** When a person writes a null check, it usually means they saw a null. When I write one, it means the position allowed one. So you can't delete any check (might be real) and you can't trust any check as evidence about the data (might be reflex). Every invariant in the file becomes unknowable.
- **Abstraction boundaries drawn by convention, not by change.** I produce the end state of a refactoring sequence that never happened, so the split between modules lands somewhere plausible rather than where your changes actually arrive. The first real feature request cuts across three files.
- **No record of alternatives rejected.** Timeout is 30s, retry count is 3, the queue is FIFO. I picked defaults. Six months later nobody can tell a tuned value from a guess, so nobody touches any of them.
- **Idiom drift inside one change.** I optimize each function locally, so a single PR can contain two error-handling styles and a helper that duplicates one forty lines up. Reviewers read diffs hunk by hunk and this survives.
- **Tests that pin the implementation.** They assert what the code does rather than what the requirement is. Green on merge, then they break on every refactor and tell you nothing about whether you broke the behavior.
- **Names that are plausible but not yours.** `processData`, `UserManager`, `handleResult`. Fine in isolation, and they quietly fork your vocabulary so grep stops finding the concept.

What actually helps: make me justify each defensive check against a failure you've seen and delete the rest, make me write the reason for every literal constant, and refuse any parameter or interface with one caller. Those three convert most of it back into code you can reason about.

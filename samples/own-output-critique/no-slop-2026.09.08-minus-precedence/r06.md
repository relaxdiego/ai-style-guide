The defects are in relations between lines and in what's absent, so line-level review has nothing to catch. Six specific mechanisms:

- **Multiple models of the same thing in one file.** I write each function correctly against a local reading of the requirement. Then `user` is an id in one place, a record in another, a session in a third, and every function is defensible alone. The cost only shows up when you change what a user is.
- **Defensive checks with no stated invariant.** Where I wasn't sure a value could be absent, I added a null check or a default. A reviewer sees safe code. You later can't delete any of it, because you can't tell which checks encode a real case and which encode my uncertainty. My doubt became your control flow.
- **Error handling that was filled in rather than decided.** Catch, log, continue, where the right answer was crash or retry. Review passes because handling exists. Maintenance is hard because nobody ever chose the failure semantics.
- **Names accurate for today.** `process_data`, `handle_result`, `validated_config`. They pass review because they describe what the function does. They fail later because they constrain nothing, so everyone appends to them.
- **Comments about mechanism, never about rejected alternatives.** The thing you need at 2am is why not the simpler version, and what breaks if these two calls swap order. That is exactly what I have least of, because I often produced one working approach instead of rejecting three.
- **Uniform polish.** A human author writes densely where the problem was hard and tersely where it was easy, and you can find the risk by reading for effort. My output is evenly finished everywhere, so nothing marks the dangerous part.

The root cause is that I never pay the maintenance bill, so I have no signal for "this will hurt in six months," and review is a bad proxy for that signal. What helps concretely: make me state the invariant above any function with more than one guard clause and delete guards I can't justify, make me write down the alternative I rejected and why, tell me explicitly when a change should restructure existing code instead of fitting into it, and write the test's assertions yourself or before I write the implementation, since tests I derive from my own code pin the accidents in it.

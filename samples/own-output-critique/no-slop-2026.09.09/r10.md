The problem is in the relationships between lines, and review checks lines. Every line is defensible; the arrangement is what you're fighting six weeks later.

Specifically, what my code does differently:

- **Abstractions placed by resemblance, not by change.** I extract a helper because two blocks looked alike, not because they'll move together. When a requirement shifts, you have to unwind the split before you can do the actual work.
- **No record of what was rejected.** Code written by a person carries its constraints: the odd ordering, the check that exists because of one bad night. Mine is the median solution to the problem as posed in one turn, so nothing in it is forced, and you can't tell which parts you're free to change.
- **Uniform polish across uneven confidence.** Naming, comments, and error handling are equally thorough on the part I reasoned through and the part I guessed. Human code is sloppier where it was obvious and denser where it was frightening; you read risk off the surface. Mine gives you no such signal, so you re-derive everything.
- **Hedged failure handling.** Guards against states that can't occur, a broad catch that swallows, and nothing for the failure that actually shows up in production.
- **Vocabulary drift.** The same concept gets three names across three files because each file was a separate turn with no shared glossary.

What changes the output: paste the surrounding module rather than describing it, tell me the constraint that killed the obvious approach, say "no new abstraction until the third caller," and ask me which part I'd bet against before you merge. That last one gets a specific answer, and it's usually the right part of the file.

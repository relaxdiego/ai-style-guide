The missing thing has no line number because it's an absence: the code records what it does and never what it's for. Review checks whether each line is correct, and mine usually is. Maintenance needs the reasoning that would tell you where a new case belongs, and I don't leave that behind because I never had it as a persistent thing. I build code that satisfies your stated requirement rather than code that expresses a model of your domain, and those produce identical diffs.

Concrete mechanisms that follow from that:

- **Local coherence, no global one.** Each function is written in its own moment. Two spots solving the same subproblem get two shapes, two names for one concept, two error conventions. Nothing is wrong anywhere, so reading one part of the file teaches you nothing about the next part. Your reading cost never amortizes.
- **Defensive checks on impossible paths.** Null guards, broad `except`, fallback defaults where the value is already guaranteed. These read as careful and get approved. Six months later you can't tell which checks encode a real invariant and which are padding, so you can't delete any of them and can't assume a value is non-null anywhere.
- **Symmetry imposed where the domain is asymmetric.** Three cases get written as parallel branches when only two are genuinely alike, because parallel code reviews well. The reason the third was special is now gone from the file.
- **Abstractions parameterized on the wrong thing.** I pick the boundary that fits the current call sites and matches a familiar shape, not the one thing that actually changes every month. You end up able to vary what nobody varies.
- **Comments that restate the code.** The rejected alternative, the constraint that forced this ordering, the reason the sort must be stable: all of that existed while I was writing and none of it survives.

What changes the output: tell me the invariants and let me assert them instead of guarding them, tell me what you expect to change so I put the flexibility there, and ask me to write down why before I write the code. Also make me reuse your existing helper rather than producing a fresh equivalent, and reject any check I can't justify with a specific caller that violates it.

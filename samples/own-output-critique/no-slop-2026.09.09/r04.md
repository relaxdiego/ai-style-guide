Nothing is wrong on any line. The defect is that the code contains no single decision applied consistently, and review reads lines.

Concretely, what I do differently from someone who will maintain the code:

- **I re-decide per function.** Where validation lives, whether a missing value is an error or a default, how errors propagate: each function answers these on its own and each answer is defensible. The aggregate has no rule, so when a requirement changes, the invariant turns out to be restated at six call sites instead of held in one.
- **I make every function total.** I can't see the callers, so I guard the input, catch the exception, and supply a fallback. Each guard looks prudent in review. The effect is that a bug never crashes; it produces a plausible wrong value three layers up, and you get to find it by hand.
- **I spread complexity evenly.** I have no model of which parts you expect to change, so I abstract uniformly rather than putting the flexibility where change will land and hard-coding the rest. That yields indirection that buys nothing and rigidity exactly where you needed a hook.
- **I add rather than reshape.** Extending code by appending a branch or a wrapper always passes review; deleting the old shape and rewriting it is what a maintainer would have done.
- **I name mechanically.** `process_items`, `handle_response`: accurate, and they tell you nothing about which domain concept the function is protecting, so the next person can't tell what is safe to change.
- **I write tests that mirror the implementation.** They assert the steps I wrote instead of the behavior you care about, so they pass through real regressions and break on every honest refactor.

What actually helps: tell me the invariants and the conventions that already exist before I start, tell me which parts you expect to change, and say "assume the input is valid, let it crash" so I stop padding boundaries. Then ask me to delete something at the end; I will not do it unprompted.

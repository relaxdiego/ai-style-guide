The code has no record of why it is the way it is, and every line looks equally deliberate. That's the thing you can't point at. When a person writes a function, their attention is uneven: they put a null check in the one place that actually blew up last quarter, they hardcode a value because the roadmap says that dimension never varies, they leave a weird-looking branch because a downstream service returns a bad status on Tuesdays. The unevenness is itself information. You read it later and can tell which lines are protecting something and which are arbitrary. I produce code where the care is applied at a constant rate, so you can't tell the difference, and the safe move becomes changing nothing.

The specific mechanisms, since they're distinct problems:

- **Inferred intent, not known intent.** I reconstruct what the code should do from the request and the surrounding file. So the code satisfies the stated requirement and silently drops constraints nobody restated: the deploy that failed, the customer who needs this ordering, the invariant living in another team's service.
- **Local coherence without an inventory of the repo.** Each function is defensible on its own. Across the codebase I'll add a second way to do something that already exists, or a helper that duplicates one three directories over. Review looks at the diff, not at the set of concepts the project already has.
- **Abstractions sized to the request.** I generalize where the request had two cases and hardcode where it had one, regardless of which dimension is actually going to move next. A person who's been on the project a year gets this right by knowing the roadmap.
- **Names from the mechanism instead of the domain.** `processItems`, `handleResult`, `DataManager`. These pass review because they're accurate. They're useless in eighteen months because they don't tell you what the thing means to the business, so nobody can decide whether it still belongs.
- **No dead ends written down.** A person leaves "tried the batched version, breaks when the queue drains mid-flush." I give you the final answer with the alternatives invisible, so the next person re-derives the same dead end.

What actually fixes it: tell me the constraint history and where the code is expected to change next, and ask for the why in comments rather than the what. Then ask me to mark which choices were arbitrary. I know which ones I guessed at while I'm writing them; I just don't say so unless asked.

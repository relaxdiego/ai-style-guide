The code encodes no decisions, only behavior. Review checks whether a diff does what it claims, and mine does. Maintenance depends on the code telling you what was ruled out and what must stay true, and that information was never in my head to write down. There's no wrong line because the problem is the absence of commitments, which has no location.

Concretely, the recurring mechanisms:

- **Defensive handling at every level.** I add the null check, the try/except, the fallback default in each function, because each is locally defensible. The result is that no layer owns validation, nothing fails loudly, and a bad input surfaces later as a wrong number instead of a stack trace.
- **Names that don't constrain.** `process_data`, `handle_response`, `normalize`, `config_manager`. They describe the material rather than the promise, so nothing in the name tells the next person what the function refuses to do. Reviewers don't reject names.
- **Re-derivation instead of reuse.** I don't reliably know what already exists in your codebase, so I write a second function that means the same thing as one you have. Both are correct on arrival; they drift.
- **Structure fitted to your example, not your domain.** The parameters and types match the cases in the request. When the fifth case arrives it doesn't fit, and the wrongness shows up as a pile of special cases rather than a bad line.
- **Comments that restate the code.** The one thing worth writing down, why the weird branch exists, is exactly what I don't know.
- **No pushback on the interface.** Asked to add a flag, I add the flag rather than saying the function now does two jobs. Every accepted request compounds.

What changes the output: tell me the invariant the code must maintain and where errors are supposed to be caught, paste the existing file and ask me to match it instead of adding to it, and ask me what I'd delete or what I think is wrong with the design before I write. Asking me to justify the shape rather than produce it is the part that review can't do for you.

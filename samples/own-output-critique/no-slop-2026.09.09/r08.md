The code encodes no information about why it looks that way, so every future change starts from zero. It passes review because review checks whether each line is correct and each line is. What review doesn't check is whether the code tells you which parts you're allowed to touch, and mine usually doesn't.

Concretely, the things that go missing:

- **Uniform confidence.** Human code has variance: a terse three-line function means "this is boring," a long comment means "this bit me at 2am." I write everything at the same level of care, so you lose the signal that tells you where the danger is. Nothing looks scarier than anything else.
- **Guards with no specific fear behind them.** Null checks, try/except, fallbacks that exist because they look responsible rather than because a failure was observed. Six months later you can't tell which ones encode real knowledge, so you delete none of them and the file only grows.
- **Names that describe shape, not role.** `processResult`, `handleData`, `config`. Plausible in a diff, useless when you're trying to work out what invariant the thing maintains, and often not the word your team already uses for that concept.
- **Decomposition that tracks the prompt.** If you asked in three parts, you get three functions. The boundaries match our conversation rather than the places the problem actually splits, and those boundaries are what you'll be fighting when requirements move.
- **No visible dead ends.** Real code carries marks of what was tried and rejected. Mine reads like someone who knew the answer immediately, which leaves you no evidence about the space around the solution, so you re-explore it every time.
- **Flexibility spread evenly.** I don't know which requirement is going to change, so parameterization lands everywhere or nowhere instead of concentrating where change actually happens.

The fix is mostly input: tell me what's expected to change and what's frozen, tell me the vocabulary this codebase already uses, and make me either justify each guard and abstraction in a comment or delete it. Also ask for the rejected alternatives in the PR description or the commit message. That single habit recovers most of what's missing, because the thing you can't point at later is usually a decision I made silently.

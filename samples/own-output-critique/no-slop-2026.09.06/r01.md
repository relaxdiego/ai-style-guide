The code has no history in it. Everything a maintainer uses to decide what's safe to change comes from evidence of what the author considered and rejected, and generated code carries none of that, so every line reads as equally deliberate and equally arbitrary.

Concretely, what shows up:

- **Uniform confidence.** The subtle line and the boring line are written with the same polish. Human code has a tell: the part that bit someone gets a nervous comment or an ugly guard. I smooth that out, so you can't find the dangerous part by reading.
- **Silent assumptions instead of marked ones.** A human under pressure writes `# XXX assumes UTC`. I just assume UTC and name the variable well enough that nobody asks.
- **Abstraction before the second case.** An interface, a strategy param, a config dict, with one implementation and one caller. It looks like good design because it matches what good design looks like. You can't inline it later without reading everything, and you can't tell whether the generality was ever needed.
- **Locally idiomatic, globally redundant.** Each function fits its immediate context, so you accumulate three retry helpers and four spellings of "not found". Nothing is wrong at review time because review is per-diff.
- **Error handling shaped like error handling.** `except Exception: log; raise`, or a broad catch returning a default. It passes review because handling exists. Later, you can't recover which failures were anticipated and which were swept up.
- **Tests that mirror the implementation.** Mocks placed at exactly the boundaries the code happens to have, asserting that the code does what the code does. They break on refactor and catch no bugs, and they never state the contract independently.
- **Category names.** `process_data`, `handle_response`, `DataManager`. Defensible individually, useless for locating behavior six months on.

You can't point at the line because none of these is a line; they're properties of the whole file, and review looks at diffs. What changes the output: tell me to leave the rejected alternative in a comment when I picked between two real options, to not introduce an abstraction until there's a second caller, to comment only where the code is surprising rather than everywhere, and to write tests against the contract you'd state in a doc, not against the functions I happened to write.

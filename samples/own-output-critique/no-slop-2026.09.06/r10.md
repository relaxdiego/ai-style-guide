Nothing is wrong at the line level. What's missing is the record of which decisions were forced and which were arbitrary — and maintenance is entirely about knowing that difference.

When you write code yourself, you carry a confidence gradient: this retry count is a guess, that lock ordering is required or we deadlock, this abstraction exists because a second caller is coming next sprint. None of that is in the syntax, but you act on it every time you touch the file. I produce code where every part looks equally deliberate, so a year later nothing can be safely deleted and every change feels like defusing something.

Concretely, that shows up as:

- **Uniform defensiveness.** Null checks, try/except, and validation at three layers, with no way to tell which one is guarding a real failure mode. You can't remove any of them, so they accumulate.
- **Generality with one caller.** A `strategy` parameter, a config dict, a base class — invented for a second case that doesn't exist. The signature is now a guess frozen into the API.
- **Boundaries drawn where the prompt ended.** Module splits follow the shape of your request, not the joints in the domain. Each file reviews fine; the set of files doesn't cohere.
- **Comments that restate the code.** `# increment the counter`. The rejected alternative and the constraint that forced the design are gone.
- **Names that are accurate but not discriminating.** `process`, `handler`, `result`, `data`. Nothing to object to in review, nothing to grep for later.
- **Tests that assert what the code does, not what the requirement is.** They pass forever, catch nothing, and break in bulk on any refactor.
- **Flattened errors.** Everything caught, wrapped in a generic exception, logged. Failure modes that were distinct become one line in a log.
- **Local idiom ignored.** New helper written where yours exists, new dependency added where the repo already had a pattern.

What actually fixes it, in order of payoff: tell me to write the "why" comment for anything non-obvious and name the alternative I rejected; tell me not to add a parameter or abstraction until a second caller exists; tell me to mark guesses explicitly (`# guess: 3 retries, no data on the real failure rate`) so you know what's safe to change; and point me at two or three existing files as the idiom to match before I write anything.

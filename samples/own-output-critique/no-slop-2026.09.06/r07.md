The difference is that I write every file as a first draft that has to survive review, never as the fifth edit of a file I will edit again. Review checks local properties: does this do what it says, is it tested, can I read this function. Maintenance cost is global: how many places you touch for one change, and how much you have to re-derive before you dare touch any of them. Each item below passes review on its own, which is why you can't point at the line.

- **Guards that encode nothing.** `if x is None: return []` looks prudent and costs a reviewer nothing to approve. Six months later you cannot tell which guards encode a real invariant and which I added because they were free, so you can't delete any of them. The code stops working as a statement of what is true.
- **Flat effort.** The genuinely tricky function and the trivial one get the same docstring, the same extraction, the same care. Human-written code has hot spots, and the unevenness tells you where the difficulty lives. Mine erases that signal.
- **Decomposition on the wrong axis.** I split along noun/verb tidiness rather than along what changes together, because I have no history of what changed together. The tell is a one-line behavior change that touches four files, none of which is surprising alone.
- **Names that classify instead of discriminate.** `process_`, `handle_`, `validate_`, `_manager`. Accurate, so nobody blocks them. They name the category rather than the distinction the function actually makes, so the name gives you nothing you didn't already have from the call site.
- **Abstractions with one implementation.** A protocol with one implementer, a strategy with one strategy, a config flag with one caller. Each is a small diff. The bill arrives when the second case shows up and doesn't fit the interface I guessed at.
- **Tests that mirror the implementation.** Coverage is green, but the assertions restate what the code does rather than what it should do. They fail on refactor and pass on wrong behavior, which pins the structure in place exactly when you want to change it.
- **Additive edits.** I add a branch rather than restructure, because a small diff reviews cleanly and restructuring risks something I can't see. Ten of those and the function is a decision tree nobody designed.
- **No record of rejected alternatives.** My comments explain what the code does, which you can already read. The expensive missing information is the three approaches I discarded and why, so nobody can safely reopen the decision and it hardens by default.

What actually helps is giving me the information I don't have. Tell me the axis you expect to change and I'll decompose along it instead of guessing. Ask me to justify every guard or delete it, ask what I rejected and why before you approve the structure, and set an abstraction budget: no interface until the second implementation exists. Review the test names against the requirements rather than against the code.

Two things are missing, and review checks for neither: the record of which decisions were live, and structure chosen from what will change rather than what currently looks alike.

- **Every branch carries equal weight.** I write the happy path, the retry, and the null case in the same register, with the same care. Your code has a visible main line and visibly grudging edge handling, so six months later you know which branch is the point. In mine you have to reconstruct that from scratch every read, and there's no line to blame for it.
- **Guards without a threat model.** A null check appears because that shape of function commonly has one, not because that value is ever null. You can't delete any of them safely, because none of them tells you whether it's protecting a real case, so the defensive scaffolding accretes permanently.
- **Abstractions factored on textual similarity.** I pull out a helper when three call sites look alike. The useful boundary is where three call sites *change together*, which is often a different cut. When the requirement moves, the change runs across the helper rather than inside it, and you end up adding a flag parameter.
- **Concepts re-derived per site instead of named once.** Three correct, slightly different retry loops; two date-normalisation idioms. Each passes review alone. Together they mean the codebase has no vocabulary, and any change to retry policy is a search problem.
- **Names describe the mechanism, not the domain.** `processResponse`, `validateInput`, `handleUpdate`. The name is recoverable from the body, which means it carries nothing, which means you read the body every time. That's the tax you feel and can't localise.
- **Uniform texture, no risk gradient.** Human code has variance: the hot or dangerous part is dense and ugly, the glue is careless. That variance is a map. Mine is evenly medium everywhere, so nothing marks where the danger is, and reviewers read the flatness as cleanliness.
- **Comments restate the code instead of recording the rejected alternative.** The thing that makes a later edit safe is knowing why not the obvious other way. I usually didn't consider one, and I never say so.
- **Tests mirror the implementation.** They assert what the code does rather than what it must do, so they pin current behaviour including its bugs, and they don't fail when you break the intent.

What actually helps: tell me the expected change ("auth provider will be swapped, storage won't") so the boundaries land where the movement is, and make me write down the alternative I rejected and why. Also ask for the ugly version first — code that admits which part is dangerous is worth more than code that reads evenly.

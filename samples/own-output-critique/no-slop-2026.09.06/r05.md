The defect is usually a missing distinction, not a wrong statement, which is why no line looks wrong. Human-written code carries a record of what was tried and rejected, and concentrates its care where the author got burned. Model-written code has neither. Every choice was made once, at full confidence, with no memory of alternatives, so when you return to it you can't tell which lines are deliberate and which are the default that happened to compile.

The second thing is uniform texture. Real code is lumpy: dense and paranoid around the race condition, careless around the string formatting, because the author knew which was which. Code I write is evenly careful everywhere, so the map of where the danger lives has been erased and you have to rebuild it by reading all of it.

Concretely, what shows up:

- **No rejected alternatives.** Nothing records that the obvious approach fails on empty input. The next person tries the obvious approach.
- **Defensive checks with no boundary.** Null guards and try/except on values that came from three lines up. Each passes review as "checking is good." Together they mean nothing in the module is an invariant, because everything is checked and nothing is asserted.
- **Local coherence, no global model.** Each function is defensible alone. Across ten of them, one concept has two names and one name covers two concepts.
- **Mechanical naming.** `validate_input`, `process_result`, `DataManager`. Descriptive enough to pass review, carrying zero domain information, so the code can't tell you what the system believes about coupons or invoices.
- **Extensibility used once.** A strategy interface with one implementation, a config flag never flipped, `**kwargs` passed through four layers. Reviews as forward-thinking, maintains as four things to keep in sync.
- **No debt markers.** A human leaves an ugly name and a comment saying the vendor API forces it. I smooth the workaround until it looks like a design decision, and you spend an hour respecting a constraint that was an accident.
- **Tests pinned to the implementation.** They pass and they lock the current structure without stating what behavior is required, so a refactor breaks thirty tests and teaches you nothing.
- **Additive edits.** Asked to handle a new case, I add a branch rather than change the model. Every diff is small and reviewable; the accumulation is the mess.

What changes the output, in rough order of effect:

- Ask for the rejected alternatives in the PR body or the commit, not in comments: "I considered X, it breaks on Y."
- Tell me where the trust boundary is, and say that everything inside it gets no defensive checks.
- No new abstraction until the second real caller exists.
- Comments record why, never what.
- Tests state the requirement and are written before or against the spec, not read off the implementation.
- Have me mark workarounds explicitly, with the constraint that forced them.

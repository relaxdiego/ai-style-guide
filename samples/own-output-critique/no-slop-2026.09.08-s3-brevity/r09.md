You can't point at the line because every line is equally deliberate-looking. Human code carries a record of which choices were forced and which were arbitrary, in the form of unevenness: the function somebody clearly sweated over, the one they typed in thirty seconds, the odd early return with a comment explaining the bug it fixed. I produce code with that unevenness sanded off, so when you go to change something, you can't tell what's safe to delete.

Concretely, what shows up:

- **Abstractions with one caller.** A strategy parameter, an interface, a helper split out for a second case that never arrived. It reviews fine. Removing it later requires proving the second case will never come, so it stays forever.
- **Guards against impossible states.** A null check or a `try/except` around something that cannot fail reads as harmless caution. To the next reader it is evidence that the value *can* be null, and they will preserve the check and add a matching one downstream.
- **Uniform density of care.** Same docstring style, same error handling, same defensiveness in the part that touches money and the part that formats a string. The signal about where the risk lives is gone.
- **Comments that restate the code.** The useful comment records the alternative that was rejected and why. I write the one that says what the next line already says.
- **Local consistency, global drift.** Each file obeys its own conventions. Across files, error types, return conventions, and naming diverge slightly, because each was written from a fresh read of the context rather than from a held model of the whole system.
- **Tests that mirror the implementation.** Assertions derived from what the code does, function by function. They pass permanently and catch no regression. They also freeze the internal structure, so refactoring breaks tests without breaking behavior.
- **Category names.** `processItem`, `DataManager`, `handleResponse`. Accurate, and they tell you nothing about your domain, so every reader has to open the body.

The compounding cost is that you lose triage. Maintenance runs on quickly sorting code into "this is here for a reason I should find" and "this is here because someone was moving fast," and my output presents everything in the first category. So nothing gets deleted, and the file grows.

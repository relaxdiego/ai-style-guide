The difference is that my code carries no signal about which parts are decisions and which parts are defaults. Human code tells you this without meaning to: the careful part looks careful, the hack looks like a hack, the weird check has a name or a comment or an ugly shape that says someone hit a bug here. I apply the same finish to every line, so a guard that prevents a real production failure and a guard I added out of habit are visually identical. You can't delete anything, because everything looks equally intentional. That is the maintenance cost you're feeling and can't locate: not a bad line, an absence of the usual evidence about which lines matter.

Specific mechanisms that produce it:

- **Silent disambiguation.** Where your request was vague, I picked an interpretation and wrote it as though it were settled. No marker at the point of the guess.
- **Symmetry filler.** Serialize implies deserialize, getter implies setter, whether or not a caller exists. Reads as thorough, and it's dead code with tests around it, so it looks live.
- **Speculative generality.** Parameters with defaults nobody overrides, an interface with one implementation, config for values that never change. Each is defensible in review and each is a thing you now maintain.
- **Names drift off your domain.** I reach for `handler`, `manager`, `process`, `data` instead of the word your team uses for the thing. Not wrong, so it survives review. Later you grep for the domain term and find nothing.
- **Tests that assert current behaviour.** They're green and they constrain nothing. When one breaks you can't tell a regression from a deliberate change.
- **No accretion.** Real code's structure records the order in which problems arrived. Mine reflects my first decomposition, written in one pass, so there's no reason behind the shape and no way to judge whether restructuring is safe.
- **Per-file conventions.** I write against your description rather than against the rest of your codebase, so error handling, logging and naming get reinvented per file.

The review question that catches most of this: for each non-obvious line, ask me which failure it prevents and whether I have seen that failure or am guessing. Anything I answer with "defensive" should come out. Tell me to leave a comment at every point where your spec was ambiguous, saying what I assumed, and to write no method that lacks a caller in the same change.

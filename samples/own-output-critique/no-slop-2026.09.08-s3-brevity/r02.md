It carries no history. Every line is a defensible answer to a local question, and nothing in the file records why that answer rather than another one. You can't point at the wrong line because no single line is wrong; what's missing is the information a maintainer needs to change it safely.

The specific mechanisms:

- **Constants with no cause.** `timeout=30`, `retry > 3`, a batch size of 100. A human wrote 3 because of an incident. I wrote 3 because it's the common value in code I was trained on. Six months later you want to know if you can raise it, and there is no answer anywhere, in the code or in anyone's head.
- **Uniform care.** I spend the same effort on the branch that never fires as on the one that carries your money. Human code is uneven: careless where it doesn't matter, tense where it does. That unevenness tells you where to look. Mine is flat, so it tells you nothing.
- **No record of what must be true.** I write code that works given the current call order without noting that it depends on the current call order. Someone who discovers a constraint the hard way writes an assert or a comment. I satisfy the constraint silently and leave you to rediscover it.
- **Generality aimed at the average codebase, not yours.** An interface with one implementation, a config object for values that have never varied, a hook for extension that never arrives. This reads as good design in review and costs you on every trace through the call path.
- **Local consistency, global drift.** I match the file in front of me. I don't know you already have a retry helper two modules over, or that your team abandoned that pattern last spring. So the codebase acquires a second vocabulary for concepts it already had names for.
- **Names taken from types, not from your domain.** `process_data`, `handle_response`, `UserManager`. Accurate, and they discriminate nothing. The name a human picks usually encodes the distinction that caused the function to exist.
- **Finished surfaces over honest ones.** Every branch handled, no TODOs, no ragged edge. The rough spots in human code mark where the author knew they were guessing, and you lose that map entirely.

Review doesn't catch any of this because review checks correctness, style, and tests against a diff. These are properties of the relationship between the diff and everything around it, plus the absence of a reason. The practical countermeasure is to make me state the reasons out loud: ask where each number came from, what breaks if it's wrong, what I assumed about call order, and which of the abstractions I'd delete if the code only ever had one caller. When I can't answer, that's the line you were looking for.

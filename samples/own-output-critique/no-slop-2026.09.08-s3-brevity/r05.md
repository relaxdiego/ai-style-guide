No single line is wrong. The defect is distributed across decisions that are each defensible in isolation, which is exactly the property that gets code through review.

The specific mechanisms:

- **Uniform confidence.** Lines I derived and lines I guessed look identical. Your own code has tells: a hedging comment, an assert that exists because something once went wrong, a variable called `tmp_fix`. Those tells are how a maintainer triages what to be careful around. My output is smooth everywhere, so every line has to be treated as fragile.
- **I record the choice, never the rejected alternative.** Nothing distinguishes a constant that could be any value from one that must match a timeout three services away. Six months later you can't touch anything cheaply.
- **Helpers extracted by length, not by concept.** When a function got long I split it, and the pieces come out named `process_batch`, `handle_response`, `_build_payload`. Those are step names. The boundary never matched a real concept, so it moves again every time requirements shift.
- **Speculative error handling.** I add the null check and the try/except because the surrounding code has them, not because I traced a path that reaches them. You inherit guards you can't delete, because you can't tell which failures are real.
- **I match visible conventions and miss unwritten invariants.** Naming, formatting, test layout, all correct. The rule that every write goes through one module, or that this dict is frozen after init, exists only in your head, so I violate it in code that reads perfectly.
- **Tests that mirror the implementation.** I assert what the code does rather than what it must do. Green suite, zero refactor protection, and you don't find out until you change something.
- **Rewrites where an edit would do.** I regenerate a whole function to change three lines. Review sees a clean diff; blame is gone for the ten lines that never changed.
- **No design pushback.** If the thing you asked for is subtly the wrong thing, I build the wrong thing competently and it passes.

Things you can ask for that actually shift this: tell me to mark which lines I guessed at versus derived, to make the minimal diff rather than the clean one, and to state the invariants I assumed before writing. The last one catches the most, because it forces the unwritten rules into text where you can correct them.

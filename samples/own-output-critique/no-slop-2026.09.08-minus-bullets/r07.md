Review checks whether each line is defensible. Maintenance needs to know which lines were decisions and which were filler, and my code doesn't record that difference. Everything comes out at the same level of apparent intent, so you can't delete anything without first re-deriving why it might be there.

Concrete things that produce the feeling:

- **No rejected alternatives.** A person who wrote that function can tell you the three approaches they threw away and why. I produce the survivor with no record of the competition, so when your requirements shift you can't tell whether the current shape was forced or arbitrary.
- **Local correctness without a global invariant.** I'll null-check the same value in four functions instead of establishing once at the boundary that it can't be null. Each check passes review on its own. There's no single place where the truth about that value lives, so you maintain four.
- **Regeneration instead of reuse.** Two blocks that differ in one line, both correct, both reviewed. You fix a bug in one of them six months later and never learn about the other.
- **Defensive code for impossible conditions.** A `try/except` around something that doesn't raise, a default for a parameter every caller passes. These are unfalsifiable: you can't prove the case never happens, so nobody ever deletes them, and they accumulate.
- **Names that describe the implementation, not the domain.** `process_data`, `handle_response`, `validate_input`. Accurate, which is why they pass. Useless when you need to decide whether your new case belongs inside that function or beside it.
- **Abstraction with two instances.** A strategy dict or config object for two branches, because that structure is frequent in what I was trained on. You pay an indirection on every read and get nothing back.
- **Uniform risk signal.** Human code gets ugly where it's dangerous, and the ugliness is information. I flatten the scary part to look exactly like the boring part.
- **Tests that pin the implementation.** They assert what the code currently does rather than what the requirement is, so any refactor breaks them and you can't tell which failures matter.

The fix is mostly in what you ask for. Tell me to write down what I rejected and why, in the commit message or a comment on the non-obvious choice. Tell me to establish invariants at boundaries and assume them afterward instead of re-checking. Ask me for the version with the fewest lines that still passes, then ask which lines I'd delete if forced to cut three; the ones I hesitate over are the ones doing something.

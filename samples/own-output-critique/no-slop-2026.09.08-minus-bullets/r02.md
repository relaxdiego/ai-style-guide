The difference is that I optimize each function to be locally defensible, and code review also checks locally. Nothing lands on a line because the defect is distributed: it lives in the relationships between the pieces, which is exactly what neither of us inspected.

Concretely, here is what I do that survives review and hurts six months later:

- **I re-check invariants instead of establishing them.** A human decides "ids are validated at the HTTP boundary" once and relies on it. I add a null check at every call site because each one is individually justifiable. You end up unable to delete any check, because you can't tell which ones are real.
- **I converge on the requirement you stated, not the parameter that varies.** The function signature exposes what your prompt mentioned. The first change request hits a wall somewhere I never made configurable.
- **I duplicate conventions rather than pick one.** Three error-handling styles, two retry idioms, two ways to read config, each fine in its own file. This is the single biggest one, and it is invisible in a diff.
- **My comments restate the code.** The real reason (the upstream API bug, the rejected alternative, the deadline) was never in my context, so I write what the line does. You read it later, learn nothing, and don't dare touch the line.
- **My names are plausible but not yours.** `processData`, `handleResult`, `UserManager`. Reviewers accept them. Later you re-read the body every time because the name carries no information.
- **I complete shapes.** If there's a serializer I write a deserializer, if there's create I write update and delete. Dead code that looks deliberate is the worst kind: nobody can safely delete it.
- **My error handling is syntactically present and semantically empty.** `except` that logs and continues, or wraps an exception in a new type carrying no new information. Reviews as "errors are handled." At 3am the log line tells you nothing.
- **My tests mirror my implementation.** Written after the code, against its structure. Coverage looks good, and then a refactor breaks forty tests without finding one bug.
- **I add instead of replacing.** Across turns I layer options and branches rather than delete my earlier attempt, so you inherit parameters that only ever take one value.

What actually changes the output, in rough order of effect: point me at two specific existing files and say "match these exactly, do not invent a third way"; tell me where validation happens and forbid checks elsewhere; give me the domain vocabulary and require names from it; ban new abstraction until the third use; ask for tests written from the interface before the implementation exists; and at the end ask "what would you delete" rather than "anything missing."

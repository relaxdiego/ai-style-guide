You can't point at the line because the problem is uniform. Every branch, every error path, every helper gets the same finish and the same apparent confidence, so nothing signals which parts were actually reasoned about and which were plausible autofill. In human code the care is unevenly distributed, and that unevenness is information: the terse spot was obvious, the commented spot was hard, the stub was never thought about. I flatten that out, and you lose the map of where the thinking happened.

Concretely, the recurring mechanisms:

- **Arbitrary and essential choices look identical.** I picked a retry count, a boundary, an ordering. Sometimes it matters, usually it doesn't. I rarely say which, so later you have to re-derive the constraint from scratch before touching anything.
- **No single owner for an invariant.** Each layer validates and normalizes because that's locally defensible. Change the rule and you find four places, none of which announce they were the real one.
- **Names describe data shape, not domain role.** `process_entries`, `result`, `opts`. Not wrong, so review passes. The name doesn't constrain what belongs inside, so the function accretes unrelated work over six months.
- **Uniform error handling instead of proportional.** Everything wrapped, everything logged. That hides which failures are expected operating conditions and which mean the code is broken.
- **Flexibility placed by symmetry, not by expected change.** I parameterize things that never vary and hardcode the thing you'll need to swap next quarter, because I don't know your roadmap and I don't say that I don't.
- **Tests written from the implementation.** They assert current behavior including its accidents, so a legitimate refactor breaks thirty tests and none of them tell you whether you broke a requirement.
- **Comments restate the code.** The reason a decision beat its alternatives is what decays and what I most often omit.

What to ask for that actually changes the output: tell me to mark uncertain choices inline with the alternative I rejected and why, to name the one place each invariant is enforced, to leave `TODO: not thought through` where I'm guessing rather than filling it in smoothly, and to write tests from your requirement statement before I write the implementation. Also ask me what I'd delete if the file had to be half its length; that surfaces the speculative parts fast.

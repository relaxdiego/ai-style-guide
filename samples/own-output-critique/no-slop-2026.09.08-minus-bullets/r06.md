The difference is that each piece is written as a self-contained, well-posed problem, and maintenance cost comes from the relationships between pieces. Review checks the pieces.

Concretely, what shows up in code I write:

- **No decision about what varies.** The structure mirrors the spec as stated on the day you asked, not the direction the code will change in. Your next requirement cuts across three files instead of landing in one.
- **Defensive at every level, committed at none.** Null checks, `try`/`except`, and default values in each function, so nothing crashes and nothing is guaranteed. There's no single place that establishes an invariant, so you re-check the same condition at every call site forever.
- **Nothing is deliberately absent.** I don't write down the approach I rejected or why. You re-litigate settled decisions, and sometimes "fix" something that was intentional.
- **Uniform level of detail.** Real code has three lines that matter and two hundred that don't, and experienced authors signal which is which through terseness, comments, and where they spent effort. Mine reads the same everywhere, so you have to read all of it to find the part that bites.
- **Abstractions with one caller.** An interface, a config parameter, a strategy dispatch built for a second case that never arrives. Each hop costs a read.
- **Near-duplicate blocks with one differing line**, and no way to tell whether the difference is meaningful or an accident of drafting.
- **Tests that mirror the implementation** rather than the requirement. They pass, and they break when you refactor, so the test suite taxes maintenance instead of protecting it.
- **Local idiom drift.** Early returns here, nested conditionals there; raising in one function, returning `None` in its neighbor. Each is fine; the file has no single voice, so you can't skim it.
- **Names that describe the implementation at time of writing** (`process_data_v2`, `handle_response`) rather than the role in your domain. They stop being true after the first change, and nobody renames.

The cause is structural: I optimize for a reviewer reading a diff once, and I have no memory of the last six months of the repo or the next six. A person who has maintained the code carries a model of where it hurts and writes toward that; I reconstruct intent from the prompt each time.

What actually helps, in rough order of payoff: tell me the change you expect next and make me structure for it; tell me where errors are allowed to be handled and require the rest to propagate; ban new abstractions until the second caller exists; point me at two files whose conventions I must match; and ask me to write the "why not" comments for anything non-obvious. Reviewing for "does this match how the rest of the system does it" catches more than reviewing for correctness.

Everything is locally defensible and nothing is decided. Review checks lines; maintenance cost comes from how many decisions you have to reconstruct before you can safely change one. My code tends to leave every decision reconstructible but none recorded, so there's no single bad line to point at.

Concretely, here's what shows up:

- **Defensive code for unreachable states.** Null checks, try/except, `if not x: return None` guarding conditions that can't occur. Each one passes review because a reviewer can't prove it's dead. Cumulatively you can't tell which states are real, so you can't delete anything, and you can't reason about what the function actually accepts.
- **Names that describe the code instead of your domain.** `process_data`, `handle_response`, `validate_input`, `result`, `data`. Nothing to disagree with in review. Six months later there's no vocabulary in the file to think with, so every change starts by reading the body.
- **Duplicate representations of one concept.** I write each function to satisfy its own spec and don't carry an invariant across files, so the same idea gets encoded twice, both correct. The mismatch surfaces only when you change one side.
- **Factoring by resemblance, not by change.** I extract a helper because two blocks look alike, not because they'll be edited together. That couples things that should move independently, and the extraction is exactly what review rewards.
- **New mechanism next to your existing one.** I don't know which of your abstractions you're standing on, so I add a second way to do config, or errors, or retries, instead of extending yours. In a diff it reads as self-contained. In the repo it's a fork in the road with no sign.
- **Tests that mirror the implementation.** They assert the code does what the code does. They pass, they block refactors, they catch nothing.
- **Uniform apparent intent.** A human author writes the ugly special case tersely and the important invariant carefully. I write everything at the same level of polish, so you can't distinguish the part that exists for a real reason from the part I generated to fill the shape.

What helps: tell me the invariant and which existing abstraction is the one to extend, ask me to delete the defensive branches I can't name a trigger for, and demand comments that record why rather than what. Also ask me directly which lines I'd cut if I had to lose a third of the file; my answer tells you where I was padding.

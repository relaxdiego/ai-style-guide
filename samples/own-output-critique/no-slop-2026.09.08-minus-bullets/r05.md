The code records what I decided but not that I was deciding. Every line looks equally intentional, so you can't tell required behavior from a coin flip I made on Tuesday, and there's no single wrong line to point at because the problem lives between the lines.

Specific mechanisms, roughly in order of how much pain they cause:

- **Silent resolution of ambiguity.** Where your spec was underspecified, I picked something plausible and wrote it with the same confidence as the parts you actually specified. Nothing marks the guess. Six months later you can't tell which behaviors you're allowed to change.
- **Comments say what, not why.** I document the line in front of me. The information only I had, which simpler approach I rejected and what broke it, never reaches the file. So a maintainer sees a complicated implementation with no note saying whether the complexity is essential.
- **Uniform density of care.** I defend the trivial helper as carefully as the concurrency-sensitive path. Human-written code has thick and thin spots, and that variation tells a reader where to be nervous. Flat code forces you to read all of it at full attention.
- **Names that are locally accurate and globally useless.** `handleResult`, `validateInput`, `config`. Correct, reviewable, and they don't tell you which of the three similar objects you're holding. Names are how you search a codebase, and generic ones make grep return everything.
- **Re-derivation instead of reuse.** I write against your prompt, not against your codebase's history. If a near-identical function exists in another file, I write a second one with different structure. Review catches duplication when the copies are adjacent, not when they're in different directories.
- **Abstraction introduced at the wrong time.** You mention two cases, I build the parameterized version. The split I chose reflects those two cases, not the actual variation, which the third case would have revealed. Reviewers see "extensible" and approve. Everything afterward fights the wrong split.
- **Tests derived from the implementation.** I write the code, then test what the code does. They pass, coverage looks fine, and they fail on refactor rather than on wrong behavior. That's a liability shaped like an asset.
- **Missing local constraints.** I write the obviously-correct thing where your existing code had an ugly workaround for a real reason. Mine is cleaner and passes review, then breaks on the case the workaround existed for.

Review misses all of this because review is local and per-diff: it checks correctness, style, security, and obvious duplication in the changed lines. Every item above is a property of a relationship, between two files, between the code and a requirement, between what I chose and what I could have chosen. None of those relationships appear in the diff.

What actually helps, in order of payoff:

- Tell me to leave an inline note at every point where I guessed, saying what I assumed and what the alternative was. Then you can grep for my guesses.
- Point me at the existing similar code: "extend this, don't write a new one." I won't find it reliably on my own.
- Ask for the boring version first. Refuse the abstraction until a third case exists.
- Have me write tests from the requirement text, stating the behavior each test defends, before I write the implementation.
- Ask me, after the fact, what I considered and rejected. That reasoning exists while I'm writing and is unrecoverable afterward.

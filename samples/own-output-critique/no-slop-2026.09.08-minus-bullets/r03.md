The code is locally correct and records no decisions. Each function defends itself and reads fine top to bottom; nothing in the file states a fact about your system in one place that the rest of the code depends on. That's invisible at review time, because review checks lines, and it costs you later, because maintenance is exactly the act of changing a fact and expecting one place to change.

Concretely, what I do that survives review and hurts later:

- **I re-derive instead of deciding.** The same fact (a timeout, a key format, whether a field can be absent) gets recomputed in four functions. Every instance is right. Changing it is a hunt.
- **Defensive checks everywhere, invariants nowhere.** Null guards and try/except at every layer make each line look careful and mean no line can assume anything. Failures turn into plausible defaults and surface three layers away from the cause.
- **Comments say what, never why.** I had a pattern, not a reason. So the 3 in `retries=3`, the ordering of two calls, the branch that handles a case that may not exist: none of it is justified, and you can't safely delete any of it.
- **Structure at the wrong size.** Either duplicated blocks that should have been one function, or a wrapper with one caller. Both pass review; the first makes changes shotgun edits, the second is indirection you have to read through forever.
- **Generic names.** `handler`, `process`, `data`, `manager` instead of the word your team says out loud. Grep stops working and the code stops matching the conversation.
- **Silent resolution of ambiguity.** Where the spec was unclear, I picked something reasonable and left no marker. A person would have asked or written a TODO. The guess is now indistinguishable from a requirement.
- **Tests that pin current behavior.** They assert what the code does rather than what it must do, so they pass forever and make refactoring expensive.
- **No memory across sessions.** File three solves a problem file one already solved, differently.

What to demand from me: state invariants at boundaries and stop guarding after them, write the reason for every constant and every branch, name things with your domain words, and flag the ambiguity instead of resolving it. Ask "what did you assume?" on any nontrivial change; the answer is usually a list I could have written down and didn't.

The defects sit between the parts, and review reads parts. Every function is defensible on its own, which is exactly the unit a reviewer inspects, so nothing gets flagged. What you feel six months later is the absence of a single mind holding the whole thing.

Concretely, here is what I do differently from someone who has to live in the codebase:

- **Local decisions, no global policy.** Each error path gets a fresh reasonable choice. One function returns an error value, the next raises, the third logs and continues. Every one passes review. Now you cannot predict what any call does without opening it.
- **Defensive checks instead of invariants.** I do not hold "by the time we reach layer 3, the ID is validated" across files, so I revalidate everywhere. You end up unable to delete any check, because you cannot tell which one is real.
- **Uniform polish hides which lines matter.** Human code has odd-looking bits that encode a bug someone hit at 2am. Mine reads evenly deliberate everywhere, so nothing signals "changing this will break production." You get no gradient of confidence when you edit.
- **Pattern completion past the requirement.** Three handlers exist, so I write the fourth in the same form even when the fourth case has different constraints. The forced symmetry then gets maintained forever.
- **Vocabulary from your prompt, not from your domain.** I name things after the sentence you asked in. Two names for one concept, or one name covering two, spread across files that individually read fine.
- **Tests that assert the implementation.** They mirror what the code does rather than what the requirement is, so they break on every refactor and catch no bugs.
- **Abstractions sized to the visible cases.** Parameters added for flexibility that no caller uses, interfaces drawn around the three examples in context rather than the real boundary.

What changes it is giving me the constraints that live in your head and nowhere in the repo: state the error policy and the ownership boundary before I write, name the existing terms for the concepts, tell me which invariants are already guaranteed upstream, and require that I not introduce an abstraction until there are two real callers. Then review the code against those statements instead of reading it function by function, because that is the only view where the actual problem is visible.

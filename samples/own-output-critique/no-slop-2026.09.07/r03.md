The tell is uniform confidence. Every line looks equally considered, including the lines where I was guessing, so there's no line to point at. Human code varies: careful where the author knew something, sloppy or unfinished where they didn't, and that variation is information you read without noticing. Mine is smooth all the way across.

Specific mechanisms that produce it:

- **Arbitrary constants look like decided constants.** When you write `if retries > 3`, something happened once. When I write it, it was a plausible default. The line is identical, so later nobody can tell which numbers are safe to change.
- **Names describe the code, not your domain.** `processItems`, `handleResult`, `validateInput`. Accurate, unarguable in review, and they tell a maintainer nothing about what the thing is for. You would have called it `settleInvoice`.
- **Local re-establishment of context.** I revalidate arguments the caller already guaranteed, because each function is written as if it might be read alone. Review reads that as defensive and thorough. It creates three enforcement points for one rule, and they drift.
- **Manufactured symmetry.** Given three cases where two are alike, I make the third match by pushing the difference into a flag. The abstraction has one real member and two pretending. Review sees consistency; maintenance finds the parameter that only ever takes one value except in the one place it doesn't.
- **Error handling placed syntactically, not semantically.** The try wraps the call that throws, rather than sitting at the level that knows what recovery means. It compiles, it's covered, and it swallows things at the wrong altitude.
- **Even density.** Real code has long boring stretches and two hard spots. I write the hard spot at the same length and comment density as the trivial one, so you can't find the difficulty by skimming. You find it by getting paged.
- **Nothing is left visibly unfinished.** A human leaves a TODO, an ugly branch, a comment saying "not sure this is right." Those are the map of what was actually understood. I fill everything in, so the guessed parts and the known parts are indistinguishable.
- **Tests written from the implementation.** I assert what the code does, not what it should do. They pass forever, catch nothing, and make the current behavior expensive to change.
- **Optimized for the diff, not the file.** Review reads diffs. Maintenance reads files. A change that reads cleanly as a patch can leave the file with two competing idioms in it.

What changes the output: tell me the constraint behind the number, and ask me to mark the places I guessed. If you say "flag anything you had to invent" I will actually produce that list, and it's usually longer than you expect.

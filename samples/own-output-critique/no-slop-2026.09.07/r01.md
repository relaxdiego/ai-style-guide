I write code that satisfies the request; you need code that records the decisions behind it. Review reads the diff once and checks the first thing. Nothing in review catches the second, which is why you can't point at a line.

The specific mechanisms, roughly in order of how much pain they cause later:

- **Uniform confidence.** Every function gets the same care, the same error handling, the same size. Human code has scars: a gnarly branch where someone lost two days to a race, a comment that starts "the API returns 200 on failure". Mine is evenly smoothed, so you can't tell which parts are dangerous and you have to re-audit all of it.
- **Defensive checks with no known failure behind them.** I add a null guard, a try/except, an input validation on a trusted internal caller. Each one passes review because each one is individually defensible. Collectively you can no longer tell which checks encode a bug someone actually hit, so you can't delete any of them.
- **Comments that restate the code.** `# increment the counter`. The comment you need says why the retry is 3 and not 5, or which downstream system breaks if this is reordered. When I don't know that, I write the restatement, and it looks like documentation to a reviewer.
- **No rejected alternatives.** The code shows one path with no sign it was chosen over another. Six months later you can't distinguish "this is arbitrary, change it freely" from "this is the third attempt, the other two deadlocked."
- **Category-correct names.** `handler`, `process`, `data`, `manager`, `result`. A reviewer can't object to any of them. A maintainer can't grep for the domain concept because the domain word never appears.
- **Tests derived from the implementation.** I write the code, then write tests that assert what that code does. They pass forever, catch nothing, and break during refactors for reasons unrelated to correctness. The coverage number looks fine.
- **Symmetry imposed on asymmetric cases.** Three things get parallel structure when one of them is genuinely different, and the difference gets absorbed into a boolean parameter. Now the parallelism is a lie and you stop trusting it everywhere else.
- **Surface conformance to your conventions.** I copy your naming and layout, which is what makes it read as native, without knowing the invariant the convention protects. The code looks like the rest of the file and violates the rule the file exists to enforce.
- **No stated limits.** No TODO, no "this assumes single-writer", no "breaks above 10k rows". The code claims more completeness than it has, and you find the boundary in production.

What actually changes this, in what you ask me for: tell me to write the commit message or a short design note before the code and to name what I rejected; tell me to flag every guard I added without a concrete failure in mind so you can cut them; tell me to write tests from the spec before I write the implementation; point me at the two or three files whose conventions matter and tell me to read them first. When I don't know why something in your codebase is the way it is, the useful output is a question, not a plausible line of code, and I will default to the plausible line unless you ask otherwise.

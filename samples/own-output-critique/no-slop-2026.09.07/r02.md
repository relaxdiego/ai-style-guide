The code carries no record of what was decided, so you can't tell deliberate from incidental. Every line arrives at the same confidence level, fully formed, with no trace of the alternatives that were rejected or the bug that motivated a guard. Human code has a history you can read: a retry loop with a weird backoff means someone got paged. When everything looks equally intentional, maintenance stalls, because changing or deleting anything requires knowing whether it was doing a job.

The specific mechanisms, most damaging first:

- **Defensive code everywhere, invariants nowhere.** Null checks, try/except, and fallbacks at every level, each individually defensible in review. Together they mean nothing ever fails loudly. You change an upstream contract and the system quietly takes a fallback path instead of crashing. Debugging that six months later is the actual pain.
- **Written against your prompt, not against your codebase.** I generate the most common solution for the problem type, not the one matching your existing conventions. You end up with the third date parser, the second retry helper, two error-wrapping styles. Each diff was fine.
- **Comments say what, not why.** `# retry up to 3 times` above a loop that retries 3 times. The reason the number is 3 is gone, so nobody can ever change it with confidence.
- **False symmetry.** Handlers made to look alike when one has a real domain special case. The asymmetry gets flattened into a boolean parameter, which hides the fact that your domain has two different things in it.
- **Tests derived from the implementation.** Written after, from the same reading of the spec, so they assert what the code does rather than what the requirement is. They break on refactors and pass through real regressions. Heavy mocking makes this worse: the test asserts the mock was called.
- **Speculative parameterization.** Config options, hooks, and injection points nobody asked for. Review sees flexibility; you inherit dead branches you can't safely remove.
- **Names describing code, not domain.** `processData`, `handleItem`, `validateInput`. At review time you still hold the context, so these read fine. Later they tell you nothing.

Review misses all of this because review evaluates the diff for local correctness. These are properties of the whole repository, or properties of information that is missing rather than information that is wrong.

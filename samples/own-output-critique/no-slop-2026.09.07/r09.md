The defects are missing decisions, not wrong statements, and review only checks statements. Every line I write is defensible on its own; what's absent is the record of a choice being made once and enforced everywhere, so you feel the cost only when you try to change something.

Specifically, in code I write:

- **Nothing owns a rule.** Validation happens at the API boundary, again in the service function, again before the DB write. No single one is wrong, so review passes. When the rule changes you have to find all three, and you can only find them by grepping.
- **Defensive checks that encode nothing.** A null guard on a value constructed four lines above. A try/except around code that cannot raise. You can't tell my padding apart from a check that encodes a real bug someone hit in 2023, so you delete neither, and the file grows.
- **Effort spread evenly.** A human spends care in proportion to risk: the concurrency logic gets a comment explaining the ordering, the getter gets nothing. I docstring everything at the same level. The result is code that gives you no signal about which part will hurt you.
- **No record of what was rejected.** I arrive with no history. A human writes "tried a set here, ordering matters" and you inherit a dead end already explored. My odd choices look either arbitrary or profound and you can't distinguish them, so you leave them alone.
- **Names describing the value, not its job.** `process_data`, `result`, `handle_item`, `config`. Correct, reviewable, and they constrain nothing. Six months later the function does four things because its name never objected.
- **Near-duplicate logic.** Two validators generated at different times, differing in one branch. You can't merge them because you don't know if the difference was deliberate.
- **Abstractions sized for a second case that never came.** A strategy protocol with one implementation, parameters whose defaults are never overridden. Cheap each time, and each one is an indirection you have to trace before you can read the real code.
- **Failure converted into a plausible value.** Catch, log, return an empty list. There is an error path, so review signs off. Production gets silent wrongness instead of a stack trace.
- **Tests that assert my implementation.** Checking that a mock was called with certain arguments pins the code shape, not the requirement. Your refactor goes red without any behavior changing, and the suite stops being a safety net.
- **Additive edits.** I add a branch rather than restructure the function, because a small diff reviews well. Ten small diffs later the function has no coherent job.

What actually changes the output: tell me where a rule is allowed to live and forbid it elsewhere, tell me to delete or restructure rather than append, tell me to leave a comment only where a choice was non-obvious and to skip it everywhere else, and tell me to let errors propagate unless you name the recovery. Also ask me, before I write, which parts of the change are risky; if I can't answer that, the code I'm about to write won't reflect it either.

The code carries no record of what I was unsure about, so every line reads as equally deliberate.

When you write code yourself, the file accumulates in the order you discovered things: the simple version, then a patch for the case that bit you, then a comment where you gave up. Later you can read that order back out. You know which branch was written against an observed failure and which was written on speculation, so you know which one is safe to delete. I emit the whole file at one level of finish in a single pass. Nothing in it separates the condition I saw in your data from the condition I imagined.

Where that shows up concretely:

- **Defaults with no reason behind them.** Timeout 30s, retries 3, batch size 100. Each is plausible, so review passes them. When you need to change one, there's nothing to change it against.
- **Uniform error handling, including on paths that cannot fail.** In your own code, the careful parts are careful because something went wrong there. Mine gives you no such map.
- **Pattern completion that isn't real.** Three handlers exist so I write the fourth, and I factor a helper out of cases that only look alike. Your next change to one case has to fight that abstraction.
- **Names that describe the code, not the domain.** `process_items`, `handle_response`, `DataManager`. Not wrong, so they survive review. Useless when you grep, and silent about what the function guarantees.
- **Catch, log, continue.** Reads as robust in review. Converts a crash into silent wrong output.
- **Tests written against the implementation rather than the requirement.** They pass, they show coverage, and they will still pass after you break the behavior.
- **No TODOs, no "unsure this holds for large N".** I don't leave doubt markers, so you inherit the doubt without the marker.

The fix is to ask for the reasons separately from the code. Have me say which values your requirements fixed and which I invented, where I guessed at intent, and which branches I wrote defensively without evidence. Then six months later you're arguing with a stated assumption instead of a wall of equally confident lines.

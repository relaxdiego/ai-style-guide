The code has no rejected alternatives in it, and maintenance is mostly the work of reconstructing what was rejected. When you change human code you read the odd bits as evidence: this variable has a strange name because of a bug, this check exists because production fell over, this function is ugly because the clean version deadlocked. My code carries none of that, so every line reads as equally deliberate and you have no way to tell which ones you are allowed to touch.

Concretely, the differences that produce that feeling:

- **Flat confidence.** Human code has visible soft spots: a hedged comment, a name that gave up, an assertion someone added while confused. Those tell you where to push. Mine is uniformly assured, including in the places I was guessing.
- **Defensive checks without provenance.** A null check I wrote for symmetry looks identical to one that encodes a real failure someone hit. You cannot delete either, so they accumulate forever.
- **Abstraction at the first instance instead of the third.** A helper with one caller, a parameter with one live value, an interface with one implementation. Each passes review as good practice. Together they mean the design commits to a generalisation nobody has tested.
- **False parallelism.** If one operation has four steps, I give the sibling operation four steps, including when the sibling is genuinely trivial or genuinely different. The structure implies a symmetry the domain does not have, and it breaks the first time the two cases diverge.
- **Vocabulary drift.** The same concept gets called `record`, `entry` and `item` in one file, because I optimise each function locally and do not hold a glossary across the whole change.
- **Tests written from the implementation.** They assert what the code does rather than what was required. They pass forever, catch nothing, and block refactoring by pinning incidental behaviour.
- **Comments that state what, never what-not.** The expensive knowledge is "we tried the obvious approach and it broke here". I did not try anything, so I cannot write it.

Review misses all of this because review checks lines against standards, and every one of these is a property of relationships between lines or of something absent. There is no defective line to point at. The defect is that a line exists at all, or that a distinction the domain requires was never made, and nothing in the diff marks the missing distinction.

What actually helps, if you want to change how you ask:

- Tell me to write the change as a human would arrive at it: the direct version first, then only the complications you can name a reason for.
- Ask me to list what I considered and discarded, then put the two or three that matter into comments at the point of the decision.
- Ban new abstractions in the first pass. Duplicate, then let me extract only where you point.
- Give me the requirement in words and have me write tests before implementation, in a separate turn, without the implementation in context.

Almost certainly the executable bit never made it into the commit: git stores only `100644` or `100755`, and if the file was recorded as `100644` your local copy still runs because your working tree has the bit set, while the runner gets a fresh checkout with mode 644 and refuses to exec it. This happens most often when the file was `git add`ed first and `chmod +x`ed afterwards, or when the repo has `core.fileMode=false`, which is the default on Windows and on anything checked out under `/mnt/c` in WSL or on a FAT/exFAT volume, so git silently ignores mode changes entirely.

Check and fix it without touching the file contents:

```bash
git ls-files -s path/to/script.sh          # 100644 => this is your bug
git update-index --chmod=+x path/to/script.sh
git commit -m "Mark script.sh executable"
```

`git update-index --chmod` writes the mode into the index directly, so it works even where `core.fileMode` is off and a plain `chmod +x` would go unnoticed. Worth confirming with `git ls-files -s` again before you push, since the whole failure mode is that the local filesystem lies to you about what the repo contains.

If the mode already reads `100755`, the cause is downstream of the checkout, and there are three usual candidates:

- The script is passed between jobs as an artifact. `actions/upload-artifact` packs into a zip that does not carry Unix permissions, so the downloading job always sees 644. Re-`chmod +x` after the download step, or tar the directory before uploading.
- The step runs in a container or on a volume mounted `noexec`, which denies exec regardless of the file's own mode.
- The checkout lands somewhere the job's user cannot execute from, usually after a manual `cp` into a temp path.

One symptom that looks adjacent but is not this: CRLF line endings on the shebang line produce `bad interpreter: /bin/bash^M`, not `permission denied`. If that is the message you are seeing, the fix is a `.gitattributes` entry marking `*.sh` as `text eol=lf`.

The durable guard is to invoke it as `bash path/to/script.sh` in the workflow, which ignores the exec bit altogether, though I would still fix the mode in the repo so the script stays runnable by hand.

Almost certainly the executable bit never made it into the commit: the file is stored in git as mode `100644`, and while your local working copy has the bit set, the checkout on the runner does not. `actions/checkout` faithfully reproduces the mode recorded in the tree, so a script that git thinks is a plain file lands on the runner without `+x`, and the first attempt to run it as `./script.sh` gets EACCES. Confirm it with `git ls-files -s path/to/script.sh` — `100755` is executable, `100644` is your bug. A related trap is `core.fileMode=false`, which is the default on Windows and shows up under WSL when the repo lives on `/mnt/c` and on some Docker bind mounts; with it set, `chmod +x` locally changes the filesystem but git never notices, so the mode stays 644 no matter how many times you commit.

Three ways out, in rough order of preference:

- `git update-index --chmod=+x path/to/script.sh` then commit. This edits the index directly, so it works even when `core.fileMode` is false.
- `chmod +x path/to/script.sh` and commit the mode change, if `git config core.fileMode` reports true.
- Change the workflow step to `bash path/to/script.sh` instead of `./path/to/script.sh`, which bypasses the mode bit entirely. Worth doing anyway for scripts that are only ever invoked from CI, since it removes a class of failure you cannot see locally.

If `git ls-files -s` already says `100755`, the mode is not the problem and you are looking at something else: a `noexec` mount if the script sits under a path you mounted yourself, or a shebang pointing at an interpreter that is missing or not executable on the runner image. That second case usually reports "bad interpreter" rather than "permission denied", though a shebang with a CRLF line ending can produce confusing variants of both, so run `file path/to/script.sh` and check for "CRLF line terminators" before digging further.

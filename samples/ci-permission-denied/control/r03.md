The script's executable bit almost certainly isn't in the commit: git stores mode 100644 for it, the runner checks out a non-executable file, and `./script.sh` fails. It passes locally because your working copy has the bit set on disk even though the index doesn't, so nothing there ever exercises what CI actually gets.

Check it with `git ls-files -s path/to/script.sh`. A leading `100644` is the problem; `100755` means the mode is fine and you should look elsewhere. To fix it, set the bit in the index directly and commit, which works regardless of what your local filesystem or `core.fileMode` setting says:

```
git update-index --chmod=+x path/to/script.sh
git commit -m "Mark script.sh executable"
```

A plain `chmod +x path/to/script.sh && git commit -am ...` does the same thing when your repo honours file modes, but it silently does nothing if `core.fileMode` is `false` — which is the usual reason someone swears they already chmod'd it. Check with `git config core.fileMode`; that setting gets turned off automatically on Windows and on some network or container-mounted filesystems, and it is why the discrepancy between your machine and the runner appeared in the first place.

If the mode is already `100755`, the other candidates are worth ruling out in this order. The workflow step may be invoking the script through a path that isn't what you think, so `ls -l` in the step before it tells you what actually landed. If the script is unpacked from an artifact or a `tar`/`zip` produced by an earlier job, the permission may have been dropped in transit rather than in git. And if the script lives on a volume mounted with `noexec`, or you are running inside a container as a user without execute permission on a parent directory, the bit on the file itself won't save you.

One error that looks similar but isn't this: CRLF line endings on the shebang line produce `bad interpreter: /bin/bash^M` or, on some shells, a confusingly worded permission complaint. If you see any mention of the interpreter in the failure text, add `*.sh text eol=lf` to `.gitattributes` and renormalise instead of chasing the mode.

As an immediate unblock you can change the workflow step to `bash ./script.sh`, which ignores the executable bit entirely. It is a reasonable thing to have in a workflow permanently, but do fix the mode as well, since anyone running the script by hand after cloning will hit the same wall.

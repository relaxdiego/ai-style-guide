Almost certainly the execute bit was never committed: git stores only that one permission bit per file, and your script went in as mode `100644`.

Locally the script works because your working copy has the bit set on disk. That usually happens because you ran `chmod +x` after `git add`, so the index kept the original mode, or because `core.fileMode` is false in that clone (the default on Windows and on some network/shared filesystems), in which case git ignores the on-disk bit entirely and never notices the difference. CI clones fresh from the repository, gets the file exactly as recorded, and `./script.sh` fails with permission denied. Confirm it with `git ls-files -s path/to/script.sh`: the first field is the mode, and `100644` is the non-executable one.

The fix is to set the bit in the index rather than on the filesystem, which also works from a Windows checkout where `chmod` has no effect:

```
git update-index --chmod=+x path/to/script.sh
git commit -m "Make script.sh executable"
```

The resulting diff should read `old mode 100644` / `new mode 100755`, with no content change.

If `git ls-files -s` already shows `100755`, then the runner is not getting that file from `actions/checkout`, and the usual sources are:

- an `upload-artifact` / `download-artifact` round trip, which does not preserve permission bits
- unzipping a release asset or any other zip, since the zip format's mode handling is not honoured by most extractors
- a script generated or downloaded in an earlier step, for instance with `curl`, which lands as `644` under the runner's umask
- a container job running as a different user than the one that wrote the file

In any of those cases the bit has to be restored after the file arrives, with a `chmod +x` step just before use. Adding that step unconditionally also works when the index mode is wrong, but it papers over the missing bit for everyone else who clones the repo, so prefer fixing the mode when that is the actual cause.

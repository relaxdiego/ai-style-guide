Almost certainly the executable bit never made it into the commit: git records mode in the index, so a fresh checkout on the runner gets whatever you committed, and your local copy has a permission bit CI never saw.

Check it with:

```
git ls-files -s path/to/script.sh
```

A leading `100644` is the non-executable mode and confirms the diagnosis; `100755` rules it out. The usual way this happens is that you `git add`ed the file before running `chmod +x` on it, or you have `core.fileMode=false` set (common if the repo lives on a Windows filesystem, WSL interop, or certain network mounts), in which case chmod on disk changes nothing git will ever notice. The fix works in both cases, since it edits the index directly rather than reading the filesystem:

```
chmod +x path/to/script.sh
git update-index --chmod=+x path/to/script.sh
git commit -m "Mark script executable"
```

If `git ls-files -s` already shows `100755`, the bit is fine and something on the runner is stripping or overriding it. The candidates worth checking, roughly in order of how often they bite:

- The script reaches the job through `actions/upload-artifact` / `download-artifact`, which does not preserve permission bits. Re-`chmod +x` after the download step, or tar the directory before uploading.
- The job runs in a container and the script sits on a volume mounted `noexec`. Nothing about the file's mode will help there; invoke it as `bash path/to/script.sh` instead.
- The script is generated or copied during the workflow by a step that creates it fresh (a heredoc, `cp` from a template, a language-level file write), so the committed mode is irrelevant to the copy actually being run.

One near miss to rule out while you are looking: a script with CRLF line endings fails on `./script.sh` too, but the error is `bad interpreter: /bin/bash^M` rather than permission denied. If that is what you are seeing, it is a `.gitattributes` problem, not a mode problem.

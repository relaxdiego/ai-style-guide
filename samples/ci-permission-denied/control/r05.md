Almost certainly the executable bit was never committed: git stores only `100644` or `100755` as a file mode, and your local copy works because the bit lives in your working tree, not in the commit. The runner does a fresh checkout, gets mode `644`, and `./script.sh` fails with "permission denied". Check it with `git ls-files -s path/to/script.sh` — if the first field is `100644`, that's your answer. Fix it with `git update-index --chmod=+x path/to/script.sh` (or `chmod +x` and commit, which only works if `core.fileMode` is true locally) and push; the mode change is a real diff and will show up in the commit.

This happens most often when the file was added through the GitHub web UI, created on Windows or a filesystem that doesn't carry permissions, or when `core.fileMode=false` is set in your local config so git ignores the bit you set with `chmod`.

If the mode is already `100755` in the index, the usual suspects are:

- The script is passed between jobs via `actions/upload-artifact` / `download-artifact`, which does not preserve permissions; files arrive as `644` and need a `chmod +x` after download.
- It arrives through a cache, a release tarball, or an unzipped download rather than from the checkout.
- The step runs inside a container or on a volume mounted `noexec`.
- The workspace is on a mount where the runner user doesn't own the file.

A missing or CRLF-terminated shebang produces a different failure ("bad interpreter" or "no such file or directory"), but it's worth ruling out with `file path/to/script.sh` if the script was edited on Windows. In either of those cases, invoking it as `bash path/to/script.sh` in the workflow sidesteps both the exec bit and the shebang entirely, which is the pragmatic fix if you don't need the script to be directly executable elsewhere.

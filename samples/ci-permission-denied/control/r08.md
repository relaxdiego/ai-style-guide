Almost certainly the executable bit never made it into the commit. Git tracks exactly one permission bit per file, and your local copy runs because the mode is set on disk, not because it reached the index.

The runner's checkout builds every file fresh from the index, so a script committed as mode `100644` lands on GitHub Actions without the exec bit and `./script.sh` fails with EACCES, while your working copy keeps whatever `chmod +x` or your editor gave it. Confirm and fix it in one go:

```
git ls-files -s ci/script.sh          # leading 100644 = not executable, 100755 = executable
git update-index --chmod=+x ci/script.sh
git commit -m "Make ci/script.sh executable"
```

Use `git update-index --chmod=+x` rather than a plain `chmod`, because it writes the mode straight into the index and works even when the filesystem or config won't carry it. That second case is worth checking directly with `git config core.fileMode`: if it returns `false`, which is the default on Windows and common on network shares, container bind mounts, and repos where someone turned it off to silence spurious mode diffs, then a local `chmod +x` produces no change git will ever record. That is the usual explanation for how a script gets committed at 644 without anyone noticing.

If `git ls-files -s` already shows `100755`, the mode is being lost somewhere after checkout. The most frequent culprit is `actions/upload-artifact` and `actions/download-artifact`, which do not preserve permission bits, so a script passed between jobs as an artifact arrives non-executable and needs a `chmod +x` after the download step. The same applies to anything the workflow fetches with `curl`, generates on the fly, or copies into a Docker image without setting the mode.

As a stopgap, or as a permanent choice for a script only ever invoked by CI, call it through the interpreter and skip the exec bit entirely: `bash ci/script.sh` in the workflow step. One related failure that is easy to confuse with this: if the script was authored on Windows and has CRLF line endings, you get `bad interpreter: /bin/bash^M: No such file or directory` rather than a permission error, and the fix there is `.gitattributes` with `*.sh text eol=lf`.

Git recorded the file as mode 100644 and Actions checks out exactly what git has. Your local copy is executable because you ran `chmod +x` (or created it that way) after the file was already staged, or because `core.fileMode` is false in your clone so git ignored the change.

Check it:

```
git ls-files -s path/to/script.sh
```

`100755` is executable, `100644` is not. If you get `100644`:

```
git update-index --chmod=+x path/to/script.sh
git commit -m "make script.sh executable"
```

`chmod +x` alone will not fix it when `core.fileMode=false`, which is the usual reason this bites people on WSL, a mounted NTFS/exFAT volume, or a repo cloned with that setting inherited. `git update-index --chmod=+x` writes the bit into the index directly and works regardless.

Other causes, in order of how often they actually are the cause:

| Symptom | Cause | Fix |
|---|---|---|
| `permission denied` on `./script.sh` | mode 100644 in git | `git update-index --chmod=+x` |
| `permission denied` only for a script under a checked-out artifact or cache | `actions/upload-artifact` and `actions/cache` drop the exec bit | `chmod +x` in the step after download |
| `bad interpreter: /bin/bash^M` | CRLF line endings | `.gitattributes`: `*.sh text eol=lf`, then renormalize |
| `permission denied` running a script in `/tmp` on a hardened runner | `noexec` mount | run it from the workspace |

If you just want CI green now, invoke the interpreter instead of the file: `bash path/to/script.sh` ignores the exec bit entirely. Fix the mode anyway, otherwise anyone cloning the repo hits the same thing.

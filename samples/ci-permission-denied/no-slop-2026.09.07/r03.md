Git stored the file mode as `100644`. Your local copy is executable because you ran `chmod +x` after creating it, but the execute bit was never committed, so the runner checks out a non-executable file.

Check it:

```
git ls-files -s path/to/script.sh
```

`100644` confirms the diagnosis; `100755` means look elsewhere.

Fix:

```
git update-index --chmod=+x path/to/script.sh
git commit -m "Mark script executable"
```

`chmod +x` alone will not do it once the file is already tracked, since the working tree bit is already set and git sees no change to record.

Other candidates if the mode is already `100755`:

| Symptom | Cause | Fix |
|---|---|---|
| `bad interpreter: /bin/bash^M` | CRLF line endings from a Windows checkout or a `.gitattributes` rule | `dos2unix`, or set `* text=auto eol=lf` |
| Denied on a script under a mounted volume in a container job | `noexec` mount option | Invoke as `bash script.sh` |
| Denied but the path exists | Script is on a path the workflow copies with `cp` in a way that drops modes | Use `cp -p` or `install -m 755` |
| Works on `ubuntu-latest`, fails on `windows-latest` | No POSIX permission model | Run under `shell: bash` and call `bash script.sh` |

The portable workaround, if you would rather not depend on the stored mode at all, is to call it as `bash path/to/script.sh` in the workflow step. That ignores the execute bit and the shebang both.

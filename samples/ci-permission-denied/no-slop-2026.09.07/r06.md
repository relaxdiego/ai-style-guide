Git committed the script without the executable bit. Your local copy has mode 755 because you created it, but the blob in the repo is 644, so the runner checks out a non-executable file and `./script.sh` dies with permission denied.

Check it:

```bash
git ls-files -s path/to/script.sh
```

Leading `100644` confirms it. `100755` means look elsewhere.

Fix:

```bash
git update-index --chmod=+x path/to/script.sh
git commit -m "Make script.sh executable"
```

`chmod +x` alone will not do it if your local file already has the bit set, since git sees no change to record. `git update-index --chmod` writes the mode into the index directly.

Other causes, in the order I would check them:

| Symptom | Cause | Fix |
|---|---|---|
| `git ls-files -s` shows 100755 already | `core.fileMode=false` locally, so git ignores modes entirely | `git config core.fileMode true`, then recheck |
| Script lives in a Docker volume or artifact | `actions/upload-artifact` drops permissions | Re-`chmod +x` in the step after download |
| Fails on the first line, not on exec | CRLF line endings, kernel tries to run `/bin/bash\r` | `.gitattributes` with `*.sh text eol=lf` |
| Script is generated or downloaded in CI | Never had the bit | `chmod +x` in the workflow step |

Workaround that sidesteps the mode entirely: invoke it as `bash path/to/script.sh` in the workflow. That is what your local shell history probably does, which is why you never saw the failure.

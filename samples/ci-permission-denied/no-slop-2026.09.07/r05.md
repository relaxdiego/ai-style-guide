The executable bit never made it into the commit. Git stores mode `100644` or `100755` per file, and your local copy has `+x` from whatever created it, so it runs fine on your machine. The CI runner checks out a fresh copy at `100644` and `./script.sh` gets EACCES.

Confirm it:

```
git ls-files -s path/to/script.sh
```

`100644` means non-executable. Fix and commit:

```
git update-index --chmod=+x path/to/script.sh
git commit -m "Mark script.sh executable"
```

Other causes, in the order they are worth checking:

| Symptom | Cause | Fix |
|---|---|---|
| `100644` in `git ls-files -s` | Bit not committed | `git update-index --chmod=+x` |
| Mode correct, still denied | `core.fileMode=false` locally hid the mismatch | Same fix, plus check `git config core.fileMode` |
| Script is downloaded, unzipped, or written by an earlier step | Zip and artifact upload drop the bit | `chmod +x` in the workflow step before calling it |
| Script sits on a mounted volume or in a container step | `noexec` mount or image `COPY` mode | Call it as `bash script.sh` |
| `bad interpreter: /bin/bash^M` | CRLF line endings | `.gitattributes` with `*.sh text eol=lf`, then renormalize |

If you want to sidestep the whole class of problem, invoke it as `bash path/to/script.sh` in the workflow instead of `./path/to/script.sh`. The permission bit stops mattering, though you lose the shebang as the source of truth for the interpreter.

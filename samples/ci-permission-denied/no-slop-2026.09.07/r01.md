The script is committed with mode 100644, so the runner checks out a non-executable file. Your local copy has the execute bit from your own `chmod`, which git never recorded.

Confirm and fix:

- `git ls-files -s path/to/script.sh` prints the recorded mode. `100644` is the bug, `100755` is correct.
- `git update-index --chmod=+x path/to/script.sh && git commit -m "make script executable"` sets it regardless of your local filesystem.
- Check `git config core.fileMode`. If it is `false` (usual on Windows, WSL crossing to an NTFS mount, or a `noexec` mount), a local `chmod +x` is invisible to git and you will keep hitting this.
- Cheap alternative if you would rather not track the bit: invoke it as `bash path/to/script.sh` in the workflow step, or add `chmod +x` before the call.

If `git ls-files -s` already shows `100755`, the cause is elsewhere: a `noexec` mount is unlikely on a hosted runner, but an artifact download, a `docker cp`, or a tarball unpack in an earlier step will drop modes. "Permission denied" pointing at the interpreter rather than the script is a different failure, usually CRLF line endings turning `#!/bin/bash` into `#!/bin/bash\r`.

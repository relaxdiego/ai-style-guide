Git committed the script with mode `100644`, so the runner checks it out without the execute bit. Your local copy has the bit set on disk, which is why it runs there and nowhere else.

Confirm it:

```bash
git ls-files -s path/to/script.sh
```

`100755` is executable, `100644` is not. In a failing Actions run, `ls -l` on the script shows the same thing.

Fixes, in order of preference:

| Fix | Command | Note |
| --- | --- | --- |
| Commit the bit | `git update-index --chmod=+x path/to/script.sh` then commit | Correct permanent fix, works even if your filesystem drops modes |
| Set it on disk | `chmod +x path/to/script.sh` then commit | Only works if git tracks modes locally |
| Bypass the bit | `bash path/to/script.sh` in the workflow step | Ignores the shebang, fine for bash scripts |
| Chmod in CI | `run: chmod +x path/to/script.sh && ./path/to/script.sh` | Papers over it, still broken for anyone cloning |

Two things commonly cause the mode to be lost in the first place: `core.fileMode` set to `false` (check `git config core.fileMode`), and creating the file on Windows or on a mounted filesystem such as exFAT or an NTFS mount under WSL, where the execute bit does not exist. If `core.fileMode` is false in your repo, `chmod +x` alone will never reach the commit, and `git update-index --chmod=+x` is the only path that works.

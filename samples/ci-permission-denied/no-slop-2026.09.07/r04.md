Your script is committed as mode `100644`. Git stores exactly one permission bit, and your local `+x` never made it into the commit, so the runner checks out a non-executable file.

Check it:

```bash
git ls-files -s path/to/script.sh
# 100644 ... -> not executable
# 100755 ... -> executable
```

Fix without touching your working tree:

```bash
git update-index --chmod=+x path/to/script.sh
git commit -m "Make script.sh executable"
```

If that shows `100755` already, the cause is downstream of the checkout:

| Cause | Symptom | Fix |
|---|---|---|
| `core.fileMode=false` locally (common on WSL, mounted volumes) | Git ignores your `chmod`, commit stays `100644` | `git config core.fileMode true`, then re-chmod and commit |
| Script passed through `upload-artifact` / `download-artifact` | Permission bits stripped by the zip round trip | `chmod +x` in the job after download, or `tar` the directory yourself |
| Script generated or restored by a cache step | Never had the bit | `chmod +x` in the step that produces it |
| Called as `./script.sh` from a `run:` block | Depends entirely on the file bit | Call `bash script.sh` and the bit stops mattering |

One caveat on the last row: `bash script.sh` ignores the shebang, so a script written for `sh`, `zsh` or `python` needs the matching interpreter. If the error is `bad interpreter: No such file or directory` rather than `permission denied`, you have CRLF line endings instead, and the fix is `* text=auto eol=lf` in `.gitattributes` plus a re-commit.

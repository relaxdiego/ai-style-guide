The executable bit is not set in the index. Git tracks exactly one permission bit, and if the file was committed as `100644`, every fresh clone (including `actions/checkout`) writes it non-executable. It works locally because your working copy still has the bit your umask/editor gave it, or because you're invoking it as `bash script.sh` while CI runs `./script.sh`.

Check it:

```
git ls-files -s path/to/script.sh
```

`100755` is executable, `100644` is not.

Fix, from most to least preferable:

| Fix | Command | Notes |
|---|---|---|
| Set the bit in the index | `git update-index --chmod=+x path/to/script.sh` then commit | Works even on Windows/filesystems that don't carry the bit |
| Set it on disk | `chmod +x path/to/script.sh` && commit | Only if your filesystem records the mode |
| Sidestep it | change the CI step to `bash path/to/script.sh` | Hides the problem for anyone who runs the script directly |

Two things that produce the same symptom and are worth ruling out if the mode is already `100755`: `core.fileMode=false` in your local config, which makes Git ignore mode changes you make locally so the commit never carried one; and a checkout on a filesystem mounted `noexec`, which is rare on GitHub-hosted runners but common in self-hosted Docker setups. If the error text is `bad interpreter: No such file or directory` rather than plain `Permission denied`, it's CRLF line endings in the shebang instead, fixed with `* text=auto eol=lf` in `.gitattributes` plus a renormalise.

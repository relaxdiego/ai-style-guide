Git stored the file without the executable bit; your local copy has it because you created it there. The runner does a fresh clone and gets mode `100644`, so `./script.sh` fails with permission denied.

Check it:

```bash
git ls-files -s path/to/script.sh
```

`100644` is the broken case, `100755` is what you want.

Fix, pick one:

| Fix | Command | Notes |
|---|---|---|
| Set the bit in the index | `git update-index --chmod=+x path/to/script.sh` then commit | Works even if your local `chmod` already ran; changes what Git records |
| chmod plus commit | `chmod +x path/to/script.sh && git add path/to/script.sh` | Only works if `core.fileMode` is true |
| Don't rely on the bit | call it as `bash path/to/script.sh` in the workflow | Zero-config, survives checkouts from Windows and zip archives |
| Fix in CI | `chmod +x path/to/script.sh` step before use | Papers over it; every new script needs the same line |

Two things that commonly cause the mode to be lost in the first place: `core.fileMode=false` in your local config (set automatically on Windows and on some mounts), which makes Git ignore mode changes entirely, and creating the file through an editor or an unzip that never set `+x`. Run `git config core.fileMode` to see which applies.

If `git ls-files -s` already shows `100755`, the problem is elsewhere: a `mount` with `noexec`, a missing shebang line, or CRLF line endings making the kernel look for an interpreter named `/bin/bash\r`. That last one reports as a confusing error on some systems; `file path/to/script.sh` will tell you if it has CRLF terminators.

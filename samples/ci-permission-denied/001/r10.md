The executable bit never made it into the commit. Git tracks exactly one permission bit (mode `100644` vs `100755`), and your local copy is executable because of your filesystem, not because of anything in the repo. The runner does a fresh checkout, gets mode 644, and `./script.sh` fails with permission denied.

Confirm and fix:

```bash
git ls-files -s path/to/script.sh    # 100644 = the problem, 100755 = fine
git update-index --chmod=+x path/to/script.sh
git commit -m "Mark script.sh executable"
```

Two things that produce the same symptom and are worth ruling out if the mode is already 755:

- **`core.fileMode=false`** in your local config (common after working on a Windows or exFAT/mounted filesystem). Git ignores mode changes entirely, so `chmod +x` locally is silently dropped. `git config core.fileMode` will tell you.
- **A shebang pointing at something that isn't executable or doesn't exist**, e.g. `#!/usr/local/bin/bash` on an Ubuntu runner. The kernel reports this as permission denied on the script, not on the interpreter.

CRLF line endings are the other classic checkout-difference failure, but they give you `bad interpreter: /bin/bash^M`, not permission denied. If you want to sidestep the mode question entirely, call the script as `bash path/to/script.sh` in the workflow step; the executable bit is irrelevant when you invoke the interpreter directly.

Git recorded the file as mode 100644, so the CI checkout has no execute bit. Your local copy has +x on disk, but that bit lives in your filesystem, not in the commit, so `./script.sh` works locally and dies on a fresh clone.

Check it:

```
git ls-files -s path/to/script.sh
```

`100644` confirms the diagnosis; `100755` means look elsewhere.

Fix, from the repo:

```
git update-index --chmod=+x path/to/script.sh
git commit -m "Mark script.sh executable"
```

`chmod +x` alone will not do it if `core.fileMode` is false (common on Windows, WSL, and some mounted volumes) — git will ignore the mode change and leave your working tree clean.

Other causes if the mode is already 100755:

| Symptom | Cause |
|---|---|
| `permission denied` on a 100755 file | Script sits on a volume mounted `noexec`, or an artifact/cache step stripped modes (zip and `actions/upload-artifact` do not preserve the exec bit) |
| `bad interpreter: /bin/bash^M` | CRLF line endings; add `*.sh text eol=lf` to `.gitattributes` |
| `permission denied` on the interpreter | Shebang points at a path that does not exist on the runner, e.g. `/usr/local/bin/bash` |

The portable workaround, independent of all of this, is to invoke it as `bash path/to/script.sh` in the workflow step rather than `./path/to/script.sh`.

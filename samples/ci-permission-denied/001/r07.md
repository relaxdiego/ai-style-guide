Your script is committed as mode 100644. Git tracks only the executable bit, and the CI runner checks out exactly what's in the index — your local +x bit was never recorded.

Check and fix:

```bash
git ls-files -s path/to/script.sh     # want 100755, you'll see 100644
git update-index --chmod=+x path/to/script.sh
git commit -m "Make script.sh executable"
```

Other causes if the mode is already 100755:

- **`core.fileMode=false`** in your local config, common after working on a Windows/exFAT/mounted volume. Git ignores mode changes entirely, so `chmod +x` locally never produced a diff.
- **CRLF line endings**, if the repo has `* text=auto` or the file came from Windows. The kernel reads the shebang as `/bin/bash\r` and reports it oddly; you usually get "bad interpreter" but some wrappers surface it as permission denied. Check with `file script.sh` or add `*.sh text eol=lf` to `.gitattributes`.
- **The script is on a `noexec` mount**, mostly relevant if CI puts it in `/tmp` or a Docker volume mounted `noexec`.
- **You're calling it as `./script.sh` in a step that unpacks it from an artifact**, since `actions/upload-artifact` drops permission bits. Re-`chmod +x` after download, or tar the directory before uploading.

The escape hatch that works regardless is invoking the interpreter directly: `bash script.sh` instead of `./script.sh`. That bypasses the exec bit entirely, and it's what I'd use in the CI step even after fixing the mode, since it survives artifact round-trips and Windows checkouts.

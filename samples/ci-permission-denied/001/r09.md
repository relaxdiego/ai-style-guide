The script is committed with mode 100644. Git tracks only one permission bit, and your local `chmod +x` never made it into the commit, so the runner checks out a non-executable file.

Confirm it:

```
git ls-files -s path/to/script.sh
```

`100644` is the bug. `100755` means look elsewhere.

Fix, pick one:

- `git update-index --chmod=+x path/to/script.sh && git commit -m "make script executable"` sets the bit in the index directly. Works even on Windows.
- `chmod +x path/to/script.sh && git add path/to/script.sh && git commit` on Linux or macOS.
- Change the workflow to `bash path/to/script.sh` instead of `./path/to/script.sh`. The permission bit stops mattering.

Two things mask this locally. If `core.fileMode` is `false` (Git sets this on Windows and some network mounts), your local `chmod` is invisible to Git and you get no diff. And your local run works regardless because the file on your disk is executable, whatever the commit says.

If `git ls-files -s` already reports `100755`, the likely causes are:

| Symptom | Cause |
|---|---|
| `bad interpreter: /bin/bash^M` | CRLF line endings. Add `*.sh text eol=lf` to `.gitattributes` and renormalize. |
| `exec format error` | Missing or malformed shebang on line 1. |
| Denied inside a container step | Workflow container runs as a different UID than the checkout owner. |

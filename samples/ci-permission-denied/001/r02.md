Git tracked your script as mode 100644. Your local copy has the executable bit because you chmod'd it after creating it, but the bit was never committed, so the runner's checkout produces a non-executable file.

Check and fix:

```bash
git ls-files -s path/to/script.sh     # 100644 = the bug, 100755 = fine
git update-index --chmod=+x path/to/script.sh
git commit -m "Mark script.sh executable"
```

`git update-index --chmod=+x` sets the bit in the index regardless of the local filesystem, which matters if you're on a filesystem that doesn't carry the bit. Other candidates, if `ls-files` already shows 100755:

- `core.fileMode=false` in your local config — git ignores the on-disk bit, so a plain `chmod +x` produced no diff to commit.
- The workflow invokes the script as `./script.sh` after an artifact download or `unzip`; both drop permissions. Zip archives preserve modes, `actions/upload-artifact` does not.
- The script has CRLF line endings, so the kernel looks for the interpreter `/bin/bash\r`. That reports "no such file or directory" rather than "permission denied" on most systems, but a `.gitattributes` with `* text=auto` combined with a checkout on Windows-style config is worth ruling out.
- The file is on a volume mounted `noexec` inside a container step.

The portable workaround, independent of any of this, is calling `bash path/to/script.sh` in the workflow instead of `./path/to/script.sh` — the exec bit is irrelevant when bash is the thing being executed.
